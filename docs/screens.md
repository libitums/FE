# 화면 명세

이 문서는 **무엇을 만들지**를 적는다. 어떻게 만들지는 ADR이, 어떻게 확인할지는
`docs/e2e/`가 맡는다.

출처는 **사용자 발화 하나뿐이다** (2026-08-31 논의). 디자인 파일이나 다른 저장소를
읽어서 채우지 않았다. 발화에서 추론한 항목은 `[추론]`으로 표시했고, 확인을 받기
전까지 표시를 유지한다.

---

## 목적 (goal)

서사와 그 안의 에피소드라는 **배경** 속에서 한국어를 배워, 단어·조사·상황을 따로
외울 때 생기는 *"이해가 어렵고 기억이 안 되는"* 문제를 푼다.

습관을 세로로 쌓는 방식(듀오링고)이 아니라 **경험을 가로로 넓히는** 방식이다. 이
차이가 화면 구조에 그대로 드러난다 — 중심은 연속 기록이 아니라 여정과 에피소드다.

## 타깃 (target)

- 디바이스: 모바일 (iOS). 시연은 iOS 시뮬레이터
- 브라우저 하한: 해당 없음. Lynx는 브라우저가 아니다 (ADR-0012)

## 화면 목록

세 곳으로 나뉜다. 진입 흐름은 **탭이 아직 없는 구간**이고, 나머지는 탭 안이다.

### 진입 흐름 (탭 밖)

스플래시에서 갈린다.

```
스플래시 ─┬─ 첫 사용자   온보딩 → 로그인 → [전화번호면] 코드 검증 → 언어 선택 → 여정 선택 → 홈
          └─ 재방문      홈
```

재방문 판단은 `src/lib/storage.ts`(호스트 `StorageModule`)로 한다 — **서버가 없어도
된다.** 아래 표는 첫 사용자 경로다.

| 화면 | 내용 |
|---|---|
| 스플래시 | |
| 온보딩 | 서비스 요약 3종. **형태는 동일하고 문구·이미지만 다르다** |
| 로그인 / 회원가입 | 전화번호 · 구글 · 애플 · 페이스북 |
| 코드 검증 | 4자리. **전화번호 경로에서만** 나타난다 |
| 언어 선택 | 자신의 언어 |
| 여정 선택 | 처음으로 시작할 여정 |

### 홈 탭

| 화면 | 내용 |
|---|---|
| 홈 | streak 일수 · 클리어 에피소드 · 노티피케이션 · 선택한 여정 히어로(+변경 UI) · 하단에 현재 에피소드 진행 현황 |
| 노티피케이션 | 별도 화면 |
| *(여정 선택)* | **재활용.** 새 화면이 아니다 — 아래 "두 진입점" 참조 |

### 여정 탭

듀오링고의 레벨형 UI와 비슷한 형태다.

| 화면 | 내용 |
|---|---|
| 여정 맵 | 레벨형. 스텝을 누르면 학습으로 |
| 학습 | 아래 세 유형 |
| 평가 | 학습 완료 후 |

#### 학습의 세 유형

| 유형 | 형태 | 롤플레이 탭에 |
|---|---|---|
| **기본 학습형** | 듀오링고와 비슷한 형태 — 듣기 · 문장 순서 배치 · 단어 선택 · 말하기 · 쓰기 | 없음 |
| **학습 동반형** | 여정 속 캐릭터와 상호작용하며 배운다 | 있음 |
| **서사 주입형** | 서사만 전달한다 | 있음 |

서사 주입형과 학습 동반형은 **배우는 방식이 같고 화면만 다르다.** 그래서 학습 로직은
공유하고 표현만 가른다.

유닛은 두 종류이고, **유형이 유닛을 따라간다.**

| 유닛 | 도는 유형 | 화면 형태 |
|---|---|---|
| 일반 유닛 | **기본 학습형만** | 듀오링고식 |
| 특별 유닛 (몇 개만) | 서사 주입형 · 학습 동반형 | 비주얼 노벨 · 메신저 · 전화 통화 |

기본 학습형은 **일반 유닛에서만** 돈다. 특별 유닛으로 넘어오지 않는다. 그래서 두
갈래는 화면을 공유하지 않고, 서로 독립적으로 만들 수 있다.

### 롤플레이 탭

세 유형 중 **기본 학습형을 뺀** 것이다 — 서사 주입형과 학습 동반형만 남는다. 그래서
롤플레이는 새 학습 형태가 아니라 **기존 두 유형의 재배치**다.

| 화면 | 내용 |
|---|---|
| 롤플레이 목록 | `[추론]` — "특정 롤플레이를 통해 학습"이라는 발화에서 목록의 존재를 추론했다 |
| 롤플레이 진행 | 서사 주입 + 캐릭터 상호작용 |

### 설정 탭

| 화면 | 내용 |
|---|---|
| 설정 | 학습 옵션 |
| 사용자 프로필 | |
| 개인정보 보호 및 약관 | |

## 네비게이션 구조

### 지금 모양으로는 진입 흐름을 담을 수 없다

ADR-0007 D3이 고정한 모양은 이렇다.

```ts
Nav = { tab: Tab; stacks: Record<Tab, Screen[]> }
```

**탭 안의 스택만 표현한다.** 스플래시부터 여정 선택까지는 탭이 아직 없는 구간이라
담을 자리가 없다. 단계를 하나 얹어야 한다.

```ts
Nav = {
  phase: 'entry' | 'app'
  entry: Screen[]          // 탭 밖 구간
  tab: Tab
  stacks: Record<Tab, Screen[]>
}
```

`entry`가 비면 `app`으로 넘어간다. **ADR-0007 D3의 정정 대상이다** — 이 문서가
결정하지 않는다.

### 여정 선택 화면의 두 진입점

같은 화면이지만 **끝나는 곳이 다르다.**

| 어디서 왔나 | 끝나면 |
|---|---|
| 온보딩 (첫 여정 선택) | 홈으로 **진행** |
| 홈 (여정 변경) | 홈으로 **복귀** |

화면에 "어디서 왔는지"를 넘겨야 한다. 화면을 복제하지 않는다.

### 탭별 스택

| 탭 | 스택 | 근거 |
|---|---|---|
| 홈 | 있음 | 노티피케이션 · 여정 선택 |
| 여정 | 있음 | 맵 → 스텝 → 학습 → 평가 |
| 롤플레이 | 있음 | 목록 → 진행 |
| 설정 | 있음 | 설정 → 프로필 / 약관 |

iOS에는 하드웨어 뒤로가기가 없다. **모든 화면이 화면 안에 뒤로 갈 수단을 갖는다**
(ADR-0007).

## 제약 (constraints)

### 서버가 없다

모든 데이터는 **고정 데이터**다. 그래서 갈라지는 것:

- 로그인 · 코드 검증은 **진짜로 만들 수 없다.** 화면은 만들 수 있어도 검증이 없다
- streak · 클리어 에피소드 · 진행 현황은 전부 고정 값이다
- 저장이 필요하면 `src/lib/storage.ts`(호스트 `StorageModule`)를 쓴다. Lynx 자체에는
  영속 저장 API가 없다 (ADR-0012)

### 디자인 시스템이 확정되기 전까지 UI는 임시다

지금 만드는 시각은 **버릴 것을 전제로** 만든다. 그래서 버릴 것과 남을 것을 파일로
가른다.

```
src/styles/tokens.temp.css   :root 에 임시 값.       ← 버릴 파일
<화면>.css                    var(--...) 만 참조.     ← 남을 파일
```

컴포넌트는 임시 값을 직접 쓰지 않는다. 디자인 시스템이 오면 `tokens.temp.css`
하나가 별칭으로 바뀌거나 지워지고, 컴포넌트는 건드리지 않는다. 토큰 이름이 나중에
달라져도 폭발 반경이 파일 하나다.

CSS 변수만 쓰는 것은 ADR-0011 D1이 이미 정했다. 임시 기간에도 그 규칙을 깨지 않는다.

**ui 테스트는 시각을 단언하지 않는다.** 임시 UI가 확정 UI로 바뀔 때 색만이 아니라
마크업이 바뀐다. 그래서 이 기간의 ui 테스트는 *무엇이 보이는가*가 아니라 *무엇이
있는가*를 단언한다 — 텍스트 존재, 상호작용 후 상태 변화. 트리 전체 스냅샷은 마크업이
확정된 뒤에 쓴다.

> 기존 `HomeScreen.ui.test.tsx`는 트리 전체를 인라인 스냅샷으로 박고 있다. 확정
> UI로 갈 때 깨진다. 알고 두는 것이지 모르고 둔 것이 아니다.

## 작업 분해

### 최소 단위 = 화면 + 들어오는 전이 하나

화면만 만들면 `ui` 테스트는 통과하지만 **시뮬레이터에서 볼 수가 없다.** 도달 경로가
없기 때문이다. 이대로 쌓으면 마지막에 "네비게이션 연결" 이슈 하나가 거대해지고,
그때 몰아서 터진다.

이슈 하나가 담는 것:

- `Screen` 유니온에 이름 추가
- 화면 컴포넌트 (고정 데이터, 임시 시각)
- `ui` 테스트 — 화면 자체
- **전이 하나** + `integration` 테스트 — 도달 경로
- 시뮬레이터에서 눈으로 확인

### 예외는 하나 — 뼈대

첫 화면을 붙일 자리가 없어서 앞에 하나만 둔다.

> `Nav`에 `phase` 추가 · `Screen`/`Tab` 유니온 확정 · 바텀 네비게이션 셸 + 빈 탭 4개
> **확인**: 탭 4개가 전환된다

따로 떼는 이유는 여기에만 **모든 이슈가 건드릴 파일**(`navigation.ts`)이 모여
있기 때문이다. 먼저 확정하면 이후 화면 이슈들이 서로 충돌하지 않는다.

### 순서 — 만드는 쪽을 먼저, 요약하는 쪽을 나중에

사용자가 보는 순서와 만드는 순서는 다르다. 두 가지가 순서를 뒤집는다.

**홈은 소비자다.** streak 일수 · 클리어 에피소드 · 선택한 여정 히어로 · 현재 에피소드
진행 현황 — 홈에 있는 것이 전부 **여정과 학습이 만들어낸 결과**다. 홈을 먼저 만들면
그 값을 전부 지어내야 하고, 진짜가 생기면 다시 만든다. 그래서 여정과 롤플레이를 먼저
만들고 홈을 나중에 얹는다.

**진입 흐름은 서버가 필요하다.** 로그인과 코드 검증은 검증할 것이 없다. 게다가 먼저
만들면 이후 모든 확인이 매번 로그인을 통과해야 해서 개발이 느려진다.

```
0.  뼈대
1.  여정 맵
2.  스텝 → 기본 학습형 1종 (듣기)      ← 학습 루프의 첫 증명
3.  평가
4.  기본 학습형 나머지 (문장 순서 · 단어 선택)
5.  서사 주입형 · 학습 동반형 (비주얼 노벨 · 메신저 · 전화 통화)
6.  롤플레이 (목록 → 진행)             ← 5번의 화면을 재사용한다
7.  홈                                  ← 1~6이 만든 것을 요약한다
8.  노티피케이션
9.  설정 · 프로필 · 개인정보 및 약관
10. 여정 선택                           ← 홈의 "여정 변경"이 여는 화면
11. 진입 흐름 나머지 (언어 선택 · 코드 검증 · 로그인 · 온보딩 · 스플래시)
12. 말하기 · 쓰기
```

번호는 **구현 순서**다. 사용자가 지나가는 순서가 아니다.

앞으로 당길 수 없는 것이 셋 있다.

| 항목 | 무엇에 매여 있나 |
|---|---|
| **6. 롤플레이** | 5번. 롤플레이는 서사 주입형과 학습 동반형으로만 이뤄져 있어서, 그 둘이 없으면 만들 것이 없다 |
| **7. 홈** | 1~6번. 요약할 대상이 없으면 전부 지어낸 값이 된다 |
| **10. 여정 선택** | 7번. 이 화면으로 들어오는 전이가 홈의 "여정 변경"이다. 나중에 온보딩이 이 화면을 재활용한다 |

**12. 말하기 · 쓰기**가 기본 학습형에서 떨어져 나온 것은 성격이 다르기 때문이다.
나머지 세 종(듣기 · 문장 순서 · 단어 선택)은 화면만 있으면 되지만, 이 둘은 마이크와
키보드라는 **네이티브 능력**이 필요하고 Lynx에서 확인된 바 없다.

## 범위

**어디까지 이번에 만드는가는 이 문서가 정하지 않는다.** 작업 범위는 이슈에서 정한다.

이 문서는 화면이 **무엇인지**와 **무엇에 매여 있는지**만 적는다. 그래야 범위를 어디에
긋든 같은 문서를 쓴다. 범위를 문서에 박으면 범위가 바뀔 때마다 문서를 고쳐야 하고,
곧 문서와 실제 범위가 어긋난다.

위의 구현 순서도 마찬가지다. **순서는 의존성에서 나온 것이지 범위가 아니다.** 어디서
끊을지는 이슈가 정한다.

### 만들지 않는 것

범위와 무관하게, 제약과 이미 내린 결정에서 곧바로 따라오는 것들이다.

- **실제 인증** — 서버가 없다. 로그인·코드 검증에 통과/실패가 없다
- **디자인 시스템 적용** — 확정 전까지 임시 시각으로 둔다
- **말하기 · 쓰기** — 마이크·키보드는 네이티브 능력이고 Lynx에서 확인된 바 없다.
  확인되기 전까지는 만들 수 없다
- **Android** — ADR-0012 D1
- **다크 모드** — ADR-0011 D5

## 확인 방법

화면이 되었는지는 `docs/e2e/`의 흐름 파일이 판정한다. 흐름은 **실제로 만들 때 하나씩**
추가한다 — 만들지 않은 화면의 흐름을 미리 적지 않는다.

## 비고

### 확인이 필요한 `[추론]`

| 항목 | 무엇을 추론했나 |
|---|---|
| 롤플레이 목록 화면 | "특정 롤플레이를 통해 학습"에서 목록의 존재를 추론 |
| 스텝 상세 화면 | 맵과 학습 사이에 화면이 따로 있는지 확인 안 됨 |
| 온보딩 화면 개수 | 화면 3개인지, 한 화면에 3스텝인지 미정 — 형태가 같으므로 후자를 권함 |

### 이 문서가 만드는 후속

- **ADR-0007 D3 정정** — `Nav`에 `phase` 추가
- **ADR-0010 D1 문서 트리** — 이 문서가 들어갈 자리가 표에 없다
