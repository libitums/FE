# 카탈로그 재구성의 검증 결과 기억 — Node 측정 — 01

## 실행 조건

- 상태: 부분 측정 — Node(V8)에서 카탈로그 재구성 비용만 쟀습니다. 기기 렌더링 · 메모리 · 프레임 캡처는 돌리지 않았습니다.
- 기능 PR: 받기 중 편이 갖춰질 때마다 카탈로그를 다시 만들 때, 같은 id · 같은 원문의 sha256 · 디코드 결과를 다시 씁니다 — ADR-0071 적용 기록 ⟨2026-11-05⟩.
- 대상 commit: `main` 위의 `fix/catalog-verify-cache`
- 기기: 측정 기기 없음(Node 22, Apple Silicon). 증상은 Android Galaxy A52s(SM-A528N)에서 사용자가 보고했습니다.
- OS: 해당 없음
- Lynx SDK: 4.0.1
- 빌드: `pnpm --filter @libitums/mobile build`(CI 설정, `.env.local` 없음), 판정은 `pnpm size:check`
- 측정 일시: 2026-11-05

## 시나리오

- 수준 4 버킷 본문 18편(편당 약 165 ~ 232 kB)과 vi 번역 파일로 `buildEpisodeCatalog`를 반복 호출.
- 수정 전: 한 번 다시 만들기 약 72 ms — 그중 18편 sha256 약 53 ms, 파싱 · 디코드 약 16 ms. 받기 중 n편째마다 다시 만들므로 sha256은 1 + 2 + … + n번(6편 픽스처에서 21번).
- 수정 후: 같은 원문은 계산하지 않아 sha256은 편 수만큼(6편 픽스처에서 6번, integration VCI1). 같은 원문으로 다시 만들면 0번(unit VC1).
- 번들 크기: CI 설정 빌드 `main.lynx.bundle` 3,894.5 kB(상한 4,060.0 kB 통과).

## 이 변경이 무엇을 건드렸나

- `lib/verified-text-cache.ts`(새 파일), `lib/episode-catalog.ts`의 `checkEpisodeText`, `lib/episode-update-plan.ts`의 `matchesEntry`.

## 분석 결과

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 카탈로그 한 번 다시 만들기(Node, 18편) | 약 72 ms | 새로 바뀐 편만큼(같은 원문이면 sha256 · 디코드 0) |
| 6편을 차례로 받는 동안 sha256 호출 | 21 | 6 |

기기 값은 **없습니다** — 재지 않았습니다.

## 해석

- 받기 중 카탈로그 재구성의 계산량이 편 수의 제곱에서 편 수에 비례로 줄었습니다. 기기에서 탭 지연이 사라졌는지는 재지 않아 아직 판정할 수 없습니다(미측정의 한계).
- 대가: id마다 마지막 원문 하나를 메모리에 둡니다 — 로더가 이미 같은 원문을 들고 있어(`lastSource`) 추가는 sha256 문자열과 디코드 결과 참조뿐입니다.

## 결론과 후속

- 후속: 같은 기기(Galaxy A52s)에서 새로 설치해 받는 동안 탭 반응을 봅니다.
