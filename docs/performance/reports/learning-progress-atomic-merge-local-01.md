- 대상 commit: 178d6e7bb7fb045ebfe50967f368ef69dabf737a 위 codex/learning-progress-atomic-merge 작업 트리. 선행 PR #190을 포함합니다.

## 시나리오
동일 사용자의 두 연결이 서로 다른 진행을 동시에 저장합니다. 첫 요청의 트랜잭션을 열린 채 두고 두 번째 요청의 실제 Lock 대기를 확인한 뒤 커밋합니다. 최초 INSERT 경합·기존 행 UPDATE 경합과 양쪽 요청 순서를 모두 검증합니다. 완료 후 오래된 요청, 같은 요청 재전송, 알 수 없는 유닛 ID, 잘못된 JSON 구조·버전, 병합 결과 용량 초과, 계정 격리·삭제도 확인합니다.

## 분석 결과
- 기존 저장 RPC에서 회귀 테스트 29건 중 28건 실패, 수정 후 모두 통과했습니다. SQL NULL·입력 용량 검사까지 더한 SQL 통합 테스트는 32건입니다. 비주얼 노벨 추가 메타데이터의 활성·완료 병합 보존도 확인했습니다.
- `ON CONFLICT DO UPDATE`가 잠근 최신 행과 입력을 합칩니다. 완료 목록은 합집합, 스텝·활성 장면은 최댓값, 비주얼 노벨 완료는 유지합니다.
- 기존 RPC 인수·void 반환·사용자별 키·RLS·CASCADE를 유지합니다. 클라이언트는 내부 합치기 함수를 직접 실행할 수 없습니다.
- 지원하지 않는 버전·깨진 입력과 합친 결과가 16 KiB를 넘는 저장은 오류로 끝나며 기존 행을 보존합니다.
- 기존 마이그레이션 파일을 수정하지 않고 후속 SQL만 추가합니다. 마이그레이션은 서버에서 적용해야 하며 모바일 앱 배포가 대신하지 않습니다.
- 백엔드 통합 테스트 96건 통과. 전체 `pnpm verify`의 포맷·타입·린트·전체 테스트·빌드·번들 크기·보고서 정책 검사 통과.
- 모바일 번들: 1,383,096 bytes. 선행 PR #190과 동일하며 기존 1,384,000 bytes 예산을 유지합니다.

## 해석
측정 한계: 테스트는 PostgreSQL 17.9에서 실행했고 Supabase의 사용자 표·사용자 ID 조회 함수·역할 경계는 최소 대역으로 준비했습니다. 실제 마이그레이션과 다중 연결 잠금은 DB 엔진에서 실행했습니다. 운영 Supabase의 Auth·PostgREST, 운영 데이터의 과거 스냅숏 상태, 부하와 네트워크 지연은 검증하지 않았습니다. 이 결과만으로 운영 성능을 판정할 수 없습니다.

[PostgreSQL INSERT 문서](https://www.postgresql.org/docs/17/sql-insert.html)와 [Read Committed 동시성 문서](https://www.postgresql.org/docs/17/transaction-iso.html)의 충돌 행 갱신 의미를 기준으로 검증했습니다.

## 결론과 후속
오래된 요청이나 다른 기기의 저장이 앞서 완료된 학습을 지우는 경로를 서버에서 차단합니다. 운영 적용 후 테스트 계정으로 저장·재조회 왕복을 확인해야 합니다. 향후 새 버전이나 감소 가능한 상태를 추가할 때에는 서버 검증과 합치기 규칙을 함께 확장해야 합니다.
