# 학습 화면에 계측점을 놓고 처음으로 재다 — iPhone 17 Pro 시뮬레이터 — 01

- 측정 일시: 2026-09-28T03:52:00Z
- 상태: 측정 — 학습 화면(듣기)이 서는 pipeline과 그 직후 메모리를 **세 회차** 수집했습니다.
  **이 자리가 측정된 것은 처음입니다.**
- 기능 PR: 학습 껍데기 루트에 timing flag를 넣은 변경(이 보고서와 같은 PR). 값은
  `libitum:navigation:learning-` 뒤에 학습형 이름이 붙는 형태입니다. ADR-0019 D3 개정.
- 대상 commit: `f3fd09bf2c667ec68d0b81e4a8e962965be8ee68` 위의 작업 트리 (`feat/learning-timing-flag`)

- 실행 회차: 01 (Host를 껐다 켜는 것으로 회차를 가른 3회)

## 시나리오

- 전제: 저장된 로그인 토큰이 있어 Host가 곧장 여정 맵으로 뜹니다.
- 단계: `performance:capture -- start`로 Host를 띄우고, `주문하기` 유닛을 눌러 말풍선을
  연 뒤 `시작`을 눌러 듣기 화면으로 들어갑니다. `report`로 보고하고 `stop`으로 종료한 뒤,
  같은 절차를 두 번 더 반복합니다.
- 관찰 구간: `libitum:navigation:learning-listening` timing flag가 붙은 update pipeline과,
  그 identifier를 보고 수집기가 뜬 메모리 스냅샷입니다. 같은 캡처의
  `libitum:navigation:journey`도 함께 적습니다.

⚠ **1회차는 앱을 새로 설치한 직후입니다.** 2·3회차는 같은 설치 위에서 Host만 껐다
켰습니다. 아래 표에서 1회차만 크게 벗어나는데, 그 사정이 이 열에 있습니다.

## 이 변경이 무엇을 건드렸나

**제품 동작은 아무것도 안 바뀝니다.** 학습 껍데기의 루트 `<view>`에 속성 하나
(`__lynx_timing_flag`)가 붙습니다. 값은 계약(`learning-shell.contract.ts`)이 만들고
학습형마다 갈립니다.

바뀐 것은 **잴 수 있느냐**입니다. 이 표식이 없던 동안 학습 화면은 캡처에 entry를 한 줄도
남기지 않았습니다 — 직전 보고서(`learning-shell-and-listening-auto-advance-...`)가
「본체 미측정」으로 남은 이유가 그것이고, 이 PR이 그 후속입니다.

## 분석 결과

학습 화면 진입(`libitum:navigation:learning-listening`)의 `pipeline`입니다.

| 회차             | pipeline  | layout    | resolve  |
| ---------------- | --------- | --------- | -------- |
| 1회차(설치 직후) | 41.359 ms | 12.243 ms | 4.506 ms |
| 2회차            | 18.916 ms | 2.817 ms  | 4.689 ms |
| 3회차            | 22.017 ms | 3.137 ms  | 6.813 ms |

같은 캡처의 여정 맵 진입(`libitum:navigation:journey`)은 45.130 · 36.603 · 34.068 ms입니다.

메모리는 세 회차가 **글자 그대로 같습니다** — `elementNodeCount` 77 노드,
`elementBytes` 80,080 bytes. 같은 캡처의 여정 맵은 151 노드 · 157,040 bytes입니다.

## 해석

**첫째, 학습 화면이 여정 맵보다 가볍습니다.** 노드가 절반(77 대 151)이고 pipeline도
2·3회차에서 절반 안팎입니다. 예상과 맞습니다 — 맵은 유닛 노드와 에피소드 헤더가 줄줄이
서지만 학습 화면은 카드 하나와 보기 넷입니다. **다만 「가볍다」는 두 화면 사이의 말이지
어떤 기준을 넘었다는 말이 아닙니다** — 이 저장소에 성능 예산이 아직 없습니다
(ADR-0018·0019의 보류 항목).

**둘째, 1회차가 2·3회차의 두 배입니다.** 41.4 대 18.9 · 22.0이고, 갈린 몫은 거의 전부
`layout`입니다(12.2 대 2.8 · 3.1). 앱을 새로 설치한 직후라는 것 말고 다른 차이를 모릅니다.
**이 한 번으로 「첫 실행이 두 배」라고 일반화할 수 없습니다** — 회차가 셋이고 그중 설치
직후는 하나입니다.

**셋째, 흔들림 폭은 여전히 모릅니다.** 2·3회차가 18.9와 22.0으로 3.1 ms 갈리는데, 이것이
잡음의 폭인지 무엇의 차이인지 가릴 자료가 없습니다. 같은 한계가 앞선 보고서 다섯에서
이어져 왔고 여기서도 안 풀립니다.

**넷째, 이 값은 「화면이 처음 서는 비용」이고 그 뒤는 안 잽니다.** Lynx timing flag는
같은 값의 첫 등장만 측정합니다(ADR-0019 D3). 그래서 문항이 넘어갈 때마다의 갱신도,
2.5초 자동 넘김의 프레임 비용도 이 표에 없습니다. **자동 넘김은 여전히 미측정입니다.**

**다섯째, 메모리 세 값이 완전히 같은 것을 「안정적」으로 읽지 않습니다.** 같은 문항 하나를
같은 자리까지 연 것이라 트리가 같은 것이 당연합니다. 문항을 넘기거나 다른 학습형을 열면
달라질 수 있고, 그것은 아직 안 재 봤습니다.

## 결론과 후속

- 학습 화면 진입 비용은 18.9~41.4 ms, 메모리는 77 노드 · 80,080 bytes로 관측됐습니다.
  **이 자리의 첫 기준선입니다.**
- **직전 보고서의 첫 후속이 닫혔습니다** — 「학습 화면에 계측점을 놓는 일」입니다.
- **다음 학습형이 열리면 같은 절차로 잽니다.** 표식이 학습형마다 갈리므로 문장 배열 ·
  낱말 고르기 · 문화를 같은 축에서 비교할 수 있습니다. 오늘 잰 것은 듣기 하나입니다.
- **자동 넘김의 프레임 비용은 fluency 캡처로 미룹니다.** timing flag로는 안 잡히는
  자리입니다.
- **전환 pipeline의 흔들림 폭을 재는 일이 일곱 번째로 미뤄졌습니다.**
- ⚠ **한 실행에서 학습 화면을 두 번 재려면 고유 실행 ID가 필요합니다**(ADR-0019 D3의
  재검토 조건). 나갔다 다시 들어가도 같은 값이라 두 번째는 안 잡힙니다.
