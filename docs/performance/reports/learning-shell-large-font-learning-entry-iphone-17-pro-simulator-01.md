## 해석

1. **「기본 글꼴에서 A − B 바이트 0」이라는 기대는 문자대로는 깨졌다.** 요소 수 · `elementBytes` · `viewBytes`는
   0이지만 `mainThreadRuntimeBytes`(따라서 `totalBytes`)가 세 쌍 모두 **+80**이다(A 7,099,088 · B 7,099,008).
   계약은 이 경우 측정을 멈추게 했고 실제로 한 번 멈췄다. root의 해석은 이렇다 — **B는 `learningShellFlow`의
   함수 몸통을 상수 반환으로 바꿔 끼운 소스라, 80 bytes는 JS 런타임에 올라간 코드 크기의 차이다 [추론 — 직접
   확인하지 않았다].** 요소 트리가 같고, Android 기기에서 기본 글꼴의 멈춘 화면이 수정 전후 다른 행 0이었다
   [실측 — e2e L4]. 그래서 이 +80을 「기본 글꼴에서 달라지지 않는다」(AC13)의 반증으로 보지 않았고, 계약의
   「바이트 0」 기대가 런타임 바이트에 대해 너무 엄격했다고 기록한다. 큰 글꼴의 +80이 기본 글꼴과 같은 값인
   것도 이 해석과 맞는다. ⟨2026-10-10⟩ **계약 r05가 기준을 고쳤다** — 기본 글꼴의 판정은 `elementNodeCount` ·
   `elementBytes` · `viewBytes`의 A − B = 0(세 쌍 모두 0 — 충족)뿐이고, `mainThreadRuntimeBytes` · `totalBytes` ·
   `appBytes` · 시간은 **판정하지 않고 값만 적는다.** +80이 코드 교체에서 온다는 읽기는 여전히 [추론]이다. 기본
   글꼴의 `appBytes`는 A · B 범위가 겹친다(「비교」).
2. **Lynx snapshot의 요소 · 바이트 항목은 합침을 가르지 못했지만, 앱 전체 `appBytes`는 큰 글꼴에서만
   갈렸다.** 큰 글꼴에서 A는 합쳐졌고 B는 합쳐지지 않았는데(아래 3) 요소 수는 79 대 79로 같았다.
   `after-initial-load` 스냅샷의 Lynx 항목이 합침(측정 뒤의 두 번째 렌더)보다 앞에 찍혔기 때문으로 본다 [추론].
   계약은 그때 timing flag pipeline으로 가르게 했지만 이 캡처에서 그 flag는 초기 LoadBundle 항목에 붙어 있고
   합침 렌더의 별도 pipeline이 없어 가르는 수단이 되지 못했다. **합침 자체는 스크린샷과 접근성 트리로
   확인됐다.** 한편 같은 줄의 `appBytes`는 큰 글꼴에서 **합친 흐름(A)이 더 컸고 범위가 겹치지 않았다**
   (A 103.1 ~ 112.1 MB 대 B 100.7 ~ 102.1 MB — A가 1.0 ~ 11.3 MB 큼). 기본 글꼴에서는 겹친다. 무엇이 그 차를
   만드는지는 **[추론]이고 갈라 재지 않았다** — 합침 렌더(두 번째 렌더 · 무대와 작업 영역의 다시 mount · 합친
   스크롤의 독립 레이어 · 더 큰 그리기 면)의 메모리일 수 있고, 늘 A가 B보다 먼저 돌았으며, `appBytes`는 Lynx
   밖까지 포함한 프로세스 전체 값이라 다른 원인도 섞일 수 있다. 쌍별 차의 폭(1.0 ~ 11.3 MB)이 넓어 크기를 한
   숫자로 말하지 않는다. **이 조건의 B는 보기 영역이 0인 고장 난 배치다** — 그래서 이 A − B는 「같은 일을 더
   싸게」의 대조가 아니라 **「보기에 닿게 하는 비용」**의 대조다(계약 r05.1).
3. **iOS 재현 사실 [실측].** iPhone 17 Pro 시뮬레이터 · AX3XL에서 합침을 끈 B(수정 전의 배치)는 무대 카드가
   지시문을 덮고 화면 끝까지 차서 **보기 · 재생에 닿지 않는다** — 접근성 트리에도 없고 쓸어도 같다. 이 버그는
   Android에서만이 아니라 iOS에서도 재현된다. 수정(A)은 한 흐름으로 합쳐져 **쓸기로 마지막 보기까지 닿는다.**
   A가 합쳐졌다는 것은 iOS에서도 `layoutchange`가 와서 96 미만으로 판정됐다는 뜻으로 읽는다 [추론 — 높이
   값과 단위는 읽지 않았다]. **합쳐지기 시작하는 배율은 미측정이다** — AX3XL 한 단계만 봤고 그 아래 글꼴에서는
   재지 않았다.
4. **시간은 방향을 말할 수 없다.** 폭이 갈린 항목(기본 글꼴의 `mtsRender` · `layout`, 큰 글꼴의 `layout`)은 모두
   A가 낮은 쪽이지만, 회차가 3 대 3이고 dev 번들 · 단일 세션이며 늘 A가 B보다 먼저 돌았다. 기본 글꼴에서 B는
   A와 같은 트리를 그리는데도 갈렸으므로 이 차이를 합침이나 B의 배치로 돌릴 근거가 없다. 큰 글꼴 A의 hydrate
   pipeline(8 ~ 13 ms)이 기본 글꼴(약 3 ms)보다 큰 것은 같은 세션의 관찰이고 원인은 확인하지 않았다.
5. **정적 비용 +4,229 bytes는 세 작업이 섞인 값이다.** `fa3b261e`와 대상 commit 사이에는 이 작업과
   `learning-item-guides` · `hide-scrollbars`의 변경이 함께 있다. 이 작업의 몫만 떼어 말할 수 없다.

**제한 사항.**

- ⓐ dev 번들이다 — 절대값은 Release 내장 번들의 기록과 나란히 놓지 않는다.
- ⓑ B는 소스를 바꿔 끼운 것이다. 측정 결선 · `LearningShellBody` · 재생 훅 이동의 비용은 A · B 양쪽에 있어
  차이에 남지 않는다 — 정적 쪽만 번들 크기가 본다(그것도 세 작업 혼합).
- ⓒ 스냅샷의 Lynx 항목은 합침보다 먼저 찍힌 것으로 보인다 [추론] — 합침의 요소 · 렌더 비용은 미측정이다.
  메모리는 앱 전체 `appBytes`의 A · B 차(큰 글꼴에서 A가 1.0 ~ 11.3 MB 큼)만 있고, 그것을 합침 렌더의 몫으로 가르지
  않았다(「해석」 2).
- ⓓ 네이티브 재생 호출 수는 수집기에 없다 — ui LS3 · e2e L7이 진다.
- ⓔ 문항 전환 · 답한 순간의 맨 위로는 조작 없는 12초에 들지 않는다.
- ⓕ 듣기 한 종류 · 시뮬레이터 한 대 · 단일 세션이다. 실기 · 제품 번들 · VoiceOver는 보지 않았다.
- ⓖ 큰 글꼴 조건은 iOS 최대 Dynamic Type 하나다 — Android의 글꼴 2.2 · 2.35와 같은 창 높이가 아니다.
- 관찰(판정 아님): AX3XL에서 상단 바의 칩이 상태 바(시각 표시)와 겹쳐 보인다(A · B 모두). 큰 글꼴의 글자
  겹침(E4 류 — 학습 껍데기 밖의 머리)이고 이 작업의 범위 밖이다.

## Trace 후속 확인

- render: 해당 없음 — Trace를 수집하지 않았다. 합침 렌더의 비용을 보려면 측정 뒤 두 번째 렌더에 별도
  pipeline이 잡히는 수단(갱신에 붙는 timing flag 또는 늦춘 메모리 스냅샷)이 먼저 필요하다.
- fluency: 해당 없음 — 합친 흐름의 스크롤 프레임은 실기에서 잰다. 시뮬레이터 기록으로 대체하지 않는다.
- memory: `after-initial-load` 하나만 있다. before / peak / after 세 지점을 잡지 않았다. 큰 글꼴의 `appBytes` 차(A가
  1.0 ~ 11.3 MB 큼)는 Xcode Allocations 같은 도구로 보지 않았다.
- NativeModule: 해당 없음 — 재생 호출은 수집기에 없다(ⓓ).

## 결론과 후속

- 결론: **iPhone 17 Pro 시뮬레이터 · AX3XL에서 합침을 끄면 보기 · 재생에 닿지 않고, 이 변경(A)은 한 흐름으로
  합쳐 마지막 보기까지 닿는다 — 화면 · 접근성 트리로 확인했다. Lynx snapshot의 요소 · 바이트 항목(요소 79 대
  79 · 런타임 +80 bytes)은 두 글꼴 모두 같아 합침을 가르지 못했지만, 앱 전체 `appBytes`는 큰 글꼴에서만 A가
  1.0 ~ 11.3 MB 커 범위가 겹치지 않았다 — 원인은 [추론]이다(합침 렌더의 메모리일 수 있음 · 늘 A가 먼저 돎 ·
  프로세스 전체 값). 기본 글꼴의 판정 항목(요소 수 · `elementBytes` · `viewBytes`)은 A − B = 0이다(계약 r05).**
- 후속:
  - 합침 렌더의 비용을 재려면 측정 뒤 렌더에 잡히는 수단부터 정한다(위 render). 큰 글꼴 `appBytes` 차의 원인은
    A · B 순서를 섞은 회차와 Allocations로 가른다.
  - 합쳐지기 시작하는 iOS 배율 — AX3XL 아래 단계를 차례로 본다.
  - 실기 · 제품 번들 · VoiceOver에서의 합친 흐름 — 미확인.
  - 큰 글꼴에서 상단 칩이 상태 바와 겹쳐 보이는 것 — E4 류 후속(이 작업 밖).
