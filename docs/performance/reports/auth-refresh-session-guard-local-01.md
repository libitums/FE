## 시나리오
액세스 토큰 만료 뒤 진행 저장이 인증 갱신을 기다리는 동안 로그아웃하거나 다른 계정으로 로그인합니다. 이전·새 계정의 응답 순서를 각각 바꿔 처리하고, 같은 계정의 여러 RPC가 하나의 갱신을 공유하는지 확인합니다. 갱신 실패 뒤 재시도와 토큰 조회 직후 로그아웃도 확인합니다.

## 분석 결과
- 수정 전 회귀 테스트 6건 중 5건 실패: 로그아웃 세션 복원, 새 세션 덮어쓰기, 계정 간 갱신 공유(응답 순서 2가지), 로그아웃 이후 RPC 전송.
- 갱신 중인 Promise를 refresh token별로 관리하며, 완료·실패 뒤 해당 항목을 제거합니다. 다른 세션의 응답이 새 세션의 대기 요청을 제거하지 않습니다.
- 응답 저장 전 현재 refresh token을, RPC 전송 전 현재 access token을 확인합니다. 세션이 바뀌었으면 실패 결과를 반환하고 후속 RPC를 보내지 않습니다.
- 정상적인 같은 세션의 동시 요청은 갱신 한 번을 공유합니다. 추가 네트워크 요청·타이머·폴링·UI 상태는 도입하지 않습니다.
- 경계 대역은 네이티브 저장소와 HTTP 전송뿐입니다. 실제 인증·진행 API 코드로 요청과 세션 변경을 검증했습니다.

## 해석
실제 서버의 다른 계정 로그인이나 지연 응답을 운영 계정으로 유발하지 않았습니다. 자동 테스트는 응답 순서를 고정해 세션 격리를 검증하며, 실기 네트워크 지연이나 처리 시간으로 일반화할 수 없습니다. 사용자별 학습 기록의 저장 실패·저장 순서 문제는 별도 수정 대상입니다.

## 결론과 후속
이전 세션의 늦은 갱신으로 현재 세션을 덮어쓰거나 그 토큰으로 후속 RPC를 전송하는 경로를 차단합니다. 제품 화면과 네이티브 동작은 바뀌지 않습니다. 별도 배포 전 검토에서 확인한 학습 저장 문제는 후속 PR에서 처리합니다.
