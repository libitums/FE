## 이 변경이 무엇을 건드렸나

- 학습 껍데기: 이미 받던 `complete`를 장면(`question` · `complete`)으로 바꿔 몸통에 넘긴다. 순수 함수 둘(장면 판별 · 배치별 무대 클래스)이 완료 장면에서만 무대 · 합친 흐름 상자에 클래스를 더하고, 무대에 `data-scene="complete"`를 붙인다. `learning-shell.css`에 규칙 다섯(가운데 정렬 · 남는 세로 받기 셋 · 흐름 상자 하한)이 늘었다. 문항 장면의 DOM · 클래스는 그대로다.
- 활동 여덟(듣기 · 짝 맞추기 · 문장 순서 · 그림 보고 말하기 · 말하기 · 음절 조립 · 타자 · 낱말 고르기): 완료일 때 판정 자리(낱말 고르기는 균형 자리도)를 세우지 않는 조건 한 겹. 쓰기는 변경 없음.
- 문화 카드: keyframe 두 개의 값만 `rotateY(90deg → 0deg)` → `scaleX(0) → scaleX(1)`. 이름 · 길이(`d6`) · 가속(`enter`) · 동작 줄이기 그대로. 모션 린트 허용 목록에 이 파일 한 항목.
- 바뀌지 않은 것: 완료 카드 안(링 · 제목 · 칩 · 모션) · 이미지 · 의존성 · 호스트 코드. 완료 장면의 레이아웃 계산(남는 세로를 받는 상자 하나)이 늘었다 — 레이아웃 비용은 재지 않았다.

## 해석

- 번들이 상한 2,287,000 bytes를 넘어 실측만큼 2,290,000 bytes로 올렸다(사전 승인 범위 — 큰 값 kB 올림 + 1 kB).
- W3의 증가 원인은 추정이다. 확인하려면 W3 앞뒤 산출물에서 화면별 템플릿 수를 세어 비교해야 한다.
- 한계: 미측정 기록이다. 완료 장면의 레이아웃 · 그리기 비용, 뒤집기 중 프레임 시간은 재지 않았다. 런타임 성능 값이 없으므로 이 기록은 성능 기준선이나 회귀 통과의 증거가 아니다.

## Trace 후속 확인

- render: 해당 없음 — Trace를 수집하지 않았다. 완료 장면은 상자 하나가 남는 세로를 받는 배치 변경이다.
- fluency: 해당 없음 — 수집하지 않았다. 뒤집기는 같은 길이 · 가속의 2D 변환으로 바뀌었다(3D 회전 → 가로 배율).
- memory: 해당 없음 — 수집하지 않았다.
- NativeModule: 해당 없음 — 이 변경과 관련된 호출이 없다.

## 결론과 후속

- 결론: 번들은 +3,237 bytes(두 설정 같음)이고 상한을 2,290,000 bytes로 올렸다. ⟨2026-10-20, 이어서⟩ 뒤집는 동안 덱 숨김(사용자 결정)을 더한 뒤 CI 2,289,737 · 로컬 2,289,926 bytes — 덱 숨김분 +1,366(덱 클래스 함수 · 결선 · keyframe 둘 · 규칙 둘), main 대비 합 +4,603. 상한 2,290,000 안이라 올리지 않았다(여유 74 bytes — 다음 변경에서 넘을 수 있다).
- 후속: 2026-10-20 iOS 시뮬레이터 회차가 [완료 화면 e2e](../../e2e/learning-completion.md) 「완료 카드 자리」 CS-1 · CS-3 ~ CS-6과 [새 형식 화면 e2e](../../e2e/episode-format-screens.md) 「G2」 CF10을 통과했다. 남은 것은 CS-2 · CS-7 · CS-8 · CF2 · CF10-A(Android)다. 결정은 [ADR-0022](../../adr/0022-scroll-regions-and-fixed-affordances.md) 적용 기록 2026-10-20 · [ADR-0072](../../adr/0072-culture-card-flip.md) `정정 기록` 2026-10-20.
- 후속: W3 조건 몫 +1,563 bytes의 원인(조건부 자식이 화면마다 템플릿을 하나씩 더 세운다)은 **아직 추정**이다. W3 앞뒤 산출물에서 화면별 템플릿 수를 세어 확인하는 일이 남았다.
- 예고: 번들 상한 2,290,000 bytes까지 여유가 **74 bytes**뿐이다. 다음 번들 변경은 상한을 넘을 가능성이 높으니, 그 변경의 성능 보고서에서 증가 출처와 상한 조정을 함께 다룬다.
