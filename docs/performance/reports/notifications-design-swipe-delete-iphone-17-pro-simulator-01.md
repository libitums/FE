## 시나리오

- 전제: 저장된 로그인 토큰이 있어 Host가 곧장 여정 맵으로 뜬다. 알림은 넷이다. 시스템
  글자 크기는 기본이다.
- 단계: Host를 `--performance-capture`로 띄우고 6초 둔다. 여정 맵 머리의 알림 버튼을
  누르고 2초 둔다. 첫 알림 카드를 왼쪽으로 120pt 밀고(0.3초) 1초 둔다. 열린 `삭제`를
  누르고 2초 둔다. 캡처 파일을 분석기로 읽고 Host를 종료한다. 같은 절차를 두 번 더
  반복한다. 조작은 `idb`로 같은 좌표에 넣었다.
- 관찰 구간: timing flag가 붙은 update pipeline과 그 직후의 전역 메모리 snapshot.

다른 작업이 기본 시뮬레이터를 쓰고 있어 같은 기종 · 같은 런타임의 시뮬레이터를 따로
만들어 쟀다. 그래서 `performance:capture` 명령(`booted`를 고른다) 대신 같은 실행 인자로
`simctl launch`를 직접 부르고, 캡처 파일을 `performance:report`의 분석기로 읽었다.

## 이 변경이 무엇을 건드렸나

- 알림 화면의 머리가 낱말 나가기 + 옆 제목에서 동그란 버튼(ui-lynx `RoundButton`) +
  가운데 제목으로 바뀌었다.
- 항목이 테두리 있는 흰 카드에서 회색 면의 카드로 바뀌고, 항목마다 줄 상자가 한 겹
  더해졌다(카드와 삭제 자리를 가로로 놓는 자리). 알림이 넷이므로 노드 넷이 늘었다.
- 카드에 터치 핸들러 셋(시작 · 이동 · 길게 누르기)이 붙었다. 손가락이 움직이는 동안
  이동 이벤트마다 background thread에서 밀기 판정이 돈다 — 판정이 나기 전까지는 상태를
  바꾸지 않으므로 다시 그리기는 일어나지 않는다.
- 삭제 자리가 열리고 닫힐 때, 그리고 알림이 지워질 때 목록이 다시 그려진다.
- 알림 목록이 모듈 상수에서 `App` 상태로 옮겨졌다. 여정 맵을 그리는 경로는 바뀌지
  않았다.

## 분석 결과

여정 맵에 닿는 update pipeline(`libitum:navigation:journey`)이다.

| 회차  | pipeline  | layout    | paintingUiOperationExecute |
| ----- | --------- | --------- | -------------------------- |
| 1회차 | 30.379 ms | 16.830 ms | 5.201 ms                   |
| 2회차 | 27.566 ms | 12.919 ms | 5.809 ms                   |
| 3회차 | 28.971 ms | 14.779 ms | 5.714 ms                   |

같은 회차들의 나머지 값이다.

```text
Rendering
  FCP loadBundle: lynxFcp 73.024 / 65.269 / 85.507 ms

Memory
  after-navigation-journey-01 [complete]: totalBytes 1668688 bytes,
    elementBytes 156000 bytes, viewBytes 95360 bytes,
    mainThreadRuntimeBytes 1417328 bytes, elementNodeCount 150 nodes (세 회차 같음)
```

**알림 화면의 구간은 수집되지 않았다.** 알림 화면을 여는 전이 · 삭제 자리가 열리는
다시 그리기 · 알림이 지워지는 다시 그리기에는 timing flag가 없어 pipeline entry가 생기지
않고, 메모리 snapshot도 탭 전환에만 걸려 있다. 그 값을 추정하거나 `0`으로 쓰지 않는다.

수치와 별개로, 같은 빌드에서 동작을 눈과 접근성 트리로 확인했다.

- 목록: 카드 넷이 폭 370 · 높이 113으로 서고 간격은 16이다.
- 밀기: 첫 카드를 왼쪽으로 밀면 카드 폭이 282로 줄고 오른쪽에 폭 72의 삭제 자리가
  선다. 다른 카드는 그대로다.
- 삭제: 삭제를 누르면 그 알림만 사라지고 아래 카드들이 올라온다.
- 빈 상태: 넷을 모두 지우면 표식과 글 두 줄이 선다.

## 해석

**이 기록은 이 변경의 비용을 말하지 못한다.** 한계가 셋이다.

첫째, **잰 구간과 바뀐 구간이 다르다.** 수집된 pipeline은 여정 맵을 그리는 구간이고,
이 변경이 바꾼 것은 알림 화면이다. 위 표는 「알림 목록을 `App` 상태로 옮긴 것이 여정
맵을 그리는 경로를 눈에 띄게 바꾸지 않았다」까지만 가리키고, 알림 화면의 비용은
미측정이다.

둘째, **다른 기록과 같은 축에 놓을 수 없다.** 이번 측정은 새로 만든 시뮬레이터에서
돌았다. 같은 기종 · 같은 런타임이지만 앱이 막 설치된 상태라 캐시와 디스크 상태가 다르다.
여정 맵 pipeline이 27.6~30.4 ms로 다른 보고서들(36.8~44.2 ms)보다 낮게 나온 것을 변경의
효과로 읽지 않는다.

셋째, **단일 기기 · 세 회차다.** 전환 pipeline의 흔들림 폭을 아직 모르므로, 세 값의
차이가 회차 잡음인지 판정할 수 없다.

병목 후보로 눈여겨볼 자리는 둘이다. 하나는 카드의 이동 이벤트다 — 손가락이 움직이는
동안 이벤트가 background thread로 계속 넘어온다. 세로 스크롤 중에도 넘어오므로, 알림이
많아지면 스크롤 유창성에 닿을 수 있다. 다른 하나는 삭제 자리가 열릴 때 카드 폭이 바뀌며
문구의 줄바꿈이 다시 계산되는 것이다. 시뮬레이터에서 눈으로는 끊김이 보이지 않았지만,
그것은 측정이 아니다.

## Trace 후속 확인

- render: 여정 맵 첫 착지의 mtsRender → resolve → layout → UI operation → paint는
  기록했다. 알림 화면의 update는 미수집이고 Trace도 수집하지 않았다.
- fluency: 미측정 — 밀기와 세로 스크롤이 겹치는 구간의 프레임 단위 기록이 없다. 실기
  Trace가 필요하다.
- memory: 탭 전환 직후 snapshot만 있다. 알림 화면에 들어간 뒤와 알림을 지운 뒤의 값은
  재지 않았다.
- NativeModule: 해당 없음 — 이 변경은 NativeModule을 부르지 않는다.

## 결론과 후속

- 결론: 여정 맵을 그리는 pipeline은 27.6~30.4 ms로 관측됐다. 알림 화면을 열고 · 밀고 ·
  지우는 구간의 비용은 수집 수단이 없어 재지 못했다.
- 후속: 알림 화면을 여는 전이에 timing flag를 붙이면 그 구간을 같은 도구로 잴 수 있다.
  밀기와 스크롤의 유창성은 실기 Trace로 확인한다. 둘 다 아직 이슈가 없다.
