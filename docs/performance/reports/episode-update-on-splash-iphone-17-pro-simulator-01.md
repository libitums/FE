## 시나리오

- **스플래시 체류** — 두 갈래를 나눠 본다.
  1. 바뀐 것 없음(받을 것 없음) · 오프라인 · 매니페스트가 로고 끝 뒤에 답함 → 게이지 없음, 로고가 끝나면 바로 나감.
  2. 받을 것 있음 → 로고 아래 게이지, 로고 끝 뒤 다 받으면 바로 · 못 받으면 3초 뒤 나감.
- **번들 크기** — 이 브랜치의 단계별 산출을 main 상한과 비교했다.
- **동시 받기 4** — 에피소드 하나의 자산 받기 시간을 동시 1(바꾸기 전 빌드)과 4로, 보통 망 · Network Link Conditioner(왕복 250ms)에서 비교하는 계획이었다([e2e](../../e2e/episode-update-on-splash.md) EU-10). **돌리지 않았다.**

## 이 변경이 무엇을 건드렸나

- 백그라운드 JS: 스테이징 · 교체(`episode-staging`) · 분류 · 차례(`episode-update-plan`) · 갱신 분할(`episode-refresh-entry`) · 동시 받기 풀(`episode-asset-sync`) · 주소 키(`episode-remote`) · 스플래시 상태 리듀서 · 컨트롤러 · 훅 결선.
- 메인 + 백그라운드: 게이지 컴포넌트 · 스플래시 시간 규칙 · context · CSS 규칙 일곱 · 문구 · 첫 등장 알림.
- Android 호스트: 받기 실행기 단일 → 4 스레드(JS 번들 밖). 의존성 · 이미지 · 음원 변경 없음.
- 런타임 비용의 새 축: 게이지가 선 실행의 스플래시 체류(최대 로고 끝 + 3초), 나갈 때의 동기 교체 + 카탈로그 다시 읽기(본문 디코드 · sha256), 한 에피소드 안 최대 4개의 동시 연결.

- 계약 예측은 +6 ~ 13 kB(백그라운드 모듈 · 게이지 · 동시 받기 풀 +0.3 ~ 0.6 kB · 주소 키 +0.2 ~ 0.4 kB)였다. 결선까지 이미 예측 상단을 넘었고, **모듈별로 나눠 재지 않아 넘은 몫(약 1 ~ 3 kB)은 이 보고서에서 설명하지 못한다.** 새 의존성 · 미디어는 없다.

### 동시 받기 4

- **미측정**(EU-10은 Android 에뮬레이터 느린 망(250ms · 5Mbps)에서 게이지가 5초 무렵 약 10 %에 머물다 상한에서 넘어가는 것만 봤다 — 동시 1 vs 4 비교는 하지 않았다). 왕복 0.2 ~ 0.3초 망에서 에피소드 하나(자산 13 ~ 17개)가 차례 받기로 4 ~ 5초라는 것은 계약 단계의 어림이다 [추론]. 4개 동시가 그것을 3초 안으로 줄이는지, 음성 파일이 대역을 나눠 이득이 줄어드는지 알 수 없다.
- 자동 테스트가 지키는 것은 동작 규칙(상한 4 · 실패 뒤 새 시작 0 · `missing` 입력 순서 · 중복 1회)과 Android 호스트에서 서로 다른 경로 넷이 동시에 저장되는 것뿐이다.

## 제한 사항

- 스플래시 체류의 「약 3초」는 한 회차 · 한 기기(시뮬레이터)에서 눈으로 본 값이다 — 녹화 프레임을 재지 않았고 일반화할 수 없다. 게이지 없는 실행이 이전과 같은 길이라는 것은 설계와 integration 테스트의 근거이고 기기 측정 근거가 없다.
- 동시 받기의 효과 · 나갈 때 교체 비용(수십 ~ 100여 ms로 어림) · 렌더링 · 메모리 · 데이터 사용량은 미측정이다. Android는 스플래시 길이(오프라인 · 받을 것 없음)만 쟀다.
- 번들은 단계마다 같은 설정으로 다시 잰 값이 아니다(첫 줄은 구현 단계 보고값) — 단계별 차이는 대략의 몫으로만 읽어야 한다.
- 이 보고서는 성능 기준선이 아니다.
