# 진입 흐름 여섯 화면 — 스플래시 · 온보딩 · 로그인 · 코드 검증 · 언어 선택 · 여정 입장 — iOS Release 수동 e2e

## 판정 채널과 범위

이 문서는 처음 앱을 켠 사용자가 스플래시 → 온보딩 → 로그인 → 코드 검증 → 언어 선택 →
여정 입장을 지나 여정 맵에 들어가는 흐름을, 그리고 임시 인증 토큰(소셜) 또는 로그인
세션(전화번호, Supabase SMS OTP)이 있을 때·없을 때 재실행이 어떻게 갈리는지를 iOS
Release Host와 실기기에서 확인하는 수동 functional · Dynamic Type · 소프트 키보드 ·
VoiceOver e2e 절차다. 저장소 profile에는 `test.e2e`
명령과 runner가 없다 — **자동 E2E: not applicable(runner/command 없음)**이며, 이
계층의 「테스트를 쓰는 행위」는 이 흐름 문서를 세우는 것 자체다(LIB-247 §6.4(d)).

⚠ **이 문서의 보정 r0.3(Supabase 로그인)** — `.agent-harness/work/supabase-login/spec.md`
§12 AC8이 요구하는 실제 전화번호 인증 관찰을 「전화번호 인증(Supabase SMS OTP) 여정
E1–E7」로 더하고, 기존 T4(자릿수) · T8(재실행 갈래) · T9(문면)를 그 변경에 맞춰 고친다.
셈하는 자리는 `.agent-harness/work/supabase-login/test-plan.md` §5이고 이 문서가 절차
사본이다 — E1~E7 표 항목을 여기서 더하거나 빼지 않는다.
아래 표는 `.agent-harness/work/lib-261/spec.md` §12.1이 정본이고 이 문서가 사본이다 —
표 항목을 여기서 더하거나 빼지 않는다.

T1~T9·D1은 시뮬레이터에서 먼저 돌 수 있다. 그러나 그 결과만으로 `e2e-red`의 `moot`
값을 주장하지 않는다. **K1~K5는 실기가 답한다** — 소프트 키보드는 이 저장소에서
호스트에 처음 열리는 축이고, 시뮬레이터에는 실물 키보드 가림·완료 키 동작이 없다.
K5(코드 두 자리만 넣고 `확인`을 눌렀을 때의 반응)도 같은 이유로 실기 전용이다.
**V1~V3·V5는 iPhone 실기 · Release · VoiceOver로 사람만 판정한다**(K3·K4·V1·V5는
판정 절과 기록 절을 함께 지고, K5·V4·V6은 전부 관찰 기록형이다 — 아래 「소프트

## 전제

공통 전제([docs/e2e/README.md](README.md)) + **Release Host** + ⭐ **앱을 삭제·재설치한
새 상태**(임시 토큰도 로그인 세션도 없어야 진입 흐름이 선다. **둘 다 지우는 수단이 앱에
없다** — 아래 「재설치가 유일한 재진입 수단이다」).

**전화번호 인증(E1~E7)에 추가로 필요한 전제** — `apps/mobile/.env.local`에
`PUBLIC_SUPABASE_URL` · `PUBLIC_SUPABASE_ANON_KEY`가 채워진 Release 산출물(개발
프로젝트 — 값은 팀 내부에서 공유하고 저장소에 적지 않는다) · 그 프로젝트에 Phone Auth가 켜져
있고 Supabase 대시보드 Auth → Phone의 **테스트 전화번호와 고정 코드**가 등록돼 있다(번호와 코드도
저장소에 적지 않는다 — 번들에 든 공개 키와 합치면 누구나 세션을 만들 수 있다) · OTP 유효기간은 프로젝트 설정상 **300초**(코드 화면 카운트다운 `05:00`과 같다).
**실제 전화번호로 SMS를 받는 관찰은 Twilio 자격 증명이 프로젝트에 설정된 뒤에만 유효하다**
— 이 회차 작성 시점에는 비어 있어 테스트 번호로만 돈다(spec §12 Q-1 · Q-2,
evidence.yaml `user-decision`). 어느 경로(테스트 번호 · 실제 번호)로 돌았는지를 각 행의
결과에 적는다.

각 행의 결과에는 `통과` 또는 `실패: <관찰>`만 기록하고, 추정이나 인상은 넣지 않는다.
**관찰 기록형 자리는 결과 칸이 다르다** — `K5` 전체, `V4` 전체, `V6` 전체는
통과/실패를 가르지 않고 `기록: <관찰 그대로>`로 적는다(선례
`docs/e2e/notifications.md` V4). **`K3` · `K4` · `V1` · `V5`는 판정 절과 기록
절을 함께 진다** — 같은 칸에 `통과`/`실패: …`와 `기록: …`를 나란히 적는다(선례
`docs/e2e/settings.md` V1). `무음`도 유효한 기록값이고, 빈칸 · `미실행` ·
「확인함」 같은 요약어는 기록이 아니다. 아직 돌지 않은 행은 `미실행`, 아직 채우지
않은 증거는 `미기록`으로 둔다 — 결과 값이 아니라 결과가 아직 없다는 표시다(선례
[알림](notifications.md) · [설정](settings.md)).

### ⭐ 재설치가 유일한 재진입 수단이다 — 시작 전에 읽는다

저장소에 들어가는 항목은 **소셜 수단으로 들어오면 `libitum.auth.token` 하나, 전화번호
(Supabase OTP)로 들어오면 `libitum.auth.session` 하나**이고(spec §0.3 D-d ·
`.agent-harness/work/supabase-login/spec.md` C3), **둘 다 지우는 수단이 앱에 없다**
(로그아웃은 이번 범위 밖 — spec §11.3. 세션은 서버가 refresh를 거절할 때만 지워지는데
그 경로는 별도 이야기다 — 이 표의 T8·T9는 만들지 않는다). 한 번 T1~T7을 끝까지 돌아
토큰 또는 세션이 생기면, 그 뒤로는 앱을 재시작해도 **온보딩·로그인·코드 검증·언어
선택을 다시 볼 수 없다** — 다만 **T1~T7을 소셜로 돌았는지 전화번호로 돌았는지에 따라
재실행의 모양이 갈린다**(아래 T8 행): 소셜은 오늘처럼 스플래시 뒤 **바로** 여정 맵,
전화번호는 스플래시가 **refresh 왕복이 끝날 때까지 그대로 서 있다가** 여정 맵으로
넘어간다. 이 표를 처음부터 다시 돌려야 하면 **기기에서 앱을 삭제하고 다시 설치**하는
것이 유일한 방법이다(T9 — R2). 이것은 결함이 아니라 이 회차의 **대가**다 — 확인자는
T1~T7 회차와 T8·T9 회차를 **서로 다른 설치**에서 준비해야 한다.

⚠ **수용 기준 5(「언어를 다시 켜면 사라진다」)는 이 흐름이 답하지 못한다.** 토큰이
있으면 언어 선택에 다시 갈 수 없고, 토큰을 지우려면 재설치인데 그러면 세션 자체가
새것이라 「언어를 골랐다가 다시 켰다」를 재현할 방법이 없다. **판정자는 integration
`IE12` 하나뿐**이다 — 이 표의 어느 행도 그 기준을 판정하지 않는다. 확인자는 T6에서
언어가 세션 안에서 유지되는 것만 보고, 「다시 켜면 사라진다」는 **찾지 않는다**.

## 실행 전 증거 고정

한 회차는 아래 값이 모두 채워진 **동일한 Release 산출물**로만 판정한다. 값이 비었거나
서로 다른 빌드에서 왔다면 T1을 시작하지 않는다. 이 흐름은 작성 시점까지 한 번도
실행된 적이 없으므로, 아래 표는 실행자가 회차마다 채운다. **T1~T7 회차와 T8·T9 회차는
설치 상태가 다르므로 행을 나눠 각각 채운다**(위 「재설치가 유일한 재진입 수단이다」).

| 증거 | 실행 회차 기록 |
|---|---|
| 소스 identity(커밋과 작업 트리 상태 또는 동등한 재현 식별자) | 미기록 — 실행 시 입력 |
| iOS Host.app SHA-256 | 미기록 — 실행 시 입력 |
| `main.lynx.bundle` SHA-256 | 미기록 — 실행 시 입력 |
| 실기기 모델 · iOS 버전 | 미기록 — 실행 시 입력 |
| 빌드 종류 | 미기록 — 실행 시 입력(Release여야 한다) |
| 앱 삭제·재설치 여부(이 회차의 시작 상태) | 미기록 — 실행 시 입력(T1 시작 전 필수 · T8은 재설치하지 않음 · T9는 재설치함) |
| T1~T7에서 고른 로그인 수단(소셜 또는 전화번호) | 미기록 — 실행 시 입력(T8의 관찰이 이 값에 따라 갈린다) |
| 전화번호 인증 경로(테스트 번호 `<테스트 번호>` 또는 Twilio 설정 뒤 실제 번호) | 미기록 — 실행 시 입력(E1~E7에만 해당) |
| 확인자 · 확인 시각(시간대 포함) | 미기록 — 실행 시 입력 |

## 기능 · Dynamic Type 여정 T1–T9 · D1

앱을 **삭제하고 새로 설치한** 상태에서 시작한다(토큰 없음). 아래 표는 spec §12.1
표의 사본이다 — ID · 단계 · 관찰 · 답하는 수단 열의 문구를 여기서 고치지 않는다.
`결과` 열만 이 문서가 더한다.

| ID | 단계 | 관찰(식별 가능한 요소) | 답하는 수단 | 결과 |
|---|---|---|---|---|
| T1 | 앱을 열고 기다린다 | `splash-screen-service-name` = `Duru`. 조작 수단이 **0건**. 고정 시간 뒤 **온보딩**이 선다. **바텀 네비게이션이 없다** | 시뮬레이터 또는 실기 | 미실행 |

| T3 | 전화번호를 입력하고 `전화번호로 계속하기` | 입력한 숫자가 칸에 보인다. **코드 검증**이 선다 | 시뮬레이터 또는 실기 | 미실행 |

  진다** — 같은 칸에 `통과`/`실패: …`와 `기록: …`를 나란히 적는다(선례
  `docs/e2e/settings.md` V1). **K5는 관찰 기록형이다** — `기록: <관찰 그대로>`로
  적는다(예: `기록: 무음`, `기록: 진동 있음 · 오류 문구 없음`). `무음`·`무반응`도
  유효한 기록값이다.
- ⚠ **K3이 「덮인다」로 답하면 차단 항목이 된다**(spec §15 Q-1). 그 경우 화면 CSS를
  현장에서 고치지 않는다 — 처방 경로는 `@libitums/ui-lynx`의 키보드 회피 프롭 개방이고,
  그 프롭을 여는 것은 이 단위의 범위 밖이라 **사람(오케스트레이터)이 판단한다.**
  `실패: <덮인 높이 · 기기>`로만 적고 화면을 직접 고치지 않는다. **K3의 기록 절은
  그 판정을 바꾸지 않는다** — VoiceOver로 `확인`에 닿고 활성화된다는 관찰이 나와도
  그것이 「안 덮인다」의 근거가 되지 않는다(iOS 키보드는 별도 윈도라 덮인 요소가
  접근성 트리에서 빠지지 않기 때문이다 — `accessibility.md` (a)2).
- ⚠ **K4가 「없음」으로 답하면 `실패: 없음`이고 K3과 같은 차단 항목이 된다**(M-1,
  spec §12.1 · §12.3). `confirm-type`이 이 단위의 두 입력에 안 붙고(§11.2) 숫자
  키패드에는 return 키가 없어 「없음」이 나올 근거가 소스에 있다 — 그래서 기록형에서
  판정 항목으로 승격했다. K3(가림)과 K4(내릴 수단 없음)가 함께 「덮인다」·「없음」으로
  답하면 코드 검증 화면에서 **진행 자체가 막힌다.**
- K5는 **판정 대상이 아니다** — `확인`에 `disabled` trait을 붙이지 않은 D10 결정의
  대가를 기록으로만 남기는 자리다(m-2, spec §4.3 · §12.1).
- K1~K5가 돌지 않으면(실기가 없으면) `e2e-red`에 참인 값이 없다 — T · D만 돈 결과로
  `moot`를 주장하지 않는다(spec §12.3).

  `docs/e2e/settings.md` V1).

### V3의 배율을 산술로 닫을 수 없는 이유

코드 검증 머리는 ADR-0023 게이트 A 실패(Δ 12) → **안 B**로 갚은 형태이고, **같은
레시피에서 산술이 통과인데 실기가 뒤집은 사건이 이미 있다**(LIB-227 **E-S3**,
`docs/e2e/journey-map.md`). VoiceOver는 DOM이 아니라 프레임 위치로 순회하고 동률 ·
근접의 타이브레이크가 이 저장소에서 확인된 적이 없다. ⇒ **배율을 박는 것은 이 행에서만
답이 나오는 축이다**(선례 `docs/e2e/notifications.md` V1의 「기본 · 최대 배율 모두」).
**어긋나면 CSS를 현장에서 추측으로 고치지 않는다** — 대응 경로는 ADR-0023의 대체안
B′다.

### V4 · V6의 지위 — 판정 대상이 아니다

이 관측이 드러낼 것을 고칠 경로가 이 회차에 없다(announce를 쓰지 않는 것이 이
회차의 결정이다 — spec §4.4). 그래서 실패 조건을 두지 않는다(선례
`docs/e2e/notifications.md` V4). **V6도 같은 이유로 판정 대상이 아니다** — 여정
입장·탭 바 등장 순간의 낭독도 `announce`를 쓰지 않는 이 회차의 결정 아래에서는
고칠 경로가 없다.

### e2e-red 판정 항목 셈 — 21항목이 어떻게 갈리는가(spec §12.3, 보정 r0.3)

⚠ **보정 r0.3 — K4가 기록 항목에서 판정 항목으로 옮겨 갔다(M-1). K5·V5·V6이
신설되며 판정 항목과 기록 전용 항목의 셈이 달라졌다.**

- **판정 항목(18개)** — 실패 하나로 `confirmed`가 서는 자리: `T1~T9`(9) ·
  `D1`(1) · `K1~K4`(4) · `V1~V3`(3) · **`V5`의 판정 절**(1).
- **기록 절(판정 항목에 곁달린 넷)** — `K3` · `K4` · `V1` · `V5`의 기록 절. 판정을
  바꾸지 않지만 `moot`가 서려면 비어 있으면 안 된다.
- **기록 전용 항목(셋)** — `K5` · `V4` · `V6`. 통과/실패가 없고 `기록: …`만 있다.
  같은 이유로 `moot`가 서려면 비어 있으면 안 된다.

`e2e-red`의 `test.e2e.red-proof: moot`는 **판정 항목 18개 전부 통과** +
**기록 절 넷(K3·K4·V1·V5)과 기록 전용 셋(K5·V4·V6)이 전부 완비**됐을 때만 선다.
판정 항목 중 하나라도 실패하면 `confirmed`(실패 ID와 관찰을 적는다). **K3이
「덮인다」로 실패하면**(위 소절) 이 계약의 커밋 범위 밖 처방(`ui-lynx` 프롭 개방)이
필요한 차단 항목이 된다는 것도 여전히 참이다. K · V를 돌릴 실기가 없으면 어느 값도
기록하지 않는다(spec §12.3 「기록하지 않는다」 행) — T · D만 돈 결과로 `moot`를
주장하지 않는다. 열리는 문은 **사람(사용자)이 iPhone · Release · VoiceOver로 이
흐름을 도는 것**뿐이다.

## 이벤트 운영 범위

`EntryAppProps.entryEventSink`의 현재 제품 진입점은 명시적 `null`이다(spec §7.5).
따라서 이 문서의 어떤 관찰도 이벤트(`entry_screen_viewed` · `entry_login_method_selected` ·
`entry_completed`)가 실제 운영 집계로 전송되었다는 증거로 쓰지 않는다. 이벤트의 경계와
순서는 `integration`(`App.entry.integration.test.tsx`)이 진다. 운영 sink 연결과 서버
집계는 별도 후속 범위다. ⟨**2026-09-29** — 제품 진입점이 이제 sink를 PostHog로 잇는다(키가 있는 빌드만, [ADR-0029](../adr/0029-product-analytics-posthog.md)). 이 문서의 판정은 그대로이고, 전송 관찰은 [분석 e2e](analytics.md) 한 곳에 모은다⟩
