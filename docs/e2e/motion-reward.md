# 통과 배지 보상 모션과 문항 전환 등장이 기기에서 보인다 — 배지 확대 · 문항 흐려짐 · 전환 중 입력 · reduced 분기 (iOS · Android)

보상 모션(lesson-complete 통과 배지)과 LearningShell 문항 전환을 시뮬레이터 · 에뮬레이터에서 확인하는 **수동 절차**다. 계약은 작업 `motion-tokens-stage3`의
`spec.md` §6(AC1 · AC3 · AC5 ~ AC8 · AC11) · §11(가정 A1 ~ A5)이 진다. 이 문서는 아래 일곱 가지만 본다.

1. 통과 배지 보상 등장 — 끈(standard) 상태에서 지름 80 %(126 → 약 101 css px) · 반투명으로 시작해 약 400 ms 뒤 정착하고, 미통과(`LESSON FAILED`) 배지는 모션이 없다.
2. 문항 전환 등장 — 무대 · 작업 영역이 불투명도 0 → 1, 오른쪽 `translateX`(최대 16 css px) → 0으로 약 300 ms에 들어온다. 헤더 · 진행 바 **트랙** · 지시문 · 액션 행은 움직이지 않는다 — 진행 바 **채움**은 4단계부터 `progress`로 차오르므로 M3-I9 · M3-A9가 잰다(문항 하나짜리 유닛 · 완료 장면에서는 채움이 이미 100 %라 bbox 불변이 그대로 성립한다 — [ADR-0053](../adr/0053-motion-policy.md) D5).
3. 전환 중 입력 — 넘김 층을 누른 직후(≤ 200 ms) 다음 문항의 보기를 누르면 **새** 문항에 간다.
4. reduced 분기 — 켠 상태에서 배지는 축소 없이 불투명도만, 문항은 이동 없이 불투명도만(약 100 ms).
5. 2단계 회귀(R2 삭제 뒤) — RoundButton 눌림 95 %, 켠 상태 막 색.
6. Android `transform` 안 `var()`(M3-A8, **탐색**) — 판정이 아니라 4단계의 입력이다. *(4단계에서 전환했다 — 탐색 항목은 닫혔고, 전환 뒤 회귀는 M3-I6 · M3-A6과 아래 「4단계 회차」가 본다.)*
7. 보조기술 — VoiceOver · TalkBack을 켠 상태에서 문항 전환 직후 초점이 서는 자리 · 정지 수, 배지가 정지점이 아닌지 · 낭독(M3-I8 · M3-A7). 기기 없는 회차는 「미확인」으로 둔다.

| 이미 지는 층 | 무엇을 |
|---|---|
| unit | 보상 판정(`rewardMotionFor`) · 클래스, 전환 상태 기계(키 · 초기 상태 · 전이 · 시간 · 클래스) |
| ui | 배지 `data-reward` · 클래스 · 재렌더 불변, 무대 · 작업 영역 전환 속성과 타이머, 전환 속성이 무대 밖에 없음, RoundButton 막의 접근성 속성 부재, CSS 텍스트(keyframes · transition · reduced 규칙 · 배지 keyframe의 `scale(var(--libitum-motion-scale-reward))` 문자열 단언과 비항등 scale 리터럴 0 — 4단계 전까지는 `scale(0.8)` 숫자 대조였다), 진행 바 채움의 reduced 클래스 · `data-motion`(4단계) |
| integration | 앱 ↔ ui-lynx `MotionProvider` Context가 앱 훅까지 하나인지, 통합 25자리의 즉시 호출 불변 |

수용 기준 대응(`spec.md` §6): **AC1** = M3-I1 (a)(b) · M3-A1, **AC3** = M3-I1 (c) · M3-I7 · M3-A1, **AC5** = M3-I3 · M3-I4 · M3-A3 · M3-A4, **AC6** = M3-I3 (c) · M3-A3,
**AC7** = M3-I5 · M3-A5, **AC8** = M3-A8, **AC11**(기기 확인) = 이 문서. M3-I2 · M3-I6 · M3-A6은 회귀(수정 전후 같아야 한다).
가정 대응(`spec.md` §11): **A1**(primed → entering 두 커밋 사이 한 프레임이 그려져 0 → 1이 보임) = M3-I3 · M3-A3, **A2**(`<scroll-view>`의 `opacity` · `transform` 전환이 자식과 함께
그려짐) = M3-I3 · M3-A3, **A3**(`transition: none` 시작값을 Lynx가 기억함) = M3-I3 · M3-A3(A1과 같은 캡처), **A4**(Android `transform` 안 `var()`) = M3-A3 (b) · M3-A8,
**A5**(배지 첫 프레임 측정 방식) = 아래 「전제」 4.
접근성 대응: **M3-I8 · M3-A7**은 수용 기준이 아니라 접근성 점검이 남긴 실기 항목이다 — iOS에서는 `opacity` 전환 중 무대 · 작업 영역의 모델 alpha가 0이라 보조기술이 그 시간
동안 건너뛸 수 있다([ADR-0025](../adr/0025-ui-lynx-package-and-storybook-catalog.md) 「2026-10-09 3단계」). 실기만이 「실제로 초점이 어디에 서는가」를 안다.

## 이 절차로 확인하지 못하는 것

- **두 커밋 사이 프레임(A1) · scroll-view 전환(A2) · `transition: none` 시작값(A3)**: 기기에서 **중간 프레임이 한 장이라도 잡히면** 성립으로 적는다. 잡히지 않는다고 곧 실패는
  아니다 — 캡처 간격(수백 ms)이 300 ms보다 길 수 있다. 그래서 M3-I3은 두 프레임이 모두 정착이면 먼저 「판정 불가」로 다시 잡고, **녹화로도 중간 프레임이 없을 때만 A1 실패**로
  적는다(통과로 적지 않는다). 안 될 때의 대안(keyframe 이름 교대, 안쪽 래퍼 `<view>`에 걸기)은 이 절차의 범위 밖 — 4단계다.
- **Android에서 `transform` 안 `var()`가 풀리는가(A4)**: M3-A3 (b)의 x 오프셋 **유무**와 M3-A8의 탐색이 적는다. 통과/실패가 아니다. 안 풀리면 그 선언만 무효가 되어 이동 없는 fade로
  **조용히 열화**된다(불투명도 선언은 별도 줄). 결과 처리는 `spec.md` D8(4단계).
- **캡처 간격의 한계**: iOS `simctl io screenshot`은 수백 ms, Android `screencap`은 한 장 0.4 ~ 1.2 s다. 400 ms · 300 ms 전환의 중간 프레임을 정확한 시각에 잡을 수 없다 —
  **녹화(`recordVideo` · `screenrecord`)를 기본으로 하고 프레임을 뽑는다**([동작 줄이기 e2e의 「연속 두 장 비교」](motion-reduced.md#연속-두-장-비교)). Android의 기본 수단은 `screenrecord`이고
  (화면이 바뀔 때만 프레임을 만든다 — 변화 시 약 12 fps · 60 ~ 90 ms, **정지 구간에는 프레임이 생기지 않는다**) `screencap`은 보조다. 곡선(이징)의 모양 · 정확한 시간(400 ms ·
  300 ms · 100 ms)은 재지 않는다. 이 문서는 「첫 프레임이 작고 옅다 → 정착값」과 「정착이 약 이 시간 안에 끝난다」(±한 프레임)만 판정하고, 값은 unit(CSS 텍스트)이 진다.
- **`data-page` 속성의 잔존**: 테스트 렌더러는 한 번 붙은 `data-*`를 조건부 spread에서 빠진 재렌더에서 지우지 않아 idle 복귀 뒤에도 `data-page="entering"`이 남는다
  (`spec.md` §14.1). 실제 기기에서 속성이 남는지는 devtool이 있어야 읽을 수 있고, CSS는 클래스만 보므로 관찰 결과에는 영향이 없다. 이 절차는 읽지 않는다 — 읽는 수단을 찾으면 비고에 적는다.
- **iOS 실기**: 시뮬레이터로 판정한다. 닿으면 M3-I1 · M3-I3을 한 번 더 하고, 못 하면 「미확인」으로 적는다. 시뮬레이터 통과를 실기 통과로 적지 않는다.
- **TalkBack · VoiceOver**: M3-I8 · M3-A7이 잰다 — accessibility 단계는 기기를 쓰지 않으므로 거기에 넘기면 영원히 닫히지 않는다. 시뮬레이터 · 에뮬레이터 회차가 보조기술을 켜지
  않았으면 「미확인」으로 적고 통과로 적지 않는다.
- **재입력 · 연타**: 전환 300 ms 안에 두 번째 문항 변화가 오는 경우의 시각(entering 유지)은 재현이 어려워 관찰 항목이 아니다. 옛 문항의 사라짐(퇴장)은 적용하지 않았으므로 볼 것이 없다.
- 나머지 한계(Android 배율 0이 플랫폼 애니메이터까지 멈추는 겹침, `data-motion` 값을 직접 못 읽음): [동작 줄이기 e2e의 「이 절차로 확인하지 못하는 것」](motion-reduced.md#이-절차로-확인하지-못하는-것)과 같다.

## 전제

준비(전용 시뮬레이터 · 에뮬레이터, 전역 설정 값 기록 후 복원, 「같다 = 정지, 다르다 = 움직임」, iOS · Android 빌드 · 설치 · 캡처 · 녹화)는 [동작 줄이기 e2e](motion-reduced.md)의
「전제」 · 「iOS 준비」 · 「Android 준비」 · 「연속 두 장 비교」를, 측정 도구와 조작 습관은 [0.4.0 motion 토큰 e2e](motion-tokens.md)의 「전제」 3 · 4를 **그대로** 따르고 되풀이하지 않는다
(로그인된 상태에서 시작 — [공통 전제](README.md#공통-전제)). 이 작업만의 부분:

1. **호스트는 바뀌지 않았다 — 번들만 새로 만든다.** 단 **1단계 호스트(`reducedMotion`을 boolean으로 보내는 `d602fe08` 이후)가 설치돼 있어야** 켠 상태가 전달된다. 결과 표에 번들 SHA와 호스트 SHA를
   따로 적는다.
2. **수정 전 번들 `162f5648`과 대조한다**(2단계 병합 커밋 — 보상 · 문항 전환이 아직 없다). 아래 「red의 근거」.
3. **도달 길** — **이 빌드의 유닛은 전부 문항이 하나다**(`journey-map-learning-form.ts` 한 유닛 한 활동, 듣기 `1 of 1 question completed`). 그래서 「문항 1 → 2」는 도달할 수 없고,
   문항 전환은 같은 상태 기계의 `complete` 키 경로인 **문항 → 완료 장면(「All questions done」)** 으로 근사한다. 문항이 둘 이상인 유닛이 생기면 아래 「문항 전환」을 문항 1 → 2로 되돌리고
   M3-I3 (a)의 작업 영역(보기 영역) 부분을 다시 본다 — 완료 장면에는 작업 영역이 없어 그 부분은 이 근사로 닫히지 않는다.
   - 통과(배지): 여정 맵 → **듣기 유닛**(튜토리얼 `tutorial-listening`, 맵의 「Listen to a Hello」) Start → 보기 「Hello」 tap(정답) → **넘김 층** tap → 「All questions done」 장면 → 「See results」 →
     lesson-complete(통과 배지, `feedback-correct`).
   - **넘김 층**은 보기를 tap한 뒤 화면 전체를 덮는 조작 단위다 — `advance.delayMs` 뒤 스스로 다음으로 넘어가고, 그 전에 층을 tap하면 앞당긴다. 「See results」는 넘김 층이 아니라 문항이
     끝난 뒤 완료 장면의 액션 행 버튼이다.
   - 미통과: 같은 길에서 보기 「Thank you」(오답)를 한 번 고르면 `LESSON FAILED`(빨간 배지)에 닿는다.
   - 문항 전환: 보기 tap 뒤 넘김 층 tap 직후(문항 → 완료 장면). 헤더 · 진행 바 · 액션 행의 bbox는 완료 장면 프레임 사이에서 비교한다 — 지시문은 완료 장면에서 조건부 렌더로 빠지므로
     전환 전후 비교가 아니라 문항 장면 안에서만 불변을 본다.
   - 켠 상태: iOS는 설정 앱 › 손쉬운 사용 › 동작 › 동작 줄이기(켜고 재실행), Android는 [Android 준비](motion-reduced.md#android-준비-에뮬레이터-pixel_8-api-37)의 배율 (i) 설정.
4. **측정 단위는 css px**다 — iOS 시뮬레이터는 3x(캡처 px ÷ 3), Android는 `wm size 390x844` · `wm density 160`으로 1 px = 1 css px. 배지 지름의 **비율 기준은 같은 도구로 잰 정착 bbox**다 —
   iOS(배경과 RGB 거리 > 60인 픽셀 bbox, 3x ÷ 3) **126**, Android(같은 임계, 후광 링이 빠진다) **121**. ≤ 90 %는 그 기준으로 읽는다(iOS ≈ 113 이하 · Android ≈ 109 이하); keyframe 80 %의 기대값
   (iOS ≈ 101)은 캡처가 첫 프레임을 한 틱 뒤에 잡기 때문에 그대로 나오지 않는다. 도구는 2단계 `burst.py`(연속 캡처) · `diam.py`(원 지름) · `cardedge.py`(카드 가장자리 x)류를 재사용하고 저장소에 복사하지 않는다. 도구가 없으면 스크린샷을
   픽셀 도구로 직접 읽고 비고에 쓴 방법을 적는다. 배지 정착색과의 비교는 중심 부근 한 픽셀의 RGB로 한다(첫 프레임이 정착색보다 옅다 = 배경 쪽으로 섞인다).
5. **「중간 프레임」의 정의**: 카드 테두리 · 보기 글자 같은 요소의 대비가 정착 프레임보다 **낮은(배경과 섞인)** 프레임. 두 프레임이 모두 정착이면 판정 불가다(「같다 = 정지」와 같은 규칙).
6. **Android 에뮬레이터는 다른 세션과 번갈아 쓴다**: 쓰기 전에 다른 세션이 쓰고 있는지 확인하고, 쓰는 동안 점유를 알리고, 끝에 **시작 값으로 원복**한 뒤 쓸 수 있다고 알린다.
   사용 중이면 실행하지 않고 「미실행: 에뮬레이터 점유」로 적는다.

### 증거 파일 이름

`docs/e2e/evidence/motion-reward-<ios|android>-<id>-<off|on>-<대상>-<프레임>.png` — `<id>`는 `M3-I1` 같은 항목 id, `off`는 끈 상태 · `on`은 켠 상태, `<대상>`은 `badge`(통과 배지) ·
`badge-fail`(미통과) · `stage`(무대 카드) · `choices`(보기 영역) · `header`(헤더 · 진행 바 · 액션 행) · `map`(맵 복귀), `<프레임>`은 `f00` · `f01` …(캡처 순서; 녹화에서 뽑았으면 시각을 비고에

### 4단계 회차 — scale `var()` 전환 뒤 회귀(iOS · Android), 기준 `2debe051` 대조

4단계([ADR-0053](../adr/0053-motion-policy.md) D6)가 scale 리터럴 다섯 자리(`round-button.css` · `learning-unit.css`의 `:active`, `dialog.css` enter from · exit to, `lesson-complete-screen.css` reward from)를 `var(--libitum-motion-scale-pressed | enter | reward)`로 바꿨다. 값이 토큰과 같아
**달라야 하는 것은 없고** 아래 행은 전부 회귀다 — 통과 기준은 위 iOS · Android 회차 표와 **같은 수치(±같은 오차)** 이지 80 · 95의 정확값이 아니다. 3단계 회차와 다른 것은 둘이다.

- **M3-I1 · M3-A1 (a)(b)는 keyframe 본문 `var()`의 기기 게이트를 겸한다** — 첫 프레임이 100 %(축소 없음)면 통과가 아니라 **실패**이고 4단계 fallback(keyframe 셋만 리터럴 복귀 — ADR-0053 D6)이 선다.
  iOS는 구현 전 탐색이 Dialog · 배지 둘 다 풀림을 봤고(배지 첫 프레임 86.2 % — 위 M3-I1 기록과 일치), Android keyframe은 이 회차가 처음 본다. Dialog 쪽 게이트는 [0.4.0 motion 토큰 e2e](motion-tokens.md#결과)의
  M2-I2 · M2-A2 행이다.
- **M3-I9 · M3-A9(진행 바 채움)는 이 빌드로 관찰할 수 없다** — 문항 하나짜리 유닛뿐이라 채움이 마운트부터 100 %다. 기본값 「미확인」이고 통과로 읽지 않는다.

수정 전 대조는 기준 `2debe051`(3단계 병합)이고 호스트는 불변(`d602fe08` 이후)이다. **결과 행은 실행 회차가 채운다 — 「실행 중」인 행은 통과가 아니다.**

## 둘째 자리 — 카탈로그 에피소드 배너 ⟨2026-10-14⟩

보상 토큰 조합(`reward` · `enter-expressive` · `scale.reward`)을 쓰는 자리가 통과 배지 하나에서 **둘**이 됐다([ADR-0053](../adr/0053-motion-policy.md) D4의 날짜 주 ⟨2026-10-14⟩).
둘째 자리는 카탈로그 에피소드 배너의 글자다 — 표지 컷을 끝까지 본 뒤의 「Episode start!」, 통과 뒤 컷을 끝까지 본 뒤의 「Episode clear!」
([ADR-0058](../adr/0058-catalog-learning-session.md) 적용 기록 ⟨2026-10-14⟩). 위 일곱 가지와 수용 기준 대응은 통과 배지의 것이고 이 절은 배너만 본다.

| 이미 지는 층 | 무엇을 |
|---|---|
| unit | 변형 판정(`episodeBannerMotionOf` — `standard` → `reward`, `reduced` → `fade`) · 클래스 이름 · 유지 시간과 토큰의 관계(등장이 끝난 뒤 1초 이상 남는다) |
| ui | 글자의 `data-motion` · 클래스, reduced 변형 keyframes에 `transform` 없음(CSS 텍스트), 유지 시간 · 탭 · 시스템 뒤로와 닫힘 한 번 |

통과 배지와 다른 점 셋: ① 모션이 걸리는 것은 **글자**다(면은 첫 프레임부터 검정으로 서 있다). ② 화면이 **약 1.6초 뒤 스스로 닫힌다** — 등장(400 ms)이 끝난 뒤 약 1.2초 머문다.
③ 눌러서 넘기면 **그 자리에서 맵**이다(퇴장 없음 — 이 점은 배지와 같다).

도달 길: 튜토리얼 최종 테스트를 끝낸 계정 → 맵의 카탈로그 표지 노드 → 표지 화면 `Next` → 컷을 끝까지 → 마지막 버튼. 캡처 수단 · 측정 단위는 위 「전제」를 그대로 따른다 — **배너는 1.6초뿐이라 녹화가 기본이다.**
글자의 크기는 글자 bbox의 폭으로 잰다(정착 폭이 기준 — 기본 배율에서 한 줄).

## 유닛 탭 등장 모션 (2026-10-19, ADR-0070)

⟨2026-10-19⟩ Android 에뮬레이터 회차를 한 번 돌렸고(`d94ea84b`), 실패한 SM6만 수정 뒤 두 번 더 돌렸다(`2f7c3968` 통과 · `b524ef74` 경계 탭 확인 — 아래 「결과」, 에이전트 실행 · 사람 미확인). SM1 ~ SM9 통과 · SM10 기록이고, 대기 → 등장 경계 프레임의 시작 탭 무반응은 결함 판정 밖의 남은 위험이다([ADR-0070](../adr/0070-journey-map-sheet-entrance-motion.md) 「남은 위험」 A11Y-3). iOS 칸은 아직 비어 있다(미실행). 끈 = 동작 줄이기 끔(standard), 켠 = 켬(reduced).

여정 맵에서 유닛 탭을 누르면 노드가 한 번 튀고, 필요하면 맵이 스크롤한 뒤, 에피소드 띠가 위에서 내려오며 튀고, 조금 늦게 말풍선이 꼬리 끝에서 커진다.
결정은 [ADR-0070](../adr/0070-journey-map-sheet-entrance-motion.md)이고, 가정 A1 ~ A5 · 관찰 O-1 · 케이스 id는 저장소 밖 하네스 작업 폴더의 계약 · 테스트 계획에서 왔다. 이 절은 기기에서만 닫히는 열 가지(SM1 ~ SM10)만 본다.

| 이미 지는 층 | 무엇을 |
|---|---|
| unit | 등장 상태 기계(열림 → 측정 → 이동 → 등장 전이 · 늦은 답 버림 · 조용함 · 상한 타이머 상수), 모션 종류 · 클래스 · 말풍선 기준점 · 카운트업 값 · 노드 단계, CSS 텍스트(토큰 · reduced · `overflow: visible` 사슬 · 숨쉬기 반복 횟수) |
| ui | 말풍선 · 띠 · 노드의 클래스 · DOM · 타이머와 화면 순서(스크롤 필요/불필요 · 조용함 · 상한 · 닫기 · reduced), 대기 중 말풍선 래퍼의 탭 잡기(대기면 닫음 · 등장 뒤면 아무것도 안 함 · 시작은 받음) |
| integration | 호스트 `reducedMotion` → `MotionProvider` → 훅 → 띠 · 말풍선 · 노드가 App 경계에서 한 값인지 |

### 이 절차로 확인하지 못하는 것 · 이 절차만 닫는 것

자동 검사가 못 지는 것: 첫 프레임 깜박임(A1) · 스크롤 이벤트 간격 < 200 ms(A2) · 대기 중 말풍선 자리의 자손 탭이 `.step-sheet-pop`까지 올라와 닫는가(A3 — 테스트 DOM은 올림을 흉내 내지 않는다) · 같은 클래스 유지 시 애니메이션 재시작 없음(A4) ·
인라인 px `transform-origin`이 두 플랫폼에서 그려지는가(A5) · `overflow` 잘림(D5 · O-1) · 실제 곡선 체감 · 프레임 비용.

- **곡선 · 정확한 시간은 재지 않는다.** 판정은 「순서」(무엇이 무엇보다 먼저/뒤에 시작하는가), 「있다/없다」(깜박임 · 잘림 · 이동), 「어느 쪽에서 커지는가」뿐이다. 값은 unit(CSS 텍스트)이 진다.
- **보조기술** 점검은 이 절의 범위 밖이다. 이 절은 켜지 않고 돈다.
- **iOS 실기**는 닿으면 SM1 · SM6 · SM9를 한 번 더 한다. 못 하면 「미확인」이고 시뮬레이터 통과를 실기 통과로 적지 않는다.

### 전제

준비(전용 시뮬레이터 · 에뮬레이터, 전역 설정 값 기록 후 복원, 「같다 = 정지, 다르다 = 움직임」, iOS · Android 빌드 · 설치 · 캡처 · 녹화)는 [동작 줄이기 e2e](motion-reduced.md)의
「전제」 · 「iOS 준비」 · 「Android 준비」 · 「연속 두 장 비교」를, 측정 단위(css px)와 Android 탭 입력은 이 문서 위쪽의 「전제」 4와 「Android 항목」 도입을 **그대로** 따르고 되풀이하지 않는다.
이 절만의 부분:

1. **호스트와 번들을 둘 다 새로 빌드한다.** 번들만 새로 만들면 호스트가 `reducedMotion`을 보내지 않아 켠 상태에서도 움직이고 SM7이 「안 됨」으로 읽힌다. 결과 칸에 호스트 SHA와 번들 SHA를 따로 적는다.
2. **도달 길.** 로그인된 계정으로 여정 맵 탭에 들어간다. 진행 상태는 [두 열 배치](journey-map.md#두-열-배치--한-열-폴백--다음-유닛으로-자동-스크롤-journey-map-grid) 전제의 **(P1)** 튜토리얼 진행 중(표지 + 스텝 몇 개 완료)과
   **(P2)** 튜토리얼 전부 완료 + 카탈로그 레슨이 열린 계정이다. 저장 서버에 진행이 남으므로 두 계정이 필요하다. 「스크롤이 필요한 스텝」은 입장 직후 화면 **아래쪽**에 보이는 일반 유닛이다 —
   (P1)에서 자동 스크롤이 다음 유닛을 머리 카드 아래에 세운 뒤, 그 **아래** 유닛을 누른다. 「제자리에 선 유닛」은 자동 스크롤이 멈춘 자리의 그 다음에 풀 유닛이다.
3. **동작 줄이기 켜는 법(호스트 `reducedMotion`).** 설정은 앱을 **다시 실행**해야 호스트가 읽는다([동작 줄이기 e2e](motion-reduced.md) M-I1 · M-A1).
   - iOS: 설정 앱 › 손쉬운 사용 › 동작 › 동작 줄이기, 또는 `defaults write com.apple.Accessibility ReduceMotionEnabled -bool true` 뒤 시뮬레이터 재부팅(읽기값 1 확인). 켜고 `terminate` → `launch --bundle-url=main.lynx`.
   - Android: (i) `settings put global transition_animation_scale 0` · `animator_duration_scale 1`, 또는 (ii) 접근성 「애니메이션 삭제」(세 배율 0). 켠 직후 값을 읽어 확인하고 픽스처를 새로 시작한다(`pm clear` → `am instrument …`).
   - 끝에 시작 값으로 되돌린다(아래 「복원」).
4. **슬로 확인 방법 — 화면 녹화 · 프레임 단위.** 앱의 모션 속도를 바꾸지 않고 **녹화를 느리게 읽는다**. 녹화는 60 fps 이상이어야 한다.
   - iOS: `xcrun simctl io "$UDID" recordVideo --codec h264 /tmp/sheet-motion-ios-<id>-<off|on>.mov &` → 조작 → `kill -INT`.
   - Android: `A shell screenrecord --time-limit 10 --bit-rate 20000000 /sdcard/sm.mp4` → 조작 → `A pull`. **`screenrecord`는 화면이 바뀔 때만 프레임을 만든다**(약 12 fps · 60 ~ 90 ms, 정지 구간 프레임 없음) — 이 간격이
     SM2의 「0 ~ 약 250 ms」 판정 오차를 정한다. 순서가 가려지지 않으면 「판정 불가」로 적고, `screencap` 연속(한 장 0.4 ~ 1.2 s)은 보조로만 쓴다.
   - 프레임 뽑기: `ffprobe -v error -select_streams v -show_entries frame=pts_time -of csv=p=0 <영상>`으로 프레임 시각을 읽고, `ffmpeg -i <영상> -vsync 0 <프레임>-%03d.png`로 **전 프레임**을 뽑아 시각순으로 본다.
     슬로 재생은 `ffplay -vf "setpts=4.0*PTS" <영상>` 또는 영상 플레이어의 프레임 단위 이동을 쓴다. 표시 시각은 영상 시각이고 오차는 ±한 프레임이다.
   - Android 탭은 `adb emu event send`(좌표 css × 32767 / 390 · / 844)로 넣어 tap 시각을 영상 ±한 프레임으로 맞춘다. 맞추지 못한 회차는 SM2 · SM6의 시각 판정을 「판정 불가」로 둔다.
5. **「깜박임」의 정의(A1).** 탭 직후 ~ 띠 등장 시작 사이 프레임에서 **말풍선 또는 띠가 한 프레임이라도 설 자리에 보이면** 깜박임이다.
6. **증거 파일 이름**: `docs/e2e/evidence/motion-reward-<ios|android>-SM<n>-<off|on>-<대상>-<프레임>.png`, `<대상>`은 `map` · `band`(띠) · `sheet`(말풍선) · `node` · `halo`(SM9), `<프레임>`은 `f00` …(녹화에서 뽑았으면 시각을 비고에). 영상은 같은 이름의 `.mov` · `.mp4`로 두고 저장소에 커밋하지 않는다.
7. **Android 에뮬레이터는 다른 세션과 번갈아 쓴다** — 위 「전제」 6과 같다(사용 중이면 「미실행: 에뮬레이터 점유」).

보충:

- **SM6**: A3의 판정은 대기 중 제목 · 패널 자리 탭이 **닫는지**다(투명한 `.step-sheet-pop`이 탭을 삼켜 말풍선이 뒤늦게 서면 실패). 시작 자리는 대기 중에도 탭을 받으므로 세션이 열리는 것이 기대다
  (ADR-0053 D5 — 전환은 입력을 막지 않는다). 대기 중인지는 녹화에서 터치 시각이 띠 첫 프레임보다 앞인지로 가린다 — Android는 `settings put system show_touches 1`로 터치 점을 녹화에 남기고 끝에 `delete`한다.
- **SM9 (O-1)**: `overflow: visible`을 준 조상 사슬로 새로 **드러나는** 요소가 있는지 함께 본다 — 노드 반짝임 조각 · 후광뿐 아니라 말풍선 1.06 넘침(아래로 약 6 %), 다른 유닛의 포커스 링 · 그림자.
  그리고 **학습 완료 폭죽**(`.lesson-complete-confetti`, 0 × 0 축)이 Lynx `overflow` 기본값 `hidden` 때문에 조상에서 **잘리는지**를 학습 완료 화면에서 한 번 본다 — 이 작업이 고치지 않는 관찰 항목이다
  (잘리면 「잘림: <어느 조상에서>」로 적고 지표 모션 절(ADR-0064)의 미확인 항목으로 넘긴다). 폭죽이 안 보이는 것과 잘린 것을 가르려면 폭죽 퍼짐이 최대인 프레임을 녹화에서 뽑아 본다.
- **SM7**: 판정은 「이동 · 확대가 없다」이므로 SM1과 같은 녹화에서 띠의 y와 말풍선의 크기가 모든 프레임에서 같은지를 본다. 켠 상태 한 장만으로 통과를 적지 않고 SM1(끈)과 짝지어 적는다.
- 판정은 `통과` / `실패: <관찰>` / `판정 불가: <이유>` / `미확인` / `미실행: <이유>`로만 적는다. 「있는 그대로 기록」 항목(SM2의 맨 아래 유닛 · SM9의 다른 유닛 · SM10)은 관찰한 값을 적는다.

### 결과 — Android 1회차 (2026-10-19, iOS 미실행)

실행 회차가 채운다. 「실행 중」인 행은 통과가 아니다.

**이 회차의 방법(Android).** 로그인 픽스처 `SignedInScreenFixtureTest`에 `-e audioProgress true`(표지 + 스텝 다섯 완료 — (P1))를 주고, 픽스처의 180초 대기를 늘리는 **임시 인자**를 더해 계측 APK를 다시 빌드했다(끝에 되돌림, 커밋 없음).
자동 스크롤이 이제 다음 유닛을 화면 가운데쯤에 세우므로(위 「전제」 2의 「머리 카드 아래」는 낡음), 「스크롤이 필요한 스텝」은 입장 뒤 맵을 손으로 270 css px 내려(`input swipe 195 250 195 520 1200`)
`Asking for directions`(왼쪽, 끝냄 100 %) · `Listen to a Hello`(오른쪽, 다음 유닛 0 %) 줄을 화면 아래(y ≈ 713)에 둔 뒤 누르는 것으로 만들었다. 탭은 콘솔 `emu event send`.
`screenrecord`는 이 기기에서 **화면이 바뀌는 동안 약 60 fps(16 ~ 17 ms)** 로 프레임을 냈다(위 4의 「약 12 fps」보다 촘촘 — 정지 구간은 여전히 프레임 없음). 판정은 전 프레임을 뽑아 시각순으로 보고,
맵 이동은 프레임 사이 세로 어긋남(맵 띠 y 185 ~ 470의 픽셀 상관), 띠 등장은 y 55 ~ 175의 주황 픽셀 비율로 읽었다. 측정 단위는 css px(390 × 844 · 160 dpi에서 1 px = 1 css px).
증거(녹화 · 프레임 묶음 · `gfxinfo` 로그)는 **저장소 밖** 작업 폴더 `logs/`의 `sheet-motion-android-SM<n>-*`이고 `docs/e2e/evidence/`에는 올리지 않았다.

**SM6 재실행(같은 날, SM6 + 회귀 SM1 · SM8).** 같은 방법에 호스트 · 번들을 `2f7c3968`로 새로 빌드했다. 다른 점: 에뮬레이터를 `-gpu host`로 띄웠다(기본 선택 `swangle`에서는 녹화가 약 10 fps로 떨어져 바꿈 — 다시 약 60 fps),
`show_touches`를 켜 녹화의 터치 점으로 터치 시각을 읽었다(끝에 `delete`), 탭은 콘솔 `event mouse <물리 px>`(이 이미지에서 `event send`의 터치는 다음 입력까지 전달되지 않았다), 뒤로가기는 `input keyevent`.
맵을 손으로 내린 뒤 `Listen to a Hello`(오른쪽, 0 %)를 누르고 0.25 s 뒤 둘째 입력을 넣었다 — 이 기기에서 대기(탭 ~ 띠 첫 프레임)는 약 0.3 ~ 0.6 s다. 회차마다 픽스처를 새로 시작했다.
증거는 같은 `logs/`의 `sheet-motion-android-SM6-r2-*`(녹화 · 끝 화면 · 프레임 묶음 · 프레임별 띠/시작 버튼 픽셀 비율 `-analysis.log` · 터치 점 `-touch.log`).
