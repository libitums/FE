# Android 스플래시 워드마크 — 콜드 스타트에서 이미지가 간헐적으로 실패하지 않는가

Android 앱을 콜드 스타트하면 스플래시의 워드마크 이미지 요청이 간헐적으로 `Unsupported uri scheme`으로 실패하고, `binderror={finish}`가 스플래시를 3 ~ 283 ms 만에 닫던 결함(정상은 약 2.4 ~ 3.4 s)이
고쳐졌는지를 **실제 기기의 콜드 스타트를 반복해서** 확인한다. 원인은 Lynx 4.0.1 `LynxImageManager`의 경합이다 — `LynxMediaResourceFetcher`가 달려 있으면 URL 재작성이 다른 스레드로 넘어가
재작성되지 않은 `/static/…`으로 이미지 요청이 먼저 나갈 수 있다. 수정은 Android 호스트 Java만이다: 이미지 URL 재작성을 fetcher에서 동기 `ImageInterceptor`로 옮긴다.
순수 값(`HostImageInterceptorTest`) · 정적 결선 · 풀을 잠재워 경합을 강제하는 계측(`HW1`)은 다른 계층이 진다. 이 문서는 **자연 조건에서 반복했을 때 실패가 없는가**와
**fetcher를 떼면서 영향받을 수 있는 이미지 외 자원이 그대로인가**만 진다.
항목 정본은 작업 `android-splash-wordmark`의 계약(`spec.md` §2 · §7, r02는 `## r02`, 리뷰 뒤의 정정은 `## r03`)과 test-plan의 `## e2e` · `## r02`(SW1 ~ SW6 · SW9)다. SW7 · SW8은 이 문서가 더했다(맨 아래 「test-plan과 다른 점」).

**첫 e2e 실행(2026-10-07)이 끝났다.** 결과는 아래 「실행 상태」다. 그 실행에서 API 30의 dev 빌드가 2/67(+1/60) 실패했고, 진단(`d1-diagnosis.md`)은 그것이 **이 수정이 만든 결함이 아니라
「이미지가 늦게 뜨면 스플래시의 4 s 안전 타이머가 워드마크 재생(약 2.4 s)보다 먼저 닫는다」는 기존 성질**이라고 판정했다(수정 전 빌드도 같은 조건에서 같은 증상). 그래서 판정을 넷으로 갈랐고
(계약 r02.2 — 아래 「판정」), dev 항목은 번들 서버의 **요청 기록**을 함께 남긴다. **재실행(r02, 같은 날)이 그 판정으로 SW1 · SW9를 다시 돌았다** — 결과는 「실행 상태」의 「재실행(r02)」이다.
**수정 전 빌드와의 대조 측정(같은 날)도 끝났다** — 결과는 「실행 상태」의 「대조 측정」이다. 두 결과는 위 진단의 「기존 성질」을 그 문면대로 확인해 주지 않았다: 재실행의 늦은 도착 한 건은 서버가 즉시 응답했는데 났고,
수정 전 빌드의 자연 조건에서는 늦은 도착이 한 건도 관찰되지 않았다(「이 절차로 확인되지 않는 것」).
**최종 검증(같은 날)은 통과로 끝났다** — 첫 실행은 테스트 결함 하나(R4)로 실패했고, 그것을 고친 뒤의 재검증에서 R1을 고친 HW5 · HW6가 두 기기에서 통과했다. 결과는 「실행 상태」의 「최종 검증」이다.
**리뷰(같은 날 — 조건부 PASS)와 계약 r03이 이 문서의 문면 몇 곳을 고쳤다** — 새 실행은 없다. 「타이머로 닫히는 것은 dev 빌드의 일」이라는 앞선 문면이 틀렸고(내장 빌드의 통과 실행도 타이머 경계에 닿았다), 횟수의 계산이 점추정에 기댄다는 한계가 더해졌다.
요약은 「실행 상태」의 「리뷰와 계약 r03의 정정」, 값과 근거의 정본은 [ADR-0051](../adr/0051-android-image-url-redirect.md)의 「리뷰와 계약 r03의 정정」이다.

## 이 절차로 확인되지 않는 것

근거 수준을 적는다: **[코드 확인]** · **[바이트코드]** · **[실측]** · **[추론]** · **[미확인]**.

- **실기**: 에뮬레이터(SwiftShader · 16 KB 페이지 이미지)만 쓴다. 실기의 스레드 스케줄링에서 경합의 빈도가 어떤지, 수정이 같은 효과인지는 모른다 [미확인].
  경합은 스레드 순서에 달려 있어 기기 · 부하에 따라 빈도가 크게 다르다는 것만 알려져 있다(위 같은 HEAD의 5/70 ↔ 6/9) [실측].
- **API 37 내장 번들의 통계적 한계**: 수정 전 실패율이 1.2%(1/85)라 100회에 0건일 확률이 약 30%다 — **API 37의 SW2 100회는 「회귀가 없다」의 연기 검사일 뿐 수정의 증거가 아니다.**
  0.1% 미만에 닿으려면 584회가 필요한데 이 절차는 요구하지 않는다. 수정의 증거는 SW1(API 37 dev 67회) · API 30의 SW2 100회 · 계측 `HW1`(강제 재현 10회)이 진다.

  - **e2e의 D1 세 건(SW1 API 30의 1 · 47번, 진단 1번)이 늦은 도착이었다는 것은 [추론]이다.** 로그 모양 · 캡처가 맞지만, 그 회차의 도착 시각을 찍는 줄이 없다(진단은 「dev에서만 난다」도 근거로 들었으나 dev에 한정되는 것은 타이머로 **닫힌** 실행뿐이다 — 「리뷰와 계약 r03의 정정」). 확인되는 것은 **강제 재현**(워드마크 응답을 2.0 s 늦추면

    - **배제되지 않은 것**: **약 1% 안팎의 증가**(참 비율 1.0%에서 0건일 확률 0.22). r02의 1건과 합친 수정 후의 비율은 1/218 = 0.46%(95% 구간 0.01 ~ 2.5%)다.
    - **확인되지 않은 것**: 「LATE는 이 수정과 무관한 기존 성질」을 **자연 조건에서 직접** — 수정 전의 자연 조건 LATE가 한 건도 관찰되지 않았다. 그 판정을 받치는 것은 여전히 강제 재현(수정 전 13/15)과 바이트코드다.
    - **한계**: 조용한 시간대였을 수 있다(진단의 20/104 대 0/116) · API 30 에뮬레이터 한 대 · 앱 안의 도착 시각 계측 없음.
  - **API 37에서는 D1을 재현하려 시도하지 않았다**(부하 통제를 위해 비워 뒀다). e2e의 API 37 SW1은 0/67이었다 [실측].
  - **4 s 타이머의 설계는 이 절차의 범위 밖이다.** 워드마크가 마운트 뒤 약 1.6 s(= 4.0 − 2.4)보다 늦게 뜨면 재생 도중 스플래시가 닫힌다 [코드 확인 · 실측]. 타이머로 **닫힌** 실행이 관찰된 곳은 dev 빌드이고 내장 빌드는 첫 실행의 300회(SW2 200 · SW3 80 · SW8 20 — 위 표. 계약 r02.6은 「240회」로 적었고 r03.3이 300회로 고쳤다)에 0건이다.
    **그러나 타이머 경계에 닿은 통과 실행은 내장 빌드에서 수정 전 · 후 모두 있다** [실측 — 「리뷰와 계약 r03의 정정」]. 내장 빌드 · 실기에서 타이머로 닫히는 것은 가설이 아니라 **재지 않은 위험**이다.
    **「HTTP로 받아서 늦는다」는 원인으로 확인되지 않았다**(위 r02의 LATE — 서버는 즉시 응답했다). 실기에서는 어느 빌드도 재지 않았다 [미확인].
    고칠지는 **사용자 보고 항목 U1**이고 이 문서는 그것을 결정하지 않는다. 계약 r02.6의 권고(「그대로 두고 출시 전 실기의 내장 빌드에서 한 번 잰다」)는 dev 한정이라는 전제가 틀려 r03.6이 고쳤다 —
    **Play 내부 테스트 전에 실기의 내장 · release 빌드에서 스플래시 길이 분포를 재는 것을 출시 조건으로 둘지를 사용자가 정한다.** 이 수정의 머지는 막지 않는다.
    **2026-10-07 사용자가 「실기 측정을 출시 조건으로」를 골랐다** — 실기의 릴리스 빌드에서 재고 그 결과로 고칠지 정한다(지금 코드는 그대로 · 측정 전). 실기 절차는 [Android 출시 설정 절차](android-release-config.md)의 「R9 — 6. 확인 목록」 j가, 결정의 기록은 [ADR-0051](../adr/0051-android-image-url-redirect.md) 「미확인 · 후속」 10이 진다.
  - **내장 빌드는 늦은 도착을 가르지 못한다**: 서버가 없으므로 내장 빌드(SW2 · SW3 · SW8)의 `finalloopcomplete` 없음은 항상 FAIL(요청 없음)이다. 내장 300회(SW2 200 · SW3 80 · SW8 20)에 0건이었으므로 지금까지 문제가 되지 않았다.
    다만 그 가운데 한 건(API 37 SW2의 43번)은 `finalloopcomplete`가 타이머 경계(4059 ms)에서 왔다 — 「0건」이 「경계에서 멀다」는 뜻은 아니다.
- **네이티브(C++) 쪽 미디어 fetcher 소비자**: 계약 §9의 1은 자바 쪽 소비자만 바이트코드로 전수 검색했다. 네이티브 쪽이 `LynxMediaResourceFetcher`를 읽는지는 **미확인**이다.
  리뷰의 확인: arm64 `liblynx.so` · `liblynx_v8_bridge.so`에 미디어 fetcher 관련 문자열이 없다 — 문자열 검색 수준이고 다른 ABI · `xelement*` · `lynx-service-image`는 보지 않았다(부재의 증명이 아니다).
  SW7은 눈에 보이는 이미지 외 경로가 정상인지만 본다 — 안 보이는 소비자는 닿지 못한다.
- **`ImageInterceptor.loadImage`는 죽은 경로라는 것**: 저장소의 Lynx AAR에서는 정적 검사(HR7)가 지킨다. `xelement*` · `lynx-service-image`는 Maven에서 받아 저장소에 없어 그 검사가 보지 못한다(4.0.1은 계약 단계에서 손으로 확인 — 호출자 없음) [바이트코드].
- **`VisualNovelScene` · `Avatar`의 오류 경로**: 이 둘은 `binderror`로 그림을 치운다. SW7은 정상 경로(그림이 보임)만 본다. 그림을 실제로 못 읽을 때 이 화면들이 어떻게 보이는지는 이 절차의 범위 밖이다.
  이미지 `onFailed`가 나는 상황을 만드는 SW4는 **스플래시 한 곳**만 본다.
- **`binderror`가 없는 이미지의 조용한 이중 요청**: 수정 전에는 첫 요청이 실패한 뒤 재작성이 끝나면 다시 요청해 그림이 나왔다(눈에 안 보임). 이 절차는 logcat `onFailed` 0줄로 그 이중 요청이 없어졌는지를 보지만,
  요청이 한 번만 나가는지(성능)는 재지 않는다.
- **스플래시 길이로는 판정하지 않는다**: 길이(`onFirstScreen` → 끝 이벤트)는 부하에 따라 2.4 ~ 4.7 s로 흔들린다. 실행기가 중앙값을 적지만 **기록만** 한다. 판정은 아래 「판정」의 신호들이다.
- **release AAB의 업로드 키 서명 · Play 업로드 · 실기**: 이 절차(SW8)는 debug 키로 재서명한 AAB를 에뮬레이터에 분할 설치한다. [Android 출시 설정 절차](android-release-config.md)의 R9와 같은 한계다.
- **iOS**: 이 변경은 `apps/ios` · `apps/mobile` · 번들 설정을 바꾸지 않는다(계약 I4). iOS는 이 절차의 범위 밖이고, 증거는 파일 diff 0줄이다: `git diff --stat 28ed9265 -- apps/ios apps/mobile packages`가 비어야 한다.
- **자연 실패를 만들어 보는 수정 전 대조**: 수정 전 HEAD의 debug로 dev 자연 실패율 p를 20회 다시 재는 일은 **e2e-red 단계**가 했다(위 표: 두 기기 모두 2/20). 이 문서의 절차는 수정 후 반복만 정의한다.

## 전제

### 기기 · 빌드

| 기기 | AVD | API | 쓰는 항목 |
|---|---|---|---|
| 주 기기 | `Pixel_8` | 37 (16 KB 페이지 · SwiftShader) | SW1 ~ SW9 |
| 구 버전 기기 | `R6_API30` | 30 (4 KB 페이지) | SW1 ~ SW6 · SW7의 일부 · SW9 — **SW2의 증거를 지는 기기** |

- JDK 17 이상, Android SDK(`ANDROID_HOME`), `python3`, `curl`, Node 22, `pnpm` 의존 설치 완료. SW8은 bundletool([Android 출시 설정 절차](android-release-config.md)의 준비 4).
- **전용 에뮬레이터를 쓰고, 한 대씩 돈다.** 다른 실행(계측 · Maestro · 다른 e2e · Gradle 빌드 · 화면 녹화)이 같은 기기를 쓰면 실패율이 달라지고 판정 불가가 늘어난다. **두 에뮬레이터를 동시에 켜 두고 돌리지도 않는다** —
  이 결함의 판정(늦은 도착)은 부하에 흔들린다. 한 기기를 도는 동안 다른 기기는 끈다(`A emu kill`). 에뮬레이터는 `emulator -avd <AVD> -no-snapshot-save -no-boot-anim -no-audio`로 켠다(하나만 켜면 어느 AVD든 `emulator-5554`가 된다 —
  `adb devices`로 ID와 API를 확인한다). **그래서 `--label`에 API와 빌드를 넣는다**(예: `--label sw1-a30-debug`). 기본 라벨 `<기기 ID>-<빌드>-<cold>`는 ID가 같아 두 기기의 로그를 가를 수 없다(r02에서 로그 이름의 `a30` · `a37`로 구분했다).
- **시작과 끝에 `uptime`을 적는다.** 실행기는 요약 줄에 호스트 1분 부하(시작 → 끝)와 회차마다 `load=`를 적는다. 부하가 높았던(예: 8 이상) 실행은 결과 표에 그 값을 함께 적는다.
- **번들은 모의 값으로 만든다**(실제 서버 주소가 번들에 들어가지 않게). 모의 값 번들의 로그인은 서버에 닿지 않는다 — 이 절차는 스플래시와 온보딩까지의 콜드 스타트를 본다.
- **3000 포트를 쓰지 않는다.** debug를 extra 없이 시작하면 `10.0.2.2:3000`을 읽는데 그 포트는 다른 작업의 개발 서버일 수 있다. **debug 명령은 늘 `--es bundle-url`을 붙인다**(실행기도 dev에서 `--bundle-url` 없이는 멈추고 3000 포트는 거절한다).
- **번들 서버 포트 표**(이 문서 전체에서 같은 번호를 쓴다). 서버는 모두 `apps/android/tools/wordmark-delay-server.py`(요청 기록 서버)이거나 SW4의 `python3 -m http.server`다.

  | 18790 | `apps/mobile/dist`(정상) | 없음 — **요청 기록** | SW1 · SW5 |
  | 18791 | 워드마크 파일을 지운 `dist` 사본 | 없음 | SW4 |

- **전역 설정을 바꾸지 않는다**(야간 모드 · 애니메이션 배율 · 글꼴 배율 · `wm size`/`wm density`). 시작 전에 값을 기록하고(`globals` — [Android 시작 색과 적응형 아이콘](android-launch-appearance.md)의 「시작 전 전역 설정」),
  바꿨다면 끝에서 되돌린다. 애니메이션 배율을 0으로 끄면 스플래시 구간이 달라지므로 1.0 또는 기본(`null`)이어야 한다.

- 끝나면 원 워크트리 HEAD의 debug + androidTest APK를 다시 설치한다(이 절차가 bundled · release AAB로 덮었다).

### 빌드 · 설치 (저장소 루트에서, **검증할 커밋의 SHA를 결과에 적는다**)

```sh
git rev-parse --short HEAD
# 1) 번들 — 모의 값
PUBLIC_SUPABASE_URL=https://example.invalid PUBLIC_SUPABASE_ANON_KEY=local-bridge-test pnpm bundle:android
# 2) bundled APK (SW2 · SW3 · SW6 · SW7) — release 와 같은 설정, debug 키 서명. 번들이 assets/ 에 들어가므로 1) 뒤에 다시 만든다

BUNDLED_APK=apps/android/app/build/outputs/apk/bundled/app-bundled.apk
# 3) debug APK (+ 계측 APK) (SW1 · SW4 · SW5 · SW9)

DEBUG_APK=apps/android/app/build/outputs/apk/debug/app-debug.apk
# 4) 번들 서버(dev 항목) — 요청 기록 서버. 18790 에서 apps/mobile/dist 를 서빙하고 요청마다 시각 · 경로 · 상태를 한 줄씩 남긴다
```

bundled와 debug는 같은 패키지 · 같은 서명이라 `install -r`로 서로 덮어쓴다.

### 요청 기록 서버

`apps/android/tools/wordmark-delay-server.py <번들 디렉터리> <포트> [워드마크 지연 ms]` — `python3 -m http.server`를 대신하는 서버로, `127.0.0.1`에만 묶고(에뮬레이터의 `10.0.2.2`가 닿는다) 3000 포트는 거절한다.

- 경로에 `logo-handwriting`이 들면 응답하기 **전에** 지연 ms를 기다린다. 지연을 안 주면 지연 없이 기록만 한다(SW1용).
- 요청마다 표준 출력에 두 줄을 flush한다(호스트 시계): `HH:MM:SS.mmm START <클라이언트 포트> <경로>` · `HH:MM:SS.mmm END   <클라이언트 포트> <경로> <상태> <걸린 ms>ms`.
  실행기는 이것을 `--server-log`로 읽는다. HEAD(사전 점검의 `curl -I`)는 기록하지 않는다.
- 같은 서버를 계측에도 쓴다: `SplashWordmarkHostTest`의 HW5 · HW6 · HW7(`-e wordmarkDelayMs 2000` · `1000` · `8000`)이 이 서버를 전제한다 — 실행법은 그 클래스의 주석에 있다. **계측은 매 시작 전에 앱의 이미지 캐시를 스스로 비운다**(「재실행(r02)」의 R1) — 반복 실행 앞에 `pm clear`를 넣을 필요가 없다.

## 판정 — 실행 한 번 (계약 r02.2)

**신호**(그 실행의 logcat 전체. 아래 **그 회차 프로세스의 logcat만** 읽는다):

1. `LynxImageManager: onFailed` — 워드마크뿐 아니라 어떤 이미지든.
2. `SendCustomEvent event name:finalloopcomplete` — 스플래시가 정상으로 끝났다.
3. `LynxTemplateRender: onFirstScreen` — 번들이 실제로 로드됐다.
4. `SendCustomEvent event name:error` — 이미지 오류 이벤트.
5. (dev) 서버 요청 기록에서 이 실행의 구간 — 그 실행의 번들 요청부터 끝까지, `/static/image/logo-handwriting.*`에 **200으로 응답한 기록**의 수.

| 판정 | 조건 | 횟수에 |
|---|---|---|
| **PASS** | `onFirstScreen` ≥ 1 · `onFailed` 0 · `finalloopcomplete` ≥ 1 | 유효 시도 |
| **FAIL(결함)** | `onFailed` ≥ 1(어떤 이미지든) | 유효 시도 — 한 건이면 그 기준은 실패 |
| **FAIL(요청 없음)** | `onFirstScreen` ≥ 1 · `onFailed` 0 · `finalloopcomplete` 0 이고 **아래 LATE의 증거가 하나라도 빠진다** | 유효 시도 — 한 건이면 실패. **내장 빌드(SW2 · SW3 · SW8)는 서버가 없으므로 `finalloopcomplete` 없음이 항상 이것이다** |
| **LATE(늦은 도착)** | **dev에서만 가를 수 있다**(서버 기록이 있어야 한다 — 늦은 시작이 dev에서만 난다는 뜻이 아니다). `onFirstScreen` ≥ 1 · `onFailed` 0 · `error` 이벤트 0 · `finalloopcomplete` 0 **그리고** (a) 그 실행의 서버 구간에 워드마크 200 응답이 **정확히 1건** **그리고** (b) 스플래시가 첫 화면 뒤 **3.0 s 이후**에 끝났다 | **통과도 이 결함의 실패도 아니다.** 유효 시도에서 빼고 다시 채운다. 건수를 따로 적는다 |
| 판정 불가 | `onFirstScreen` 0 — 번들 미로드(서버 · 네트워크 · 대화상자 · 기기 불안정) | 뺀다 — 통과로 세지 않는다 |

- **근거 — 진단 요약**(`d1-diagnosis.md`, 기준 HEAD `05b8cae6`. **재실행 · 대조 측정 뒤의 근거 수준으로 적는다** — 정본은 [ADR-0051](../adr/0051-android-image-url-redirect.md)의 「재실행과 대조 측정」이다):
  - **「D1(워드마크 없이 4초 뒤 닫힘)은 수정이 만든 결함이다」는 반증됐다.** `ImageInterceptor.loadImage`를 부르는 곳이 Lynx 4.0.1에 없다 [바이트코드] · 탐침 220회에 호출 0 [실측] · 수정 전 빌드도 같은 강제 조건에서 같은 증상(13/15) [실측].
  - **강제 실험이 보인 것은 「워드마크 응답이 늦으면 이 증상이 난다 — 수정 전 · 후 모두」까지다.** 응답을 2.0 s 늦추면 수정 후 10/10 · 수정 전 13/15가 같은 증상이고 1.0 s · 1.4 s 지연은 전부 정상이다 [실측].
    그 기제는 `SplashScreen`의 4000 ms 안전 타이머가 이미지가 늦게 떠도 늘어나지 않아 재생(약 2.4 s)보다 먼저 닫는 것이다 [코드 확인].
  - **자연 조건의 늦은 도착이 왜 나는지는 [미확인]이다.** 수정 후 빌드에서 1/218(0.46%)로 관찰됐고, 그 한 건은 서버가 0 ms로 응답했는데 났다 — **늦은 곳은 서버 응답 뒤의 어딘가**이고 어느 단계인지 가를 계측이 없다. 「HTTP 응답이 늦어서」라는 설명은 서지 않는다.
  - **수정 전 빌드의 자연 조건에서는 늦은 도착이 한 건도 관찰되지 않았다**(대조 측정 150회 — 일찍 닫힌 12회를 뺀 유효 138회에 0건). 그래서 「수정 전에도 있던 기존 성질」은 강제 조건에서만 선다(r03: 간접 근거가 하나 더 있다 — 수정 전 빌드의 통과 실행 가운데 타이머 경계에 닿은 것. 타이머로 닫힌 것은 아니다 — 「실행 상태」의 「리뷰와 계약 r03의 정정」).
    같은 측정에서 수정 후도 0/150이었고 그 비율의 단측 95% 상한은 약 2%(1.98%)다 — 「2% 이상으로 늘렸다」는 기각되고 약 1% 안팎의 증가는 배제하지 못한다.
  - 진단의 자연 D1 20건(탐침 빌드)은 전부 「요청은 재작성된 URL로 제때 만들어졌고 이미지가 1.5 ~ 3.5 s에 도착」이었다 [실측]. e2e 첫 실행의 D1 세 건이 그것이었다는 것은 [추론]이고 미해결이다(「이 절차로 확인되지 않는 것」).
- **LATE가 이 작업의 결함을 가리지 못하는 까닭**: 이 작업의 결함은 「재작성 전 URL로 나간 요청」이다. 그 요청은 Fresco가 즉시 거절해 `onFailed`를 찍고 서버에 닿지 않는다 — (a)를 채울 수 없다.
  요청이 아예 만들어지지 않는 회귀도 (a)를 채우지 못해 FAIL(요청 없음)이 된다. 일찍 닫히는 회귀는 (b)를 채우지 못한다.
- **스플래시 끝 표지**: (b)의 끝 시각은 `DestroyLayoutNodeBeforeRemoveFromParent tag:image`(스플래시 그림 노드가 지워진 줄 — 안전 타이머가 끝낸 시각과 맞는다)를 먼저 쓰고, 그 줄이 없을 때만 **마지막**
  `StorageModule.get.libitum.auth.session` 조회를 쓴다. 계약은 둘을 같은 급으로 적었으나 **첫 `auth.session` 조회는 스플래시 도중(0.2 ~ 2.6 s)에도 나온다** [실측 · API 30] — 끝 표지로 쓰면 늦은 도착을 「일찍 닫힘」으로 오판한다(실행기 확인에서 드러났다).
- **LATE의 상한**: 한 기기의 한 케이스에서 LATE가 **시도의 5%를 넘으면 그 실행 전체를 「환경 부적합」으로 버린다**(통과가 아니다 — 실행기가 종료 코드 5로 끝난다). 단독 기기로 다시 돈다. 5%는 진단의 조용한 구간(0/116 — 95% 상한 2.5%)의 두 배다.
  **5%는 결함을 막는 방어선이 아니다** — 그 실행을 증거로 쓸 만한가를 가르는 실행 품질의 문턱이고, 「두 배」는 임의의 여유라 통계적 의미가 없다(계약 r03.3). LATE가 문턱 아래여도 「늦은 도착이 0이 아니다」는 그대로 보고한다. 「시도」는 판정이 난 시도(PASS + FAIL + LATE)다.
  FAIL이 하나라도 있으면 그것이 먼저다(종료 코드 1, 요약에 환경 부적합도 함께 적는다).
- **그 실행의 pid logcat만 읽는다**(T1): API 30에서는 `logcat -c`가 버퍼를 비우지 않아 앞 회차의 꼬리가 다음 회차에 섞인다(가짜 PASS · 겹친 회차). 실행기는 `am start -W` 뒤 `pidof`로 pid를 잡고 `logcat -d --pid`로만 읽는다. pid를 못 얻으면 빈 로그 → 판정 불가.
- **스플래시 길이만으로 판정하지 않는다.** 길이는 실행기가 적는 기록이다.
- **`finalloopcomplete` 없음의 판별(T5)**: 요약 줄의 이유가 `no-finalloopcomplete(<빠진 증거>)`다. 빠진 증거로 읽는다.

  | 빠진 증거 | 뜻 | 먼저 할 것 |
  |---|---|---|
  | `no-server-record` | 서버 구간이 없다 | 내장 빌드면 정상 규칙(FAIL). dev인데 이것이면 `--server-log`를 빠뜨렸거나 서버 기록이 비었다 — 다시 한다 |
  | `wordmark-200-count=0` | 서버가 워드마크에 200으로 응답한 적이 없다 | **요청이 안 나갔거나 틀린 URL이다 — 이 작업의 결함 후보.** 서버 기록의 `/static/…` 줄과 logcat `onFailed`를 본다 |
  | `wordmark-200-count=N`(N ≥ 2) | 한 실행에 응답이 둘 이상 | 앱이 두 번 요청했다 — 성능 · 이중 요청 후보 |
  | `ended-early(<ms>)` | 첫 화면 뒤 3.0 s 전에 닫혔다 | 일찍 닫히는 회귀 후보(이전 결함의 모양) |
  | `error-event` | `error` 이벤트가 있다(`onFailed`는 없다) | 이미지 외 오류 신호 — logcat을 읽는다 |
  | `no-splash-end-mark` | 스플래시가 끝난 표지가 없다 | **`--wait`(기본 12초)가 스플래시보다 짧거나 앱이 죽었다.** logcat 파일을 읽어 `onFirstScreen` 뒤에 무슨 일이 있었는지 확인한다 |

  **D1과 대기 부족을 가르는 법**: D1(늦은 도착)은 `onFirstScreen` 뒤 약 4.0 s에 `DestroyLayoutNodeBeforeRemoveFromParent tag:image`와 `StorageModule.get.libitum.auth.session`이 찍혀 끝난다. 그 줄들이 있으면 대기 부족이 아니다 —
  서버 구간의 워드마크 200을 보고 LATE(증거 충족) 또는 FAIL(요청 없음)로 갈린다. 그 줄들이 없으면 대기 부족이다.
- 판정 불가가 계속 나면(상한 안에 유효 시도를 못 채우면 실행기가 종료 코드 3으로 끝난다) 실패율을 줄이는 쪽으로 읽지 않는다 — **환경을 고치고 다시 한다.**

## 반복 실행기

`apps/android/tools/splash-wordmark-repeat.sh` — bash · zsh 둘 다 돈다(adb는 함수이고 배열 · bash 전용 문법을 쓰지 않는다).
회차마다: 기기 확인 → `am force-stop` → [`pm clear` / 제거 후 설치] → (dev) 서버 기록의 줄 수를 센다 → `am start -W` → `pidof` → 끝 표지(`finalloopcomplete` · `error` · 스플래시 그림 노드 제거)가 그 pid의 logcat에 찍힐 때까지
1초 간격으로 확인(고정 sleep 아님) → `logcat -d --pid`를 **회차 번호가 든 파일**에 저장 → (dev) 서버 기록에서 그 실행의 구간을 `<label>-<회차>.server.log`로 저장 → 판정 → 요약 한 줄.

```sh
# dev (debug + 요청 기록 서버) — pm clear 뒤 67회, 한 기기씩. 서버 기록을 꼭 준다
"$RUN" --serial "$ID" --build dev --bundle-url "$BUNDLE" --server-log "$OUT/server-18790.log" --count 67 --cold clear --out "$OUT/sw1-$ID"
# 내장 (bundled) — pm clear 뒤 100회
"$RUN" --serial "$ID" --build bundled --count 100 --cold clear --out "$OUT/sw2-$ID"
# force-stop 뒤(데이터 유지) 20회 · 제거 → 설치 직후 첫 시작 20회
"$RUN" --serial "$ID" --build bundled --count 20 --cold stop --out "$OUT/sw3-stop-$ID"
"$RUN" --serial "$ID" --build bundled --count 20 --cold "install:$BUNDLED_APK" --out "$OUT/sw3-install-$ID"
# 판정 로직만 기기 없이 확인 (--samples 는 선택: logcat 표본 디렉터리 — 이름 규칙은 아래)
"$RUN" --selftest
"$RUN" --selftest --samples "$SAMPLES_DIR"
```

| 인자 | 뜻 |
|---|---|
| `--serial` | adb 기기 이름 |
| `--build dev\|bundled` | dev는 `--bundle-url`이 필수이고 3000 포트는 거절한다. bundled는 extra를 건네지 않는다 |
| `--server-log` | (dev) 요청 기록 서버의 표준 출력 파일 — 절대 경로. **없으면 LATE를 가를 수 없어 `finalloopcomplete` 없음이 전부 FAIL(요청 없음)이 된다.** bundled에서는 무시한다 |
| `--count` | **유효 시도**(PASS + FAIL) 목표. LATE · 판정 불가는 세지 않는다 |
| `--cold clear\|stop\|install:<apk>` | `pm clear`(데이터 삭제) · `force-stop`만(데이터 유지) · 제거 후 설치(첫 설치 직후) |
| `--out` | 절대 경로 디렉터리. 거기에 `<label>-<회차>.log` · `.start.txt` · `.server.log` · `<label>.summary.txt`가 쌓인다 |
| `--wait` | 끝 표지를 기다리는 최대 초(기본 12) |
| `--max-attempts` | LATE · 판정 불가를 다시 채우는 상한(기본 `count * 2 + 10`) |
| `--label` | 파일 이름 접두(기본 `<기기>-<빌드>-<cold>`). **어느 AVD든 하나만 켜면 `emulator-5554`라 기본값으로는 API를 알 수 없다 — API · 빌드를 넣는다**(예: `sw1-a30-debug`) |
| `--expect pass\|load-failure` | `load-failure`는 SW4의 판정(아래) |
| `--shot` | 시작 0.6 s 뒤 무손실 캡처를 `<label>-<회차>.png`로 저장(SW6) |
| `--stop-on-fail` | 첫 FAIL에서 멈춘다 |

- **번호는 이어 붙인다.** 같은 `--out` · `--label`로 다시 부르면 이미 있는 `<label>-<N>.log`보다 큰 번호부터 쓴다 — 요약 줄 수로 번호를 정하지 않는다
  (앞선 실행기가 요약 줄 수로 번호를 정해 API 37의 첫 실패 logcat을 덮어쓴 적이 있다). 합계는 **그 호출의 것**이다. 여러 번에 나눠 돌렸다면 `.summary.txt`에서 `verdict=FAIL` · `verdict=LATE`를 세어 합친다.
- **요약 줄**(회차마다): `verdict=PASS|FAIL|LATE|UNDECIDED kind=defect|no-request|- reason=… splashMs=… … wordmark200=<서버 구간의 워드마크 200 수> … load=<호스트 1분 부하>`.
  마지막 줄: `== <label>: 실패 F(결함 D · 요청 없음 R) / 유효 시도 V (목표 N) · LATE L (x.x%) · 판정 불가 U · 시도 A/상한 · 부하(1분) 시작 → 끝 · 통과 실행의 스플래시 길이 중앙값 M ms(기록만) · PASS|FAIL|INCOMPLETE|INTERRUPTED|환경 부적합`.
- **종료 코드**: 0 PASS · 1 FAIL(결함이든 요청 없음이든 1건 이상) · 2 사용법 · 사전 조건 오류 · 3 INCOMPLETE(판정 불가 때문에 상한 안에 채우지 못함) · **4 INTERRUPTED(기기가 사라졌다 — T2)** · **5 환경 부적합(LATE가 시도의 5% 초과 — 통과가 아니다)**.
- **기기가 사라지면 멈춘다(T2)**: 모든 `adb` 호출은 `ADB_TIMEOUT`초(기본 60)를 넘기면 죽고, 회차 시작마다 `get-state`로 기기를 확인한다. 응답이 없으면 그 회차까지의 합계를 적고 종료 코드 4로 끝난다(`- waiting for device -`에서 영원히 멈추지 않는다).
- 실패 logcat은 지우지 않는다. 결과 표에는 FAIL 회차 번호와 그 로그의 `onFailed` 줄(FAIL(요청 없음)이면 `reason=`)을 인용한다.
- 환경 변수 `ADB`로 adb 실행 파일을 바꿀 수 있다(실제 기기 없이 모의 adb로 반복 · 번호 이어 붙임 · 판정 불가 다시 채우기 · 기기 소실을 확인할 때 쓴다).

**selftest가 지는 것**: 판정 함수가 합성 logcat과 저장된 대표 표본(실패 → FAIL(결함), 성공 → PASS, 신호 없음 → 판정 불가, 끝 이벤트 없음 → FAIL(요청 없음), 다른 이미지의 `onFailed` → FAIL, 자정을 넘긴 길이,
`load-failure` 판정)을 맞게 가르는지, **LATE의 증거가 하나씩 빠질 때마다 FAIL(요청 없음)이 되는지**(서버 기록 없음 · 구간이 빔 · 응답 404 · 응답 없음 · 응답 2건 · 상태 칸 없는 옛 기록 · 3.0 s 전에 닫힘 · `error` 이벤트),
이른 `auth.session`이 끝 표지로 읽히지 않는지, 서버 기록에서 그 실행의 구간만 잘리는지(앞 실행의 늦은 응답은 빠진다), LATE 5%의 경계(3/70 안 · 4/71 밖 · 1/20 안), 멈춘 adb가 상한 안에 124로 끝나는지.
**`--samples <디렉터리>`는 실제 logcat 표본**을 본다. 파일 이름 규칙: `<이름>-FAIL*.log`(FAIL(결함)) · `-OK*.log`(PASS) · `-NOREQ*.log`(FAIL(요청 없음)) · `-LATE*.log`(LATE).
같은 이름 뒤에 `.server.log`를 붙인 파일(`<이름>-LATE.server.log`)이 있으면 그것이 그 표본의 서버 구간이다. 이번 실행의 표본: 진단의 실제 D1 logcat(`logs/d1/samples/a30-head-delay2000-3-D1.log` + 같은 시각의 서버 기록 — 옛 서버 형식에 없던 상태 `200`을 더해) → LATE,
같은 logcat에 서버 기록을 안 줌 → FAIL(요청 없음), e2e의 D1 세 건(SW1 API 30의 1 · 47번, 진단 1번 — 서버 기록이 없다) → FAIL(요청 없음), e2e-red의 `Unsupported uri scheme` 실패(API 37 17번 · API 30 1 · 5번) → FAIL(결함),
SW2의 성공 → PASS, 진단의 1400 ms 지연 정상 종료 → PASS. 표본 파일은 저장소에 두지 않는다(용량) — 하네스 작업 폴더의 `logs/`에서 모은다.
**지지 않는 것**: 실제 `adb` 출력의 모양(기기 · adb 버전에 따라 `logcat` 형식이 다를 수 있다 — 실행기는 `-v threadtime`을 명시한다), 다른 앱이 같은 줄을 찍는 경우. 실행기가 실제 adb와 만나는 부분은 아래 「실행기 확인」이 본다.

### 실행기 확인 (이 절차를 쓰기 전에 한 번 — 2026-10-07, API 30 단독)

SW9의 자기 검사와 같은 것을 실행기에 대해 한 번 기기에서 돌렸다: R6_API30 한 대만 켜고(API 37은 끈 채) debug + 요청 기록 서버, 호스트 1분 부하 약 3 ~ 5.

| 지연 없음(18790) | `--count 5 --cold clear` | **PASS 5 / 5**(실패 0 · LATE 0), 스플래시 2988 ~ 3006 ms, 종료 코드 0 |

## 횟수의 계산과 우연 통과 확률

수정 전 실패율이 p일 때, **고치지 않았는데** n회 연속 통과할 확률은 (1−p)^n이다. 이를 0.1% 미만으로 하려면 n > ln(0.001) / ln(1−p). 이 문서는 계산값에 1을 더한다.

```sh
# p 를 넣으면 n 이 나온다 (예: p=0.10 → 67)
awk -v p=0.10 'BEGIN{ n=-log(0.001)/-log(1-p); c=int(n); if(c<n)c++; printf "n > %.2f -> %d회 (+1 여유 포함), (1-p)^n = %.2e\n", n, c+1, (1-p)^(c+1) }'
```

| 항목 | 수정 전 p (근거) | 횟수 | 고치지 않았는데 전부 통과할 확률 | 판정에 쓰는가 |
|---|---|---|---|---|
| SW1 dev, API 37 | 0.10 (2/20, e2e-red — HEAD 수정 전 debug, 확인됨. **점추정** — 아래 「통계의 한계」) | 67 | 0.9^67 = 8.6×10⁻⁴ (< 0.1%) | 증거 |
| SW1 dev, API 30 | 0.10 (2/20, e2e-red — 사본 실행기. **점추정**) | 67 | 0.9^67 = 8.6×10⁻⁴ (< 0.1%) | 증거 |
| SW2 내장, API 30 | 0.071 (5/70, 계약 단계 값. **점추정**) | 100 | 0.929^100 = 6.3×10⁻⁴ (< 0.1%) | 증거 |
| SW2 내장, API 37 | 0.012 (1/85, 계약 단계 값) | 100 | 0.988^100 ≈ 0.30 | **증거 아님(연기 검사)**. 0.1% 미만에는 584회가 필요하다 |
| SW3 force-stop · 첫 설치 | API 30에서 2/25 · 2/20 | 각 20 | 0.92^20 ≈ 0.19 · 0.9^20 ≈ 0.12 | **가드** — 증거로 세지 않는다 |
| SW4 · SW5 · SW6 · SW7 · SW8 · SW9 | 결정적이거나 가드 | 3 · 1 · 1 · 1 · 20 · 3 | — | 가드 · 회귀 |

- **SW1의 p는 e2e-red가 수정 전 HEAD의 debug로 기기마다 20회 다시 쟀다**: 두 기기 모두 2/20 = 0.10 → n = 67. (옛 값 0.30 · 0.20은 탐침 로그가 든 사본 빌드의 것이었다.) 식으로 p가 낮을수록 n이 늘어난다:
  p=0.25 → 26 · 0.20 → 32 · 0.15 → 44 · 0.10 → 67. 20회 가운데 실패가 **0건**이면 red가 성립하지 않으므로 20회를 더 돈다.
- **통계의 한계**(리뷰 P1-5 · 계약 r03.4 — 위 표의 「< 0.1%」는 이 한계 아래에서 읽는다):
  - **SW1의 p = 0.10은 2/20 두 번의 점추정이다.** HEAD 그대로의 수정 전 dev를 합치면 16/190 = 8.4%(e2e-red 2/20 · 2/20 + 대조 측정 12/150)이고, 이 값이면 **n ≥ 79**가 필요하다 — 67회의 우연 통과 확률은 8.6×10⁻⁴이 아니라 **2.8×10⁻³**이다(기준 10⁻³ 초과).
    **결론은 67회가 아니라 합산 분모가 진다**: 수정 후 dev에서 FAIL(결함) 0건인 판정 난 시도가 API 30 **218회**(재실행 68 + 대조 측정 150) · API 37 **134회**(첫 실행 67 + 재실행 67)이고, p = 8.4%에서 우연히 0건일 확률은 각각 4.7×10⁻⁹ · 7.6×10⁻⁶이다.
  - **SW2 내장 API 30의 6.3×10⁻⁴도 점추정**(5/70 = 7.1%)에 기댄다. p의 95% 하한 2.4%를 쓰면 100회의 우연 통과 확률은 **0.088**이다. 이 p는 e2e에서 다시 재지 않았다(계약 단계 값).
  - 이 절차를 다시 돌 때 SW1의 횟수를 79로 올릴지는 계약이 정하지 않았다 — 아래 항목의 67은 그대로다.
- **SW1의 유효 시도에는 LATE가 들지 않는다.** LATE는 빼고 다시 채우므로 67 PASS를 채우려면 시도가 67 + LATE 건수다(상한 `count × 2 + 10`).
- **「연속 통과」는 FAIL이 한 번이라도 나오면 끊긴다.** 한 번 실패한 뒤 횟수를 늘려 통과로 채우지 않는다 — 실패를 적고 원인으로 되돌린다.
- 판정 불가는 유효 시도가 아니다. 상한이 모자라 INCOMPLETE가 나면 환경 문제다(번들 서버 · 대화상자 · 기기 불안정). 실패율 계산에서 빼기만 하고 넘어가지 않는다.
- **실패할 수 없는 기준이 되지 않게**: SW1의 n은 수정 전 실패율을 같은 빌드 종류로 다시 잰 기록이 있어야 쓸 수 있다(위 e2e-red). SW2의 API 37은 스스로 증거가 아니라고 적었다. SW9는 가드이고 red를 요구하지 않는다 — 실행기의 분류가 동작하는지만 본다.

## 항목

공통: 시작 전 `A shell getprop ro.build.version.sdk`와 위 「전제」의 `globals` · `uptime` 값을 기록한다. 항목마다 실행기가 만든 `<label>.summary.txt`와 FAIL · LATE · 판정 불가 회차의 logcat을 결과에 붙인다.
**콜드 스타트 방식을 구분해 적는다**: `pm clear`(데이터 삭제 후 시작) · `force-stop`만(데이터 유지) · 제거 후 설치 직후 첫 시작 — 계약 §2.1의 실측에서 세 방식 모두 실패가 났다.

### SW1 — dev 자연 조건 (수용 기준 AC2)

- **빌드**: debug + 요청 기록 서버(18790). debug 앱은 `--es bundle-url`을 줘야 한다 — 실행기가 준다.
- **조작**: **기기마다 한 대씩**(다른 에뮬레이터는 끈다. 시작과 끝의 `uptime`을 적는다).
  ```sh
  A install -r "$DEBUG_APK"
  "$RUN" --serial "$ID" --build dev --bundle-url "$BUNDLE" --server-log "$OUT/server-18790.log" --count 67 --cold clear --out "$OUT/sw1-$ID"
  ```
  횟수 67은 p=0.10 기준이다(「횟수의 계산」). **API 37은 이미 0/67로 충족했다 — 다시 돌 것은 API 30뿐이다.** 앞선 API 30의 2/67 + 1/60은 서버 기록이 없어 버린다(「실행 상태」).
- **기대 결과**: 유효 시도 67회 전부 PASS — 워드마크가 써지고 약 2.4 ~ 3.4 s 뒤 스플래시가 끝나 온보딩이 선다. `onFailed` 0줄. LATE는 상한(시도의 5%) 안.
- **판정**: 종료 코드 0. FAIL이 한 번이라도 나오면 항목 실패(결함이든 요청 없음이든). LATE는 건수를 적고 다시 채운다. LATE가 5%를 넘으면 종료 코드 5 — 환경 부적합이므로 단독 기기로 다시 돈다.
  **FAIL(요청 없음)이 한 건이라도 나오면 진단(「D1은 늦은 도착이다」)이 틀린 것이다** — 그 회차의 logcat과 서버 구간을 읽고 계약(`spec.md`)으로 되돌린다.
- **수정 전의 모양**: 20회 가운데 `onFailed … Unsupported uri scheme! Uri is: /static/image/logo-handwriting…`이 1건 이상(e2e-red: 두 기기 각 2/20)이고 스플래시가 3 ~ 283 ms 만에 `error`로 끝난다.

### SW2 — 내장 번들 자연 조건, `pm clear` 뒤 (수용 기준 AC3)

- **빌드**: bundled(모의 값 번들).
- **조작**: 기기마다
  ```sh
  A install -r "$BUNDLED_APK"
  "$RUN" --serial "$ID" --build bundled --count 100 --cold clear --out "$OUT/sw2-$ID"
  ```
- **기대 결과 · 판정**: 유효 시도 100회 전부 PASS. **R6_API30의 결과가 증거**다(0.929^100 = 6.3×10⁻⁴ — 점추정이다. 「횟수의 계산」의 「통계의 한계」). **Pixel_8(API 37)의 결과는 결과 표에 「연기 검사 — 증거로 세지 않음」이라고 적는다** — 통과해도 수정의 증거가 아니고,
  FAIL이 나면 그것은 회귀 신호이므로 항목 실패다. 내장 빌드에서는 `finalloopcomplete` 없음이 항상 FAIL(요청 없음)이다(서버가 없다).
- **수정 전의 모양**: API 30 100회 가운데 1건 이상(7.1%면 0건일 확률 0.06%).

### SW3 — 내장 번들, `force-stop` 뒤 · 첫 설치 직후 (가드)

- **빌드**: bundled.
- **조작**: 기기마다 각 20회.
  ```sh
  "$RUN" --serial "$ID" --build bundled --count 20 --cold stop --out "$OUT/sw3-stop-$ID"
  "$RUN" --serial "$ID" --build bundled --count 20 --cold "install:$BUNDLED_APK" --out "$OUT/sw3-install-$ID"
  ```
- **판정**: 20회 전부 PASS. 20회 통과로는 우연 통과 확률이 0.1 ~ 0.2라 **증거로 세지 않는다** — 데이터 유지 · 첫 설치 경로에서 새 실패가 생기지 않았는지의 가드다.

### SW4 — 로드 실패 경로: 워드마크가 없는 번들에서도 스플래시가 끝난다 (수용 기준 AC4 · 불변 I1)

이미지를 **정말** 못 읽을 때 `binderror={finish}`가 여전히 스플래시를 끝내는지 본다 — 수정이 오류 신호를 삼키지 않았다는 가드다(수정 전에도 통과한다).

- **빌드**: debug + 파일을 지운 번들 서버 사본(18791). (워드마크 webp를 뺀 bundled APK는 `verifyBundledAssets`가 막을 수 있어 이 문서는 dev 경로로 대신한다.)
- **준비**:
  ```sh
  rm -rf "$OUT/dist-nowordmark" && cp -R apps/mobile/dist "$OUT/dist-nowordmark"
  rm "$OUT"/dist-nowordmark/static/image/logo-handwriting.*.webp
  ls "$OUT"/dist-nowordmark/static/image | grep -c logo-handwriting      # 0
  python3 -m http.server 18791 --bind 0.0.0.0 --directory "$OUT/dist-nowordmark" >"$OUT/server-18791.log" 2>&1 &
  curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18791/static/image/$(ls apps/mobile/dist/static/image | grep logo-handwriting | head -1)    # 404
  ```
  끝나면 서버를 내린다(`kill %1` 등 이 셸이 띄운 것만).
- **조작**: 기기마다 3회.
  ```sh
  A install -r "$DEBUG_APK"
  "$RUN" --serial "$ID" --build dev --bundle-url http://10.0.2.2:18791/main.lynx.bundle --count 3 --cold clear --expect load-failure --out "$OUT/sw4-$ID"
  ```
- **기대 결과 · 판정**(`--expect load-failure`): 회차마다 `onFirstScreen` 있음 · 워드마크 `onFailed` 1줄 이상 · **그 `onFailed` 줄 어디에도 `Unsupported uri scheme`이 없다**(404 · 열기 실패 등 다른 이유) ·
  `event name:error` 있음(스플래시가 끝났다) · 시작 구간 뒤 `uiautomator dump`에 온보딩 「Next」가 있다(실행기가 `next=y`로 적는다). 하나라도 어긋나면 FAIL.
  `Unsupported uri scheme`이 나오면 그것은 이 항목의 실패가 아니라 **원래 결함(경합)** 이다 — SW1로 되돌린다.
- **확인된 모양(첫 e2e 실행)**: 실제 실패 이유는 `Image URL http://10.0.2.2:18791/static/image/logo-handwriting.31d15f7dc3.webp returned HTTP code 404`다. 「Next」는 접근성 트리에서 `content-desc="Next"`로 드러난다(`artifacts/e2e/sw4-emulator-5554-1.ui.xml`) —
  실행기의 정규식이 그대로 맞는다(T4).
- 정상 번들(18790)로 다시 한 번 시작해 워드마크가 다시 뜨는지 본다(서버 사본이 오염을 남기지 않았는지).

### SW5 — 첫 화면 밖의 그림 (수용 기준 AC8, 계약 §9의 위험 1)

fetcher를 떼면서 로그인 뒤 화면의 이미지가 영향받지 않는지 본다. 이 화면은 사본 검증에서 보지 않았다.

- **빌드**: debug + 계측 픽스처(`SignedInScreenFixtureTest`).
- **조작**: [Android 시스템 뒤로가기](android-system-back.md)의 「앱 구간 진입 (로그인 없이)」의 1) ~ 5)를 따른다(번들 서버 18790 · 5)의 `pm clear` · 픽스처 시작). 단 **5)의 `pm clear` 직후 · 픽스처 시작 전에 `A logcat -c`를 한다**
  (API 30에서는 `logcat -c`가 비우지 않으므로 그 실행의 pid로만 읽는다: `A logcat -d --pid="$(A shell pidof $PKG)" -v threadtime`).
  여정 맵이 서면 스크린샷을 남기고(`A exec-out screencap -p > "$OUT/sw5-$ID.png"`) logcat을 저장한다.
  ```sh
  A logcat -d --pid="$(A shell pidof $PKG | tr -d '\r')" -v threadtime > "$OUT/sw5-$ID.log"
  grep -c "LynxImageManager: onFailed" "$OUT/sw5-$ID.log"       # 0
  A shell am broadcast -a com.libitum.host.test.STOP_SIGNED_IN_FIXTURE
  ```
- **기대 결과**: 스크린샷에서 **그림이 그려진 영역이 하나 이상** 보이고(여정 맵의 그림 — 어느 영역인지 스크린샷을 보고 결과에 적는다), 그 실행 전체의 `onFailed`가 0줄이다.
- **판정**: 둘 다 맞으면 통과. 그림이 없는 단색 화면이면 어느 이미지가 비었는지 적고 실패. 여기서는 `finalloopcomplete`(스플래시)를 쓰지 않는다 — **`onFailed` 0줄과 그림의 존재**만 본다.
- 첫 e2e 실행에서 여정 맵에는 래스터 그림이 없었다(SVG 아이콘뿐). 그림이 있는 화면(프롤로그 · 비주얼 노벨)까지 진행해서 보았다.

### SW6 — 무손실 캡처 (기록)

- **조작**: 기기마다 bundled로 `--shot`을 붙여 한 번 이상 돈다.
  ```sh
  "$RUN" --serial "$ID" --build bundled --count 1 --cold clear --shot --out "$OUT/sw6-$ID"
  ```
  `<label>-<회차>.png`(시작 약 0.6 s 뒤)를 본다.
- **기대 결과**: 성공 실행의 캡처에 **워드마크의 흰 획**이 있다. (수정 전 실패 실행은 같은 시점에 이미 온보딩이다 — 대조 구도는 계약 단계의 `artifacts/screens/`.)
- **판정**: **기록이다.** 통과 · 실패의 판정은 logcat 신호가 한다. 캡처가 시스템 스플래시(주황)만이면 시점이 이른 것이다 — 판정하지 않고 시점을 적는다.

### SW7 — fetcher 제거의 회귀: 이미지 외 자원 (수용 기준 AC7의 확장, 불변 I6)

`LynxMediaResourceFetcher`를 떼므로 그것을 읽던 이미지 외 소비자가 있으면 깨진다. 자바 쪽 소비자는 이미지 경로뿐이라고 바이트코드로 확인됐지만(계약 §9의 1) **네이티브 쪽은 미확인**이므로,
눈에 보이는 자원 경로를 실제로 돌려 본다. 효과음 · 대사 오디오는 호스트 모듈(`AudioAssetPath` · `SoundEffectAsset`)이 자체 경로를 쓰지만 같은 실행에서 확인한다.

- **빌드**: bundled(release와 같은 설정). 기기마다 한다. 로그인 뒤 화면이 필요한 부분은 SW5의 픽스처 구성을 쓴다(debug).
- **조작과 판정**: 각 항목은 이미 있는 절차를 가리키고, 이 변경에서 **새로 얹는 판정**을 적는다. 모든 항목에서 그 실행의 `LynxImageManager: onFailed`가 0줄이어야 한다(항목 시작 직전에 `A logcat -c`, 읽을 때는 `--pid`).

| # | 자원 | 절차 | 판정 |
|---|---|---|---|
| a | 효과음 | [Android 효과음 · 대사 오디오 · 서사 배경 그림](android-assets.md)의 E2(온보딩 `Next` → 효과음) · E3(학습 정답 · 오답) | logcat `SoundEffectsModule.play.<id>`와 새 플레이어 `started`가 짝으로 있고 `SoundEffects` 태그 `W` · `FATAL` 0 |
| b | 대사 오디오 | 같은 문서의 E5(방송 줄 재생) | `AudioPlaybackModule.play.<id>` → `started` → `stopped`, `AudioPlayback` 태그 `W` · `FATAL` 0 |
| c | 서사 · 비주얼 노벨 그림 | 같은 문서의 E6(서사 배경 S1 ~ S4 — 그림이 그려지고 움직임). 비주얼 노벨 화면은 [비주얼 노벨](visual-novel.md)의 안드로이드에서 닿는 장면(해당 문서 「기능 여정」) | 배경 그림이 **단색이 아니라** 그림이다(스크린샷). 수정 전의 단색 `#1b1613`이 나오면 실패 |
| d | 아바타 | 서사 · 대화 장면(`Avatar`가 쓰이는 `DialoguePanel`이 서는 화면 — c에서 지나는 장면)의 스크린샷 | 아바타 그림이 있다. 어느 장면의 어느 아바타인지 결과에 적는다. **이 장면까지 닿지 못하면 「닿지 못함」으로 적고 판정하지 않는다** |

- 위 절차들이 AAB(Play 형태)를 전제로 쓰였다면 bundled APK로 같은 조작을 하되 결과 표에 빌드를 적는다(소리 · 그림 경로는 둘이 같지만 무압축 항목 검사 E1은 AAB 전용이다).
- 이 항목의 통과는 **이미지 외 경로가 눈에 보이는 범위에서 그대로**라는 뜻이다. 네이티브 쪽 소비자의 부재를 증명하지 않는다(「확인되지 않는 것」).

### SW8 — release AAB 스모크 (bundletool)

Play가 내려주는 것과 같은 형태에서도 워드마크가 뜨는지. 판정은 SW3과 같은 가드 수준이다 — 반복 횟수는 증거가 아니다.

- **빌드**: release AAB를 debug 키로 재서명해 분할 설치 — [Android 출시 설정 절차](android-release-config.md)의 「AAB 만들고 분할 설치」(1) ~ 4)를 그대로. `google-services.json`이 없으면 `bundleRelease`가 멈춘다(의도된 게이트) — 그 메시지를 적고 이 항목은 「미실행(빌드 불가)」로 둔다.
  **release AAB는 debug 키와 다른 서명일 수 있다 — 설치돼 있던 bundled · debug는 `A uninstall $PKG` 뒤에 깐다.**
- **조작**: 설치 직후 `--build bundled --cold stop`로 20회(이 빌드는 `bundle-url`을 무시하는 내장 번들이다).
  ```sh
  "$RUN" --serial "$ID" --build bundled --count 20 --cold stop --out "$OUT/sw8-$ID"
  ```
- **판정**: 20회 전부 PASS. 가드이며 증거로 세지 않는다.

### SW9 — 늦은 도착 가드: 지연 서버에서 실행기가 LATE를 가르는가 (r02 · 가드 — 수용 기준 AC9)

D1의 모양이 「늦은 도착」이 만든다는 것을 고정하고, 실행기의 LATE 분류가 실제로 동작하는지 보는 **자기 검사**다. 수정 전 빌드도 같은 판정이 나온다(진단: 수정 전 2000 ms 13/15 · 1000 ms 9/10, 나머지는 옛 결함) — 재현 테스트가 아니라 가드이고 red를 요구하지 않는다.

- **빌드**: debug + 지연 서버 둘 — 18793(2000 ms) · 18794(1000 ms). **기기를 한 대씩** 돈다.
- **준비**:
  ```sh
  python3 apps/android/tools/wordmark-delay-server.py apps/mobile/dist 18793 2000 >"$OUT/server-18793.log" 2>&1 &
  python3 apps/android/tools/wordmark-delay-server.py apps/mobile/dist 18794 1000 >"$OUT/server-18794.log" 2>&1 &
  ```
- **조작**: 기기마다 각 3회.
  ```sh
  A install -r "$DEBUG_APK"
  "$RUN" --serial "$ID" --build dev --bundle-url http://10.0.2.2:18793/main.lynx.bundle --server-log "$OUT/server-18793.log" --count 3 --max-attempts 3 --cold clear --label sw9-2000-$ID --out "$OUT/sw9-$ID"
  "$RUN" --serial "$ID" --build dev --bundle-url http://10.0.2.2:18794/main.lynx.bundle --server-log "$OUT/server-18794.log" --count 3 --cold clear --label sw9-1000-$ID --out "$OUT/sw9-$ID"
  ```
- **기대 결과 · 판정**:
  - **2000 ms**: 3회 모두 **LATE**(`wordmark200=1`, 스플래시 약 4.0 s). 유효 시도가 0이고 LATE가 100%이므로 실행기는 **종료 코드 5**로 끝난다 — 이 자기 검사에서는 그것이 맞다(상한은 자연 조건 SW1을 위한 것이다).
    PASS나 FAIL(요청 없음)이 나오면 **실행기 결함**이다(분류가 동작하지 않는다) 또는 서버가 워드마크를 늦추지 않고 있다(서버 기록의 워드마크 `END` 줄이 약 2000 ms인지 본다).
  - **1000 ms**: 3회 모두 **PASS**(첫 화면 → `finalloopcomplete` 약 3.5 s, 스플래시 약 3.5 ~ 3.7 s). 이 지연에서 여유는 약 0.5 s뿐이라 자연 조건의 늦은 도착이 겹치면 LATE로 나올 수 있다 — 3회 가운데 LATE가 나오면 다시 돌고 건수를 적는다.
- 「Next」가 서는 것(계약의 AC9: 첫 화면 뒤 3.0 s ~ `entrySplashDurationMs` + 2 s 사이)은 이 항목이 아니라 계측 `HW5`가 본다. 실행기는 스플래시가 끝난 표지(`DestroyLayoutNodeBeforeRemoveFromParent tag:image`)의 시각으로 (b)를 가른다.

- FAIL이 있으면 회차 번호 · `onFailed` 줄(FAIL(요청 없음)이면 `reason=`과 서버 구간) · 같은 로그의 `lynx_PaintingContext: createViewAsync not done, will create on ui thread, tagName:image` 유무(수정 전 실패 16건에는 항상 있었다 — 계약 §2.3).

## test-plan과 다른 점

- test-plan의 e2e 표는 SW1 ~ SW6(+ r02의 SW9)이다. 이 문서는 **SW7(이미지 외 자원 회귀)** 과 **SW8(release AAB 스모크)** 를 더했다. test-plan에는 없고, 계약 §9의 위험 1(네이티브 소비자 미확인)과 test-plan의 「실기 · release AAB는 판정 밖」 문장을 받아 둔 것이다.
  SW8은 판정 밖이 아니라 **가드로 두었고 증거로 세지 않는다.**
- 반복 실행기는 test-plan이 `artifacts/run.sh`를 바탕으로 저장소에 둘 자리를 정하라고 한 것에 따라 `apps/android/tools/splash-wordmark-repeat.sh`로 두었다(문서 부록이 아니다 — 코드 블록을 파일로 꺼내는 단계를 없애려고).
  `run.sh`와 다른 점: 번호를 요약 줄 수가 아니라 **기존 로그 파일의 번호**로 이어 붙인다(덮어쓰기 결함), 판정 불가를 횟수에서 빼고 상한까지 다시 채운다, 고정 `sleep` 대신 끝 표지를 기다린다,
  `onFailed`가 **워드마크가 아닌 이미지**에서 나도 FAIL이다(계약 §7의 「어떤 이미지든」 — `run.sh`는 `logo-handwriting`만 세었다), `onFirstScreen`은 있는데 `finalloopcomplete`가 없으면 LATE가 아닌 한 FAIL(요청 없음)이다, 탐침 로그(`SplashProbe`) 열을 뺐다.
- SW4의 「온보딩이 선다」는 `uiautomator dump`에서 「Next」 표지를 찾는 방식이다(기존 [Android 시스템 뒤로가기](android-system-back.md)가 `Journey, selected`를 dump로 읽는 것과 같은 방식). **`content-desc="Next"`로 드러나는 것이 확인됐다**(T4, 첫 e2e 실행) — 실행기의 정규식이 그대로 맞는다.
- **r02에서 실행기가 계약과 다르게 한 것**: ① LATE의 (b)의 끝 표지로 `DestroyLayoutNodeBeforeRemoveFromParent tag:image`를 먼저 쓰고 `auth.session`은 없을 때의 마지막 조회만 쓴다(첫 `auth.session` 조회는 스플래시 도중에도 나온다 — 「판정」). 계약은 둘을 같은 급으로 적었다.
  ② SW9의 「Next가 선다」는 e2e 실행기가 아니라 계측 HW5가 본다(실행기는 스플래시가 끝난 표지로 (b)를 가른다).
  ③ 종료 코드 4(기기 소실 — T2)와 5(환경 부적합)를 더했다.
- 계약 §7의 AC1(계측 HW1) · AC5 · AC6 · AC7의 자동화 부분은 이 문서의 범위가 아니다.
