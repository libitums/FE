# ADR-0007 — 앱 내부: 상태 관리 · 라우팅 · 데이터 페칭 · 에러 경계

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: 상태 관리, 라우팅, 데이터 페칭, 에러 경계

## 맥락

네 축을 한 문서에 둔다. 넷이 서로를 정의하기 때문이다 — 라우팅을 어디가 소유하느냐가
에러 경계를 놓을 자리를 정하고, 데이터 페칭이 캐시를 갖느냐가 전역 상태가 맡을 범위를
정한다. 따로 정하면 반드시 어긋난다.

**ReactLynx로 확정됐다는 사실이 이 네 축을 자동으로 결정해 주지 않는다.** 다만 그
이유가 호환은 아니다. Lynx는 DOM이 아니지만, 공식 문서가 zustand·jotai·valtio,
TanStack Query, react-router·TanStack Router의 통합 방법을 각각 제공한다.
**호환은 미지의 영역이 아니다.**

그래서 이 ADR이 라이브러리를 넣지 않는 이유는 **위험이 아니라 필요**다 — 아직 필요가
오지 않았다. 일관된 판단은 이것이다:

> **라이브러리를 넣지 않는다. 대신 넣을 조건을 수치로 못박는다.**

조건 없이 "나중에"라고 쓰면 영원히 다시 보지 않고, 조건이 있으면 그 조건이 왔을 때
논쟁 없이 넣는다. 호환이 아니라 필요가 근거이므로 **조건이 오면 곧바로 넣을 수 있다** —
그 시점에 호환을 검증하느라 멈추지 않는다.

## 결정

### D1. 상태 관리 — 전역 상태 라이브러리를 도입하지 않는다

React 내장(`useState` · `useReducer` · `useContext`)만 쓴다.

**단, 서버 상태와 클라이언트 상태를 개념적으로 구분해서 부른다.** 라이브러리가 없어도
이 구분은 유지한다. 구분이 없으면 나중에 라이브러리를 넣을 때 무엇을 어디로 옮길지
알 수 없다.

- **서버 상태**: 서버가 진실의 출처인 것. 화면 로컬에 두고, 화면을 벗어나면 버린다.
- **클라이언트 상태**: 앱이 진실의 출처인 것 (현재 화면, 입력 중인 폼, UI 토글).

**저장소 모듈에 명시적으로 넣은 것만 앱 재시작 후 남는다.** Lynx 자체에는 영속 저장소
API가 없고, 자체 호스트가 제공하는 **저장소 모듈**이 그 자리를 맡는다(ADR-0012 D2).
호스트가 여는 네이티브 능력이 그 하나뿐이라는 뜻은 아니다 — 목록은
`docs/adr/README.md`의 **호스트 모듈 표**에 있다(ADR-0017 D2).
**첫 단계에 그 모듈을 쓰는 것은 로그인 토큰뿐이다** — 화면 상태나 서버 응답을 거기
넣기 시작하면 무효화가 사람 손으로 넘어오고, 그건 D2가 금지하는 것과 같은 실패다.
라이브러리 선택과 무관한 제약이다.

**도입 조건 (둘 중 하나):**

- 서로 다른 화면 **3개 이상**이 같은 상태를 읽거나
- prop 전달 깊이가 **3단계**를 넘으면

→ **zustand를 먼저 검토한다.** Context보다 재렌더 범위를 좁히기 쉽고 provider 트리를
늘리지 않기 때문이다.

### D2. 데이터 페칭 — 캐시 라이브러리를 도입하지 않는다

`src/lib/api-client.ts`에 `fetch` 기반 얇은 클라이언트 하나를 두고, 화면에서 호출한다.

**금지 규칙 하나: 서버 응답을 전역 store에 저장하지 않는다.**

서버 상태를 클라이언트 상태로 다루기 시작하면 무효화(언제 다시 받아오는가)가 사람
손으로 넘어온다. 그러면 "왜 옛 데이터가 보이나"를 디버깅하게 되고, 그 버그는 재현이
어렵다. 이 금지가 D1과 D2를 이어주는 규칙이다 — 라이브러리가 없어도 경계는 지킨다.

**근거:**

- API 명세가 아직 없다. 명세 없이 캐시 키와 무효화 전략을 정하면, 명세가
  나온 뒤 전부 다시 짠다.
- Lynx의 `fetch`는 웹 `fetch`와 표면이 다르다(아래 제약). 캐시 라이브러리를 얹으면
  그 차이를 라이브러리 안쪽까지 끌고 들어가게 된다. 얇은 클라이언트 하나면 차이가
  한 파일에서 끝난다.

**도입 조건 (둘 중 하나):**

- 같은 엔드포인트를 화면 **2곳 이상**이 부르거나
- 낙관적 갱신 또는 자동 재검증이 필요해지면

→ **TanStack Query를 검토한다. 이때 D1과 함께 본다** — Query가 서버 상태를 가져가면
전역 store가 맡을 범위가 줄어들어, D1의 도입 조건이 안 올 수도 있다. 둘을 따로 도입하면
서버 상태가 두 곳에 생긴다.

> **제약 (확인됨)**: Lynx 런타임은 `fetch`를 제공한다. 다만 웹 `fetch`와 같지 않다 —
> **CORS · redirect · keepalive 미지원, FormData · Blob 미지원.** 공식 문서도 React
> 생태계 라이브러리를 적응시켜야 할 수 있다고 명시한다.
>
> 클라이언트를 한 파일로 모아둔 이유가 이것이다 — 차이를 흡수할 자리가 한 곳이다.
> **파일 업로드가 필요해지면** FormData·Blob이 없으므로 D2를 갱신한다
> (방식은 ADR-0010 D10).

### D3. 라우팅 — 라우터 라이브러리를 도입하지 않는다

`src/app/`이 화면 전환을 소유한다. **하단 탭 바가 있고 일부 탭이 자기 스택을 갖는다**
(디자인 시스템의 `bottom-navigator` 스펙). 그래서 스택은 하나가 아니라 **탭별로** 둔다.

**탭이 아직 없는 구간이 앞에 있다.** 스플래시부터 여정 선택까지가 그렇다
(`docs/screens.md`). 그래서 스택은 탭별 스택 하나로 끝나지 않고, 그 앞에 진입 구간이
붙는다.

```ts
type Tab = 'home' | 'journey' | 'roleplay' | 'settings';   // 탭 목록과 1:1
type Screen = { name: 'home' } | { name: 'journey-map' } | ...;
type Nav = {
  entry: Screen[];                    // 탭 밖 구간. 비면 앱 구간이다
  tab: Tab;
  stacks: Record<Tab, Screen[]>;
};
```

**`phase: 'entry' | 'app'` 같은 필드를 두지 않는다.** 그 값은 `entry`가 비었는지에서
그대로 나온다. 파생 가능한 값을 따로 상태로 두면 둘이 어긋날 수 있고, 어긋났을 때
어느 쪽이 옳은지 코드가 답하지 못한다.

- 화면 이름과 탭 이름을 각각 union 타입으로 선언한다. 확정된 목록과 1:1로 대응한다.
- `useReducer`로 `Nav`를 관리한다. 동작은 **다섯**이다.

| 동작 | 어디에 작용하나 |
|---|---|
| `push` · `back` · `replace` | **활성 스택.** `entry`가 비어 있지 않으면 `entry`, 아니면 현재 탭의 스택 |
| `switchTab` | 탭만 바꾸고 각 스택은 보존한다. **앱 구간에서만 의미가 있다** |
| `enterApp` | `entry`를 비운다. **단방향이다** |

> **진입 구간으로 되돌아가는 경우는 정하지 않았다.** 로그아웃이 그런 경우일 텐데,
> 화면 목록에 없다. 없는 것을 추측으로 채우지 않는다(ADR-0010 D6). 필요해지는 시점이
> `enterApp`의 짝을 정하는 시점이다.
- 화면 파라미터는 union의 필드로만 넘긴다. 전역 상태나 모듈 변수로 넘기지 않는다.
- `screens/`의 화면 컴포넌트를 switch로 렌더한다.

**세 번째 스택 축을 만들지 않는다.** 탭 안에 또 탭이 필요해지면 그건 우회할 대상이
아니라 재검토 트리거다.

**`entry`는 이 규칙을 어기지 않는다.** 이 규칙이 막으려는 것은 축이 **동시에 중첩되는**
것이다. `entry`와 탭별 스택은 **배타적**이다 — `entry`가 비면 앱이고, 안 비면 진입이며,
둘이 함께 활성일 때가 없다. 그래서 어느 시점에도 살아 있는 스택은 하나다.

**근거:**

- **Lynx에는 브라우저 히스토리도 URL도 없다.** 호스트 앱이 로드하는 번들이기 때문이다
  (ADR-0012 D1). react-router의 DOM 라우터는 애초에 쓸 수 없다.
- memory router를 쓴다 해도 얻는 것은 데이터 로더와 중첩 라우트인데, 프로토타입에는
  **둘 다 없다.** 얻는 것 없이 설정 비용만 낸다 — TanStack Router 쪽은 rspack 설정
  3곳과 엔트리 1곳을 건드린다.
- 화면 목록이 확정이라 union 타입으로 전부 표현된다(`docs/screens.md`). 화면이 늘면
  타입이 강제로 알려준다 — switch의 exhaustiveness 검사가 빠진 화면을 컴파일 타임에
  잡는다.
- **탭별 스택도 순수 함수로 그대로 표현된다.** `Record<Tab, Screen[]>`이 전부다.
  라우터가 중첩에서 실제로 값을 하는 부분 — URL 동기화·딥링크·라우트별 로더·라우트
  단위 코드 분할 — 은 **우리에게 하나도 없다.** 중첩이 곧 라우터라는 등식은 성립하지 않는다.

화면 전환 리듀서는 순수 함수이므로 **`unit` 계층 테스트 대상**이다(ADR-0006 D4).
라이브러리를 안 쓴 덕에 오히려 전환 로직을 직접 테스트할 수 있다.

> **제약 (확정)**: **모든 화면에 화면 내 back 수단을 반드시 둔다.**
>
> 이건 확인 대상이 아니다. 판정 환경이 **iOS**이고(ADR-0012 D1) iOS에는 하드웨어 백
> 버튼이 **아예 없다.** 화면 안에 빠져나갈 수단이 없으면 정말로 빠져나갈 방법이 없다.
>
> Android 하드웨어 백을 Explorer가 전달하는지는 **Android 지원이 요구될 때** 확인한다
> (ADR-0012 D1의 재검토 조건). 그때도 이 규칙은 유지된다 — 하드웨어 버튼에만 의존하면
> 두 플랫폼에서 동작이 갈린다.

### D4. 에러 경계 — 루트에 **하나만** 둔다

`src/app/`에 에러 경계 하나를 둔다. 화면별 경계를 두지 않는다.

경계가 제공하는 것 둘:

1. 사람이 읽을 수 있는 실패 화면 (흰 화면 금지)
2. 재시도 — 루트 화면 상태를 초기값으로 리셋

**네트워크 실패를 에러 경계로 올리지 않는다.** 에러 경계는 **예상하지 못한 렌더
예외**를 위한 것이고, 네트워크 실패는 **예상된 실패**다. 예상된 실패는 화면 로컬
상태로 처리해 그 화면 안에서 재시도하게 한다. 이 둘을 섞으면 API가 한 번 느릴 때
앱 전체가 실패 화면으로 넘어간다.

**근거**: 이 축은 원래 라우팅에 막혀 있었다 — 경계를 놓을 자리가 라우팅 구조에
달려 있기 때문이다. D3에서 **루트가 화면 전환을 소유**하기로 정했으므로, 경계를 놓을
자리도 루트 하나로 자연히 결정된다. 두 축을 한 ADR에 둔 이유가 이것이다.

> **확인됨 (2026-08-25)**: ReactLynx가 `componentDidCatch`를 표준대로 지원한다.
> Explorer 4.0.1 / iOS 시뮬레이터에서 화면 컴포넌트에 렌더 예외를 던져 확인했다 —
> 흰 화면이 아니라 실패 화면과 재시도가 떴다. **이 결정이 성립한다.**

### D5. 임시 입력값 — 진짜가 오기 전이라는 이유로 **옵셔널을 쓰지 않는다**

> **2026-09-07에 더했다** — 이 ADR의 채택일 이후다. ADR-0010 D10의 *"없던 축을 처음
> 정한다"* 줄에 따라 **새 번호가 아니라 이 ADR의 D-번호**로 들어왔다. 그 줄의 판별
> 기준은 **기존 ADR의 `다루는 축`이 덮는가**이고 — 덮는다(**데이터 페칭**) — 「덮는다」
> 칸이 정한 조치는 *"그 ADR에 D-번호를 더한다. 축 추적표에 행을 더해 표에서도 보이게
> 한다"* 다. **판별 기준과 조치를 함께 따른다.** `docs/adr/README.md`의 축 추적표가
> 「데이터 페칭」 행에서 `D2·D5`로 보인다.
>
> **행을 새로 만들지 않는다.** ADR-0013이 *"축 추적표는 **축 하나에 ADR 하나**를 매단다.
> 새 축은 새 행이 필요하고"* 라고 적어, **새 행은 「새 축이다」라는 신호**다. 이 결정은
> 새 축이 아니라 **D2와 같은 축의 나머지 절반**이다 — D2가 그 계약이 **어디 있나**(한
> 파일)를 정했고, D5는 그 계약의 **모양**을 정한다.
>
> **왜 데이터 페칭인가.** ADR-0010 D6이 *"데이터 형태를 가정으로 굳히지 않는다 —
> ADR-0007 D2가 API 클라이언트를 한 파일로 모아둔 이유가 이것이다"* 로 이미 이 물음을
> 이 축으로 보냈다. 이 ADR이 타입 모양을 정하는 것도 처음이 아니다 — **D3이 `phase`
> 필드를 두지 않기로 하면서 「타입에 무엇을 넣지 않을지」를 한 번 판단했다.**
>
> **D1~D4 중 어느 것도 `대체됨`으로 밀려나지 않는다.** D5는 어느 결정도 부정하지
> 않는다. 그래서 `정정 기록`도 남기지 않는다.

**새로 만든 규칙이 아니라 이미 두 곳이 지키고 있는 것의 추인이다.**

- `apps/mobile/src/screens/listening/listening.ts`의 **`ListeningQuestion.audioSource`** —
  주석이 *"옵셔널이 아니다 — `audioSource?`면 「아직 없는 문항」이 타입에 생긴다"* 라고
  적고 필드를 `readonly audioSource: string`으로 둔다. **아직 없는 것은 자산이지 문항이
  아니다.**
- `apps/mobile/src/screens/journey-map/journey-map.ts`의 **`learningFormByStep`** — 같은
  판단을 union 쪽에서 한다. *"`LearningForm` union에 빈 값(`""`도 `null`도)이 없고
  `Record`가 다섯 키를 전부 요구한다"* 라 빈 채로 둘 수 없었고, 그래서 다섯 값이
  **배정이 아니라 전사(轉寫)**라는 것을 주석이 진다.

**정하는 것.** 진짜 값이 아직 없다는 이유로 **필드를 옵셔널(`x?`)로 만들지 않는다.**
값이 없어도 타입은 **있을 때의 모양**을 그대로 진다.

**근거.** 「아직 없다」를 타입에 넣으면 그 분기를 **소비자 전부가 진다.** 그리고 그
분기는 **컨텐츠가 오는 날에도 사라지지 않는다** — 옵셔널을 좁히려면 소비자를 전부 다시
열어야 한다. 그것이 D2가 *"차이를 흡수할 자리가 한 곳이다"* 로 사려던 바로 그 비용이고,
**옵셔널은 교체 지점을 한 곳에서 소비자 수만큼으로 늘린다.**

**금지하지 않는 것 둘.**

- **도메인상 없을 수 있는 값.** 「아직 안 왔다」가 아니라 「원래 없을 수 있다」면 대상이
  아니다 — `ListeningSessionState.selectedChoiceIndex: number | null`이 그 예다. 미응답은
  도착을 기다리는 상태가 아니다.
- **타입에 이미 자연스러운 빈 값이 있는 경우.** 문항 배열은 `[]`로 둘 수 있고 실제로
  그렇게 서 있다(`sentenceOrderQuestionsByStep` · `wordChoiceQuestionsByStep`). 금지하는
  것은 **빈 값을 새로 만들어 union에 더하는 것**이다.

## 버린 대안

**상태 관리**

- **zustand 선제 도입** — 공식 문서가 지원한다(jotai·valtio도 마찬가지고, 셋 다 별도
  설정을 요구하지 않는다). 검증 비용이 없다. 넣지 않는 이유는 **지금 전역이 필요 없다**는
  것 하나뿐이고, 이 근거는 D1의 도입 조건이 오는 순간 그대로 사라진다.
- **Redux Toolkit** — 보일러플레이트가 1주 일정에 맞지 않는다.
- **Context로 전역 통일** — 전역이 늘면 재렌더 범위가 넓어지고, 프로토타입 후반
  QC 루프에서 성능 문제로 돌아온다. 그때 고치는 비용이 크다.

**데이터 페칭**

- **TanStack Query 선제 도입** — 이유는 **명세 부재** 하나다. 캐시 키와 무효화를 근거
  없이 정하게 된다. 호환은 이유가 아니다 — 공식 문서가 데이터 페칭의 **주 권장**으로
  제시한다. 도입 시점에 마찰이 없다는 뜻이다.
- **axios** — `fetch`로 되는 일에 의존을 늘린다. 게다가 axios는 XHR을 전제하는데,
  Lynx가 제공하는 것은 `fetch` 표면이다.
- **서버 응답을 전역 store에 저장** — D2가 명시적으로 금지한다. 무효화가 사람 손으로 넘어온다.
- **옵셔널 필드(`x?`) + 소비자가 분기** — 값을 지어내지 않아도 되는 것이 이득이다.
  버린 이유는 D5의 근거다. `listening.ts`의 `audioSource` 주석이 그 자리에서 이미 버렸다.
- **union에 빈 값(`""` · `null`)을 하나 더해 「아직 없음」을 표현** — `learningFormByStep`이
  이 물음을 명시적으로 받았고(*"왜 빈 채로 둘 수 없나"*) 당시의 답은 **「union에 그런 값이
  없다」는 사실**이었다. D5가 그 사실을 규칙으로 추인한다 — **더하지 않는다.** 더하면
  옵셔널이 이름만 바꿔 돌아오고 소비자 전부가 다시 그 분기를 진다.

**라우팅**

- **react-router memory router** — 공식 문서에 통합 방법이 있다. 버리는 이유는 URL·
  딥링크가 없어 얻는 것이 거의 없다는 것. 문서가 명시하는 제약도 함께 붙는다 —
  ReactLynx가 React 17 API만 제공해 **v6로 고정**되고, `<Link>`·`<NavLink>`가 없어
  이동은 `useNavigate`로만 한다.
- **파일 기반 라우팅** — **TanStack Router로 가능하다**(rspack 플러그인, memory
  history). 버리는 이유는 화면 수가 적어 규약이 주는 이득보다 설정 비용이 크다는 것.
- **라우팅 없이 단일 화면** — 화면 목록이 여럿이라 성립하지 않는다.

**에러 경계**

- **화면마다 경계** — 한 화면이 죽어도 나머지가 산다는 이득이 있지만, 프로토타입에서는
  **어느 화면이 죽었는지 즉시 아는 것**이 더 중요하다. 경계가 여럿이면 실패가 국소적으로
  삼켜져 조용히 이상한 상태가 된다.
- **경계 없음** — Explorer에서 흰 화면만 보이고 원인을 알 수 없다. 시연 중 최악의 상태다.

## 대가

- **prop drilling이 일정 기간 존재한다.** D1의 도입 조건(깊이 3단계)에 닿기 전까지
  참는다. 코드가 보기에 세련되지 않다.
- **상태가 예상보다 빨리 얽히면 중간에 도입 비용을 낸다.** 조건을 수치로 박아둔 이유가
  이 시점을 놓치지 않으려는 것이다.
- **캐시가 없으므로 같은 데이터를 화면 전환마다 다시 받는다.** 프로토타입 규모에서는
  체감되지 않을 가능성이 높지만, 목록→상세→목록 같은 흐름에서 깜빡임이 보일 수 있다.
- **라우터가 없으므로 딥링크·화면 전환 애니메이션·하드웨어 뒤로가기를 직접 다뤄야 한다.**
  탭별 스택까지는 리듀서가 덮지만, **탭 안의 탭처럼 축이 하나 더 생기거나** 화면이 크게
  늘면 직접 만든 것이 부채가 된다.
- **마이그레이션이 싼 것은 규율이 지켜질 때뿐이다.** 화면이 스택 배열을 직접 읽고 쓰거나,
  화면 간 값을 전역·모듈 변수로 넘기거나, 전환 애니메이션을 스택 위에 직접 만들면
  호출부가 타입으로 열거되지 않게 되고 라우터로 옮기는 비용이 급격히 오른다.
- **공식 지원이 무비용을 뜻하지 않는다.** TanStack Router를 나중에 넣으면 `isServer: false`
  강제, `react$` → `@lynx-js/react/compat` alias, `url-search-params-polyfill` 등 빌드
  설정이 늘어난다. 검증 비용이 없을 뿐, 도입 시점에 이 설정 비용은 낸다.
- **`fetch`에 FormData·Blob이 없다.** 파일 업로드가 요구되는 순간 클라이언트 구현이
  통째로 바뀐다. 지금은 업로드 요구가 없다는 전제 위에 서 있다.
- **경계가 하나이므로 한 화면의 렌더 예외가 앱 전체를 실패 화면으로 만든다.** 시연 중에
  이것이 발생하면 재시도로 복구해야 한다 — 그래서 D4가 재시도를 필수로 넣었다.
- **임시 값이 진짜처럼 보인다.** 타입이 「없음」을 표현하지 않으므로 채워 둔 값이 결정으로
  읽힌다 — `learningFormByStep`의 다섯 `"listening"`이 그것이다. 막는 것은 **주석과 보류
  표뿐이고 강제 수단이 없다.**
- **값을 반드시 채워야 한다.** 「지어내지 않는다」와 표면상 부딪히는 자리가 생긴다. 가르는
  선은 **그 값이 판단인가**다 — 판단이면 채우지 않고 미룬다. 그 판정의 자리는
  `docs/screens.md`의 「홈은 소비자다」(파생값)이고, 규약 재진술은
  `docs/conventions/code.md`의 「임시 입력값의 이음매」다.

## 재검토 조건

- 화면 3개 이상이 같은 상태를 읽거나 prop 깊이 3단계 초과 → D1 (zustand)
- 같은 엔드포인트를 화면 2곳 이상이 호출하거나 낙관적 갱신 필요 → D2 (TanStack Query),
  **D1과 함께**
- **URL·딥링크가 요구되거나**, 화면 전환에 **라우트별 데이터 로더 또는 코드 분할**이
  필요해지는 시점 → D3 (라우터). 이때 할 일은 호환 검증이 아니라 **공식 문서의 레시피
  적용**이다
- 스택 축이 **셋 이상**이 되는 시점(탭 안의 탭) → D3
- D3의 규율 넷 중 하나라도 깨진 것이 발견되는 시점 → 그 자리에서 되돌리거나 D3를 다시 본다
- 파일 업로드가 요구되는 시점 → D2 (`fetch`에 FormData·Blob이 없다)
- 확인 목록(`docs/adr/README.md`)의 가정이 어긋나는 시점 → 해당 결정
- **보류 표의 「오디오 자산의 출처·형식」 또는 「스텝별 학습형 배정」이 닫히는 시점 → D5.**
  그날 검산할 것은 하나다 — *"형태는 한 글자도 안 바뀐다"*(`learningFormByStep` 주석)가
  실제로 지켜졌는가. **바뀌었으면 이 결정이 값을 못 한 것**이므로 그 자리에서 다시 본다
- **API 명세가 도메인상 없을 수 있는(nullable) 필드를 처음 주는 시점 → D5.** 위 「금지하지
  않는 것」의 경계가 실물에 처음 닿는 자리다. 경계가 흐리면 이 금지가 도메인 nullable까지
  막는 것으로 읽힌다
- **이음매 자리가 넷째로 생기는 시점 → D5.** 지금은 둘이고(`audioSource` ·
  `learningFormByStep`) 문화 컨텐츠가 셋째로 예정돼 있다. 넷째가 오면 규칙만으로 되는지
  공용 모듈 하나가 필요한지 다시 본다

## 정정 기록

**2026-08-25 — 근거 정정.** 결정 넷은 그대로다. 근거에서 "Lynx 런타임 미검증"을 걷어냈다.

최초 작성 시 맥락에 *"Lynx는 DOM이 아니므로 웹 React 생태계의 기본 선택지 상당수가
그대로 쓸 수 있는지조차 확인되지 않았다"* 를 깔고, D1·D2·D3의 근거를 여기에 걸었다.
**확인해보니 틀렸다.** Lynx 공식 문서에 zustand·jotai·valtio, TanStack Query,
react-router·TanStack Router가 각각 문서화돼 있다. `fetch`도 제공된다.

고친 곳: 맥락 전제, D2 근거와 `확인 필요` 블록, D3 근거, 버린 대안 다섯 줄,
대가 둘, 재검토 조건 둘.

**어떻게 틀렸나** — 공식 문서를 읽지 않고 *"Lynx는 DOM이 아니다"* 라는 사실 하나에서
*"그러므로 생태계 전반이 미검증이다"* 를 일반화했다. 결론이 안전한 쪽이라 검토에서
걸러지지 않았다. 근거로 쓰기 좋은 문장이었던 것이 문제다.

같은 방식으로 틀렸을 곳을 이어서 훑었다 — **ADR-0006**은 러너 검토 부재가 같은 모양으로
나왔고(그쪽 정정 기록 참조), **ADR-0008**은 전제 자체가 틀려 **ADR-0011로 대체**됐다.
**ADR-0002**도 이어서 훑었다.
**"확인되지 않았다"를 근거로 쓰기 전에 공식 문서를 먼저 본다.**

**2026-08-25 — D3 재검토 트리거가 발동했고, 트리거 쪽을 고쳤다.**

화면 목록에 **하단 탭 바가 있고 일부 탭이 자기 스택을 갖는 것**이 확인됐다. D3의 재검토
조건이 *"중첩 네비게이션(탭 안의 스택)이 필요해지는 시점 → 라우터"* 였으므로 트리거가
그대로 걸렸다.

검토 결과 **라우터로 넘어가지 않고 트리거를 고쳤다.** 그 조건은 *중첩이 곧 어렵다*는
가정 위에서 쓴 것이었는데, 실제 모양(탭 N개 × 독립 스택, URL 없음)은 `Record<Tab,
Screen[]>` 하나로 표현되고 순수 함수도 유지된다. 라우터가 중첩에서 값을 하는 부분은
전부 URL을 전제한다.

조건을 **"URL·딥링크가 요구되거나, 라우트별 로더·코드 분할이 필요해지는 시점"** 으로
바꾸고, 축이 셋 이상이 되는 경우를 따로 남겼다. 결정(라우터를 넣지 않는다)은 그대로다.
**트리거가 발동했는데 조용히 넘어가지 않았다는 것을 남기려고 여기 적는다.**

**2026-08-31 — D3이 딛고 선 사실을 정정. `Nav`에 진입 구간을 더했다.** 결정은 그대로다.

D3의 `Nav = { tab, stacks }`는 **모든 화면이 탭 안에 있다고 가정**했다. `docs/screens.md`가
탭 밖 구간을 드러냈다 — 스플래시 · 온보딩 · 로그인 · 코드 검증 · 언어 선택 · 여정 선택.
담을 자리가 없었다.

`entry: Screen[]`를 더하고, 동작을 넷에서 다섯으로 늘렸다(`enterApp`). `entry`가 세 번째
스택 축이 아닌 이유도 적었다 — 배타적이라 동시에 활성이지 않다.

`phase` 필드는 두지 않았다. 화면 명세의 초안이 그렇게 제안했지만, 그 값은 `entry`가
비었는지에서 그대로 나온다.

고친 곳: D3의 타입 블록, 동작 표, "세 번째 스택 축" 문단, 근거 한 줄.

**어떻게 틀렸나** — **가진 화면들의 공통 구조를 보고 그것을 전부라고 적었다.** 당시
알던 화면이 전부 탭 안에 있었고, 그 모양을 그대로 타입으로 굳혔다. 타입은 "지금 아는
것"이 아니라 "있을 수 있는 것"을 담아야 하는데, **아는 것만으로 닫아버렸다.**

D1의 저장소 제약이 같은 검사를 통과한 것과 대조된다. 그쪽은 *"넣는 것은 로그인
토큰뿐"* 이라고 **범위를 좁게 못 박아서**, 뒤에 재방문 판단이 들어왔을 때 상충이 곧바로
드러났다. D3은 반대로 **모양을 넓게 그려놓고 그것이 전부인 척했기 때문에** 상충이
드러나지 않았다.

같은 방식으로 틀렸을 곳을 훑었다. **ADR-0003**의 `screens/` 폴더 규칙은 화면이 탭 안인지
밖인지에 기대지 않아 그대로다. **ADR-0006 D4**의 계층 표도 마찬가지다.

**타입이 닫힌 집합을 주장할 때는 그 집합이 어디서 왔는지 함께 적는다.** 화면 목록에서
왔다면 화면 목록이 바뀔 때 타입도 바뀐다는 뜻이다.

**실체화는 이 정정이 하지 않는다.** `navigation.ts`는 아직 옛 모양이고, 뼈대 이슈가
새 모양으로 바꾼다. 지금 `Screen`에 `'home'` 하나뿐이라 여기서 고치면 항상 비어 있는
`entry`만 생긴다.

**실체화됨 (2026-09-02).** 뼈대 이슈가 `navigation.ts`의 `Nav`를 위 모양(`entry` 포함)으로
바꿨다.
