# ADR-0047 — Android 화면 방향과 구성 변경: 휴대폰은 세로로 고정하고, 선언한 구성 변경은 Activity를 다시 만들지 않고 받는다

- 상태: **채택.** D1(Android만 세로 고정)과 D2의 `assetsPaths` 직접 처리는 **사용자 결정으로 확정됐다**(2026-10-06 — 아래 「사용자 결정」 U1 · U4).
  iOS iPhone은 가로를 허용하고 있어 두 플랫폼의 휴대폰 동작이 다르다 — 알고 정한 차이다.
  에뮬레이터 두 대(Pixel_8 AVD · API 37, R6_API30 AVD · API 30)에서 실행했다(2026-10-05 ~ 06).
  ⚠ **휴대폰 세로 고정은 WCAG 2.1 AA SC 1.3.4(Orientation) 불충족이다 — 알고 받아들인다**(D1의 「접근성」). 가로 레이아웃은 후속 작업이다.
  ⚠ **API 31 ~ 35 · 실기 · 제조사 스킨 · 실제 태블릿 · 폴더블 · 실기 TalkBack 낭독은 확인하지 않았다. 「큰 화면에서 플랫폼이 스스로 방향 고정을 무시한다」는 것도 증명하지 못했다**(「확인한 것과 확인하지 못한 것」).
  이 ADR의 첫 판은 사실 둘을 틀리게 적었다 — 「정정 기록」.
- 날짜: 2026-10-06
- 다루는 축: Android `MainActivity`의 화면 방향 · 매니페스트 `configChanges`의 값 집합(무엇을 재생성 없이 받고 무엇에서 재생성을 받아들이는가) ·
  구성 변경 때 호스트가 Lynx에 다시 넘기는 것 · 방향 고정이 듣지 않는 큰 화면에서의 최소 보장
- 이어받는 결정: [ADR-0038](0038-android-minimal-host.md)(Android 최소 호스트), [ADR-0044](0044-android-tappable-inset.md) D1 · D4(safe area 두 키와 `globalPropsMode: "event"` —
  구성 변경 뒤의 여백 갱신이 이 위에 선다), [ADR-0043](0043-android-system-back.md)(뒤로가기의 「JS 준비」 상태 — 재생성이 사라져 구성 변경을 건너 유지된다),
  [ADR-0046](0046-android-play-release.md) D2(`targetSdk` 36 — 큰 화면에서 방향 고정이 무시되는 조건이 여기서 온다),
  [ADR-0020](0020-dynamic-type-font-scale.md) D2(글꼴 배율은 「다음 실행에 반영」 — iOS 결정이고, Android에서 같은 결론을 재생성으로 얻는 것이 D3이다).
  **바꾸는 결정은 없다** — 공유 JS(`apps/mobile/src`) · `packages/ui-lynx` · iOS 호스트 · Gradle 의존 · `MainActivity`의 다른 메서드가 그대로다.

## 맥락

이 변경 전 `MainActivity`에는 `android:screenOrientation`도 `android:configChanges`도 없었다. 회전 · 다크 모드 전환 · 화면 크기 변경 · 시스템 언어 변경 · 키보드 연결 —
어떤 구성 변경이든 Activity가 파괴되고 `onCreate`가 처음부터 돌았다. 결정이 딛고 선 사실은 아래다(작업 `android-orientation`의 계약 단계, 2026-10-05).

1. **재생성은 화면 상태 전체를 버린다.** LynxView와 JS 컨텍스트가 새로 만들어져 스플래시부터 다시 서고, 내비게이션 스택 · 메모리의 학습 진행 · 입력이 사라진다.
   `onDestroy`가 대사 재생 · 효과음 · 음성 인식 세션 · 푸시 권한 요청 대기 · 진행 중인 웹 인증 콜백을 정리한다. 뒤로가기의 「JS 준비」 상태도 새 인스턴스에서 처음부터라
   재생성 직후의 뒤로가기는 `finish()` 경로다. 남는 것은 SharedPreferences(로그인 세션 · 푸시 열림 기록) · 서비스 · 인텐트 extra뿐이다.
2. **화면은 세로로만 설계됐다.** iOS 시뮬레이터에서 가로로 돌리면 온보딩 레이아웃이 아래로 넘쳐 잘린다(작업 `android-tabbar-inset`의 산출물 `ios-rotation.md`, 2026-10-05, iPhone 17 Pro 시뮬레이터).
3. **iOS iPhone은 가로를 허용한다.** `apps/ios/Host.xcodeproj/project.pbxproj`의 `INFOPLIST_KEY_UISupportedInterfaceOrientations_iPhone`이 세로 + 가로 왼쪽 + 가로 오른쪽이다
   (두 빌드 구성 모두. 거꾸로 선 세로만 없다). 코드의 재정의(`supportedInterfaceOrientations` · `shouldAutorotate`)는 없다. iPad 값은 `TARGETED_DEVICE_FAMILY = 1`이라 쓰이지 않는다.
   요구사항의 「휴대폰 세로 고정 — iOS와 같은 동작」은 **사실과 다르다.** iOS의 가로는 설정하지 않아 남은 Xcode 기본값이고, 가로에서 화면이 잘린다.
4. **Lynx 4.0.1은 구성 변경을 스스로 듣지 않는다.** `vendor-maven`의 `lynx-4.0.1.aar`와 xelement · 서비스 AAR의 `classes.jar`를 `javap -p -c`로 본 결과
   `onConfigurationChanged` · `ComponentCallbacks` 문자열이 0건이다. 축마다 따라가는 방식이 다르다.

   | 축 | Lynx의 경로 | 재생성 없이 따라가는가 |
   |---|---|---|
   | LynxView 크기(viewport) | `LynxView.onMeasure` → `LynxTemplateRender.updateViewport` — 앞선 측정과 다르면 네이티브에 넘긴다 | **스스로 따라간다** — LynxView가 content view(`MATCH_PARENT`)라 창 크기가 바뀌면 측정이 다시 돈다 |
   | 화면 크기(screen metrics) | `LynxView.updateScreenMetrics(int, int)`. 처음 값은 생성 때 `DisplayMetricsHolder`(`Display.getRealMetrics`)에서 읽는다 | **호스트가 불러야 한다** — 안 부르면 생성 시점 값에 머문다 |
   | 밀도 | 생성 때 복사한 값을 계속 쓴다. 실행 중에 바꾸는 공개 진입점이 없다 | **못 따라간다** |
   | 글꼴 배율 | `LynxView.updateFontScale(float)`은 있다 | **[추론] 화면을 다시 그리지 않을 수 있다** — iOS에서 같은 코어 경로가 값을 갈고도 다시 그리지 않는 것이 확인돼 있다(ADR-0020 D2). **Android에서 재지는 않았다** |
   | 색 구성 | `LynxView.updateColorScheme`은 있다. 앱이 쓰지 않는다 | 해당 없음 |

5. **앱은 구성 값을 거의 소비하지 않는다.** `res/`에 야간 · 방향 · 크기 · 키보드 한정자가 0이고 테마는 `Theme.Material.Light.NoActionBar` 고정, `supportsRtl` 선언이 없다.
   공유 JS에 `SystemInfo` · `pixelRatio` · `rpx` · `prefers-color-scheme`이 0건이고, UI 언어는 시스템 로캘이 아니라 저장소 값이다. safe area는 globalProps로 받고
   `globalPropsMode: "event"`라 갱신이 오면 바로 다시 그린다(ADR-0044 D4). 즉 대부분의 구성 변경은 **재생성해도 같은 화면을 그린다 — 잃기만 한다.**
6. **방향 고정이 듣지 않는다고 알려진 곳은 큰 화면이다 — 플랫폼 문서 기준이고 이 작업에서 증명하지 못했다.** `targetSdk` 36 + 기기 API 36 이상 + 디스플레이 최소 너비 600dp 이상이면
   `screenOrientation` · `resizeableActivity="false"` · 비율 제한이 무시된다고 한다. 이 작업이 본 것은 휴대폰 AVD에 `wm set-ignore-orientation-request true`를 **걸어서** 만든 가로다 —
   그 설정 없이 큰 화면에서 무엇이 일어나는지(무시인지 레터박스인지)는 큰 화면 AVD나 실기 없이는 모른다.
7. **분할 화면에서는 방향 고정이 유지된다.** API 37 에뮬레이터의 분할 화면에서 앱 영역이 **가로로 넓은 모양**(1080x823)이 되면 시스템이 세로 창을 가운데 세우고 좌우를 비운다
   (창 `Rect(133,0-948,823)` — 좌우 133px씩, `dumpsys activity`의 `letterboxReason=FIXED_ORIENTATION`). **세로 모양 영역**(1080x1187 · 1080x1551)에서는 창을 채운다. 앱에는 어느 쪽이든 크기 변경만 온다(2026-10-06, 2회 재현).
   자유 창 · 다른 API · 태블릿의 분할 화면은 재지 않았다.
   같은 조작을 이 변경 전의 빌드(기준선 `47600f41`)로도 돌렸다: 그 빌드는 같은 영역에서 가로 폭을 전부 쓰고 레터박스가 없으며, **분할 진입 · 분할선 이동 · 복귀마다 재생성되어 문항 도중이면 맵 맨 위로 돌아갔다.**
8. **`assetsPaths`는 compileSdk 36부터 `configChanges`에 선언할 수 있다.** 런타임 리소스 오버레이의 경로가 바뀔 때(내비게이션 모드 전환 · 시스템 글꼴 · 테마 오버레이) 오는 구성 변경
   (`ActivityInfo.CONFIG_ASSETS_PATHS`, `0x80000000`)이다. SDK의 `platforms/android-36` 매니페스트 속성 정의에 `assetsPaths` · `resourcesUnused`가 있고 android-35에는 둘 다 없다(SDK 파일 대조 —
   플랫폼 소스나 공개 문서로 다시 확인하지는 않았다). 이 저장소의 `compileSdk`는 36이다(ADR-0046 D2).
   **이 ADR이 「API 36 이상 / 35 이하」라고 적는 경계는 여기서 온 추론이다** — 기기에서 잰 것은 API 37(선언이 듣는다)과 API 30(무시된다) 두 점뿐이고, API 36 자체 · 26 ~ 29 · 31 ~ 35는 재지 않았다.

## 결정

### D1. 휴대폰에서 `MainActivity`는 세로로 고정한다 — `android:screenOrientation="portrait"` (사용자 결정으로 확정, 2026-10-06)

근거는 **화면이 세로로만 설계됐다**는 것이다(맥락 2). 「iOS와 같아서」가 아니다 — iOS iPhone은 가로를 허용한다(맥락 3).

- 값은 `portrait`다. 똑바로 선 세로 하나이고, 휴대폰에서는 기기를 돌려도 구성 변경 자체가 오지 않는다.
- **이 결정으로 두 플랫폼이 달라진다**: Android 휴대폰은 세로 고정, iOS iPhone은 가로 허용(잘린 채). iOS를 맞추는 일은 이 작업의 범위 밖이다(수용 기준 「iOS 동작 불변」).
- 고정이 듣지 않는 곳(맥락 6)에서는 D2 · D4 · D5가 받는다. 분할 화면에서는 고정이 유지돼 가로 모양 영역에 레터박스가 선다(맥락 7 · D5).
- `android:resizeableActivity` · `min/maxAspectRatio` · `<supports-screens>` · `android.window.PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY`를 **선언하지 않는다**(「버린 대안」).

#### 접근성 — SC 1.3.4(Orientation) 불충족을 알고 받아들인다

**휴대폰 세로 고정은 WCAG 2.1 AA SC 1.3.4(Orientation)를 충족하지 못한다**(실패 기법 F97). 이 기준은 특정 표시 방향이 **필수적**일 때만 제한을 허용하는데, 이 앱(언어 학습)에는 방향이 필수적인 화면이 없다.
「화면이 세로로만 설계됐다」는 예외 사유가 아니다 — **필수 예외를 주장하지 않는다.** 변경 전에는 방향을 제한하지 않았으므로 형식상 이 변경이 불충족을 새로 들였다
(다만 그때의 가로는 회전마다 재생성으로 진행을 잃는 가로였다). 판정은 이 작업의 접근성 점검(2026-10-06)이 했다.

| | |
|---|---|
| 받아들이는 이유 | 레이아웃이 세로 전제라, 가로를 허용하면 화면이 아래로 잘려 주 버튼이 화면 밖으로 나가 진행이 막힐 수 있다. 잘려서 누를 수 없는 버튼은 누운 버튼보다 나쁘다. **단 Android 휴대폰 가로에서 실제로 무엇이 잘리는지는 재지 않았다** — iOS 시뮬레이터의 기록(맥락 2)과 Android 큰 화면 흉내(절차 문서 O4 — 진행 알약이 하단 주 버튼에 가려짐)에서 미뤄 본 것이다 |
| 영향 받는 사용자 | 기기를 가로로 거치해 쓰는 사용자(휠체어 · 침상 거치대 등). 내용과 조작부는 전부 있고 동작하지만 **90도 누워 있다.** 휴대폰에는 사용자가 앱별로 방향을 풀 설정이 없다 |
| 고정이 풀리는 곳 | API 36 이상 · 최소 너비 600dp 이상의 큰 화면(맥락 6 — **플랫폼 문서 기준이고 증명하지 못했다**). 거기서는 가로가 되지만 D5의 최소 보장뿐이고 잘림은 남는다. **분할 화면은 풀리는 곳이 아니다**(맥락 7) |
| 그대로 걸리는 곳 | **휴대폰 전부**(분할 화면 포함 — 가로 모양 영역에서는 세로 창이 레터박스로 선다)와 API 35 이하의 큰 화면(레터박스된 세로) |
| iOS | 가로를 허용하므로 SC 1.3.4는 형식상 지나간다. 그러나 가로에서 화면이 아래로 잘려 내용 · 조작부를 잃는다(맥락 2) — 충족이 사용 가능을 뜻하지 않는다 |
| 해소 조건 | **가로 레이아웃 후속 작업이 끝나면 `android:screenOrientation` 한 줄을 지운다.** `configChanges`와 `onConfigurationChanged`(D2 · D4)는 그대로 두면 회전이 재생성 없이 온다. `mainActivityOrientation` 판정과 IC4 · O1을 함께 바꾼다 |

### D2. 구성 값 11개는 Activity를 다시 만들지 않고 받는다 — `android:configChanges`

원칙: **재생성한 Activity가 지금 화면과 똑같이 그릴 값은 직접 처리한다**(앱이 그 값을 소비하지 않는다 → 잃기만 한다 — 맥락 5).

```xml
<activity android:name=".MainActivity" android:exported="true" android:launchMode="singleTask"
    android:screenOrientation="portrait"
    android:configChanges="orientation|screenSize|smallestScreenSize|screenLayout|uiMode|locale|layoutDirection|keyboard|keyboardHidden|navigation|assetsPaths">
```

병합된 매니페스트의 값은 `screenOrientation=1` · `configChanges=0x80002ff4`다(`assetsPaths`가 `0x80000000`, 나머지 10값이 `0x2ff4`). 더한 속성은 이 둘뿐이고 `exported` · `launchMode` · 인텐트 필터는 그대로다.

| 값 | 언제 오는가 | 직접 처리해도 되는 근거 — 그리고 그 책임을 누가 지는가 | 대가 |
|---|---|---|---|
| `orientation` | 회전. 휴대폰은 D1로 오지 않는다 — 큰 화면(고정 무시) · 가로인 다른 Activity(Custom Tab) 뒤에서 온다. **분할 화면에서는 오지 않는다** — 고정이 유지되고 크기 변경만 온다(맥락 7) | viewport는 Lynx가 스스로, screen metrics · safe area는 D4 | 가로 레이아웃은 세로 설계 그대로다(D5) |
| `screenSize` | 회전 · 분할 화면 · 자유 창 · `wm size` | 위와 같다. 회전에는 `orientation`과 **함께** 오므로 하나만 선언하면 재생성된다 | 없음 |
| `smallestScreenSize` | 분할 화면 진입 · 디스플레이 이동 · `wm size` | `res/`에 `sw` 한정자 0 | 없음 |
| `screenLayout` | 크기 등급 · 길쭉함 변화, 다른 디스플레이 | `res/`에 크기 한정자 0 | 없음 |
| `uiMode` | 다크 모드 전환(**일몰 예약으로 학습 도중에 온다**) · 절전 모드 · 거치대 | 야간 리소스 0 · 테마 Light 고정 · JS에 `prefers-color-scheme` 0 · 상태바 아이콘 색은 코드가 고정 | 리소스가 다시 로드되지 않는다 — 다시 로드할 것이 없다. **다크 테마를 만들면 D4에 `updateColorScheme` 전달이 필요해진다**(「재검토 조건」) |
| `locale` · `layoutDirection` | 시스템 언어 변경 | UI 언어는 저장소 값. 네이티브 문자열 둘(`values-ko`)은 알림을 만들 때 애플리케이션 컨텍스트로 읽는다. `supportsRtl` 없음 | 이미 그려진 글자의 시스템 글꼴 대체는 다음에 그릴 때 바뀐다 |
| `keyboard` · `keyboardHidden` · `navigation` | 블루투스 · USB 키보드 · 스캐너의 연결과 해제 | 키보드 한정자 리소스 0. Lynx 입력은 뷰가 그대로 선다 | 없음 |
| `assetsPaths` | 런타임 리소스 오버레이의 경로 변경 — 내비게이션 모드 전환 · 시스템 글꼴 오버레이(둘은 실측), 동적 색상 · 시스템 오버레이 갱신(추론) | 이 Activity가 다시 읽을 리소스가 없다(맥락 5 — `res/`는 아이콘과 알림 채널 문자열뿐이고 문자열은 서비스가 쓸 때 읽는다). `assets/`(내장 번들 · 대사 · 효과음)는 Activity가 아니라 **애플리케이션 컨텍스트**로 읽는다 — `AndroidTemplateProvider` · `AudioPlaybackController` · `SoundEffectsController`가 생성자에서 `getApplicationContext()`를 잡아 그 `getAssets()`로 연다. 그림을 그리는 Fresco는 `DuruApplication`에서 초기화한다. 오버레이가 inset을 바꾸면 D4의 기존 리스너가 `tappableBottomInset`을 다시 보낸다 — `MainActivity`는 이 값 때문에 바뀌지 않았다 | **API 36 이상에서만 듣는다고 본다**(경계는 추론 — 맥락 8. 실측은 API 37). API 35 이하에서는 선언이 무시되어 재생성된다(실측은 API 30 — 아래) |

**`assetsPaths`에 대해서는 이렇다.**

> `assetsPaths`(런타임 리소스 오버레이의 경로 변경 — 내비게이션 모드 전환 · 시스템 글꼴 · 테마 오버레이)를 `configChanges`에 **선언해 직접 처리한다.** 이 값은 compileSdk 36부터 선언할 수 있다.
> **API 36 이상**에서는 그 변경에 `MainActivity`가 재생성되지 않는다 — API 37 에뮬레이터에서 내비게이션 모드 왕복과 글꼴 오버레이 켬 · 끔에 생성 · 파괴 0회, 탭 바가 새 모드 위치(3버튼 2243 / 제스처 2369px)로 옮겨 가고 화면 상태가 남는 것을 확인했다(2026-10-06).
> **API 35 이하**에서는 선언이 무시되어 전과 같이 재생성된다 — API 30에서 확인했고 API 31 ~ 35는 재지 않았다. 그 기기에서는 재생성 뒤 정상 화면이 다시 서는 것이 보장의 전부다.
> **대가**: 오버레이가 바뀌어도 Activity가 리소스를 다시 읽지 않는다 — 이 Activity가 읽는 리소스가 없어(아이콘과 알림 채널 문자열뿐이고 문자열은 서비스가 쓸 때 읽는다) 지금은 잃는 것이 없다. 호스트가 테마 · 치수 리소스를 읽기 시작하면 이 결정을 다시 본다.
> **확인하지 못한 것**: API 31 ~ 35, 실기 · 제조사 스킨, 배경화면 기반 동적 색상이 이 경로로 오는지, 맵 밖 화면(학습 · 소리 재생 · 입력 중)에서의 직접 처리, 실제 설정 앱 UI 조작(오버레이 명령으로 대신했다).
> `resourcesUnused`는 다른 플래그를 전부 덮어 `density` · `fontScale`의 재생성까지 막으므로 쓰지 않는다.

위 「확인하지 못한 것」 가운데 **맵 밖 화면은 그 뒤 일부 확인됐다**(2026-10-06, `4f3b2927` · API 37): 학습 화면 도중 · 학습 화면의 하단 주 버튼 · 대사 재생 중 · 전환 뒤 뒤로가기 · 탭 전환에서 생성 · 파괴 0회였다.
**입력 중**(텍스트 입력 상태)은 여전히 재지 않았다. 나머지 항목은 그대로 미확인이다.
위 문면의 「API 36 이상」 · 「API 35 이하」는 맥락 8의 추론 위에 선 경계다 — 실측은 API 37과 API 30 두 점이다.

재생성이 없으면 `onStop` · `onDestroy`도 불리지 않는다. 그래서 **대사 재생 · 효과음 · 음성 인식 · 진행 중인 인증 콜백 · 뒤로가기의 준비 상태가 구성 변경을 건너 이어진다** — 이 결정이 새로 보장하는 것이다.

값 집합은 닫혀 있다. `devtools/android-bundle/host-config-changes.mjs`의 `mainActivityConfigIssues(manifestXml)`가 매니페스트 원문을 받아
이 표와 D1 · D3 · 「버린 대안」의 선언 금지를 위반 목록으로 판정하고(`handledConfigChanges` 11 · `recreatedConfigChanges` 2 · `mainActivityOrientation`), `pnpm test:android-bundle`이 실제 매니페스트에 건다.
`assetsPaths`를 포함해 11값 가운데 하나라도 빠지면 `config-missing`, `density` · `fontScale`을 선언하면 `config-forbidden`, 두 목록 밖의 값(`resourcesUnused` 포함)을 선언하면 `config-unlisted`다.
`resourcesUnused`는 정적 결선 검사(HO5)가 따로 한 번 더 막는다.
**값을 더하거나 빼려면 이 ADR과 그 함수를 함께 고친다.**

### D3. `density` · `fontScale`과 선언하지 않은 값은 재생성을 받아들인다

원칙: **Lynx 엔진이 실행 중에 따라가지 못하는 값은 재생성을 받아들인다.**

| 값 | 언제 오는가 | 왜 재생성인가 | 대가 |
|---|---|---|---|
| `density` | 설정 「디스플레이 크기」 · 밀도가 다른 디스플레이로 이동 · `wm density` | Lynx가 생성 때의 밀도를 들고 있고 바꿀 진입점이 없다(맥락 4) — 직접 처리하면 **크기가 전부 틀린 화면**이 남는다 | 상태를 잃는다(변경 전과 같다) |
| `fontScale` | 설정 「글꼴 크기」 · 빠른 설정 타일 | 재생성만이 새 배율을 확실히 그린다(`builder.setFontScale`). 직접 처리는 「옛 크기로 그려진 화면 + 새로 그리는 요소만 새 크기」가 될 수 있다(맥락 4 [추론]). 접근성 설정이라 즉시 반영이 낡은 화면보다 낫다 | 상태를 잃는다(변경 전과 같다) — 글꼴 크기를 바꾸면 앱이 처음 화면으로 돌아가고 새 크기로 그린다 |
| 그 밖(`mcc` · `mnc` · `touchscreen` · `colorMode` · `fontWeightAdjustment` · `grammaticalGender`) | SIM 교체 · 굵은 글꼴 설정 등 | 요구가 든 변경이 아니고 드물다. 값 집합을 닫아 둔다 | 그때 상태를 잃는다 |
| `resourcesUnused` | (선언하면) 모든 구성 변경 | **선언 금지.** 「이 Activity는 리소스를 쓰지 않는다」는 뜻이라 다른 플래그를 전부 덮는다 — `density` · `fontScale`의 재생성까지 막아 위 두 행이 깨진다 | — |

- 여러 값이 한꺼번에 바뀌고 그중 하나라도 선언에 없으면 시스템은 재생성한다. 그래서 `onConfigurationChanged`는 밀도 · 배율이 바뀐 구성을 받지 않는다.
- `density` · `fontScale`을 매니페스트에 선언하면 `mainActivityConfigIssues`가 `config-forbidden`으로 잡는다.
- **내비게이션 모드 전환 · 시스템 글꼴 오버레이는 이 표에 없다** — `assetsPaths`로 선언해 직접 처리한다(D2). 다만 **API 35 이하에서는 그 선언이 무시되어 재생성된다.**
  (경계 36은 추론이고 실측은 API 30이다 — 맥락 8.) 그 기기에서는 글꼴 · 밀도 변경과 같은 급의 알려진 재생성이고, 재생성 뒤 번들을 다시 읽어 정상 화면이 서고 탭 바가 새 모드의 자리에 선다(API 30: 알약 아래 끝 2175 → 2307 → 2175px).
  이 ADR의 첫 판은 이것을 「선언할 수 없어 API와 무관하게 재생성된다」고 적었다 — 틀렸다(「정정 기록」).

### D4. `MainActivity.onConfigurationChanged`는 두 가지만 한다

```java
@Override public void onConfigurationChanged(Configuration newConfig)
```

| 순서 | 책임 | 방법 | 왜 |
|---|---|---|---|
| 1 | 상위 호출과 가드 | `super` 뒤 `lynxView == null` · `isFinishing()` · `isDestroyed()`면 끝 | `onCreate` 전 · 파괴 중 호출 |
| 2 | **screen metrics를 Lynx에 다시 넘긴다** | `DisplayMetricsHolder.getRealScreenDisplayMetrics(this)`의 가로 · 세로 → `lynxView.updateScreenMetrics(w, h)` | Lynx가 처음 읽는 것과 같은 출처라 「재생성했을 때의 값」과 같다. 값이 같으면 Lynx가 버린다 |
| 3 | **safe area를 다시 계산하게 한다** | `ViewCompat.requestApplyInsets(lynxView)` | 기존 inset 리스너(`publishSafeAreaInsets`)가 다시 불린다. 같은 값이면 보내지 않는다 |

- **구성 값으로 분기하지 않는다.** 무엇이 바뀌었는지 가르지 않고 2 · 3을 늘 한다. 그래서 호스트 Java에 새 판정이 없다(판정은 D2의 Node 순수 함수 하나다).
- **하지 않는다**: `renderTemplateUrl` 재호출 · LynxView 재생성 · `setContentView` · `recreate()` · `setRequestedOrientation` · `updateFontScale` · `updateColorScheme` · `updateViewport` 직접 호출.
  viewport는 Lynx가 측정에서 스스로 갱신한다(맥락 4).
- 구성 변경 뒤의 상태: 같은 `MainActivity` 인스턴스 · 같은 LynxView · 같은 JS 컨텍스트. LynxView 크기 = 창 크기. Lynx의 screen metrics = 실제 디스플레이.
  globalProps `safeAreaInsets` · `tappableBottomInset` = 새 창의 inset.
- iOS가 같은 책임을 이미 진다 — 회전 · 크기 변화에서 번들을 다시 읽지 않고 `viewDidLayoutSubviews`가 safe area와 크기를 다시 넘긴다. 「재생성 없이 따라간다」는 쪽은 두 플랫폼이 같아진다.

### D5. 큰 화면(최소 너비 600dp 이상)에서는 최소 보장만 진다

세로 고정이 듣지 않아 가로가 된 창(API 36 이상의 큰 화면 — 맥락 6)과 분할 화면의 임의 크기 영역에서 지는 것은 다섯이다.

| | 보장 |
|---|---|
| G1 | **초기화되지 않는다** — 같은 Activity · LynxView · 화면 · 진행 상태 |
| G2 | **세로 모양 영역에서는 창을 채운다. 가로 모양 영역에서 세로 고정이 듣는 한 시스템이 레터박스를 둔다(빈 띠를 받아들인다) — 레터박스 안의 터치는 듣는다.** 고정이 무시되어 가로가 된 창에서는 창을 채운다 |
| G3 | **시스템 바에 가리지 않는다** — safe area가 새 창의 값으로 다시 간다 |
| G4 | **죽지 않는다** — 크래시 · ANR 없음, 뒤로가기 · 소리가 이어진다 |
| G5 | **세로로 돌아오면 원래 모습** |

**분할 화면에서 보장하는 것**은 이렇다: 재생성 없음 · 상태 유지 · 크래시 없음 · 전체 화면 복귀 뒤 원래 모습 · 세로 모양 영역에서는 창을 채움 · 가로 모양 영역에서는 시스템의 레터박스(빈 띠를 받아들인다) · 레터박스 안의 터치가 듣는다.

**분할 화면에서 보장하지 않는 것**: 낮은 창(가로 모양 영역)에서 세로 전제 화면의 아래가 잘려 **조작부에 닿지 못할 수 있다.** 아래 「보장하지 않는다」의 「큰 화면 가로에서 아래 잘림」과 같은 급이다 — 판정이 아니라 관찰로 적는다.
확인창이 상태바 쪽으로 가려지는 것도 같다.

- **관찰된 잘림**(API 37 에뮬레이터 1대 · 듣기 문항 하나 · 창 높이 823px ≈ 313dp): 카드 위쪽(y ≈ 660px)부터 아래가 창 밖이라 **답 버튼과 재생 버튼이 보이지 않아 그 문항을 풀 수 없다. 스크롤로도 닿지 않았다**
  (앱 노드에 `scrollable`이 없고 스와이프 두 가지에 화면이 변하지 않았다). 나가기 확인창의 제목이 상태바 쪽으로 일부 가려졌다. 세로 모양 영역(높이 1187)에서도 같은 문항의 답 버튼은 창 밖이었다 — 화면이 창 높이에 적응하지 않는다.
  상태는 잃지 않는다: 분할선을 끌어 올리거나 전체 화면으로 돌아오면 같은 문항이 이어진다.
- **이 잘림은 이 변경의 회귀가 아니다 — 기준선 대조로 확정했다.** 기준선 `47600f41`도 같은 높이(823)에서 같은 자리부터 잘리고 같은 요소가 보이지 않았다. 기준선이 더 보여 주는 것은 가로 폭(좌우 133px씩)뿐이고,
  기준선은 그 대신 분할 진입 · 이동 · 복귀마다 재생성되어 진행을 잃는다. 이 변경이 새로 만든 것은 레터박스이고 없앤 것은 그 재생성이다. (대조의 범위: API 37 에뮬레이터 1대 · 듣기 문항 하나 · 높이 823. 두 빌드가 같은 JS 번들을 썼다.)
- **레터박스는 U1의 귀결이다(U5).** 없애려면 `screenOrientation`을 풀어야 한다. 세로 고정이 만든 **보이는 변화**다(기준선에는 없었다 — 관찰).
- **후속 과제**(이 작업 범위 밖): 작은 창 · 가로 모양 창에의 적응 — 하단 조작부가 창 높이를 넘으면 스크롤되게 하는 등([ADR-0022](0022-scroll-regions-and-fixed-affordances.md)의 고정/흐름 분할과 닿는다). U1의 「가로 레이아웃 후속」과 한 묶음으로 연다.
- **분할 화면은 큰 화면의 가로를 대신 증명하지 못한다.** 고정이 풀리는 경로가 아니기 때문이다. 큰 화면 가로의 증거는 흉내(`wm set-ignore-orientation-request true`) 하나뿐이다.

**보장하지 않는다**: 가로에서의 보기 좋음. 세로 전제 화면은 iOS 가로와 같이 아래가 잘릴 수 있다. 열린 말풍선의 위치(여정 맵의 말풍선은 **열 때** 한 번 화면 높이를 잰다),
가로에서 옆에 서는 3버튼 바(ADR-0044의 범위 밖 그대로), 폴더블 힌지, 태블릿 전용 배치.

## 버린 대안

| 대안 | 버린 이유 |
|---|---|
| `screenOrientation`을 선언하지 않고 `configChanges`만 둔다(가로 허용 — iOS와 같다) | 세로 전제 화면이 가로에서 잘린다(맥락 2). **U1에서 사용자가 「iOS처럼」을 고르면 이 값이 된다** |
| `userPortrait` · `sensorPortrait` | 거꾸로 선 세로를 허용한다 — iOS iPhone 목록에도 없는 방향이고 얻는 것이 없다 |
| `nosensor` · `locked` | 실행 시점의 방향에 묶인다 — 가로로 들고 켜면 가로다 |
| `assetsPaths`를 선언하지 않고 재생성을 받아들인다(변경 전과 같은 동작) | API 36 이상에서 내비게이션 모드 · 시스템 글꼴을 바꿀 때마다 스플래시부터 다시 서고 진행을 잃는다. 선언은 매니페스트 한 값이고 `MainActivity`는 그대로이며, 실측에서 대가가 보이지 않았다. 계약 단계의 기본값이었다가 사용자 결정(U4)으로 직접 처리가 됐다 |
| `resourcesUnused`를 선언한다 | 다른 플래그를 전부 덮어 `density` · `fontScale`의 재생성까지 막는다 — D3이 깨진다 |
| `resizeableActivity="false"`(U6 — 작은 창 적응 전까지 휴대폰에서 분할 화면 진입 자체를 막는 수단) | 얻는 것은 휴대폰(API 35 이하 전부, API 36 이상의 최소 너비 600dp 미만)에서 「문항을 풀 수 없는 낮은 창」이 생기지 않는다는 것이다. 버린 이유는 넷이다: (1) 분할 화면을 쓰는 사용자에게서 기능을 뺀다 — 세로 모양 영역(관찰한 두 높이)에서는 창을 채우고 상태가 남는다. (2) API 36 이상 큰 화면에서는 무시된다(플랫폼 문서 기준 · 미증명) — 막히는 곳이 휴대폰뿐이다. (3) 잘림의 원인(화면이 낮은 창에 적응하지 않음)은 그대로 남는다 — 큰 화면 가로에서 같은 문제를 다시 만난다. (4) 잘려도 상태를 잃지 않고 경계를 끌어 올리거나 전체 화면으로 돌아오면 이어진다(관찰). 뒤집으려면 매니페스트 한 줄 + 검사 함수의 `resizeable` 규칙(지금은 값과 무관하게 금지)을 「`false`만 허용」으로 바꾸고 계약을 다시 고정한다 |
| 임시 opt-out `PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` | 큰 화면에서 세로 고정을 되살리지만 `targetSdk` 36에서만 듣고 다음 target에서 사라진다(U3) |
| `fontScale`을 직접 처리하고 `updateFontScale`을 부른다 | 상태는 남지만 화면이 새 크기로 다시 그려진다는 보장이 없다(맥락 4 [추론] — Android 실측 없음). 접근성 설정이 반쯤 반영된 화면은 재생성보다 나쁘다 |
| `density`를 직접 처리한다 | Lynx에 밀도를 바꿀 진입점이 없다 — 크기가 전부 틀린 화면이 남는다 |
| 구성 변경마다 `onSaveInstanceState`로 상태를 살리고 재생성은 둔다 | 범위 밖으로 뒀다. JS 컨텍스트 · 재생 중인 소리 · 인증 콜백은 번들로 옮길 수 없다 |
| `onConfigurationChanged`에서 바뀐 필드를 가려 필요한 것만 한다 | 두 호출 모두 값이 같으면 아무 일도 하지 않는다. 분기는 호스트에 판정을 하나 더 만들 뿐이다 |

## 대가

- **두 플랫폼의 휴대폰 방향 동작이 다르다**(D1 · U1). 알고 정한 차이이고, 가로 레이아웃 후속 작업이 끝날 때까지 남는다.
- **휴대폰에서 WCAG 2.1 AA SC 1.3.4(Orientation)를 충족하지 못한다**(D1의 「접근성」). 가로로 거치해 쓰는 사용자는 누운 화면을 쓴다. 가로 레이아웃 후속 작업이 끝날 때까지 남는 불충족이다.
- **글꼴 크기 · 디스플레이 크기를 바꾸면 여전히 앱이 처음 화면으로 돌아간다**(D3). **API 35 이하에서는 내비게이션 모드 · 시스템 글꼴 오버레이를 바꿀 때도 그렇다**(`assetsPaths` 선언이 무시된다). 글꼴 크기는 접근성 설정이라, 큰 글꼴이 필요한 사용자가 학습 도중 크기를 조정할 때 진행 상태를 잃고 TalkBack 포커스도 첫 요소로 돌아간다(U2). 변경 전과 같은 동작이고 SC 1.4.4(Resize Text)는 충족한다 — 위반이 아니라 사용성 대가다.
- **직접 처리한 값은 리소스를 다시 로드하지 않는다.** 지금은 다시 로드할 리소스가 없어 대가가 0이지만, 야간 리소스 · 방향별 리소스 · 다크 테마를 더하는 순간 화면이 낡는다.
  그 변경은 D2의 표를 먼저 고쳐야 한다(「재검토 조건」).
- **재생성이 가려 주던 낡은 값이 드러날 수 있다.** 구성 변경 뒤에만 틀리는 여백 · 크기는 이제 다음 재시작까지 남는다. 에뮬레이터에서 본 범위(다크 모드 · 크기 변경 · 큰 화면 가로)에서는 나오지 않았다.
- **분할 화면의 가로 모양 영역에서 좌우가 빈다**(D5 · U5). 1080x823 영역에서 좌우 133px씩이었다.
- **낮은 분할 창에서 아래 조작부에 닿지 못할 수 있다**(D5). 창 높이 823px에서 듣기 문항의 답 · 재생 버튼이 창 밖이었고 스크롤로도 닿지 않았다. 이 변경 전에도 같았지만(기준선 대조) 고쳐지지 않은 채 남는다 — 후속 과제다.
- **오버레이가 바뀌어도 Activity가 리소스를 다시 읽지 않는다**(D2의 `assetsPaths`). 지금은 읽는 리소스가 없어 잃는 것이 없지만, 호스트가 테마 · 치수 리소스를 읽기 시작하면 낡은 값이 남는다.
- **`assetsPaths`의 이득은 API 36 이상에만 있다.** 그 아래 기기는 선언 전과 같다.
- **큰 화면 가로는 잘린 채 나간다**(D5). 에뮬레이터의 큰 화면 흉내에서 가로일 때 「1 of 1 question completed」 알약이 하단 주 버튼에 가려지고 오른쪽 약 183px이 비어 보였다(관찰 — 원인은 가리지 않았다).
- **값 집합이 두 곳에 있다**(매니페스트와 `host-config-changes.mjs`). 한쪽만 고치면 `pnpm test:android-bundle`이 실패한다 — 의도한 대가다.
- **계측 `ConfigurationChangeTest`는 에뮬레이터 전역 설정을 바꾼다**(야간 · 크기 · 밀도 · 글꼴 배율 · 회전 · 내비게이션 모드 오버레이). 기존 계측 일괄에서 빼고 따로 돌려야 하고, 중간에 죽으면 설정이 남는다.

## 정정 기록

- **2026-10-06 — 「`CONFIG_ASSETS_PATHS`는 `configChanges`로 선언할 수 없다」는 틀렸다.** 첫 판(같은 날)의 D3과 재검토 조건은 내비게이션 모드 전환을 「매니페스트의 공개 값에 없어 선언할 수 없고 API와 무관하게 재생성된다」고 적었다.
  compileSdk 36부터 `assetsPaths`로 선언할 수 있다(맥락 8). 리뷰가 SDK의 속성 정의와 `aapt2 link`로 가렸고, 선언한 빌드에서 API 37의 재생성이 사라지는 것을 실측했다.
  틀린 근거에서 나온 「재생성 수용」을 사용자 결정(U4)으로 「직접 처리」로 바꿨다 — D2가 10값에서 11값이 됐고 D3의 그 행을 지웠다. 「API와 무관하게」도 틀렸다: 재생성은 API 35 이하의 이야기다.
- **2026-10-06 — 「분할 화면 · 자유 창에서는 방향 고정이 창에 적용되지 않는다」는 틀렸다.** 첫 판의 맥락 6 · D1 「고정이 풀리는 곳」 · D5가 그렇게 적었다.
  API 37 에뮬레이터의 분할 화면에서 고정이 **유지됐고** 가로 모양 영역에 레터박스가 섰다(맥락 7). D5의 G2 「창을 채운다」를 조건부로 고쳤다. 자유 창은 재지 않았다 — 어느 쪽으로도 적지 않는다.
- **2026-10-06 — D5의 G2에 있던 「그때 내용과 조작부는 전부 보이고 조작되며」와 「대가」의 「내용은 잘리지 않는다」는 관찰 없이 쓴 문면이었다 — 뺐다.** 계약 r03의 문면을 근거 없이 옮긴 것과 이 문서가 덧붙인 것이다.
  실제로 돌려 보니 낮은 분할 창(높이 823)에서 답 · 재생 버튼이 잘려 닿지 못했다. 계약 r04가 보장을 「레터박스 안의 터치가 듣는다」까지로 줄이고 잘림을 「보장하지 않는 것」으로 옮겼다.
  같은 자리의 「이 변경 전에는 레터박스가 없었다는 것은 추론」도 고쳤다 — 기준선 대조로 관찰이 됐다.
- **2026-10-06 — D1의 「사용자 확인 전 기본값」이 확정됐다.** 사실 오류가 아니라 상태의 변화다(U1).

## 재검토 조건

- **가로 레이아웃 · 작은 창 적응 후속 작업이 열리면** → D1 · D5의 레터박스(U1 · U5). 작업이 끝나면 `screenOrientation`을 지워 SC 1.3.4 불충족과 분할 화면의 레터박스를 함께 푼다. 판정 함수 · IC4 · O1 · O6의 기준을 같이 바꾼다. 낮은 창에서 조작부에 닿게 되면 D5의 「보장하지 않는 것」을 보장으로 옮긴다.
- **다크 테마 · 야간 리소스(`values-night` 등) · 방향별 · 크기별 리소스를 더하면** → D2의 `uiMode` · `orientation` · `screenSize` 행. 직접 처리를 유지하려면 D4에 전달(`updateColorScheme` 등)을 더한다.
- **태블릿 배치가 요구되거나, 큰 화면에서 플랫폼이 방향 고정을 실제로 어떻게 다루는지가 큰 화면 AVD · 실기에서 관측되면** → 맥락 6 · D5.
- **Lynx 버전을 올리면** → 맥락 4를 새 AAR에서 다시 본다(구성 변경 수신 · 밀도 변경 진입점 · `updateFontScale`의 다시 그림). 밀도나 배율을 따라갈 수 있게 되면 D3.
- **`targetSdk`가 37 이상이 되면** → 맥락 6과 D5. 큰 화면의 방향 · 크기 제한 규칙을 다시 대조한다([ADR-0046](0046-android-play-release.md)의 재검토 조건과 같은 사건이다).
- **Android에서 `updateFontScale`이 화면을 다시 그리는 것이 실측되면** → D3의 `fontScale`(U2).
- **호스트가 테마 · 치수 · 문자열 리소스를 Activity에서 읽기 시작하면** → D2의 `assetsPaths`(그리고 `uiMode` · `locale`). 직접 처리한 변경 뒤에 낡은 리소스가 남는다.
- **API 31 ~ 35나 실기에서 내비게이션 모드 · 글꼴 · 배경화면 색 변경 뒤의 동작이 관측되면** → D2의 `assetsPaths` 문면(어느 API부터 듣는가).
- **선언하지 않은 값(`mcc` · `fontWeightAdjustment` 등)으로, 또는 API 35 이하에서 오버레이 전환으로 진행 상태를 잃는다는 보고가 나오면** → D3. 선언해서 듣는 값은 D2로 옮기고, 그렇지 않은 것은 상태 복원(`onSaveInstanceState`)을 다시 본다.
- **실기 · 태블릿 · 미확인 API에서 재생성 · 낡은 여백 · 크래시가 나오면** → D2 · D4. 구현을 덧대기 전에 이 ADR로 돌아온다.
