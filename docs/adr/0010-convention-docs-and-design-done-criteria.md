# ADR-0010 — 규약 문서와 설계 완료 조건

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: 규약 문서, 설계 완료 조건

## 맥락

이 저장소에서 규약 문서는 보통보다 무겁게 작동한다. 이유 둘:

1. **구현 상당 부분을 에이전트가 만든다.** 규약을 매번 프롬프트로 넘겨야 하고,
   경로가 예측 가능하지 않으면 넘길 때마다 찾아야 한다.
2. **CI와 브랜치 보호가 없다**(ADR-0009). 강제 수단이 없으므로 규약이 실제로 문서
   하나에 걸려 있다.

즉 문서가 약한 장치라는 것을 알면서도, **지금 가진 유일한 장치**다. 그렇다면 최소한
찾기 쉽고 짧아야 한다.

## 결정

### D1. 규약은 `docs/conventions/` 아래 주제별 파일로 둔다

```text
README.md                      목차. 여기서 아래로 간다
docs/
  screens.md                   화면 목록과 그 사이의 의존성 (ADR-0010 D6의 입력)
  conventions/
    code.md                    네이밍 · 폴더 · import 규칙 (ADR-0003, ADR-0004에서 나옴)
    workflow.md                브랜치 · 커밋 · PR · 머지 방식 · verify 절차 (ADR-0006, ADR-0009에서 나옴)
  e2e/                         수동으로 통과시킬 흐름. 파일 하나 = 흐름 하나 (ADR-0006 D6)
    README.md                  형식·갱신 규칙·공통 전제. 목록은 두지 않는다
  adr/                         결정 기록. 왜 그렇게 정했는지
```

**네 종류이고, 각각 다른 질문에 답한다.** 하나가 두 질문에 답하기 시작하면 그때부터
어느 쪽도 제대로 답하지 못한다.

| 어디 | 답하는 질문 | 섞이면 생기는 일 |
|---|---|---|
| `screens.md` | **무엇이** 있는가 | — |
| `conventions/` | 무엇을 **해야 하는가** | 근거를 늘어놓으면 길어져서 안 읽힌다 |
| `e2e/` | 되었는지 **어떻게 아는가** | — |
| `adr/` | **왜** 그렇게 정했는가 | 실행 지침만 있으면 나중에 바꿀 근거가 없다 |

특히 `screens.md`와 `adr/`을 가르는 이유가 분명하다. **화면 목록을 ADR에 넣으면 화면이
바뀔 때마다 결정 기록을 고치게 된다.** 결정은 느리게 변하고 화면은 빠르게 변한다.
같은 파일에 두면 빠른 쪽이 느린 쪽의 이력을 더럽힌다.

`screens.md`와 `conventions/`도 마찬가지다. 화면 목록은 지켜야 할 규약이 아니라 만들
대상이다. 규약을 어기면 잘못이지만, 화면 목록과 코드가 다르면 **둘 중 어느 쪽이 옳은지
그때그때 다르다.**

규약 문서는 각 항목 옆에 해당 ADR을 링크한다. 규약을 지키기 싫어진 사람이 근거를
바로 찾을 수 있어야 한다.

### D2. 문서 본문은 한국어, **파일명은 영문 kebab-case**

경로가 도구·URL·에이전트 프롬프트를 오간다. ADR 파일명도 같은 규칙을 따른다
(`docs/adr/README.md`의 형식 절).

### D3. `README.md`는 목차와 첫 실행만 담는다

- 이 저장소가 무엇인가 (한 문단)
- 첫 실행: corepack 활성화 → `pnpm install` → `pnpm dev` → Explorer 연결
- `docs/conventions/`와 `docs/adr/`로 가는 링크

README에 규약을 인라인하지 않는다. 인라인하면 규약이 두 곳에 생기고 갈라진다.

corepack 활성화를 첫 실행 단계에 넣는 것은 ADR-0005 D3의 대가를 완화하기 위한 것이다 —
corepack이 꺼져 있으면 `packageManager` 고정이 작동하지 않는다.

### D4. 규약을 바꾸는 변경은 **같은 PR에서** 문서를 고친다

문서와 코드가 갈라지는 것을 막는 유일한 수단이다. 강제할 도구가 없으므로
(ADR-0009 D6) 이것도 약속이다. `workflow.md`에 적는다.

### D5. 미결정 항목은 `docs/adr/README.md`의 **보류 표**에 모은다

ADR 본문에만 적어두지 않는다. 본문에 흩어두면 그 ADR을 다시 열 일이 없어서 영영
안 본다. **한 표에 모여 있으면 훑을 수 있다.**

보류 표의 각 행은 넷을 갖는다: **축 · 왜 못 정하나 · 막고 있는 것 · 푸는 시점.**
"막고 있는 것"이 비어 있으면 그건 보류가 아니라 **누락**이다.

같은 이유로 `docs/adr/README.md`에 **실체화 전 확인 목록**을 따로 둔다. 이 저장소에는
"ReactLynx에서 이것이 되는가"류의 **가정**이 여럿 있고, 가정과 결정을 섞어두면
검증되지 않은 것이 결정처럼 읽힌다.

### D6. 후속 구현 이슈의 입력 산출물

구현 이슈는 아래 넷을 입력으로 받는다. **없는 것을 추측으로 채우지 않는다.**

| 입력 | 상태 |
|---|---|
| 이 ADR 묶음 (`docs/adr/`) | 있음 |
| 화면 목록 | 있음 — **저장소 안이다.** `docs/screens.md` |
| 와이어프레임 | 있음 (확정) — 저장소 밖 |
| API 명세 | **없음** — 도착 전까지 화면의 데이터 계약을 확정하지 않는다 |

API 명세가 없는 동안 화면을 만들 수는 있다. 다만 데이터 형태를 **가정으로 굳히지
않는다** — ADR-0007 D2가 API 클라이언트를 한 파일로 모아둔 이유가 이것이다. 명세가
도착하면 교체 지점이 한 곳이다.

### D7. 저장소 골격을 실체화하기 전 체크리스트

저장소 골격을 만들기 시작하기 전에 확인한다.

1. `docs/adr/README.md` **축 추적표**의 모든 축이 결정 또는 보류로 처리됐는가
2. **보류 표**의 모든 행에 "막고 있는 것"이 있는가 (D5)
3. 결정끼리 모순이 없는가 — 특히 아래 넷
   - 상태 관리 ↔ 데이터 페칭 (ADR-0007 D1·D2: 도입 조건이 서로를 참조하는가)
   - 명령 인터페이스 ↔ 테스트 계층 (ADR-0006 D1·D4: `test`가 도는 계층만 선언됐는가)
   - package 경계 ↔ 의존 방향 (ADR-0004 D2·D4: 생성 조건과 방향 규칙이 같은 전제인가)
   - 문서 파일명 규칙 ↔ ADR 파일명 (D2: 둘 다 영문 kebab-case인가)
4. 첫 단계 **제외 범위**가 ADR-0001 D3에 명시돼 있는가
5. **성공 확인 기준**(ADR-0001 D4)이 재현 가능한 명령으로 적혀 있는가
6. **실체화 전 확인 목록**(`docs/adr/README.md`)의 가정을 실체화 중에 확인하고,
   어긋나면 해당 ADR을 **D10에 따라** 갱신할 준비가 됐는가 — 사실만 틀렸으면 제자리,
   그 위에 이미 무언가가 지어졌으면 새 번호

### D8. 설계 단계 완료 조건

위 체크리스트 6개가 전부 만족되면 설계가 끝난 것이다.
**"모든 것이 정해졌을 때"가 아니라 "정하지 못한 것이 전부 기록됐을 때"가 완료다.**

이 구분이 중요하다. 1주짜리 프로토타입에서 모든 것을 정하는 것은 불가능하고, 그것을
완료 조건으로 잡으면 설계가 끝나지 않는다. 기록된 미결정은 관리 가능하지만,
기록되지 않은 미결정은 구현 중에 **에이전트가 조용히 채운다.**

### D9. 문서는 `[Frontend]` 이슈 외의 이슈를 링크·언급하지 않는다

성격상 D1~D4와 같은 문서 규약이다. 번호만 뒤에 붙었다.

이 저장소의 문서(ADR · `docs/conventions/` · `README.md`)는 **`[Frontend]`로 만든
이슈만** 참조한다. 기획·디자인·백엔드 이슈는 재구성되거나 범위가 바뀔 수 있고, 그러면
문서에 남은 참조가 가리키던 것을 잃는다. 낡은 참조는 없는 것보다 나쁘다 — 읽는 사람이
그것을 근거로 믿기 때문이다.

**대신 사실을 적는다.**

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| 화면 목록(LIB-81)이 확정이다 | 화면 목록이 확정이다 |
| API 명세(LIB-85)가 아직 없다 | API 명세가 아직 없다 |
| QC 루프 10회(LIB-91)가 예정돼 있다 | QC 루프 반복이 예정돼 있다 |

근거는 그대로 남고 참조만 사라진다. 이슈가 바뀌어도 문서는 계속 읽힌다.

`[Frontend]` 이슈를 예외로 두는 이유: 그것은 이 저장소의 작업 단위와 대응하므로, 바뀌면
저장소 쪽도 같이 바뀐다. 참조가 **조용히** 낡지 않는다.

이 규칙은 이 ADR 묶음 전체에 소급 적용됐다. 그래서 본문에 이슈 번호가 하나도 없다.

### D10. ADR을 고치는 방식 — 새 번호는 **추적할 것이 있을 때만**

성격상 D1~D4·D9와 같은 문서 규약이다.

| 무엇이 바뀌었나 | 어떻게 | 왜 |
|---|---|---|
| **결정** — 이미 무언가가 그 위에 지어진 뒤 | 새 번호를 붙이고 옛 것을 `대체됨`으로 | 옛 결정으로 짜인 코드나 파일이 남아 있다. 어느 시점에 무엇이 옳았는지 추적할 수 있어야 한다 |
| **결정** — 아직 실체화되지 않은 것 | 제자리에서 고치고 `정정 기록`을 남긴다 | 추적할 대상이 없다. 설계 단계에서 결정을 고칠 때마다 번호가 늘면 **추적 가치는 없이 기록만 불어난다** |
| **결정이 딛고 선 사실** | 제자리에서 고치고 `정정 기록` 절을 남긴다 | 결정이 같은데 번호가 갈라지면 다른 ADR의 참조가 흩어지고, 폐기된 근거가 `대체됨` 문서에 남아 계속 읽힌다 |
| **결정 여러 개가 한 번에** — 실체화 여부와 무관 | 새 번호로 **묶는다** | 제자리로 흩으면 *왜* 한꺼번에 바뀌었는지가 사라진다. 대개 바깥에서 새 사실이 들어온 경우다 |
| **없던 축을 처음 정한다** | 아래 판별 기준 | 바뀐 것이 없으므로 위 세 줄이 답을 주지 않는다 |

**"실체화됐는가"의 기준은 파일이다.** 그 결정대로 만들어진 코드·설정·문서가 저장소에
있으면 실체화된 것이다. 결정만 문서에 있고 아무것도 만들어지지 않았으면 아니다.

**없던 축을 처음 정할 때의 판별 기준: 기존 ADR의 `다루는 축` 줄이 그것을 덮는가.**

| | 어떻게 | 예 |
|---|---|---|
| **덮는다** | 그 ADR에 D-번호를 더한다. 축 추적표에 행을 더해 표에서도 보이게 한다 | 린터·포매터 **도구**는 명령 인터페이스 축이다 → ADR-0006 D1 |
| **안 덮는다** | 새 번호. 인접한 ADR에는 *"이 축은 NNNN이 맡는다"* 한 줄만 남긴다 | npm 의존의 버전 표기는 런타임·패키지매니저 축이 아니다 → ADR-0013 |

실체화 여부와 무관하다. 덮이지 않는 축을 억지로 밀어 넣으면 그 ADR의 제목과
`다루는 축` 줄이 거짓이 되고, 축 추적표의 두 행이 같은 번호를 가리키게 된다.

**결정은 맞는데 실체화가 그것을 만족하지 않는 경우는 ADR을 고치는 일이 아니다.**
파일을 고친다. 다만 **결정 문구가 그 어긋남을 허용했다면 그건 ADR의 결함**이므로,
문구를 조이고 `정정 기록`을 남긴다. 실제로 한 번 일어났다 — ADR-0005 D3의 `.nvmrc`
칸이 *"정확한 버전(`22.x.y`, 22.12 이상)"* 이라 **하한을 그대로 적은 값이 규칙을 어기지
않고 통과했다.** 하한과 확정값을 한 칸에 적으면 하한이 확정값으로 굳는다.

네 번째 줄이 있는 이유: ADR-0011과 ADR-0012는 아무것도 실체화되지 않은 상태에서 새
번호를 받았다. 둘 다 **바깥에서 들어온 사실**(design-system 저장소의 존재, 화면 목록의
로그인)이 여러 결정을 한꺼번에 무너뜨린 경우다. 그 이야기를 한 문서에 담는 편이,
0008과 0002를 제자리에서 조각조각 고치는 것보다 읽힌다.

`정정 기록`에는 **무엇이 틀렸는지보다 어떻게 틀렸는지**를 쓴다. 한 번 틀린 방식은
대개 다른 문서에서도 같은 모양으로 틀려 있기 때문이다. ADR-0007의 정정 기록이
이 형태의 첫 예다.

## 버린 대안

- **`CLAUDE.md` 하나에 전부** — 에이전트가 자동으로 읽는 이점이 있지만, 사람용 규약과
  에이전트 지시가 섞이고 길어지면 무엇이 최신인지 안 보인다. 규약과 근거도 섞인다.
- **문서 없이 코드로만** — 에이전트가 규약을 코드에서 추론하게 되고, 추론은 매번 다르다.
  코드가 적은 초기에는 추론할 근거조차 없다.
- **위키 / Notion** — 검색은 편하지만 저장소와 버전이 함께 움직이지 않는다. 코드는
  바뀌었는데 문서는 옛 브랜치 기준으로 남는다.
- **규약을 ADR에만 두기** — ADR은 길다. 매번 실행 지침을 찾으려고 근거를 읽게 된다.
- **미결정을 각 ADR 본문에만 기록** — 흩어지면 훑을 수 없어 다시 보지 않는다 (D5).
- **완료 조건을 "모든 축 결정"으로** — 도달할 수 없어서 설계가 끝나지 않는다 (D8).

## 대가

- **문서가 코드와 갈라질 수 있다.** D4로 완화하지만 D4 자체가 강제되지 않는 약속이다
  (ADR-0009 D6). 이것이 이 ADR의 가장 큰 약점이고, 완화 수단이 없다.
- **문서를 만들고 유지하는 시간이 1주 일정에서 나온다.** 그래서 규약 문서를 둘로 제한했다.
  셋째 문서를 만들고 싶어지면 먼저 기존 둘에 들어갈 수 없는지 본다.
- **보류 표가 한곳에 모여 있어도 아무도 안 볼 수 있다.** 표는 열람을 쉽게 할 뿐
  강제하지 않는다. 완화: 체크리스트(D7)가 실체화 시작 시점에 이 표를 읽게 만든다.
- API 명세를 기다리는 동안(D6) 화면의 데이터 계약이 열린 채 남아, 명세 도착 시
  화면 수정이 발생한다.

## 재검토 조건

- 규약 문서가 셋을 넘어가는 시점 → D1의 분류 방식
- `docs/screens.md` 하나로 화면 목록이 안 읽히는 시점 → 탭별로 쪼갠다. `e2e/`가 흐름
  하나에 파일 하나인 것과 같은 이유다
- 두 번째 사람이 저장소에 합류하는 시점 → D4의 강제 수단 (CI, ADR-0009 D3와 함께)
- API 명세 도착 → D6

## 정정 기록

**2026-08-31 — D1이 딛고 선 사실을 정정. D6도 함께.** 결정은 바뀌지 않았다.

D1의 트리에 `docs/screens.md`의 자리가 없었다. 화면 목록은 규약도 흐름도 결정 기록도
아니라서 셋 중 어디에도 안 들어간다. 네 번째 종류를 인정하고, 네 종류가 각각 어떤
질문에 답하는지를 표로 갈랐다. 하는 김에 `e2e/`의 역할도 문장으로 적었다 — 이름만
있고 무엇에 답하는 문서인지가 없었다.

D6도 고쳤다. 화면 목록을 `있음 (확정)`이라고만 적어 **어디에 있는지가 없었다.**

**어떻게 틀렸나** — **그때 있던 문서를 나열해 놓고, 그것이 문서 종류의 전부인 것처럼
굳었다.** 트리는 "지금 이 저장소에 있는 것"의 목록으로 그려졌는데 "문서는 이런 종류가
있다"로 읽혔다. 나열은 완결을 주장하지 않는데 트리 모양은 완결처럼 보인다.

D6의 `있음 (확정)`이 같은 실수의 다른 얼굴이다. 있다는 것만 적고 어디 있는지를 안
적었으니, **저장소 밖에 있다는 가정이 적히지 않은 채로 굳었다.** 실제로 그 가정 위에서
D1의 트리가 그려졌다 — 밖에 있는 것에 자리를 만들 이유가 없으니까.

같은 방식으로 틀렸을 곳을 훑었다. **ADR-0003**이 *"폴더를 열어 화면 목록과 대조할 수
있다"* 고 적으면서 그 목록이 어디인지를 안 적었다 — 한 줄 가리키게 고쳤다. **ADR-0001**과
**ADR-0002**의 화면 목록 언급은 존재 여부만 근거로 쓰고 위치에 기대지 않아 그대로 둔다.

**목록을 적을 때 그것이 닫힌 집합인지 지금 가진 것인지를 밝힌다.** 트리와 표는 특히
닫힌 집합처럼 읽힌다.
