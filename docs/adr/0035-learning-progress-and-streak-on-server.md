# ADR-0035 — 학습 진행 · 연속 학습 · 트로피를 서버에 둔다

- 상태: **제안** — 저장 위치 · 연속의 하루 · 트로피의 뜻은 사용자 결정이다(2026-09-30). 운영 DB에 표를 적용하기 전이다.
- 날짜: 2026-09-30
- 다루는 축: **학습 진행의 영속**(첫 서버 저장) · **상단 지표 칩 둘의 값**
- 부분 대체: [ADR-0007](0007-app-internals-state-routing-data-errors.md) D1의 「진행은 **영속하지 않는다** — 앱을 다시 켜면 처음으로」.
  세션 옵션 · 남은 알림 · 젬은 그대로 영속하지 않는다.
- 적용 기록(결정을 바꾸지 않는다): [ADR-0032](0032-account-sign-out-and-deletion.md) — 계정을 지우면 두 표도 CASCADE로 지워진다.

## 맥락

- 상단 칩 둘(불꽃 = 연속 학습, 트로피 = 끝낸 에피소드 수)은 화면 · 모달만 있고 값이 `0`으로 박혀 있었다(다섯 자리).
- 진행 자체가 영속하지 않아 앱을 다시 켜면 맵이 처음으로 돌아갔다 — 연속 학습도 트로피도 저장 없이는 뜻이 없다.

## 사용자 결정 (2026-09-30, 다시 묻지 않는다)

| # | 물음 | 결정 |
|---|---|---|
| U1 | 어디에 두나 | **서버(Supabase)** — 기기를 바꿔도 이어지고, 계정 삭제 때 함께 지워진다 |
| U2 | 연속의 「하루」 | **활동 하나를 끝낸 날**(스텝 · 표지 · 특별 유닛 · 최종 테스트), 기기 시간대의 날짜 |
| U3 | 트로피 | **끝낸 에피소드 수** — 모달 문구(`N episodes cleared`) 그대로 |

## 결정

### D1. 표 둘 · RPC 넷, 앱은 표에 닿지 않는다

마이그레이션 `apps/supabase-functions/supabase/migrations/20260930150000_learning_progress.sql`.

- `learning_progress(user_id PK → auth.users CASCADE, progress jsonb ≤ 16KB, updated_at)` — 앱의 진행 스냅숏 하나.
- `learning_days(user_id, day date, PK 둘)` — 활동을 끝낸 날.
- RLS를 켜고 정책 없이, 앱 역할의 표 권한도 걷는다(`push_devices`와 같은 방식, ADR-0034 D1). RPC는 `auth.uid()` 기준
  `security definer`: `load_learning_progress()` · `save_learning_progress(p_progress)` · `record_learning_day(p_day)` ·
  `learning_streak(p_today)`.
- `record_learning_day`는 기기 날짜가 서버 UTC 날짜와 **하루 넘게 다르면 적지 않는다** — 시간대 차이는 받고, 날짜를 바꿔
  연속을 부풀리지 못하게 한다.
- `learning_streak`: 오늘을 했으면 오늘까지, 안 했으면 **어제까지**의 연속(오늘 하면 이어진다). 둘 다 없으면 0.

### D2. 스냅숏은 버전을 싣고, 앱이 읽을 때 검증한다

- `LearningProgressSnapshotV1`(`lib/learning-progress.contract.ts`) — 스텝 수 · 표지 · 메신저 · 전화 · 비주얼 노벨 · 최종 테스트.
- 읽을 때(`app/learning-progress.ts`) **이 앱에 있는 유닛 ID만** 남긴다(유닛 타입의 모든 값을 키로 가진 표 — 유닛이 늘면
  컴파일이 선다). 버전이 다르거나 모양이 틀리면 버리고 지금 진행을 둔다.

### D3. 불러오면 **합친다**, 불러오지 못했으면 **저장하지 않는다**

- 로그인 직후(부팅의 세션 갱신 · 새 로그인 모두 `storeSession` 한 자리) 서버 진행을 받아 지금 진행과 합친다 — 완료 목록은
  합집합, 스텝 수는 큰 쪽, 비주얼 노벨은 더 나아간 쪽. 오프라인에서 진행했거나 다른 기기에서 진행했어도 잃지 않는다.
- 진행이 바뀔 때마다 사용자 ID별 미전송 스냅숏을 네이티브 저장소(`libitum.progress.pending.<userId>`)에 먼저 적고 서버로 보낸다.
  서버의 성공 응답 또는 불러온 서버 진행에 포함된 것을 확인한 뒤에만 지운다. 저장 중 추가된 진행은 앞선 응답으로 지우지 않는다.
- 한 세션의 저장 요청을 순서대로 보내며, 실패하면 서버를 다시 불러와 합친 뒤 재전송한다. 재시도 간격은 1·5·15·30·60초,
  이후 최대 60초다. 성공하면 재시도 타이머가 없고, 로그아웃·계정 전환·언마운트 후에는 이전 작업이 상태나 저장소를 바꾸지 않는다.
- 로그인 직후 같은 사용자의 미전송 진행을 즉시 복구한다. 로그아웃은 보관하고 계정 삭제 성공은 해당 사용자 기록만 지운다.
  다른 사용자의 진행은 합치지 않는다. 이 기록은 서버 응답 캐시가 아니며, 서버에 확인된 진행은 계속 서버에서 불러온다.
- **불러오기가 한 번도 성공하지 않았으면 저장하지 않고 다시 불러온다** — 실패를 「빈 진행」으로 읽어 서버를 덮어쓰지 않는다.
  「저장된 적 없음」(`null`)과 「요청 실패·깨진 JSON·지원하지 않는 스냅숏」을 가른다. 빈 서버 응답으로 복구돼도 미전송 기록이 있으면 즉시 저장한다.
- 액세스 토큰이 만료에 가까우면 먼저 갱신해 저장한다(`currentAccessToken`).
- 모두 기다리지 않고 실패를 삼킨다 — 진행 저장은 학습을 막지 않는다.

### D4. 칩 둘의 값

- 연속: 부팅 · 로그인 뒤 미전송 날짜를 먼저 복구하고, 대기열이 없으면 `learning_streak(오늘)`을 읽는다. 활동 완료 날짜 저장은 D6을 따른다.
- 트로피: **진행에서 파생**한다 — 항목을 모두 끝낸 에피소드 수(유닛이 아직 없는 에피소드는 세지 않는다). 따로 저장하지 않는다.
- 상태는 `app/use-journey-progress.ts` 한 훅이 들고(`AppSession`에서 옮김), 화면 결선이 칩을 그리는 다섯 자리에 내린다.

### D5. 서버 저장도 원자적으로 합친다

- 후속 마이그레이션 `20260930190000_merge_learning_progress.sql`은 기존 `save_learning_progress(jsonb) → void` 계약을 유지하며 구현을 교체한다.
- `INSERT ... ON CONFLICT DO UPDATE` 안에서 잠근 최신 행과 입력을 합친다. 별도 SELECT로 읽은 오래된 값에 기대지 않는다.
  완료 목록은 중복 없는 합집합, 완료 스텝 수·활성 장면은 최댓값, 비주얼 노벨 완료는 유지한다. 최초 저장이 겹쳐도 같은 규칙이다.
- v1 필드와 JSON 타입을 검증한다. 완료 목록의 유닛 ID는 현재 앱의 ID로 제한하지 않아 구버전 앱이 모르는 완료도 보존한다.
  잘못된 입력이나 기존의 지원하지 않는 스냅숏 버전은 오류로 중단하고 기존 행을 보존한다. 버전 변경 시 서버 합치기도 함께 갱신한다.
- 입력과 최종 저장 결과는 기존 16 KiB 상한을 따른다. 합친 결과가 상한을 넘으면 저장 전체를 롤백한다.
- 내부 합치기 함수는 클라이언트 실행 권한이 없다. 저장 RPC는 계속 `auth.uid()`의 행만 다루고 RLS·계정 삭제 CASCADE를 유지한다.
- 새 마이그레이션은 운영 DB에 별도로 적용해야 한다. 코드 병합이나 iOS 앱 빌드만으로 운영 RPC가 바뀌지는 않는다.

### D6. 오프라인 학습 날짜를 계정별로 재전송한다 (2026-10-01)

- `libitum.learning-days.pending.<userId>`에 완료한 원래 기기 날짜를 중복 없이 보관한다. 서버 성공 응답을 받은 날짜만 제거하며 진행 스냅숏 대기열과 별도로 관리한다.
- `20261001010000_replay_learning_days.sql`의 새 RPC `record_learning_days(p_days date[], p_today date)`는 최대 64일씩 멱등 저장하고 **현재 날짜 기준** 연속을 반환한다. 오래된 날짜를 재전송했다고 과거 연속을 오늘의 연속으로 표시하거나 축하하지 않는다.
- 기존 단일 날짜 RPC의 ±1일 제한은 그대로 유지한다. 새 RPC는 가입 UTC 날짜 −1일부터 서버 UTC 오늘 +1일까지 허용한다. `p_today`는 UTC 오늘 ±1일이어야 한다. null·무한 날짜·잘못된 배치는 전체 거절한다. 가입 이전 기록을 막지만 클라이언트 날짜의 진실성을 증명하지는 못한다.
- 통신 실패는 1·5·15·30·60초 간격으로 재시도한다. 앱 재실행/재로그인 시 계정별 대기열을 복구하며 로그아웃 뒤 늦은 응답은 UI와 저장소에 반영하지 않는다. 다른 계정으로 보내지 않는다.
- 로그아웃은 미전송 날짜를 보존하고, 계정 삭제 성공은 해당 계정의 날짜 대기열도 지운다. 날짜 전송 중 추가된 새 날짜는 이전 응답으로 삭제하지 않는다.
- **배포 순서: 새 SQL을 운영 DB에 먼저 적용한 뒤 앱 배포.** RPC가 없는 서버의 404는 성공으로 취급하지 않아 날짜를 보존한다. 사용자가 완료했다고 알린 기존 운영 DB 적용에는 이 후속 SQL이 포함되지 않는다.

## 버린 대안

- **기기 안 저장소만 사용** — 기기를 바꾸면 진행을 잃는다(U1). 서버가 정본이며 기기에는 사용자별 미전송 기록만 둔다.
- **서버가 진행을 정본으로 들고 앱이 매번 기다리기** — 부팅 · 모든 완료가 네트워크를 기다린다. 합치기로 충분하다.
- **활동 하나하나를 행으로** — 지금 필요한 것은 「끝낸 것」과 「그날 했는가」뿐이다. 분석은 PostHog가 진다.
- **트로피를 표로** — 진행에서 파생되는 값을 둘로 두면 어긋날 자리가 생긴다(ADR-0007 D3).

## 대가

- 개인정보 처리방침이 「진행은 기기에만 있다」를 더는 말할 수 없다 — **학습 진행 · 학습한 날짜가 서버에 저장된다**를 적어야 한다.
- 이 RPC는 진행을 앞으로만 합친다. 학습 진행 초기화나 콘텐츠 리셋은 별도 명시적인 계약이 필요하다. 현재 앱에는 진행 초기화 기능이 없다.
- 진행과 날짜의 미전송 기록은 앱 삭제 시 사라진다. 서버 확인 전까지 앱을 삭제하지 않은 경우 재실행과 오프라인 복귀에 걸쳐 보존한다.
- 다시 돌아오기 알림(ADR-0034)은 여전히 「앱을 연 날」 기준이다 — `learning_days`로 바꾸는 것은 후속.

## 재검토 조건

- 스냅숏 모양이 바뀌면 `version`을 올리고 이전 버전을 읽는 길을 둔다.
- 스냅숏에 감소 가능한 값이나 새로운 진행 필드가 생기면 클라이언트·서버의 합치기 규칙을 함께 검토한다.
