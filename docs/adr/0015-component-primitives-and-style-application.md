# ADR-0015 — 컴포넌트 프리미티브와 스타일 적용 지점

- 상태: 채택
- 날짜: 2026-09-02
- 다루는 축: 컴포넌트 프리미티브
- 이어받음: **ADR-0011 D3** (위치·승격 시점), **ADR-0008 D4** (승격 규칙)

## 맥락

**이 축은 지금 대체 없이 비어 있다.** ADR-0008 D5가 *"`<view>`·`<text>`·`<image>`를 직접
쓰지 않고 래퍼를 통해 쓴다"* 를 정했는데, ADR-0011이 0008을 통째로 대체하면서 **그 결정만
후속 없이 사라졌다.** 남은 것은 위치와 승격 시점(ADR-0011 D3)뿐이고, 그마저 `대체됨`
표시가 붙은 문서 안에 있어 **축 추적표까지 가야 "이 D3만은 유효하다"를 알 수 있다.**

D5가 지려던 것은 추상화가 아니라 **토큰 적용 지점을 한 곳으로 모으는 것**이었다.
그 목적을 지금 무엇이 지는지가 어디에도 없고, **공백이 낸 결과가 이미 하나 나왔다** —
`apps/mobile/src/app/error-boundary.css`가 `--libitum-*`이 아닌 다른 이름 계열
(`--color-bg-surface`·`--spacing-16`)을 쓰는 채로 남았고 아무도 못 봤다
(ADR-0014 `정정 기록` 2026-09-02).

**전제가 둘 바뀌었다.** D5를 그대로 되살릴 수 없는 이유다.

1. **토큰의 단일 출처가 저장소 밖으로 나갔다.** D5는 `src/styles/tokens.css` 하나를 이
   저장소가 소유한다는 전제(ADR-0008 D1) 위에 있었다. 지금 값은
   `@libitums/design-tokens`가 소유한다 — *"한 곳만 고치면 전체가 바뀐다"* 를 래퍼가
   아니라 **패키지가 진다.**
2. **컴포넌트 스펙이 밖에 있다.** design-system이 Button 5종 · Dialog · Bottom Sheet ·
   Bottom Navigator · Header · Indicator를 스펙으로 갖고 있고 **스펙이 기준**이다
   (ADR-0014 D4). 우리가 만들 컴포넌트는 그 스펙의 구현이지 내장 요소의 래퍼가 아니다.

화면은 아직 `HomeScreen` 하나이고 만들 화면이 스무 개 남짓 남아 있다
(`docs/screens.md` 구현 순서 0~12). **지금 정한 형태가 그대로 복사된다.**

## 결정

### D1. 래퍼 프리미티브를 만들지 않는다 — 내장 요소를 화면에서 직접 쓴다

`<view>` · `<text>` · `<svg>`를 화면 컴포넌트가 직접 쓴다. **ADR-0008 D5를 되살리지
않는다.** 지금 코드가 하고 있는 것을 추인하는 결정이다.

근거 셋:

- **목적의 절반을 이미 패키지가 진다.** 값이 한 곳에서 오고 화면은 이름만 참조한다.
  래퍼가 없어도 색 하나를 바꾸는 자리는 여전히 한 곳이다 (맥락 1).
- **나머지 절반은 래퍼로 막히지 않는다.** 래퍼가 있어도 화면이 `<view>`를 그냥 쓸 수
  있고, **그것을 막는 도구가 없다** — oxlint에 JSX 내장 요소를 금지하는 규칙이 없다.
  실제로 막는 것은 D2의 파일 규약과 ADR-0014 D8의 검사다. 래퍼는 규칙을 하나 더
  선언할 뿐 지키게 하지 않는다.
- **래퍼는 prop을 다시 열어야 한다.** Lynx 요소의 prop이 DOM과 다르고
  (`bindtap` · `content` · `current-color`) 화면마다 필요한 것이 다르다. 통과시킬 prop
  목록을 유지하는 비용이 화면 수만큼 붙는다. `<svg>`가 그 예다 — 세 prop 중 둘을
  아이콘마다 다르게 넘긴다 (ADR-0014 D2·D6).

### D2. 시각 값은 **컴포넌트와 1:1인 CSS 파일**에만 둔다

D5의 목적을 이 규칙이 이어받는다.

- **컴포넌트 파일 하나에 CSS 파일 하나.** 그 컴포넌트를 정의한 모듈이 import 한다.
- **TSX에는 `className`만 둔다. 인라인 `style`을 쓰지 않는다.** 색·간격·크기·타이포
  리터럴이 TSX에 있으면 안 된다.
- **예외는 하나 — 아이콘 색**(`current-color`). ADR-0014 D2가 **CSS로 불가능해서** 연
  자리다. 선례로 쓰지 않는다.
- CSS 파일 안에서 시각 값은 `var(--libitum-*)`로만 쓴다 (ADR-0014 D1). `display` ·
  `flex-direction` 같은 **레이아웃 구조 값**은 토큰이 아니므로 리터럴로 적는다.
  토큰이 덮는 것은 색 · 간격 · 타이포 · radius · 아이콘 크기다.

**"토큰 적용 지점을 한 곳으로 모은다"를 지는 것은 이제 셋이다.**

| 무엇 | 지는 것 |
|---|---|
| `@libitums/design-tokens` | **값**의 단일 출처. 한 곳을 고치면 전체가 바뀐다 |
| 컴포넌트 : CSS 파일 1:1 (D2) | **적용 지점**. 한 컴포넌트의 시각 값이 어디 있는지 — 파일 하나 |
| 접두사 검사 (ADR-0014 D8) + `docs/e2e/` 눈 확인 (ADR-0006 D6) | **어긋남을 발견하는 자리** |

래퍼 하나가 지던 것을 셋이 나눠 진다. **어느 하나가 빠지면 `error-boundary.css` 같은
자리가 다시 생긴다** — 셋 중 세 번째가 없어서 실제로 생겼다.

### D3. 위치와 승격 — ADR-0011 D3을 여기로 옮긴다

```text
화면 1개만 쓴다   →  그 화면 폴더 안에 둔다 (src/screens/<화면>/)
화면 2개가 쓴다   →  src/components/ 로 올린다
앱 2개가 쓴다     →  packages/ui-lynx/ 로 올린다
```

- **미리 올리지 않는다.** 두 번째 사용처가 **실제로 생겼을 때** 옮긴다.
- **예외는 design-system이 스펙을 가진 컴포넌트다**(Button · Dialog · Bottom Sheet ·
  Bottom Navigator · Header · Indicator). **두 번째 화면을 기다리지 않고 바로
  `src/components/`에 만든다** — 첫 사례에서 그렇게 판단했다
  (2026-09-02, `정정 기록`). `packages/` 승격은 그대로 앱 2개일 때다.
- **세는 단위는 "화면"이지 "렌더 횟수"가 아니다.** 한 화면이 같은 것을 세 번 그려도
  화면 폴더에 남는다.
- `packages/ui-lynx`는 ADR-0004 D2 그대로 — **두 번째 소비자가 나타날 때.** 이름은
  예약돼 있다고 본다. `packages/` 아래에는 지금 아무것도 만들지 않는다.

**결정 자체는 바뀌지 않았다.** ADR-0011 D3과 ADR-0008 D4가 정한 것을 그대로 옮긴다.
옮기는 이유는 하나 — **살아 있는 결정이 `대체됨` 문서 두 곳에 흩어져 있었다.**
링크를 두 번 타고 축 추적표까지 가야 유효 여부를 알 수 있는 결정은 다음 사람이
읽지 않는다.

## 버린 대안

- **ADR-0008 D5를 그대로 되살린다 (`Box`·`Text` 래퍼)** — 토큰 사용처가 좁아지고
  D5의 목적이 원래 자리로 돌아온다. 버린 이유는 D1의 셋이다. 특히 **강제 수단이
  없어서** "래퍼가 있는데 안 쓴 화면"이 새로 생기고, 그건 지금 문제(이름 계열이 둘)와
  **같은 모양의 실패**다. 규칙을 하나 더 두는 것으로는 안 지켜지는 규칙이 하나 더
  생길 뿐이다.
- **CSS Modules 또는 css-in-js** — 클래스 이름 충돌이 구조적으로 사라진다. 버린 이유는
  rspeedy에서 **확인한 바가 없고**, Lynx의 스타일 처리가 웹과 다른 자리가 이미 둘
  나왔다는 것이다 (중첩 `var()` · `<svg>`의 `color`. ADR-0014). 검증 비용을 지금 낼
  이유가 없다. 충돌은 클래스 접두사(ADR-0003 D7)로 막힌다.
- **화면 단위로 CSS 파일 하나** (컴포넌트가 아니라 화면) — 파일 수가 준다. 그러나 화면
  폴더 안의 컴포넌트가 D3으로 승격될 때 **스타일을 어디서 떼어낼지 매번 판단하게
  된다.** 1:1이면 파일이 컴포넌트를 따라 같이 움직인다.
- **전역 스타일 파일(`src/styles/`)에 공통 클래스를 모은다** — 화면 간 중복이 준다.
  그러나 값은 패키지에서 오고 **지금 공통으로 뽑을 것이 없다.** 폴더는 필요해질 때
  만든다 (ADR-0003 D5).
- **프리미티브 몇 개를 미리 만들어 둔다** — ADR-0008이 이미 버린 것이고 근거가 그대로
  유효하다. 쓰이지 않는 것의 유지 비용이 QC 루프 내내 든다.

## 대가

- **비슷한 시각이 화면마다 중복된다.** 두 번째 화면이 나올 때까지 공통화하지 않으므로
  헤더·여백 조합이 여러 CSS 파일에 같은 모양으로 생긴다. ADR-0008이 적은 대가를 그대로
  진다 — **중복이 보기 싫어도 참는 것이 규칙이다.** D3의 승격 조건이 그것을 걷는다.
- **내장 요소 직접 사용도, 인라인 `style` 금지도 도구가 막지 않는다.** PR diff를 사람이
  읽을 때 본다 (ADR-0009 D4와 같은 형태의 약속). 잊으면 `verify`는 통과한다.
- **CSS 파일이 컴포넌트 수만큼 는다.** 래퍼 방식보다 파일이 많다.
- **나중에 프리미티브가 필요해지면 그때 사용처를 전부 고친다.** 래퍼를 미리 두는 비용을
  지금 안 내는 대신, 승격 시점의 비용을 낸다. D3의 "화면 2개" 규칙이 그 폭발 반경을
  좁히는 유일한 장치다.

## 재검토 조건

- **같은 시각 덩어리가 화면 2개에 나타나면** → D3. `src/components/`로 올린다
- **`src/components/`가 20개를 넘으면** → 분류 방식을 다시 본다 (ADR-0003 D5와 함께.
  ADR-0008이 남긴 조건을 그대로 이어받는다)
- ~~**design-system 스펙 컴포넌트를 만들게 되면** → D3~~ — **발동했고 판단이 끝났다**
  (2026-09-02, `정정 기록`). 답은 D3에 들어가 있다. 이 조건은 소진됐다
- **인라인 `style`이 실제로 필요한 사례가 나오면**(계산된 값 · 애니메이션) → D2.
  그 사례를 근거로 연다. 미리 열지 않는다 (ADR-0014 D1의 "여는 조건"과 같은 형태)
- **두 번째 앱이 생기면** → D3의 `packages/ui-lynx` 승격 (ADR-0004 D2)
- **JSX 내장 요소를 금지하는 lint 규칙을 쓸 수 있게 되면** → D1. 래퍼 강제를 도구로
  걸 수 있는지 다시 본다. **D1이 버린 이유 하나가 그때 사라진다**

## 정정 기록

**2026-09-02 — 재검토 조건이 발동했고, 첫 사례에서 판단했다.** 결정은 그대로다. D3이
스스로 *"두 번째 화면을 기다리지 않고 바로 `src/components/`로 갈 수 있는지 그 첫
사례에서 판단한다"* 로 미뤄 둔 것을 채웠다.

첫 사례는 뼈대 이슈의 **바텀 네비게이션 셸**이다. design-system이 스펙을 가진 여섯 중
처음 만든 것이고, 이것이 `src/components/`의 첫 입주자다.

**판단: 스펙 컴포넌트는 두 번째 화면을 기다리지 않는다.** 근거 둘 —

- **스펙이 있다는 것은 두 번째 사용처가 예정돼 있다는 뜻이다.** D3의 "미리 올리지
  않는다"가 막으려던 것은 **오지 않을 두 번째 사용처를 가정하는 것**인데, 스펙은 그
  가정을 저장소 밖에서 이미 확정해 준다. 세는 대신 대조하면 끝난다.
- **이 컴포넌트는 어느 한 화면의 것이 아니다.** 탭 넷 위에 걸려 있어서 "화면 1개면 그
  화면 폴더"를 적용할 화면 자체가 없다. 넷 중 하나를 골라 넣으면 그 선택에 근거가 없다.

`packages/ui-lynx`로는 올리지 않는다. 앱이 아직 하나다 (ADR-0004 D2). D3의 세 칸 중
**둘째 칸의 조건만** 스펙 유무로 갈렸고 셋째 칸은 그대로다.

**제자리에서 고친 이유**(ADR-0010 D10): 결정이 바뀐 것이 아니라 D3이 비워 둔 칸을
채운 것이고, 옛 문구로 지어진 것이 없다 — 이 판단 이전에 만들어진 스펙 컴포넌트가
저장소에 하나도 없다.

고친 곳: D3에 예외 한 줄, 소진된 재검토 조건 한 줄,
`docs/conventions/code.md`의 폴더 절과 컴포넌트 절 (ADR-0010 D4).
