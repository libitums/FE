# ADR-0027 — 전화번호 로그인을 Supabase SMS OTP로 연다 (인증 제공자 · 설정 주입 · 세션 저장과 갱신)

- 상태: 채택
- 날짜: 2026-09-29
- 다루는 축: 인증 (제공자 · 접속 값 주입 · 세션 저장과 갱신 · 서버 연동 테스트의 대역)
- 부분 대체: 없음. 아래 셋은 **적용 기록**이고 결정을 바꾸지 않는다 —
  [ADR-0001](0001-repository-goal-and-scope.md) D3의 「인증 인프라」 · 「`integration`의 서버 연동
  케이스」 제외가 **전화번호 수단 하나에서** 풀린다. [ADR-0006](0006-command-interface-and-test-layers.md)
  D4 · [ADR-0013](0013-dependencies-and-version-notation.md) D6의 *"목킹 도구는 서버 연동 케이스를
  넣을 때 함께 들인다"* 가 발동했고 **들이지 않았다**(D5). [ADR-0007](0007-app-internals-state-routing-data-errors.md)
  D2의 `api-client.ts`가 처음 실물이 됐다(D1).

**왜 새 번호인가** — 인증은 **없던 축**이다. ADR-0001 D3은 「인증 인프라」를 제외 목록에 넣었을
뿐 무엇으로 할지를 정한 ADR이 없고, 기존 ADR의 `다루는 축` 어느 것도 인증 제공자 · 세션을
덮지 않는다(ADR-0010 D10 「없던 축을 처음 정하면」). 그리고 이 회차의 계약은 `.agent-harness/`
(추적 제외)에 있어 **저장소에 남지 않는다** — 결정의 근거가 남을 자리가 여기다(ADR-0016 D11이
같은 이유를 적었다).

## 맥락

진입 흐름(2026-09-17)은 로그인을 **임시 토큰**으로 세웠다. 수단을 고르는 순간 고정 리터럴 하나가
`libitum.auth.token` 키로 저장되고, 스플래시는 그 키의 유무만 봤다. 서버가 없어 발급도 검증도
없었다([진입 흐름 스펙](../specs/entry-flow.md) · [ADR-0012](0012-native-host-app-minimal.md) D5의 ⚠ 블록).

2026-09-28 사용자 결정 셋이 이 회차의 범위를 정했다.

| # | 결정 |
|---|---|
| 1 | **전화번호 OTP만** 먼저 잇는다. 소셜 셋(apple · google · facebook)은 임시 토큰 그대로 · 호스트 네이티브 변경 없음 |
| 2 | Supabase 프로젝트는 조직의 개발 프로젝트 **Duru**다 |
| 3 | 세션을 **저장하고 앱 시작 때 refresh로 갱신**한다. 실패하면 로그인으로 보낸다 |

이 저장소의 사실(2026-09-28 실측).

1. **`apps/mobile/src`에 `fetch` 호출이 0건이었다.** ADR-0007 D2가 `src/lib/api-client.ts`를 정해
   뒀지만 파일이 없었다.
2. `@lynx-js/types`가 `fetch`를 **`lynx.fetch`(메서드)로만** 선언한다. 전역 `fetch` 선언이 없고
   Lynx의 `RequestInit`은 `body` · `headers` · `method`뿐이다. `URL` · `Headers` · `AbortController` ·
   `localStorage`는 타입에 없다.
3. iOS 호스트는 `LynxService/Http`를 이미 넣었다(`apps/ios/Podfile`).
4. rspeedy는 `loadEnv`가 기본이라 `.env*`의 `PUBLIC_` 접두 변수를 `import.meta.env.PUBLIC_*`로
   번들에 치환한다. `.env` · `.env.*`는 이미 추적 제외다(`.gitignore`).
5. 코드 검증은 4자리였다. Supabase SMS OTP의 기본은 6자리다.

## 결정

### D1. Supabase Auth REST를 `lib/api-client.ts`가 직접 부른다 — `supabase-js`를 넣지 않는다

부르는 엔드포인트는 셋이다 — `/auth/v1/otp`(요청 · 재전송) · `/auth/v1/verify`(검증) ·
`/auth/v1/token?grant_type=refresh_token`(갱신). 셋 다 `lib/api-client.ts` 한 파일이 부르고,
**네트워크는 그 파일 밖에서 나가지 않는다.**

- 요청 헤더는 `apikey`와 `Content-Type` 둘이다. **`Authorization`을 싣지 않는다** — publishable
  키는 JWT가 아니다.
- 전송 함수는 `globalThis.fetch`가 있으면 그것, 없으면 `lynx.fetch`다. 응답은 10초 안에 오지 않으면
  `network`로 끝난다.
- **세 함수는 어떤 경우에도 던지지 않는다.** 결과는 성공 또는 실패 이유 하나(`network` ·
  `unavailable` · `unconfigured` · `rate-limited` · `rejected` · `invalid-code`)로 돌아오고, 실패
  이유 → 화면 문구의 표는 `lib/auth-failure.ts` 하나다(두 화면이 같은 실패를 다르게 말하지 않는다).
- 응답 파싱은 손 파서다(zod를 넣지 않는다 — 같은 이유).

**호출 주체는 화면이 아니라 결선(`app/entry-wiring.ts`)이다.** ADR-0007 D2는 *"화면에서 호출한다"*
고 적었는데, 성공의 뒤처리(세션 저장 · 이벤트 · 전이)가 이미 결선의 몫이고 `screens/ → app/`
import가 금지돼 있다. 화면이 api-client를 부르면 저장과 전이를 화면이 지게 된다. 화면은 콜백의
결과(성공 · 실패 이유)만 받아 요청 중 · 실패를 그린다. **서버 응답은 여전히 전역 store에 가지
않는다** — D2의 금지 규칙은 그대로다.

**2026-09-29 실측** — Lynx Explorer(iPhone 시뮬레이터, dev 번들)에서 실서버로 OTP 요청 · 오답 ·
재전송 · 검증이 실제로 돌았다. **이 저장소에서 `fetch`가 처음 돈 날이다.**

### D2. 접속 값은 `apps/mobile/.env.local`의 `PUBLIC_SUPABASE_URL` · `PUBLIC_SUPABASE_ANON_KEY`로 주입한다

- rsbuild가 빌드 때 `import.meta.env.PUBLIC_*`를 치환한다. `lynx.config.ts`는 **한 줄도 안
  고쳤다.** `pnpm build` 산출물에서 URL이 들어가고 변수 이름이 남지 않는 것을 확인했다(2026-09-29).
- 읽는 자리는 `lib/supabase-config.ts` 하나이고 **리터럴 멤버 접근으로, 호출마다** 읽는다 —
  구조 분해 · 동적 키로 읽으면 치환이 안 되고, 모듈 상수로 굳히면 테스트가 케이스마다 값을 바꿀
  수 없다.
- URL이 `https://`로 시작하지 않거나, 키가 비었거나 **`sb_secret_`로 시작하면 설정이 없는 것**으로
  본다. 그때 api-client는 요청을 보내지 않고 `unconfigured`로 끝나며, 전화번호 로그인은
  *"Phone sign-in isn't available right now."* 를 띄운다 — **앱은 죽지 않는다.**
- **service_role(비밀) 키는 어디에도 두지 않는다.** anon/publishable 키는 번들에 들어가는
  **공개 값**이다. 그래도 값을 문서 · 커밋에 적지 않는다 — 파일 하나(`.env.local`)가 진다.
- `.env.example`을 두지 않는다. `.gitignore`의 `.env.*`가 그것까지 막고, 뚫으려면 `.gitignore`를
  고쳐야 한다. 변수 이름과 만드는 절차는 [루트 README](../../README.md) 「Supabase 접속 값」이 진다.

### D3. 세션은 새 키 `libitum.auth.session` 하나에 둔다 — 임시 토큰 키와 섞지 않는다

- 값은 `{ accessToken, refreshToken, expiresAt }`의 JSON이다(`lib/auth-session.ts`).
- 기존 `libitum.auth.token`은 **소셜 셋 전용으로 그대로** 둔다. `lib/auth-token.ts`는 한 줄도 안
  바뀌었다. 한 키에 두 형식을 섞으면 그 파일과 그 테스트가 함께 바뀌고, 결정 1이 건드리지 말라고 한
  소셜 경로가 흔들린다.
- **전화번호 경로는 검증이 성공한 뒤에만 저장한다.** 그전(번호 제출 · OTP 요청)에는 저장소에
  아무것도 쓰지 않는다 — 임시 토큰 시절에는 수단을 고르는 순간 저장했다.
- 새 설치에서 전화번호로 들어오면 키가 `libitum.auth.session` 하나, 소셜로 들어오면
  `libitum.auth.token` 하나다. 둘이 다 있으면 세션이 이긴다.
- 세션 JSON이 깨져 있으면 **없는 것으로 본다. 지우지는 않는다** — 읽기가 쓰기를 부르지 않게 한다.
- 이 변경 전에 전화번호로 들어와 임시 토큰을 가진 설치는 **이주하지 않는다** — 그대로 임시 토큰
  갈래로 들어간다.
- 저장은 평문이다(호스트 `StorageModule`, ADR-0012 D2). Keychain 전환은 이 ADR이 하지 않는다.

ADR-0007 D1의 *"저장소에 넣는 것은 로그인 토큰뿐"* 은 **그대로 참이다** — 세션은 로그인 자격이다.
키가 둘로 는 것이지 저장하는 **종류**가 는 것이 아니다.

### D4. 갱신은 스플래시 애니메이션이 끝난 뒤 한다 — 끝날 때까지 스플래시가 선다

```text
스플래시 애니메이션 끝 ─▶ 저장소를 읽는다
   ├─ 세션 있음        ─▶ refresh 요청 … 스플래시가 계속 선다 …
   │                        ├─ 성공 ─▶ 새 세션 저장 · 앱으로
   │                        └─ 실패 ─▶ (서버가 거절했을 때만 세션 삭제) · 로그인
   ├─ 임시 토큰만 있음 ─▶ 곧장 앱 (동기, 이전과 같다)
   └─ 둘 다 없음      ─▶ 온보딩 (동기, 이전과 같다)
```

- **애니메이션과 갱신을 병렬로 돌리지 않는다.** 스플래시 화면과 그 계약을 안 고치고, 세션 없는
  두 갈래를 **동기로 지킨다** — 기존 integration 파일 열둘이 「임시 토큰 + 시간 경과 → 곧장 앱」을
  동기로 기대고 있다.
- **갱신 성공 때 새 세션을 반드시 저장한다.** Supabase는 refresh 토큰을 회전시키고 옛 토큰의
  재사용을 탈취 신호로 본다.
- 갱신은 만료 여부와 무관하게 **매 실행마다** 한다. `expiresAt`은 저장만 하고 아직 읽는 자리가 없다.
- **실패의 목적지는 로그인**이고 진입 스택은 `[온보딩, 로그인]`이다 — 로그인의 뒤로가기가 온보딩에
  닿는다. 세션을 지우는 것은 **서버가 거절(`rejected`)했을 때뿐**이다. 네트워크 · 서버 오류로
  실패하면 세션을 지키고 다음 실행에서 다시 시도한다.
- 거절 때의 삭제가 **저장소 모듈 `remove`의 첫 호출자**다(ADR-0012 D2).
- 최장 체류는 애니메이션(약 2.4초 · 최대 4초) + 요청 제한 10초다.

### D5. 서버 연동 테스트의 대역은 `vi.stubGlobal("fetch")`다 — msw를 넣지 않는다

`integration`의 서버 연동 케이스가 **이 회차에 처음 섰다**(ADR-0006 D4의 셋째 행). 대역은
`vi.stubGlobal("fetch", …)` + `vi.stubEnv("PUBLIC_SUPABASE_*", …)`다.

- 대역 자리가 `NativeModules`(호스트 모듈 대역)와 같은 **전역 경계 하나**가 된다. api-client가
  `globalThis.fetch`를 먼저 찾는 이유가 이것이다(D1).
- msw는 같은 전역을 가로채는 도구라 얻는 것이 없고, devDependency와 ADR-0013 D1 절차만 는다.
- ADR-0006 D4가 걱정한 *"명세 없이 목을 만들면 목과 실제가 갈라진다"* 는 여기서 해소된다 —
  Supabase Auth REST는 **공개 명세**이고, 대역이 흉내 내는 응답 모양을 실서버로 한 번 확인했다
  (D1의 실측).

⚠ **서버 연동 보류가 닫힌 것은 아니다.** 명세가 있는 것은 Supabase Auth 하나이고, 이 앱의 다른
API(진행 · 학습 데이터)의 명세는 여전히 없다([보류 표](README.md#보류-표)).

### D6. 코드는 6자리다

`verificationCodeLength = 6`. 프로젝트 설정도 OTP 6자리 · 유효 300초로 맞췄다(화면의 5분
카운트다운과 같다). 칸 여섯이 320pt 폭 한 줄에 서도록 칸 크기를 `s`로 내렸다.

## 개발 절차 — `.env.local`과 Duru 프로젝트의 현재 설정

새 체크아웃은 `apps/mobile/.env.local`을 만들어야 전화번호 로그인이 선다. 만드는 절차는
[루트 README](../../README.md) 「Supabase 접속 값」이 정본이다 — 여기 복사하지 않는다.

프로젝트 쪽은 값이 아니라 **무엇이 켜져 있는가**만 적는다(2026-09-29).

| 설정 | 값 |
|---|---|
| Phone Auth | 켜짐 |
| OTP 길이 · 유효 시간 | 6자리 · 300초 |
| 테스트 전화번호 | 하나 등록돼 있다(고정 코드, SMS가 나가지 않는다). **번호와 코드는 저장소에 적지 않는다** — 번들에 든 공개 키와 합치면 누구나 이 프로젝트에 인증 세션을 만들 수 있어, 팀 내부에서만 공유한다 |
| SMS 공급자(Twilio) | **비어 있다** — 실제 번호로는 SMS가 오지 않는다. 대시보드에서 자격 증명을 넣은 뒤에만 된다 |

수동 절차와 실측 기록은 [진입 흐름 e2e](../e2e/entry-flow.md)의 E1–E7이 진다.

| 한 키(`libitum.auth.token`)에 세션과 임시 토큰을 함께 | D3 — 소셜 경로와 그 테스트가 함께 흔들린다 |
| 애니메이션과 갱신을 병렬로 | 스플래시 계약과 동기 갈래가 깨진다(D4). 얻는 것은 최장 체류 몇 초다 |
| msw | D5 |

## 대가

- **스플래시가 길어질 수 있다.** 세션이 있는 설치는 매 실행마다 애니메이션 + refresh 왕복을
  기다리고, 네트워크가 없으면 최장 약 14초를 스플래시에서 보낸 뒤 로그인으로 간다.
- **네트워크가 없으면 세션이 있어도 로그인으로 간다.** 세션은 지켜지지만 그 실행에서는 앱에
  못 들어간다 — 오프라인 진입을 포기했다.
- **로그인 수단 둘의 강도가 다르다.** 전화번호는 서버가 검증한 세션이고 소셜 셋은 여전히 고정
  리터럴이다. 저장소 키도 둘로 갈렸다.
- **세션이 평문이다.** 호스트 저장소가 암호화하지 않는다.
- **로그아웃이 여전히 없다.** 두 키 다 지우는 수단이 앱에 없고, 진입 흐름을 다시 보려면 재설치가
  유일하다(서버 거절 때의 세션 삭제는 예외다).
- **개발 루프에서 재실행 유지를 못 본다.** Explorer에는 `StorageModule`이 없어 D4는 호스트 앱에서만
  확인된다(ADR-0012 D3의 이중 트랙).
- **로컬 파일 하나가 없으면 전화번호 로그인이 서지 않는다.** `.env.local`이 없는 체크아웃은
  빌드는 되지만 전화번호 로그인이 `unconfigured`로 선다. CI 산출물도 마찬가지다.

## 재검토 조건

- **소셜 로그인 중 하나라도 진짜 인증이 요구되는 시점** → D3. 키 둘의 공존 규칙과 스플래시 갈래를
  다시 본다. 소셜은 호스트 네이티브를 요구할 가능성이 높아 ADR-0017 D1의 조건도 함께 걸린다
- **액세스 토큰을 싣는 첫 API가 생기는 시점** → D1 · D4. 만료(`expiresAt`)를 읽는 자리와 요청 중
  갱신이 그때 필요해진다
- **로그아웃이 화면 목록에 들어오는 시점** → D3. 두 키를 지우는 수단과 ADR-0007 D3의 「진입 구간으로
  되돌아가기」가 함께 정해진다
- **세션 저장을 Keychain으로 옮기라는 요구가 오는 시점** → D3. 호스트 모듈 표에 행이 는다
- **`import.meta.env` 치환이 어느 빌드 경로에서 깨지는 것이 확인되는 시점** → D2. `source.define`으로
  바꾼다
- **Supabase에서 읽어 온 같은 서버 상태(예: 사용자 정보)를 화면 둘 이상이 읽거나 자동 재검증이
  필요해지는 시점** → ADR-0007 D2의 도입 조건. `/auth/v1/otp`가 이미 화면 둘에서 나가지만 캐시할
  것이 없는 쓰기라 그 조건으로 세지 않았다(ADR-0007 `정정 기록` 2026-09-29)
- **실기에서 스플래시 체류가 사용자 불만으로 확인되는 시점** → D4. 병렬 갱신을 다시 본다
