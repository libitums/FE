# ADR-0069 — 기존 회원 로그인은 언어 선택 · 여정 입장을 건너뛰고 바로 여정 맵으로 간다 (서버 기록으로 판정 · 최대 3초 대기 · 실패하면 지금 흐름)

- 상태: **채택 — 클라이언트 쪽.** 서버 · 호스트 변경은 0이다(새 RPC · 마이그레이션 · globalProps 키 0).
  사용자 결정(2026-10-18)은 셋이다 — **서버에 학습 기록이 있거나 학습자 프로필 행이 있으면 기존 회원**이다 · 판정이 실패하면 **지금 흐름**(언어 선택 → 여정 입장 → 맵)이다 ·
  UI 언어는 **저장값 → 기기 언어(지원할 때) → 영어**다. 대기 3,000 ms · 바로 맵 경로에서 알림 권한을 묻는 것 · 그 경로에서 `entry_completed`를 내지 않는 것 · 새 측정 이벤트는
  요구사항의 [추론] 기본값을 그대로 썼고, 열린 질문 넷(Q1 ~ Q4)은 **메인이 추천안을 골랐다** — 사용자 명시 승인이 아니다(아래 「열린 질문과 메인 추천안」).
  ⚠ **기기 확인이 아직 없다** — [기존 회원 로그인 e2e](../e2e/returning-user-login.md) RUE1 ~ RUE5는 실행된 회차가 없다.
- 날짜: 2026-10-18.
- 다루는 축: **로그인 뒤 진입 흐름의 갈래** — 누가 기존 회원인가(판정 신호) · 무엇을 조회하는가 · 얼마나 기다리는가 · 실패 · 시간 초과를 어떻게 읽는가 · 기다리는 동안 무엇이 보이는가 ·
  학습자 프로필 동기화가 언제 시작하는가 · 언어 선택을 건너뛴 로그인의 UI 언어 · 그 경로의 알림 권한 · 측정 이벤트, 그리고 소셜 로그인 버튼의 로딩 스피너 자리.
  **다루지 않는 것**: 세션 갱신 부팅(이미 바로 맵 — 그대로), 진행 동기화의 시작 시점(세션 저장 직후 그대로), 판정 중 뒤로가기 경합(「대가」 4), 손님 프로필이 서버 프로필을 덮는 규칙(보류 표),
  호스트가 기기 언어를 넘기는 경로(보류 표), 판정 실패 · 시간 초과의 측정(Q3).
- 이어받는 결정(결정 문장은 바꾸지 않는다 — 각 ADR에 적용 기록):
  [ADR-0031](0031-ui-language-catalog.md) D4(「쓰는 때」에 둘째 자리 — 재검토 조건 「UI 언어를 바꾸는 둘째 자리」 발동 · 판정),
  [ADR-0034](0034-server-push-notifications.md) D4(「진입 흐름의 끝」이 둘 — 둘 다 `ask: true`),
  [ADR-0057](0057-meta-app-events.md) 맥락 3 · 대가 4 · [ADR-0063](0063-airbridge-events.md) 「사용자 확인 필요」 5(「가입 완료」가 기록 있는 계정의 재로그인 · 재설치에서 더는 나지 않는다 — 해석 단절),
  [ADR-0059](0059-learner-profile.md) D3(로그인 두 경로의 동기화 시작이 판정 뒤로),
  [ADR-0062](0062-progress-cache-first.md) D5(문턱 1,000 ms의 기점 해석 — 그대로).
  분석 이벤트 이름이 하나 늘었다(이름 39 → 40 · 모양 43 → 44 — 정본은 `lib/analytics.contract.ts`, 전송 규칙은 [ADR-0029](0029-product-analytics-posthog.md) 그대로).

**왜 새 번호인가** — 진입 흐름의 전이 표([진입 흐름 계약](../specs/entry-flow.md) §3 — ADR-0007 D6 계열) · ADR-0031 D4 「쓰는 때」 · ADR-0034 D4 「묻는 자리」 · ADR-0057/0063의 「가입 완료」 해석 위에
코드 · 테스트 · 측정이 이미 지어졌고, 이 변경이 그 결정 여럿을 **한꺼번에** 건드린다(ADR README 「형식」의 첫째 · 둘째 줄). 제자리로 쓰면 다섯 문서에 조각이 흩어진다.
0068은 다른 브랜치(특별 유닛 맵 표식)가 쓰고 있어 0069다.

근거 표시: **[코드]** 저장소 코드(`apps/mobile/src/` 기준) · **[실측]** 빌드 · 테스트 실행 · **[사용자]** 요구사항의 사용자 결정 · **[추론]** 관찰 없이 이어 붙인 것.
계약의 정본은 저장소 밖 작업 폴더의 spec이고 이 문서는 그중 **결정**만 옮긴다. 시그니처는 코드가 진다.

## 맥락

1. **재설치하거나 로그아웃 뒤 다시 로그인한 기존 회원도 처음 사용자 화면을 다시 지났다** [코드]. 소셜 교환 · 코드 검증이 성공하면 결선(`app/entry-wiring.ts`)이
   언제나 언어 선택을 `push`했고, 그 뒤 여정 입장 → 맵이었다. 세션 갱신 부팅만 바로 맵이었다.
2. **판정에 쓸 서버 기록은 이미 둘이 있다** [코드]. `load_learning_progress`(진행 스냅숏 — 저장된 적 없으면 `raw: null`)와 `load_learner_profile`(행 없으면 `record: null`).
   둘 다 던지지 않고 실패를 `{ ok: false }`로 낸다.
3. **진행 · 프로필 동기화 객체는 판정 정보를 주지 않는다** [코드]. 진행 동기화는 `onLoadSettled("loaded" | "failed")`만 내고 서버 원본을 내지 않으며 저장 루프 · 학습 날짜까지 끝나야 settle한다.
   프로필 동기화는 손님 칸이 있으면 **조회 없이 먼저 올린다**(`learnerProfileCacheAfterSignIn` → `upload`).
4. **그 업로드가 판정을 오염시킬 수 있다** [코드]. 지금 순서(세션 저장 직후 프로필 동기화 시작)를 두면, 온보딩 넷째 스텝에서 이름을 적은 **신규 사용자**의 `save_learner_profile`이
   판정 조회보다 먼저 서버 행을 만들어 기존 회원으로 오판될 수 있다.
5. **앱은 기기 언어를 알 길이 없다** [코드]. PrimJS에 `Intl`이 없고, `SystemInfo`에 로케일이 없고, 호스트 globalProps(`safeAreaInsets` · `reducedMotion` · `fontScale` · `viewportWidth` 등)와
   [호스트 모듈 표](README.md#호스트-모듈-표)의 어느 메서드도 언어를 주지 않는다. 그리고 고를 수 있는 언어가 영어 하나이고 `vi` · `es` · `ja` 문구표가 비어 있다 —
   **기기 언어를 알아도 지금 화면은 달라지지 않는다.**
6. **로그인 화면 · 코드 검증 화면은 콜백 promise가 끝날 때까지 로딩을 유지한다** [코드]. `LoginScreen`은 `requesting`, `VerificationCodeScreen`은 `verifying`을 세우고 결선의 promise를 기다린다 —
   결선이 판정까지 기다리면 **화면 변경 없이** 스피너가 이어진다.
7. **소셜 버튼의 로딩 스피너가 왼쪽 위 모서리에 섰다** [코드]. `login-screen.css`의 `.login-screen-social .ui-lynx-button-spinner-wrap` 덮어쓰기(`left: spacing-24` · icon-xs 크기)가
   ui-lynx `Button` 기본 래퍼(전면 · 가운데)가 `absolute`가 되기 전의 근거로 남아, 기본 래퍼의 `top: 0`과 합쳐져 상자가 (24px, 0)에 섰다.

## 결정

### D1. 판정은 순수 함수, 조회 · 시간은 얇은 비동기 모듈 하나

- `app/returning-learner.ts`(순수 — IO import 0)가 응답 → 신호, 신호 → 경로를 정한다. 신호는 판별 유니온 `"pending" | "present" | "absent" | "unknown"`, 경로는 `"journey-map" | "language-select"`다 —
  불리언 둘(`hasProgress` · `hasProfile`)을 들고 다니지 않는다.
- `app/returning-learner-probe.ts`가 두 요청을 **같은 틱에** 시작하고 3초 타이머와 경주시킨다(의존성 주입 — 테스트가 가짜 loader · 짧은 대기로 상태 기계를 본다). 한 호출 = 한 인스턴스이고
  모듈 전역 상태가 없다. **reject하지 않는다.** 경로가 정해지면 타이머를 지우고 한 번만 resolve하며, 늦은 응답 · 늦은 타이머는 무시한다.
- `entry-wiring.ts`가 그 promise 하나를 기다린다. `AppSession.tsx` · `screen-wiring.ts`(각 300줄)와 `EntryWiringArgs` · 콜백 시그니처는 그대로다. 컴포넌트 · props · testid 변경은 0이다.

### D2. 별도 조회 — 동기화 객체에서 빌려 오지 않는다

판정은 기존 RPC `load_learning_progress` · `load_learner_profile`을 **판정용으로 한 번씩 더** 부른다(맥락 3). 새 RPC · 마이그레이션은 0이다. 진행 동기화(`syncProgress`)는 지금처럼 세션 저장 직후 시작한다 —
신규 사용자는 합친 결과가 비어 서버에 쓰지 않으므로 판정과 경합하지 않는다 [코드].

### D3. 학습자 프로필 동기화는 판정 뒤

로그인 두 경로(소셜 · 코드 검증)에서 `storeSession`이 프로필 동기화를 시작하지 않고, **판정이 끝난 직후**(갈래와 무관하게) 시작한다. 세션 갱신 부팅은 판정이 없으므로 지금처럼 세션 저장 직후 시작한다.
판정의 프로필 조회가 늘 손님 업로드보다 먼저 나가 맥락 4의 오판이 생기지 않는다. 업로드 자체는 그대로 일어난다.

### D4. 판정 규칙

| 진행 응답 | 신호 |
|---|---|
| `{ ok: false }` · `{ ok: false, invalidResponse: true }` · reject · 동기 throw | `unknown` |
| `{ ok: true, raw: null }` | `absent` |
| `{ ok: true, raw }`인데 모르는 버전 · 모양(`journeyProgressFrom` → `null`) | `unknown` |
| 해석됨 · 학습 기록 없음 | `absent` |
| 해석됨 · 학습 기록 있음 | `present` |

**학습 기록 있음**(`hasLearningRecord`) = 완료 활동 수(`completedActivityCount`) > 0 **또는** 비주얼 노벨 비트 진행 > 0 — 진행 중인 이야기(VN `active` · `beatIndex: 1`)도 기록으로 본다.
첫 유닛 안내의 「신규」 조건과 같은 정의다 [코드].

| 프로필 응답 | 신호 |
|---|---|
| `{ ok: false }`(요청 실패 · 깨진 응답 · 규칙에 어긋난 행) · reject · throw | `unknown` |
| `{ ok: true, record: null }` | `absent` |
| `{ ok: true, record }` | `present` |

| 진행 \ 프로필 | pending | present | absent | unknown |
|---|---|---|---|---|
| **pending** | 기다림 | 맵 | 기다림 | 기다림 |
| **present** | 맵 | 맵 | 맵 | 맵 |
| **absent** | 기다림 | 맵 | 언어 선택 | 언어 선택 |
| **unknown** | 기다림 | 맵 | 언어 선택 | 언어 선택 |

- `present`가 하나라도 오면 **나머지를 기다리지 않고** 맵이다. 둘 다 끝나면 즉시 정한다.
- **최대 대기 3,000 ms**(`returningLearnerWaitMs` — 모션 토큰이 아니다). 시간이 다 되면 `pending`을 `unknown`으로 읽어 같은 표를 쓴다 — 「기다림」 칸은 전부 언어 선택이 된다.
- 한 번 정한 경로는 바꾸지 않는다 — 언어 선택이 선 뒤 늦게 온 `present`로 맵으로 튀지 않는다.
- 「기록 없음 + 실패」는 신규 흐름이다 — 실패 = 신규 흐름(사용자 결정)이고, 실패한 쪽에 기록이 있었는지 모른다. 규칙에 어긋난 프로필 행은 요청 실패와 구분되지 않는 `ok: false`라 보수적으로 `unknown`이다.

### D5. 언어 선택을 건너뛴 로그인의 UI 언어 — 규칙은 셋을 다 갖고, 지금 결선의 기기 입력은 `null`

- `returningUiLanguageFrom(stored, deviceLanguageTag)`: ① 저장값이 `entryLanguages`의 멤버면 그대로(고를 수 있는지 보지 않는다 — `uiLanguageFrom`과 같은 규칙, ADR-0031 D4 「이상한 값」 행)
  ② 아니면 기기 태그의 주 하위 태그(`ja-JP` → `ja`, `_` 구분자 · 대소문자 무시)가 **고를 수 있는 언어**(`isEntryLanguageAvailable`)면 그것 ③ 아니면 `en`.
- `loadReturningUiLanguage()` = `returningUiLanguageFrom(저장값, null)` — 기기 입력 `null`은 맥락 5의 사실이다. 고를 수 있는 언어가 영어뿐이라 `null`과 실제 기기 언어의 결과가 지금 **모든 입력에서 같다.**
- 바로 맵 경로는 그 값을 `saveUiLanguage`로 **저장하고** `setEntryLanguage`로 세운다 — 진입 흐름을 마친 뒤 저장 키 집합 `[libitum.auth.session, libitum.ui.language]`(ADR-0031 D4)를 이 경로도 지킨다.
  같은 기기에 이미 저장된 값(로그아웃 뒤 재로그인)은 덮어쓰지 않고 그대로 쓴다.

### D6. 바로 맵 경로의 순서 · 이벤트 · 알림 권한

| 순서 | 무엇 |
|---|---|
| 1 | 세션 저장 → 진행 동기화 시작 → 분석 식별(지금 그대로). 소셜이면 `entry_login_method_selected`(교환 성공의 관측 — 판정 전, 지금 자리) |
| 2 | 판정 대기(D4) — 그동안 누른 소셜 버튼은 `requesting`, 코드 검증 버튼은 `verifying` 그대로 |
| 3 | 프로필 동기화 시작(D3) |
| 4a 맵 | UI 언어 결정 · 저장(D5) → **`entry_returning_learner_entered { method }`** → `enterApp` → `syncPushDevice({ ask: true })`(기다리지 않음) |
| 4b 언어 선택 | `entry_screen_viewed("language-select")` → `push(language-select)` — 이후 지금 흐름 그대로(`entry_completed` · `ask: true`는 여정 입장 시작에서) |

- 바로 맵 경로에서 `entry_completed` · `entry_screen_viewed(language-select · journey-entry)`는 **나지 않는다** [추론 — 요구사항].
- 알림: 새 설치는 미요청이라 시스템 다이얼로그가 맵 위에 한 번 뜬다. 이미 정해진 설치(로그아웃 뒤 같은 기기)는 다이얼로그 없이 등록만 한다 — ADR-0034 D4 「미요청일 때만 묻는다」 그대로.
- Airbridge · Meta로 새 이벤트를 보내지 않는다(`airbridgeEventFrom` → `null`).

### D7. 소셜 로그인 스피너 — 덮어쓰기 삭제, 새 시각 없음

`login-screen.css`의 `.login-screen-social .ui-lynx-button-spinner-wrap` 규칙과 그 주석을 지운다 — ui-lynx `Button` 기본 래퍼(전면 · 가운데)가 선다. 새 토큰 · 새 선택자 · 새 화면 · 새 문구는 0이고,
ui-lynx `button.css`는 바뀌지 않는다. 로고 배치 규칙(`-surface` relative · `-icon` absolute)은 남는다. 디자인 판정은 「새 시각 없음 — 스피너는 Button 기본 배치」다.
대기가 길어져도(≤ 3초) 따로 안내하지 않는다 — 소셜 교환 대기와 같은 표시다.

### D8. 로그아웃 뒤 같은 기기 재로그인에도 같은 규칙

판정은 「어떻게 설치했나」를 모르고 서버 기록만 본다. 로그아웃 뒤 다시 로그인해도 기록이 있으면 맵으로 간다(지금까지는 언어 선택 → 여정 입장). 같은 기기라 저장된 UI 언어가 남아 D5 ①이 그것을 쓴다.

|---|---|---|---|
| `entry_returning_learner_entered` | `method`(`phone` \| `google` \| `apple` \| `facebook`) | 판정이 `journey-map`으로 끝난 로그인에서 UI 언어 저장 뒤 · `enterApp` 직전 1회 | 신규 흐름(실패 · 시간 초과 포함) · 세션 갱신 부팅 · 로그인 실패 · 취소 |

- **기존 이벤트로는 바로 맵 경로를 가를 수 없다** [코드] — 전화의 `entry_login_method_selected("phone")`는 OTP 요청 때(검증 전) 나고, 소셜도 「선택 뒤 언어 선택 열람 없음」이 바로 맵 · 대기 중 종료 · 대기 중 실패를 가르지 못한다.
- 읽는 법: 기존 회원 비율 = `entry_returning_learner_entered` ÷ (`entry_returning_learner_entered` + `entry_screen_viewed{screen: "language-select"}`). 로그인 성공 1회당 보통 둘 중 하나가 난다 — 판정 대기 중 앱이 끝나면 둘 다 0이고, 판정 중 뒤로가기 경합(「대가」 4)이 나면 둘이 날 수 있다.
- payload에 진행 · 프로필 값 · 대기 시간 · 사용자 식별자를 싣지 않는다(속성은 문자열만 — `AnalyticsContractChecks`).
- ⚠ **해석 단절(2026-10-18 이 변경부터)**: `entry_completed`와 그것을 옮기는 Airbridge `airbridge.user.signup`(「가입 완료」)이 **기록 있는 계정의 재설치 · 재로그인에서 더는 나지 않는다.**
  가입 완료 수가 줄어 보이는 것은 정의 변경이다([운영 안내](../airbridge-events.md)).
- GitHub wiki 「이벤트 사전」은 저장소 밖이다 — 새 행과 해석 단절은 사람이 고친다(후속).

## 버린 대안

1. **서버 플래그 RPC 신설**(「이 계정은 기존 회원인가」 하나를 돌려주는 함수) — 마이그레이션이 필요하고, 같은 답을 기존 RPC 둘이 이미 준다.
2. **동기화 객체에서 판정 정보를 빌려 오기** — 진행 동기화는 원본을 내지 않고 늦게 settle하며, 프로필 동기화는 손님 값이 있으면 조회를 하지 않는다(맥락 3).
3. **응답이 올 때까지 무한히 기다리기** — 오프라인 · 느린 망에서 로그인이 막힌다. 실패 = 신규 흐름(사용자 결정)과 맞지 않는다.
4. **판정 전에 언어 선택을 먼저 보이고, 기록이 오면 맵으로 보내기** — 언어 선택이 섰다가 맵으로 튄다. 그 사이 고른 언어 · 누른 버튼의 처리가 두 갈래로 갈린다.
5. **`syncLearnerProfile` 순서를 그대로 두기** — 온보딩에서 이름을 적은 신규 사용자를 기존 회원으로 오판한다(맥락 4 · D3).
6. **지금 호스트에 기기 언어 globalProps 키를 세우기** — iOS · Android 네이티브 · 호스트 테스트 · e2e가 늘고, 고를 수 있는 언어가 영어뿐이라 관찰 가능한 차이가 0이다(Q1).
7. **「새 설치」에서만 바로 맵** — 설치 표지를 새로 저장해야 하고(저장소 예외 하나 더, ADR-0007 D1) 요구사항이 그 구분을 요구하지 않았다(Q4).

## 열린 질문과 메인 추천안

| # | 물음 | 고른 것 | 대안 |
|---|---|---|---|
| Q1 | 기기 언어를 줄 호스트 경로가 없다 | **이번엔 호스트 변경 0** — 규칙은 순수 함수에 셋 다 두고 결선은 기기 `null` | 지금 globalProps 키(예 `deviceLanguage`)를 세운다 |
| Q2 | 「지원 언어」의 뜻 | **고를 수 있는 언어**(`isEntryLanguageAvailable` — 지금 영어 하나). 신규 사용자와 같은 집합 | 목록 넷(`entryLanguages`) — 기기가 일본어면 `ja`가 저장되지만 문구표가 비어 화면은 영어이고, 신규 사용자는 고를 수 없는 값이다 |
| Q3 | 판정 실패 · 시간 초과를 잴까 | **이번엔 재지 않는다** — 지표가 「바로 맵 진입 수」만 물었다 | 지금 속성을 더한다 — 신규 흐름 쪽 이벤트 모양이 바뀌어 퍼널 해석이 하나 더 단절된다 |

## 대가

1. **로그인마다 RPC 읽기 +2.** 진행 동기화의 `load_learning_progress`와 같은 순간에 같은 RPC가 한 번 더 나간다 [추론 — 부담은 무시할 만하다고 본다].
2. **로그인 뒤 최대 3초 대기가 생긴다.** 소셜 교환 · 코드 검증이 성공한 뒤 판정 응답까지 누른 버튼이 로딩인 채 기다린다. 기존 회원은 `present`가 오는 즉시, 신규 사용자는 두 응답이 끝나는 즉시 넘어가지만,
   망이 느리거나 끊기면 3초를 다 기다린 뒤 언어 선택이 선다. 이 체감 지연을 기기에서 잰 적은 없다([성능 보고서](../performance/reports/returning-user-login-iphone-17-pro-simulator-01.md)).
3. **프로필 업로드가 최대 3초 늦다** — 레슨 전이라 관찰할 수 없다고 본다 [추론]. 학습자 프로필 e2e의 업로드 결과는 시점만 늦다.
4. **판정 중 뒤로가기 창이 길어졌다.** 판정 동안(≤ 3초) 로그인 화면의 뒤로가기 · Android 시스템 뒤로가 동작하면 결과 `dispatch`가 온보딩 위에 쌓일 수 있다 — 소셜 교환을 기다리는 지금도 같은 창이 있고 길이만 늘었다.
   막으려면 화면 쪽 busy 가드가 필요하고 이 변경 범위 밖이다.
5. **「가입 완료」 수의 해석이 끊긴다**(「측정」). 광고 매체 최적화 신호가 기존 회원의 재설치에서 줄어든다.
6. **기록 있는 계정으로는 진입 흐름 뒤쪽(언어 선택 · 여정 입장)을 다시 볼 수 없다** — 재설치해도 바로 맵이다. 수동 확인은 **새 계정**이 필요하다([진입 흐름 e2e](../e2e/entry-flow.md) 머리 메모).
7. **언어 선택을 떠난 신규 사용자가 재설치하면 기존 회원이 된다** — 그 사이 올라간 프로필 행 때문이다. 「프로필 행 = 기존 회원」(사용자 결정)의 귀결이다.
8. **번들 +4,036 bytes**(main 2,169,219 → CI 설정 2,173,255, 로컬 설정 2,173,444). 상한을 2,170,000 → 2,175,000 bytes로 올렸다(`devtools/bundle-size/budget.json` note).

## 재검토 조건

- **둘째 UI 언어를 여는 변경**(`isEntryLanguageAvailable`이 둘째 언어에 참) → 그 변경이 **호스트의 기기 언어 경로**(globalProps 키 — 예 iOS `Locale.preferredLanguages.first` · Android `LocaleList.getDefault()[0].toLanguageTag()`)와
  호스트 테스트를 함께 세우고, `loadReturningUiLanguage`의 기기 입력 `null`을 그 값으로 바꾼다(D5 · 보류 표 「기기 언어의 호스트 경로」). ADR-0031의 같은 재검토 조건(ui-lynx 문구 주입)과 같은 날이다.
- **3초가 짧다는 관측**(실기에서 기존 회원이 언어 선택을 보는 사례 · 판정 결과 측정을 붙인 뒤 시간 초과 비율이 눈에 띌 때) → 대기 시간과 Q3(판정 결과 이벤트)를 다시 정한다.
- **손님 프로필이 서버 프로필을 덮는 규칙을 고칠 때**(보류 표) → D3의 순서와 「프로필 행 = 기존 회원」의 귀결(대가 7)을 함께 본다.
- **판정에 쓸 서버 기록이 하나 더 생길 때**(예: 계정 수준의 「온보딩 완료」 표시) → D2의 「기존 RPC 둘」과 D4의 표를 다시 본다.
- **로그인 화면에 busy 가드가 생길 때** → 대가 4를 닫는다.
