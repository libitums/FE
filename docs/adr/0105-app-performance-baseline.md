# ADR-0105 — 앱 성능 기준선과 기기 측정 통로

- 상태: **채택 — 단계별.** 1단계(이 문서의 D1 · D2 · D3 — 기준선 · 측정 통로)가 먼저 들어가고, 2단계(D4 — 기준 안으로 줄이기) · 3단계(D5 — 스켈레톤)는 각자의 PR에서 적용 기록을 단다.
- 날짜: 2026-11-05.
- **사용자 결정**(2026-11-05): 「특정 기준선을 잡고 기준 이상이면 스켈레톤 뷰 등 뭐든 넣어야 한다」 → 기준선 **50 ms / 1초**, 순서 **측정 → 줄이기 → 스켈레톤**, 측정 통로는 **네이티브 로그 모듈**.
- 다루는 축: 백그라운드 JS가 한 번에 스레드를 막아도 되는 시간, 기다림이 길 때 보이는 피드백, 그 둘을 기기에서 재는 통로.
  **다루지 않는 것**: 번들 크기 예산(`devtools/bundle-size`), 개별 화면의 애니메이션 길이(모션 토큰).

## 맥락

1. **받기 중 탭이 늦었다**(2026-11-05 Android Galaxy A52s, 사용자 보고). 원인 하나는 카탈로그를 다시 만들 때마다 받아 둔 본문 전부를 다시 검증한 것이었다(#378, ADR-0071 적용 기록). 고친 뒤에도 편 하나마다 수 ms(Node) — JIT 없는 기기 엔진에서는 그 수십 배 — 의 반복 비용이 남는다 [추정].
2. **기기 로그(8분)**: 백그라운드 → 화면 갱신(`rLynxChange`) 약 5,000번, 받기 중 초당 최대 약 25번, 그중 바뀐 것 없는 갱신(`NoPatch`) 약 8,000번, 레이아웃 노드 파괴 약 3.7만 줄. 어느 컴포넌트인지는 로그로 가릴 수 없다.
3. **출시형 빌드의 JS `console`은 logcat에 찍히지 않는다** — 개발 도구 이벤트(`__OnBTSConsoleEvent`)로만 간다. 기기에서 잴 통로가 없었다.
4. ReactLynx에서 탭 처리(`bindtap`)는 받기 · 카탈로그 계산과 **같은 백그라운드 스레드**에서 돈다. 스레드가 막히면 스켈레톤을 띄우라는 명령도 늦게 처리된다 — 그래서 기준선은 「막지 않기」와 「기다림 피드백」 둘로 나눈다.

## 결정

### D1. 기준선

| 구분 | 기준 | 넘으면 |
|---|---|---|
| 한 번에 도는 동기 JS 작업(백그라운드) | **50 ms 이하** | 쪼개거나 · 모으거나 · 기억한다(D4). 측정 빌드는 넘는 작업을 이름과 시간으로 남긴다(D2) |
| 탭 반응(눌림 표시) | 100 ms 이내 | 눌림 표시는 메인 스레드에서 처리한다 |
| 탭 후 화면 전환 | 300 ms 이내 | 화면 틀을 먼저 띄우고 내용을 채운다 |
| 기다림 1초 이상 | **스켈레톤** | D5 |
| 기다림 10초 이상 | 진행률 | 받기(스플래시 게이지와 같은 방식) |

### D2. 측정 통로 — 네이티브 로그 모듈, 측정 빌드에서만

- Android 호스트 모듈 `PerfLogModule.log(line)` → `Log.i("DuruPerf", line)`. 줄 길이는 500자로 자른다. 어떤 실패도 던지지 않는다.
- JS `lib/perf-probe.ts`가 빌드 때 `PUBLIC_PERF_PROBE=1`이고 모듈이 있을 때만 켜진다. 꺼져 있으면 측정 함수는 감싼 함수를 그대로 부를 뿐이다(시간을 재지 않음).
  - `measureTask(name, fn)`: 동기 작업 하나의 시간 — **50 ms 이상**이면 `long name=<이름> ms=<시간>`을 남긴다.
  - `countRender(name)`: 컴포넌트가 커밋할 때마다 센다 — 5초마다 `renders <이름>=<횟수> …`를 남긴다.
- `.env.local`에 적지 않는다 — 측정 번들을 지을 때 명령 앞에만 붙인다(`PUBLIC_PERF_PROBE=1 pnpm bundle:android`, ADR-0087 D3의 테스트 버킷과 같은 규칙). 출시 빌드에 켜지지 않았는지는 번들에 문자열 `DuruPerf`가 아니라 env 치환값으로 확인한다(대가 2).
- iOS는 아직 없다 — 모듈이 없으면 JS가 아무것도 하지 않는다. iOS 측정이 필요해지면 같은 모양으로 더한다.
- 1단계 측정 지점: 카탈로그 읽기(`loadEpisodeContent`), 세션 병합, UI 언어 적용, 지도 구획 계산, 받기 차례 전체 · 본문 검증, 번역 받기, 음성 정보 파싱. 커밋 수: 셸(`AppSession`), 여정맵, 학습 셸, 컷(비주얼 노벨) 대사.

### D3. 측정 결과는 성능 보고서로 남긴다

- 기기 · 시나리오(새 설치 → 받기 중 지도 · 레슨 · 컷 화면 조작) · `DuruPerf` 로그 요약을 `docs/performance/reports/`에 남긴다. D4 · D5는 그 숫자를 근거로 한다.

### D4. (2단계) 기준 안으로 줄이기 — 측정 뒤 적용 기록

- 후보: 받기 중 다시 읽기를 모으기(편마다 → 일정 간격 · 차례 끝), 번역 디코드 · UI 언어 적용을 편 단위로 기억, 바뀐 것 없는 커밋(`NoPatch`) 줄이기.

### D5. (3단계) 스켈레톤 — 측정 뒤 적용 기록

- 후보 자리: 여정맵의 받는 중 구획, 레슨을 열 때 계획을 준비하는 순간, 오프라인 첫 실행의 카탈로그 대기.

## 대가

1. 측정 빌드는 출시 빌드와 다르다 — `measureTask`가 시간을 재는 비용(밀리초 해상도 `Date.now` 두 번)이 더해진다. 값은 근사다.
2. 출시 빌드에 측정이 켜지지 않게 막는 것은 빌드 명령 규칙뿐이다(ADR-0087 대가 3과 같은 결). 켜져도 사용자에게 보이는 것은 없고 logcat에 줄이 찍힐 뿐이다.
3. iOS는 측정하지 않는다(D2).

## 측정

이 문서 자체가 측정 장치다 — D3의 보고서가 결과다.
