# ADR-0050 — Android 상태바 아이콘 명암: 화면이 표지를 달고, 호스트가 Lynx 화면 갱신 콜백 안에서 트리를 읽어 맞춘다

- 상태: **채택.** 「화면에 표지, 호스트가 읽음」(U5) · 「첫 단원 안내 스크림 위는 밝은 아이콘」(U1) · 「연속 학습 모달의 운석을 상태바 아래로 내림」(B1)은 **사용자 결정이다**(2026-10-06 — 아래 「사용자 결정」).
  젬 구매 화면에 표지 없음(U3) · 표면 목록의 정정(U4)은 **묻지 않고 기본값으로 진행했다.**
  스크림 0.45 위의 어두운 아이콘 유지(U2)는 **2026-10-07 사용자가 수용했다**(실측 범위: API 30 실측 3.81 · API 31 ~ 36 미측정 — 질문에 그 범위를 적어 물었다). 처음에는 root가 기본값으로 진행했고 2026-10-06의 재보고에는 응답이 없었다 — 그 문면은 이 결정으로 대체된다(아래 「사용자 결정」).
  ⚠ **「표면과 아이콘이 같은 프레임에 바뀐다」는 처음의 목표는 Android에서 성립하지 않는다** — 확인한 Pixel/AOSP 에뮬레이터 이미지 둘(API 37 · API 30)에서 아이콘은 SystemUI가 120 ms 애니메이션으로 바꾼다(제조사 SystemUI는 확인하지 않았다). 기준을 「앱 안」과 「화면」 둘로 갈랐다(D7).
  ⚠ **화면 지연을 실제로 판정한 환경은 API 30 에뮬레이터 하나다.** 실기 · 호스트 GPU로 띄운 API 37은 재지 않았다.
  ⚠ **e2e의 세 번째 실행은 「제한적 passed」다**(test-runner, 2026-10-06). 기준 A는 PASS이고, 기준 B는 **API 30 에뮬레이터에서만** 판정됐다 — API 37은 지연 판정 0개, 판정 불가(환경)이며 통과가 아니다.
  수치와 그것을 누가 · 무엇으로 냈는지는 「확인한 것과 확인하지 못한 것」의 「e2e 실행 결과」가, 항목별 실행 상태는 [절차 문서](../e2e/android-status-bar-icons.md)의 「실행 상태」가 진다.
  ⚠ **API 31 ~ 36의 어두운 아이콘 색 · API 26 ~ 29의 적용 경로 · 실기 · 제조사 상태바 · `journey-entry`의 기기 화면은 확인하지 않았다.** iOS에서 내려간 운석은 시뮬레이터 한 기종 · dev 전용 번들 · 한 장면만 봤다(「확인한 것과 확인하지 못한 것」).
- 날짜: 2026-10-06
- 다루는 축: Android에서 앱의 창이 뜬 뒤 상태바 아이콘(시계 · 알림 · 신호 · 배터리)의 명암을 누가 · 언제 · 무엇을 보고 정하는가 ·
  화면(공유 JS)이 호스트에 「지금 상단 띠가 어둡다」를 알리는 접점 · 새 화면이 그 접점을 빠뜨리지 않게 하는 검사 · 전환 지연의 기준과 판정 환경 ·
  받아들인 대비의 범위
- 이어받는 결정: [ADR-0049](0049-android-launch-appearance.md) U1 · 「후속 과제」 1(이 전환을 후속 작업으로 분리했다 — 이 ADR이 그 작업이다. 스플래시 표면은 검정 아이콘 유지 · API 31+ 시작 창의 명암은 앱이 못 바꾼다는 것도 그대로 받는다),
  [ADR-0044](0044-android-tappable-inset.md)(edge-to-edge · 투명 시스템 바 — `MainActivity.layoutEdgeToEdge`가 기본 명암을 적는 자리),
  [ADR-0047](0047-android-orientation-config-changes.md) D2(`uiMode` · 화면 크기 변경에서 Activity를 다시 만들지 않는다 — D3의 수명 규칙이 이 위에 선다),
  [ADR-0017](0017-host-native-capabilities-and-audio.md) D1(호스트 모듈의 입장 조건 — **이 결정은 모듈을 더하지 않아 그 조건이 발동하지 않는다**),
  [ADR-0014](0014-design-system-consumption-verified.md) D7(다크 모드 제외).
  **바꾸는 결정은 없다.** iOS 호스트 · `packages/ui-lynx` · `AppSession.tsx` · 뒤로가기 스택 · safe area 전달 · 테마 리소스 · 매니페스트 · Gradle이 그대로다.
  공유 JS(`apps/mobile/src`)가 바뀌어 성능 보고서 게이트 대상이다 — [회차 하나](../performance/reports/android-status-bar-icons-app-launch-iphone-17-pro-simulator-01.md) · [전후 비교](../performance/reports/android-status-bar-icons-ab-app-launch-iphone-17-pro-simulator-05runs.md).

근거 표시는 작업 `android-status-bar-appearance`의 계약을 그대로 옮긴다. **[코드 확인]** 이 저장소의 파일을 읽었다 · **[바이트코드]** AAR의 클래스를 `javap`로, 기기의 SystemUI를 `dexdump`로 읽었다 ·
**[SDK 파일]** Android SDK의 소스 · `api-versions.xml`을 읽었다 · **[실측]** 2026-10-06, 에뮬레이터 두 대(Pixel_8 AVD · API 37, R6_API30 AVD · API 30)에서 잰 값(무손실 `screencap`의 픽셀 · 탐침 로그 · `dumpsys`) ·
**[계산]** 색 값에서 낸 대비(캡처 없음) · **[추론]** 관찰 없이 이어 붙였다.
어휘: **밝은 아이콘 / 어두운 아이콘**은 시계 · 아이콘 자체의 색이다. Android API의 `setAppearanceLightStatusBars(true)`는 「밝은 바」 = **어두운 아이콘**이라 뒤집혀 있다 — 이 문서와 코드의 이름은 전부 아이콘 색 기준이다.

## 맥락

1. **호스트는 아이콘 명암을 `onCreate`에서 한 번 고정했다** [코드 확인]. `MainActivity.layoutEdgeToEdge`가 `setAppearanceLightStatusBars(true)` · `setAppearanceLightNavigationBars(true)`를 부르고, 바꾸는 경로가 없었다.
2. **Android는 스스로 바꾸지 않는다** [실측 — API 37]. 어두운 표면(에피소드 표지의 띠 `#1B1613`) 위에서도 아이콘이 `#000000`이었고 창의 `apr=`는 어느 화면에서나 `LIGHT_STATUS_BARS`였다.
   어두운 표면의 색 쌍 대비는 구현 전 1.17 ~ 1.46:1이었다 [실측 — 접근성 점검이 저장된 캡처를 다시 잰 값]. 화면이 떠 있는 내내 시계 · 신호 · 배터리가 사실상 보이지 않는다 — 앞선 접근성 점검이 가장 무겁게 본 지적(A1)이다.
3. **어두운 표면은 route가 아니라 컴포넌트 단위로 갈린다** [코드 확인]. `episode-prologue`는 한 route 안에서 어두운 서사와 밝은 채팅 · 통화가 `segmentIndex`로 바뀌고, `episode-final`은 `stage`로 바뀐다 — **둘 다 화면 로컬 상태라 `AppSession` · `Nav`가 모른다.**
   지표 모달과 첫 단원 안내는 route가 아니라 밝은 화면 위에 뜨는 `position: fixed` 레이어다. 반대로 **떠 있는 동안 명암이 바뀌는 컴포넌트는 없다** — 컴포넌트가 떠 있으면 어두운 표면이다.
4. **요구사항이 센 「어두운 표면 8종」은 틀렸다** [코드 확인]. 젬 구매 화면(`GemPurchaseScreen`)은 제품에서 그려지지 않고(폴더 밖 import가 테스트 둘뿐), 디자인 단계가 최종 테스트의 서사 단계 · 표지 위 확인창 · 서사 위 안내를 더했다.
5. **iOS에는 이 일을 하는 코드가 없다** [코드 확인] — `apps/ios`(Pods 제외)에 `preferredStatusBarStyle` 등이 0건이다. 그런데 같은 route 안에서 서사일 때 흰 글자, 채팅일 때 검정 글자다.
   앱이 정하는 것이 아니라 시스템이 띠 뒤의 내용에 맞춰 고른다고 본다 [추론 — 코드 0건 + 캡처. 플랫폼 문서 · SDK 헤더에서 이 동작을 적은 문면은 찾지 못했다].
6. **내비게이션 바는 전환이 필요 없다** [실측 — API 37, 3버튼]. 어두운 화면 위에서도 시스템이 밝은 띠(`#E9E8E8`)를 깔고 어두운 버튼(`#666666`)을 그린다(약 4.7:1). 제스처 손잡이는 스스로 밝은 색으로 바뀐다.
7. **「어두운 아이콘」은 API 수준에 따라 다른 색이다** [실측 — 앞선 작업들의 캡처]. API 37은 검정 100%(`#000000`), **API 30은 검정 60%**(밝은 띠 위 `#666565`, 스크림 위 `#3D3D3D`)다. 밝은 아이콘은 두 기기 모두 `#FFFFFF`다.
   **API 31 ~ 36에서 어느 쪽인지는 모른다** — 캡처가 30과 37뿐이다.
8. **`AppSession.tsx`는 300줄이고 oxlint `max-lines`가 300이다** [코드 확인]. 이 파일에 한 줄도 더할 수 없다.

### D1. 화면이 마크업 표지를 달고, 호스트가 Lynx UI 트리에서 읽는다 (사용자 결정 U5)

```text
[JS] 상단 띠를 어둡게 칠하는 면의 요소에 표지 하나
       <view className="episode-intro-screen" data-statusbar={lightStatusBarIcons}>     ← 값 "light-icons"
[Android] LynxViewClient.onFirstScreen / onPageUpdate (메인 스레드, 같은 콜 안에서 — post하지 않는다)
       StatusBarIconSync.sync(lynxView)
         ├ Lynx UI 트리를 걸으며 getDataset()["statusbar"] 값을 모은다
         ├ StatusBarIcons.toneFor(값들)  (순수)  — "light-icons"가 하나라도 있으면 LIGHT, 없으면 DARK
         └ 직전에 적용한 명암과 다를 때만 setAppearanceLightStatusBars(!LIGHT)
[iOS] 표지는 읽는 쪽이 없는 속성이다. 호스트 변경 0 — 시스템이 지금처럼 스스로 고른다.
```

- **기본값은 어두운 아이콘이다**(표지 없음 = 이 변경 전의 동작). 스플래시 · 밝은 화면 · 스크림 0.45는 표지를 달지 않는다.
- **규칙은 「표지가 하나라도 있으면 밝은 아이콘」이다. 개수를 보지 않고 스택을 두지 않는다.** 지금 있는 겹침은 「어두운 화면 + 스크림」과 「밝은 화면 + 어두운 층」뿐이라, 층이 닫히면 남은 표지의 유무가 곧 아래 표면의 명암이다.
  스택이 필요한 경우(어두운 화면 위에 **밝고 불투명한** 층)는 지금 없다.
- **JS 쪽에는 로직이 없다** [코드 확인]. `apps/mobile/src/lib/status-bar-icons.ts`는 타입 하나와 상수 하나(`lightStatusBarIcons = "light-icons"`)다 — 함수 · 훅 · 스토어 · 네이티브 호출을 두지 않는다.
  새 토큰 · 문구 · testid · `Screen` 멤버 · `NavAction` · 네이티브 모듈 · 분석 이벤트가 0건이다.
- **속성 이름은 한 낱말이다.** `data-*` 속성이 Android의 `LynxBaseUI.getDataset()`에 `data-` 없는 키로 실리는 것을 잰 것은 `data-testid` → `testid` 하나다 [실측]. 여러 낱말 키가 어떤 모양이 되는지는 재지 않았다.
- **「호스트가 마크업의 dataset을 읽는다」는 이 저장소에서 처음 쓰는 패턴이다.** `getDataset` · `onPageUpdate`는 둘 다 public API이고 [바이트코드 — lynx 4.0.1], 이 호스트는 `AccessibilityTapBridge`로 이미 같은 콜백 · 같은 트리 걷기를 쓰고 있었다 [코드 확인].
- 비용 [실측 — API 37, 계약 단계의 탐침]: 트리 걷기 37 µs(42노드 · 200회 7.3 ms), 적용 호출 0.8 ms. 여정 맵(170 ~ 171노드)에서 `sync` 200회 평균은 계측 실행마다 12 ~ 437 µs였고 최종 검증의 실행에서는 499 µs였다(예산 4 ms — 계측 HI7).

### D3. 호스트 — 순수 판정 · 트리 읽기 · 결선. 기본값과 내비게이션 바는 그대로다

- `StatusBarIcons.java`(Android · Lynx import 0): 상수 `DATASET_KEY = "statusbar"` · `LIGHT_ICONS = "light-icons"`, `Tone { DARK, LIGHT }`, `toneFor` · `lightStatusBarsFlag` · `needsApply`. 빈 목록 · `null` · 모르는 값은 DARK이고 던지지 않는다.
- `StatusBarIconSync.java`: `lynxView.getLynxUIRoot()`에서 `getChildren()`을 따라 걷고 `LIGHT_ICONS`를 만나면 멈춘다. 루트가 `null`이면 직전 명암을 둔다. 「직전에 적용한 명암」의 초기값은 DARK다.
  적용은 `WindowCompat.getInsetsController(...).setAppearanceLightStatusBars(...)` 하나다 — **내비게이션 바 메서드는 부르지 않는다**(맥락 6).
- `MainActivity`: `layoutEdgeToEdge`는 **그대로**다. `onFirstScreen` · `onPageUpdate` **안에서 곧바로** `statusBarIcons.sync(lynxView)`를 부른다. **`post`로 미루지 않는다** — 미루면 62 ~ 210 ms 늦는다 [실측 — 계약 단계의 탐침]. 기존 `AccessibilityTapBridge.sync`의 `post`는 건드리지 않았다.
- 수명:
  - 번들이 뜨기 전 · 로드 실패 · JS 스플래시는 기본값(어두운 아이콘)으로 선다.
  - `uiMode` · 화면 크기 구성 변경과 HOME → 복귀에서는 호스트가 아무것도 다시 하지 않아도 값이 남는다 [실측 — `dumpsys`의 `apr=`].
  - 재생성(글꼴 배율 등) 뒤에는 `onCreate`의 기본값에서 시작하고 JS가 다시 그린 화면의 표지를 따라간다 [실측 — 재생성 뒤 `LIGHT_STATUS_BARS` 복귀].
  - API 31+ 시작 창의 아이콘 명암은 플랫폼이 정한다 — 이 결정이 바꾸지 않는다([ADR-0049](0049-android-launch-appearance.md) 「이 작업이 만든 변화」). **API 31+에서 실행할 때 흰색 → 검정으로 한 번 뒤집히는 것은 이 작업 뒤에도 남는다.**
- `androidx.core` 1.15.0의 `WindowInsetsControllerCompat`은 API 26 ~ 29에서 `decorView`의 `SYSTEM_UI_FLAG_LIGHT_STATUS_BAR`를, API 30 ~ 34에서 그 플래그와 `setSystemBarsAppearance`를 둘 다, API 35+는 `Impl35`를 쓴다 [바이트코드]. 실제 동작을 본 것은 API 30과 37이다.

### D5. 연속 학습 모달의 운석 c를 상단 inset 아래로 내린다 (사용자 결정 B1)

- **무엇이 문제였나** [코드 확인 · 실측 — 접근성 점검이 저장된 캡처를 다시 잰 값]. 지표 모달의 장식 층은 `position: absolute; top: 0`이라 모달의 inset padding을 따르지 않는다. 운석 셋 가운데 c가 `right: 21px; top: -17px`(86 × 86)이어서 **상태바 띠 안에** 놓였고, Wi-Fi · 배터리 · 셀룰러 아이콘 바로 뒤가 브랜드 주황 `#F46B18`이었다.
  D1로 아이콘이 흰색이 되면서 그 자리의 색 쌍이 **흰색 / 주황 = 3.016:1**(여유 0.016)이 됐다 — 구현 전 그 자리는 검정 / 주황 6.96:1이었으므로 **이 자리만은 이 작업이 나쁘게 만들었다**(모달의 나머지 띠는 1.46 → 14.36으로 좋아졌다). [ADR-0049](0049-android-launch-appearance.md)가 스플래시에서 피한 색 쌍이 모달이 떠 있는 내내 생긴다.
- **결정**: 운석 c의 상자 위쪽 끝을 상단 safe area inset과 같게 둔다. `JourneyStatModal`이 c에만 인라인 ``style={{ top: `${insets.top}px` }}``를 주고(이미 읽고 있던 `insets`), CSS의 `.journey-stat-modal-meteor-c`에서 `top`을 뺐다 [코드 확인]. `right: 21px`과 크기, **운석 a · b와 장식 층은 그대로다.**
- 표지 · 호스트 · 명암 규칙은 바뀌지 않는다. 이 모달에서만 아이콘을 어둡게 돌리지 않는다(시계 쪽이 1.46으로 돌아간다).
- **iOS에서도 이 한 곳은 바뀐다.** 같은 JS · CSS가 iOS에도 실리고, c가 iOS의 `insets.top`만큼 내려간다(iPhone 17 Pro 시뮬레이터에서 62pt — 아래 「iOS 관찰」).
  **요구사항의 「iOS 동작 불변」은 이 장식 하나에 한해 사용자 결정으로 예외다.** iOS 호스트 파일 변경 0 · 상태바 스타일은 시스템이 고른다는 것은 그대로다.
- **iOS 관찰** [실측 — test-runner, 2026-10-06. iPhone 17 Pro 시뮬레이터(iOS 26.5) · Debug 호스트 · **dev 전용 playground 번들** · 스트릭 0 한 장면].
  - 변경 뒤: 운석 c는 상태바 · 다이내믹 아일랜드 아래에 있다 — 주황의 맨 위가 약 79pt이고, inset 62pt 위의 주황 픽셀이 0이다. 뒤로 버튼 · 불꽃 · 큰 숫자 · 운석 a · b와 겹치지 않는다.
  - 변경 전(`dca104d8`의 번들, 같은 시뮬레이터 · 같은 화면): 운석이 Wi-Fi · 배터리 아이콘을 덮었다(inset 위 주황 픽셀 10185). **Android의 B1 결함이 iOS에도 있었고 같은 변경이 고쳤다.**
  - 한계: playground 번들은 dev 전용이고 **제품 `main` 번들이 아니다**(모달 컴포넌트 · CSS는 같은 소스다). 한 기종 · 한 장면만 봤다 — 로그인 뒤의 제품 경로 · inset이 다른 기종 · 다른 스트릭 값은 보지 않았고, iOS 상태바 글자의 색 · 대비는 재지 않았다.

### D7. 전환 지연 — 「앱 안」은 판정하고, 「화면」은 하드웨어 가속 조건에서만 판정한다

**정정: 계약과 디자인의 처음 전제가 틀렸다.** 「목표 같은 프레임 · 디자인 상한 100 ms · 한계 300 ms」는 표면과 아이콘이 같은 프레임에 바뀔 수 있다는 전제 위에 있었다. Android에서 그 전제는 성립하지 않는다(아래 근거가 닿는 범위는 Pixel/AOSP 에뮬레이터 이미지 둘이다):

- 표면은 앱이, 아이콘은 SystemUI 프로세스가 그린다. 아이콘 색은 **120 ms 애니메이션**(`LINEAR_OUT_SLOW_IN`)으로 바뀐다 [바이트코드 — Pixel/AOSP 에뮬레이터 이미지 둘(API 37 · API 30)에서 꺼낸 SystemUI dex. **제조사 SystemUI는 확인하지 않았다** — 거기서 길이가 같은지 모른다].
- 앱이 바꾼 플래그는 즉시 나가지 않고 다음 traversal의 `relayoutWindow`에서야 창 속성으로 나간다 [SDK 파일 — `ViewRootInsetsControllerHost` · `ViewRootImpl`]. 한 프레임(9 ~ 35 ms, 중앙 19 ~ 20)이고 앱이 줄일 수 없다 [실측].
- Lynx는 `onPageUpdate`를 그 패치를 그린 draw **뒤에** 부른다(같은 vsync 안, 1 ~ 11 ms) [실측 — draw 시각과 영상의 한 프레임 차. Lynx 소스에서 호출 자리를 읽지는 않았다].
- 그래서 API 30 에뮬레이터(호스트 GPU)에서 잰, 아이콘이 다 바뀔 때까지의 바닥은 **약 150 ~ 160 ms**이고 그 가운데 앱 몫은 약 17 ms다 [실측 — API 30 에뮬레이터 하나. 실기 · 다른 API 수준의 하드웨어 가속 값은 없다].

계약 r01이 적은 「상태바에 그려지기까지 한두 프레임」도 틀렸고, 「UI 패치와 같은 메인 스레드 콜 안」은 정확히는 「패치를 **그린 뒤의** 콜」이다. 디자인 문서의 그 규칙 둘은 고치지 않았다 — 계약이 우선하고, 아래 두 기준으로 읽는다.

**기준 A — 앱 안(판정한다).**

> 표지가 생기거나 사라진 화면 갱신의 `onPageUpdate` 콜 안에서 `setAppearanceLightStatusBars`가 불린다 — 같은 메인 스레드 콜, 16 ms 이하. 그리고 표지는 그 표면의 루트 요소(또는 등록부의 기준 요소)와 같은 패치로 붙는다.

- 지금 값 [실측 — 진단 단계, API 37 54회 · API 30 26회]: 콜백에서 적용 호출까지 **0.04 ~ 5.15 ms**(탐침의 부담 포함 — 상한으로 읽는다). 여기에 플래그가 창 속성으로 나가는 **한 프레임**이 붙는다.
- 이 기준은 렌더러 · 호스트 부하와 무관하게 선다. 앱이 책임지는 것은 여기까지다.
- **지키는 것은 둘이다.**
  - 정적 규칙 `host-wiring`(SM15 · HS1): `MainActivity`의 두 콜백이 `post` 밖에서 `sync`를 부르고, `StatusBarIconSync.java`에 `post(` · `postDelayed(` · `Handler` · `Executor` · `new Thread`가 없다. `pnpm verify`에서 돈다.
  - 계측 **HI8**: 테스트가 자기 `LynxViewClient`를 더해 그 `onPageUpdate` **안에서** 트리의 명암과 창의 플래그를 견준다. 맵 → 표지 → 뒤로 → 지표 모달 열기 → 닫기 동안 어긋난 콜 0회 · 명암이 바뀐 콜 4회 이상.
    적용을 `post`로 감싼 변이에서 HI8은 실패했고(어긋남 3 ~ 4), 그 변이에서 HI1 ~ HI7은 통과했다 [실측 — test-design의 보고, API 37. **원본 로그가 남아 있지 않다** — 남은 것은 작업 증거의 요약 한 줄이고, 리뷰는 HI8의 구분력을 테스트 코드 읽기로 확인했다] — **HI2 ~ HI6은 50 ms 폴링 · 상한 8초라 「같은 콜」을 증명하지 못한다.**
- **HI8의 한계.**
  - Lynx가 클라이언트를 더한 순서대로(앱의 것 먼저) 부른다는 전제에 선다. 계약은 이것을 [추론]으로 적었고, 그 뒤 test-design이 Lynx AAR 4.0.1에서 확인했다 [바이트코드 — `LynxViewClientGroup`이 `CopyOnWriteArrayList`에 더한 순서대로 같은 스레드에서 부른다]. Lynx를 올리면 다시 본다. 순서가 반대가 되면 명암이 바뀌는 콜마다 어긋나 **시끄럽게 실패한다** — 조용히 통과하지 않는다.
  - **실행값 `toneChanges=4`가 단언의 하한 4와 같다 — 여유가 0이다** [실측 — API 37 · API 30 모두 `calls=10 toneChanges=4 mismatched=0`. test-runner, 세 번째 e2e 실행]. 이 수는 Lynx가 화면 갱신을 지금처럼 묶어 콜백을 부를 때의 값이다. 묶는 방식이 바뀌어 명암이 바뀐 콜이 줄면 제품이 그대로여도 이 단언이 실패한다 [추론].
  - 계측은 에뮬레이터가 필요해 `pnpm verify`에 없다.

**기준 B — 화면(조건부로 판정한다).**

> 렌더링이 정상인 기기에서, 표면이 바뀐 프레임부터 아이콘 색 전환의 시작까지 100 ms 이하 · 끝(시계 명암이 맞는 프레임)까지 300 ms 이하.

- **조건(둘 다)**: `dumpsys SurfaceFlinger`의 `GLES:` 줄에 `SwiftShader`가 없다 · 영상에서 전환 직후 프레임 간격의 중앙이 25 ms 이하.
- 조건이 서지 않으면 **FAIL이 아니라 「판정 불가(환경)」** 로 적고 값만 기록한다. PASS로 세지 않는다.
- 「같은 프레임」은 끝에 걸 수 없다(120 ms 애니메이션). 걸 수 있는 것은 시작이다.
- 한 전환에 명암 변화 1회 이하 · 같은 명암끼리 0회 · 닫힌 뒤 복귀는 **조건 없이 판정한다** — 순서와 횟수는 프레임이 느려도 읽힌다.
- **이 기준을 실제로 판정하는 곳은 API 30 에뮬레이터(호스트 GPU) 하나뿐이다.** `emulator-5554`(API 37)는 SwiftShader(CPU 소프트웨어 렌더링)로 떠 있었고 [실측 — `dumpsys SurfaceFlinger`], 그렇게 뜨는 한 거기서는 늘 「판정 불가」다. API 30에서도 조건이 서지 않으면 그 실행에서 기준 B는 **판정되지 않은 것**으로 보고한다 — 통과가 아니다.

실측 [진단 단계 — 탐침 빌드 + SurfaceFlinger의 상태바 레이어 프레임. 탐침은 일회용 사본에서만 만들었고 제품에 들어 있지 않다]:

| | API 30(호스트 GPU) · 26회 | API 37(SwiftShader) · 54회 |
|---|---|---|
| 콜백 → 적용 호출 | 두 기기 합쳐 0.04 ~ 5.15 ms | 〃 |
| 적용 → 플래그가 나가는 traversal | +5 ~ +30 ms(중앙 17) | +1 ~ +35 ms(중앙 13) |
| 상태바 프레임 간격(중앙) | 16 ~ 18 ms | 71 ~ 223 ms(전체 중앙 100) |
| **적용 → 아이콘 마지막 프레임** | **153 ~ 180 ms**(중앙 166) | 389 ~ 1124 ms(중앙 573) |
| 표면 프레임 → 아이콘 첫 프레임 | −9 ~ +32 ms(중앙 +28) | −346 ~ +208 ms(중앙 +106) |
| 표면 프레임 → 아이콘 마지막 프레임 | +126 ~ +174 ms(중앙 +161) | +1 ~ +1082 ms(중앙 +502) |

SwiftShader에서도 앱 안의 값은 그대로였다 — 「앱이 늦게 바꾼다」는 회귀는 기준 A가 어느 환경에서나 잡고, 잡히지 않는 것은 「플랫폼 · SystemUI 쪽이 느려졌다」뿐이며 그것은 앱의 통제 밖이다.

**가려지지 않은 인과(리뷰의 유보).** 같은 `emulator-5554`가 첫 e2e 실행에서는 프레임 간격 17 ~ 21 ms였고, 그때의 렌더러 기록은 없다. 그래서 API 37에서의 지연이 「SwiftShader라서」인지 「호스트 부하 때문」인지는 가려지지 않았다 — 어느 쪽이든 앱 밖이다(그 조건에서도 앱 안의 값은 위와 같았다).
부하가 원인이라면 기준 B의 렌더러 줄 조건은 판정할 수 있는 환경까지 배제할 수 있다.

### D8. 새 화면의 규칙과 빠뜨림을 막는 검사

> **상단 띠를 스스로 칠하는 면(가장자리까지 까는 화면 · `position: fixed` 레이어 · 0.45가 아닌 스크림)을 만들면, 띠에서 가장 밝은 지점의 합성색 휘도가 0.18 이하일 때 표지를 단다. 달지 않으면 어두운 아이콘이다.**

- 휘도가 0.18 ~ 0.49 사이인 상단 띠는 만들지 않는다(60% 검정 기기에서 어느 쪽으로도 시계 4.5:1이 서지 않는다). 지금 그 범위에 있는 것은 스크림 0.45 · 첫 단원 안내 0.6 · 스플래시 셋이다.
- 그림을 상단까지 깔 때는 256px 명암 또는 Fog(dark)를 얹는다.
- **검사**: `devtools/android-bundle/host-status-bar-icons.mjs`의 `statusBarMarkerIssues`(순수 함수)와 등록부 `statusBarSurfaceRegistry`가 `pnpm test:android-bundle`(= `pnpm verify`)에서 돈다. 규칙은 아홉이다 [코드 확인].

  | rule | 위반 조건 |
  |---|---|
  | `marker-value` | JS 상수의 값과 `StatusBarIcons.LIGHT_ICONS`가 다르거나 어느 한쪽을 못 찾는다 |
  | `marker-key` | 컴포넌트가 쓰는 속성 이름에서 `data-`를 뗀 것과 `StatusBarIcons.DATASET_KEY`가 다르다 |
  | `carrier` | 등록부가 표지를 요구하는 파일에 표지가 없다. 기준 클래스가 있는 파일은 그 `className`과 같은 여는 태그 안에 있어야 한다 |
  | `stray-marker` | 등록부 밖의 파일에 `data-statusbar`가 있다, 또는 값이 상수가 아닌 리터럴 · 조건식이다 |
  | `full-bleed-registry` | `isFullBleedScreen`의 route 집합이 등록부의 `fullBleedRoutes`와 다르다 |
  | `fixed-layer-registry` | `position: fixed`를 선언한 CSS 파일 집합이 등록부의 `fixedLayers`와 다르다 |
  | `host-wiring` | `MainActivity`가 두 콜백에서 `sync`를 직접 부르지 않는다, 또는 `StatusBarIconSync`가 적용을 미루는 수단을 쓴다 |
  | `host-default` | `layoutEdgeToEdge`의 기본값 둘이 없다, 또는 호스트 어디든 `setAppearanceLightNavigationBars(false)`가 있다 |
  | `band-decor` | 운석 c의 CSS에 `top` 선언이 있다, 또는 TSX에서 그 `top`이 `insets.top`에서 오지 않는다 |

- **이 검사는 「분류됐는가」만 본다. 「어두운 색을 칠했는가」를 보지 못한다.** 분류는 사람이 위 한 줄 규칙으로 한다. 보지 못하는 것:
  이미 분류된 면의 색이 나중에 바뀌는 경우(스크림 값 · 그림 · 장식) · 띠 안에 놓이는 다른 장식(`band-decor`는 운석 하나만 본다) · 가장자리까지 깔지도 `position: fixed`도 아닌 방식으로 띠를 칠하는 길(지금은 셸 배경 클래스 `app-splash` · `app-call`뿐).
  색을 보는 것은 [절차 문서](../e2e/android-status-bar-icons.md)의 캡처 판정뿐이다.
- **스캔 범위 밖에 있는 것** [코드 확인 — `devtools/android-bundle/host-status-bar-icons.mjs`와 그 통합 테스트가 넘기는 입력].
  - `fixed-layer-registry`는 `apps/mobile/src` 아래 CSS 파일의 `position: fixed` 선언만 본다. **`packages/ui-lynx`의 CSS(`dialog.css` · `bottom-sheet.css` · `overlay.css`가 `position: fixed`를 선언한다)와 TSX의 인라인 `style`로 준 fixed는 스캔하지 않는다** — 그 길로 띠를 칠하는 층이 생기거나 바뀌어도 등록부는 모른다.
  - `host-wiring`은 `MainActivity`의 두 콜백 본문과 `StatusBarIconSync.java`의 문면만 본다. **`sync`가 다른 클래스에 위임하고 그 클래스가 적용을 미루는 간접 경로는 정적 검사에 걸리지 않는다 — 잡는 것은 계측 HI8뿐이다**(에뮬레이터가 필요해 `pnpm verify`에 없다).

## 버린 대안

**방식** — 요구사항의 세 방식에 조사 중 찾은 넷째(채택한 것)를 더해 견줬다.

- **(a) 화면 · 층이 선언하는 훅 + 스택 → 새 호스트 모듈.** 성립한다(뒤로가기의 선례). 버린 이유: 채택한 방식보다 JS 다섯 파일 · 네이티브 모듈 하나가 더 들고 얻는 것이 없다.
  새 모듈은 [ADR-0017](0017-host-native-capabilities-and-audio.md) D1의 입장 조건을 다시 통과시켜야 하고, `AppSession.tsx`(300줄 한도)를 건드려야 한다.
  **새 경합도 생긴다** — 언마운트 정리는 diff 중 동기로, 마운트 effect는 그 뒤 마이크로태스크로 돈다 [SDK 파일 — `@lynx-js/react` 0.125.0]. 어두움 → 어두움 교체에서 스택이 잠깐 비어 「기본값으로 갔다가 다시」가 나오고, 그것을 합치는 장치가 따로 든다.
  JS 스레드 → 모듈 → 메인 `post`의 지연은 재지 않았다 [추론: 수십 ms].
- **(b) 중앙 표에서 파생.** **성립하지 않는다** — 단계(`segmentIndex` · `stage`)와 모달 열림이 화면 로컬 상태다(맥락 3). 표를 쓰려면 그 상태를 `ScreenWiring`으로 끌어올려야 한다.
- **(c) 호스트가 상단 띠의 픽셀을 표본해 스스로 정한다.** 공유 JS 변경 0 · 빠뜨릴 수 없다는 것이 이점이다. 버린 이유 [실측 — API 37]: 표본 한 번이 5.5 ms(최대 47 ms, 1/8로 줄이면 오히려 10.1 ms)로 트리 걷기의 150배이고, 그리는 프레임마다 걸어야 해 애니메이션이 도는 화면에서 계속 든다.
  그린 뒤 표본하므로 뒤집힘이 표면 교체보다 늘 늦는다 [추론]. **띠 안에 앱의 그림이 들어오는 표면이 실제로 있어**(연속 학습 모달의 주황 운석 — 계약 단계의 판독 도구가 그것을 아이콘으로 읽었다) 밝기 판정이 내용에 흔들리고, 문턱 근처(스크림 0.6)에서 떨린다.

**전환 지연을 앱에서 줄이는 방법 셋** — 진단이 견줬고 채택하지 않았다.

- **표지 판독을 `onPageUpdate`보다 앞으로 옮긴다.** 얻는 것이 150 ms 바닥에서 최대 한 프레임(약 17 ms)이다. Lynx의 UI 반영 시점에 끼어드는 공개 훅이 없다.
- **전환을 미리 알린다**(JS가 화면을 바꾸기 전에 명암을 먼저 요청). 이전 표면 위에서 아이콘이 먼저 뒤집혀 **안 보이는 구간이 생긴다**(밝은 맵 위 흰 아이콘). 표지 한 군데로 모은 구조도 깨진다.
- **서사 화면의 시작 부하를 줄인다**(페이드 · 확대를 한 프레임 늦춘다). 연출 변경이라 범위 밖이고, 하드웨어 가속에서는 효과가 10 ms 안이다.

**운석(B1)**

- **장식 층 전체를 inset만큼 내린다.** 운석 a · b의 자리가 모든 기기에서 inset만큼 바뀌고, c는 그래도 `top: -17px`이라 띠에 17px 걸친다.
- **이 모달에서만 아이콘을 어둡게 돌린다 · 운석의 색을 바꾼다.** 시계 쪽이 1.46으로 돌아간다.
- **다음 작업으로 넘기고 3.02를 받아들인 값으로 적는다.** 접근성 점검이 낸 다른 선택지였다. 사용자가 이 작업에 넣기로 했다.

**첫 단원 안내(U1)**

- **어두운 아이콘 유지**(계약의 첫 기본값). API 37에서는 4.47 ~ 4.67로 비슷하지만 API 30 계열에서 2.88 ~ 2.96이다.
- **스크림을 0.65로 올린다.** 밝은 아이콘이 세 바탕 모두에서 4.5를 넉넉히 넘는다. 화면 디자인 변경이라 범위 밖이다.

## 대가

- **호스트가 Lynx의 `LynxBaseUI.getDataset()` · `LynxViewClient.onPageUpdate()` · 클라이언트 호출 순서에 기댄다.** Lynx를 올리면 깨질 수 있고, 그것을 잡는 계측(`StatusBarIconsHostTest`)은 에뮬레이터가 필요해 `pnpm verify`에 없다.
- **새 어두운 화면에서 표지를 잊으면 조용히 어두운 아이콘이 된다**(이 변경 전의 동작). 등록부 검사는 분류의 유무만 강제한다(D8).
- **아이콘은 표면보다 늦게 바뀐다.** API 30 에뮬레이터(호스트 GPU) 실측으로 다 바뀔 때까지 약 150 ~ 160 ms이고 앱이 줄일 수 있는 것은 그 가운데 한 프레임이다(D7). 실기 값은 없다.
- **화면 지연의 기준은 하나의 에뮬레이터에서만 판정된다.** 그 환경이 없으면 기준 B는 판정되지 않은 채 남는다.
- **받아들인 값 셋이 남는다**(D6). 스크림 0.45 위의 시계는 범위가 「다수 기기」일 수 있다.
- **iOS에서 운석 하나의 자리가 바뀌었다.** 그 결과를 본 것은 시뮬레이터 한 기종 · dev 전용 번들 · 한 장면이다(D5의 「iOS 관찰」).
- **`StatusBarIconSync`는 트리 읽기에서 난 `RuntimeException`을 삼키고 직전 명암을 유지한다** [코드 확인 — `sync`의 `catch (RuntimeException e) { return; }`]. 해체 중인 트리가 화면 갱신을 멈추지 않게 하려는 것이고 열화 방향은 「이전 명암 유지」다.
  **로그를 남기지 않는다** — 예외가 계속 나면 명암이 조용히 굳고, 그것을 잡는 것은 계측(`StatusBarIconsHostTest`)뿐이다. 리뷰는 이것을 계약에 없는 추가로 보고 DEBUG 로그를 권했다(하지 않았다).
- **등록부 검사는 `packages/ui-lynx`의 fixed 층 · 인라인 fixed · `sync`의 간접 미루기를 보지 못한다**(D8의 「스캔 범위 밖에 있는 것」).
- **API 31+의 실행 때 뒤집힘은 그대로다**(D3).
- **성능 보고서의 측정은 표지가 달린 요소를 하나도 그리지 않는 시나리오다**(로그인 전 초기 로드). 표지 속성을 요소에 싣는 비용과 Android 호스트의 비용은 그 보고서의 범위 밖이다.

**e2e 실행 결과 — 세 번째 실행, 「제한적 passed」**(2026-10-06). 수치마다 누가 · 무엇으로 냈는지가 다르다.

- **기준 A: PASS** [test-runner의 실행] — 정적 규칙 `host-wiring`과 계측 HI8(`mismatched=0`, API 37 · API 30).
- **기준 B는 API 30 에뮬레이터(호스트 GPU)에서만 판정됐다.** 같은 영상에 수치가 둘 있다.
  - **test-runner의 실행 판정**(그 실행 때의 판정 도구): 영상 18개 · 전환 10가지가 PASS(시작 +19 ~ +66 ms · 끝 +99 ~ +166 ms), 1개는 판정 불가(환경).
    그 도구는 환경 조건을 영상 **전체**의 프레임 간격으로 봐서 전환 직후 간격이 25 ms를 넘는 둘도 PASS로 냈다 — 엄격하게는 16개다.
  - **저장 영상의 재판정**(기기 없음 — 에뮬레이터를 띄우지 않았다): 환경 조건을 계약대로 「전환 직후 0.5초」로 고친 HEAD의 판정 도구로 test-runner가 다시 냈다.
    지연이 판정된 영상 **17개 · 전환 10가지 · 시작 +19 ~ +60 ms(한계 100) · 끝 +99 ~ +142 ms(한계 300) · FAIL 0**이다. 위의 18개에서 둘이 판정 불가(환경)로, 하나가 PASS로 바뀌었다.
- **API 37(SwiftShader)은 지연 판정 0개 — 판정 불가(환경)다.** 통과로 세지 않는다. 두 번째 실행의 FAIL 4건도 같은 분류로 바뀐 것이지 통과한 것이 아니다.
- 순서 · 깜빡임은 조건 없이 판정했고 제품 쪽 FAIL은 0이다(API 37의 순서 FAIL 2건은 조작 타이밍 탓이라고 test-runner가 기록했다).
- **구현을 늦춘 변이로 기준 B가 실패하는 것을 본 실행은 없다**(리뷰) — 한 프레임짜리 미루기는 기준 B의 여유 안에 들 수 있고, 그 회귀는 기준 A가 진다.

**측정 정의의 정정.** 계약의 첫 정의는 배경을 「띠의 빈 구역에서 가장 밝은 픽셀」로 잡았고, 그림이 겹치는 표면은 판정에서 뺐다. 그 결과 가장 나쁜 자리(연속 학습 모달의 아이콘 뒤)를 재지 않았고 첫 e2e 실행이 그 표면을 14.36 PASS로 냈다 — **틀린 PASS였다**(접근성 점검이 반증했다).
지금의 정의는 **글리프 묶음(시계 · 알림 · 셀룰러 · Wi-Fi · 배터리)마다, 그 묶음에 인접한 배경의 최악 픽셀**이다. 시계 묶음은 4.5 이상, 아이콘 묶음은 각각 3.0 이상이다.

## 미확인 · 후속

1. **API 31 ~ 36 가운데 한 수준(33 또는 34)에서 어두운 아이콘의 색을 잰다.** D6의 스크림 0.45 범위 문면과 D4의 무게가 여기에 달려 있다 — 60% 검정이 API 30 이하에만 있다면 영향 범위가 좁다.
2. **출시 전 실기 확인.** 전환 지연의 체감과 수치, 제조사 상태바(글리프의 자리가 달라 운석 c와의 겹침이 달라질 수 있다), `journey-entry` 한 장, TalkBack을 켠 채 맵 → 표지 한 번.
   ⟨2026-10-07⟩ 사용자가 실기에서 볼 수 있는 것(전환 지연의 체감 · 제조사 상태바 · 1의 어두운 아이콘 색 · 10의 Android 8 ~ 10)은 [Android 출시 설정 절차](../e2e/android-release-config.md)의 「R9 — 6. 확인 목록」에 **권고 묶음**으로 넣었다 — 출시 조건으로 정해진 것이 아니다.
3. **API 37을 호스트 GPU로 띄워 화면 지연을 잰다.** 진단은 떠 있는 에뮬레이터를 다시 띄우지 않았다 — 첫 e2e 실행의 저장된 프레임 표(간격 17 ~ 21 ms)가 간접 근거일 뿐이다. `emulator-5554`가 왜 SwiftShader로 떴는지도 모른다(`hw.gpu.mode=auto` — 같은 맥에서 API 30은 호스트 GPU로 떴다). 지연의 원인이 렌더러인지 호스트 부하인지도 여기서 가려진다(D7의 「가려지지 않은 인과」).
4. **iOS의 남은 확인.** 시뮬레이터 한 기종 · dev 전용 playground 번들 · 스트릭 0 한 장면은 봤다(D5의 「iOS 관찰」). 제품 `main` 번들(로그인 뒤) · inset이 다른 기종 · 다른 스트릭 값 · 상태바 글자의 색은 보지 않았다.
5. **내려온 운석 c가 아래에 깔린 여정 맵의 알림 벨 위에 놓인다** [실측 — 구현 뒤 실행 기록의 관찰, API 37]. 구현 전에는 그 벨이 보였다. 장식 층이라 눌리는 요소가 아니라고 봤으나 터치는 해 보지 않았다. 디자인 단계의 확인이 없다(D5의 「새 자리는 디자인 실측값이 아니다」와 같은 뿌리다).
6. **채팅 → 서사 전환이 느린 렌더러에서 일관되게 더 늦는 까닭.** 서사 화면의 시작 부하(전체 화면 그림의 900 ms 페이드 · 확대)가 SystemUI의 프레임을 밀어낸다는 것은 대조 실험 없이 낸 추론이다. 저사양 실기에서 같은 일이 생기는지 모른다.
7. **알림 탭 경로(`PushNotificationTapActivity`)의 주황 시작 창**은 이 작업이 다시 보지 않았다 — [ADR-0049](0049-android-launch-appearance.md) 「후속 과제」 1이 함께 닫으라고 넘긴 둘 가운데 열려 있는 쪽이다(접근성 점검).
8. **디자인 값 수준의 해결**(안내 스크림 0.6 → 0.61 이상 · 공용 스크림 토큰)은 다음 디자인 손질의 일이다.
9. **등록부에 분류의 근거를 값으로 적게 하는 일 · 등록부와 e2e 항목의 짝을 정적 검사로 보는 일**은 접근성 점검의 권고이고 하지 않았다.
10. **API 26 ~ 29 경로는 한 번도 실행되지 않았다.** minSdk가 26인데, `WindowInsetsControllerCompat`의 하위 구현(`decorView`의 `SYSTEM_UI_FLAG_LIGHT_STATUS_BAR`를 쓰는 길 — D3)을 탄 기기 · 에뮬레이터가 없다. 근거는 바이트코드 읽기뿐이다.

## 적용 기록

**2026-10-09 — 학습 문항 안내가 아홉째 표지 요소가 되고 등록부에 키 하나가 섰다([ADR-0054](0054-learning-item-guides.md) D9). 결정은 그대로다.** 규칙(D1 · D8) · 호스트(D3) · 검사의 규칙 아홉은 바뀌지 않았다. 「재검토 조건」의 둘째 줄(`position: fixed` CSS를 새로 만들면)이 그대로 적용된 것이다.

- **표지**: `components/LearningItemGuide.tsx`의 루트에 `data-statusbar={lightStatusBarIcons}`를 조건 없이 단다. 스크림(`Overlay`)에는 달지 않는다. 떠 있는 동안에만 마운트되므로 표지를 켜고 끄는 것은 마운트다(D2의 첫 줄 그대로). 지는 표면은 학습 셸(문장 만들기 · 말하기 · 쓰기) · 메신저 · 전화 · 비주얼 노벨 위의 안내다.
- **등록부**: `statusBarSurfaceRegistry.fixedLayers`에 **새 키** `components/learning-item-guide.css`(`light-icons`, carrier `components/LearningItemGuide.tsx`). 기존 키 `components/first-unit-guide.css`의 carriers는 그대로다 — 새 안내의 루트는 자기 CSS 파일에서 `position: fixed`를 선언한다. 표면마다 스크림 세기가 다르다는 것이 키로 드러난다.
- **표지 수**: 학습 셸 · 메신저 · 전화 위에서는 0 → 1 → 0, 비주얼 노벨 위에서는 1 → 2 → 1(명암이 그대로라 적용 호출 0번 — D4의 서사 위 안내와 같다).
- **새 표면의 스크림은 0.8이다**(사용자 결정 — ADR-0054 U5. 첫 단원 안내는 0.6 그대로다). 기대 대비는 아래와 같다 — **[계산]은 토큰 값으로 낸 것이고 기기 실측이 아니다.**
