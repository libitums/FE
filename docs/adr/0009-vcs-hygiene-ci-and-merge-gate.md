# ADR-0009 — 형상 관리 위생 · CI · 머지 게이트

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: 형상 관리 위생(.gitignore), CI, 브랜치 보호·머지 게이트

## 맥락

세 축이 하나의 질문으로 이어진다: **깨진 것이 `main`에 들어가는 것을 무엇이 막는가.**

`.gitignore`는 들어가면 안 될 **파일**을, CI는 들어가면 안 될 **상태**를, 브랜치 보호는
그 CI를 **우회하지 못하게** 막는다. 셋을 따로 정하면 "CI는 있는데 우회 가능"이나
"보호는 있는데 검사할 것이 없음" 같은 어긋남이 생긴다.

이 저장소의 사실: 커밋하는 사람이 **1명**이고, 남은 기간이 **1주**다.

## 결정

### D1. `.gitignore`에 넣을 것

> 이 ADR은 **파일을 만들지 않는다.** 내용만 정한다. 실체화는 이후 단계에서 한다.

```gitignore
node_modules/
dist/
.rspeedy/
coverage/

.env
.env.*
!.env.example

*.log
.DS_Store
.idea/
.vscode/

# iOS 호스트 (apps/ios) — ADR-0012 D7
build/
DerivedData/
xcuserdata/
*.xcuserstate
Pods/
```

**`Podfile.lock`은 추적한다.** D2가 `pnpm-lock.yaml`을 추적하는 이유와 같다 — 네이티브
의존이 환경마다 다르게 풀리면 "내 Xcode에서만 나는 실패"가 생긴다.

**`.npmrc`를 여기 넣지 않는다.** private registry 설정은 추적돼야 한다 — registry 연결
한 줄만 들어가므로 새는 것이 없고, 넣지 않으면 새 환경에서 `pnpm install`이 어느
registry를 봐야 하는지 알 수 없게 된다 (ADR-0014 D3).

> **정정 (2026-09-01)** — 원래 이 자리에 *"토큰 `${NODE_AUTH_TOKEN}` 참조만 들어가므로"*
> 라고 적었다. **인증 항목은 이제 저장소 `.npmrc`에 넣지 않는다** — pnpm이 무시한다.
> 저장소에는 registry 연결만 커밋하고 인증은 `~/.npmrc`에 둔다. 같은 이유로
> `.env.example`도 지웠다 — 거기 넣어도 동작하지 않아 **틀린 안내**가 된다 (ADR-0014 D3).

### D2. `pnpm-lock.yaml`은 **반드시 추적한다**

이게 D1보다 중요하다.

잠금 파일이 없으면 에이전트가 도는 환경과 사람의 로컬에 **다른 트리**가 설치된다.
그러면 한쪽에서만 나는 실패가 생기고, 원인이 코드가 아니라 설치 결과라서 재현이
안 된다. 1인이 이런 실패를 디버깅하면 하루가 사라진다. ADR-0005가 Node·pnpm 버전을
고정하는 것과 같은 이유이며, 잠금 파일 없이는 그 고정이 절반만 작동한다.

`.env.example`을 예외로 추적하는 것도 같은 이유다 — 어떤 환경 변수가 필요한지가
저장소에 없으면 새 환경에서 앱이 왜 안 뜨는지 알 수 없다.

`.vscode/`를 통째로 무시하는 것은 **팀이 1인이기 때문**이다. 두 번째 사람이 오면
공유할 설정(권장 확장·포맷터)만 예외로 추적하는 것을 다시 본다.

### D3. CI를 첫 단계에 구성하지 않는다 — **대신 CI가 돌 명령을 지금 확정한다**

> **후속 결정 (2026-09-04)** — 아래 유예 조건 중 프로토타입 시연일이 지났고 저장소를
> 계속 사용하게 되어 CI를 도입했다. 현재 Linux Verify, 성능 보고서 정책, 선택적 iOS
> smoke의 명령·trigger·비차단 경계는 [ADR-0021 D1~D5](0021-performance-report-ci-automation.md)가
> 결정한다. 이 절은 첫 단계에서 유예한 근거와 도입 조건의 기록으로 남긴다.

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

이는 `pnpm verify`(ADR-0006 D1)에 설치 단계를 더한 것이다. **로컬과 CI가 같은 명령을
쓴다**(ADR-0006 D3).

**안 하는 근거**: CI는 근본적으로 "**다른 사람의 변경으로부터 나를 지키는**" 장치다.
커밋하는 사람이 1명이면 그 다른 사람이 없다. 지금 GitHub Actions를 붙이면 워크플로
디버깅(캐시·러너·Node 설정)에 시간을 쓰게 되고, 1주 일정에서 그 시간은 화면 하나와
맞바꿔진다.

**명령만 미리 확정하는 근거**: 명령이 정해져 있으면 나중에 CI 파일을 쓰는 일은 30분이다.
지금 안 하는 것은 워크플로 파일이지 **결정**이 아니다. 결정을 미루면 나중에 CI를 붙이는
사람이 무엇을 돌릴지부터 다시 정해야 한다.

**도입 시점 (먼저 오는 쪽):**

- **두 번째 사람이 이 저장소에 커밋하게 되는 시점** — 근거가 성립하지 않게 되는 순간이다
- **프로토타입 시연(2026-08-31) 직후** — 저장소를 계속 쓴다면

### D4. 머지 규약 — `main`에 직접 push하지 않고 PR로 머지한다

**1인이어도 지킨다.**

근거: 구현 상당 부분을 에이전트가 만든다. 에이전트가 만든 변경을 **사람이 한 번
읽는 지점**이 구조적으로 필요하다. PR이 그 지점이다. 혼자라서 리뷰어가 없다는 것과
읽는 지점이 필요 없다는 것은 다르다.

절차:

1. 브랜치를 판다
2. PR 전 로컬에서 `pnpm verify`를 돌린다 (ADR-0006 D1)
3. PR을 올리고 diff를 **사람이 읽는다**
4. 머지한다

### D5. 머지 방식은 **squash 하나로 고정한다**

`main`의 커밋 하나가 **PR 하나**와 일치한다.

**근거는 이력이 깔끔해서가 아니다. 되돌릴 수 있는 단위가 일치해야 하기 때문이다.**

- squash면 `git revert <sha>` 하나로 PR 하나가 통째로 돌아간다.
- rebase나 merge commit이면 되돌릴 때 여러 커밋을 골라야 하고, 그 사이에 다른 변경이
  끼어 있으면 충돌한다. CI가 없는 동안(D3) 깨진 것을 되돌리는 것이 유일한 복구 수단이라
  이 차이가 실제로 아프다.
- 브랜치에는 "오타 수정" · "다시 시도" 같은 중간 커밋이 쌓인다. 그건 작업의 흔적이지
  `main`이 기억해야 할 단위가 아니다.

**GitHub 저장소 설정에서 squash만 남기고 merge commit·rebase를 끈다.** D5가 강제할 수
없는 것(브랜치 보호)과 달리 **이건 지금 켤 수 있는 강제 수단**이다. 규약을 문서에만
두지 않는다.

**커밋 제목은 PR 제목을 쓴다.** squash 커밋의 기본값이 그렇고, 그러면 `main`의 한 줄이
곧 "무엇을 왜 넣었는가"를 가리키는 PR로 이어진다.

> 설계 단계의 ADR 11개는 이 결정 **이전에** rebase로 머지됐다. PR마다 커밋이 정확히
> 하나였으므로 결과는 squash와 같다. 이 결정은 코드가 들어오는 시점부터 의미를 갖는다.

### D6. 브랜치 보호로 이 규약을 **강제하는 것은 보류한다**

> **후속 결정 (2026-09-04)** — CI는 [ADR-0021](0021-performance-report-ci-automation.md)으로
> 도입됐다. 그러나 branch protection API의 HTTP 403은 그대로여서 검사를 required check로
> 묶지 못한다. 아래 두 번째 장애물은 해소됐고, 첫 번째 장애물만 남았다. 강제 보류와
> "강제되지 않는다"는 표시는 ADR-0021 D6이 이어받는다.

D4·D5는 정책이고, 이 결정은 그 정책의 **강제 수단**에 관한 것이다. 강제할 수 없다.

**막고 있는 것 둘:**

1. 저장소가 private이고 현재 GitHub 플랜에서
   `repos/libitums/FE/branches/main/protection` 조회가 **HTTP 403**이다.
   설계 조사에서 확인했고, 파일 밖 설정이라 저장소를 읽어서도 확인할 수 없다.
2. ~~필수 상태 검사로 걸 CI가 아직 없다.~~ Linux Verify가 생겨 해소됐다
   ([ADR-0021 D1](0021-performance-report-ci-automation.md)).

**푸는 시점**: GitHub 플랜 또는 저장소 공개 범위가 바뀌어 branch protection API를 사용할
수 있게 되는 시점이다. 지금은 실제로 "CI는 있는데 우회 가능한" 상태이며 이를 문서와
PR에서 숨기지 않는다.

**그전까지**: 규약 문서(ADR-0010)에 적힌 약속과 PR에 표시되는 CI 결과로 지킨다. 규약에
**"이것은 강제되지 않는다"고 명시한다.** 강제되는 줄 알고 방심하는 것이 규약이 아예
없는 것보다 나쁘기 때문이다.

## 버린 대안

- **첫 커밋부터 CI** — 1주 일정에서 워크플로 디버깅 시간이 회수되지 않는다 (D3).
- **CI를 영영 안 씀** — QC 반복과 백엔드 연동이 붙으면 회귀를
  사람이 못 잡는다. 그래서 "안 함"이 아니라 "시점 유예"로 정했다.
- **1인이니 `main`에 직접 push** — 가장 빠르다. 하지만 에이전트가 만든 변경을 사람이
  읽는 지점이 사라진다 (D4).
- **`pnpm-lock.yaml`을 무시** — 충돌을 피할 수 있지만 재현성을 잃는다. 이 저장소에서
  재현성은 일정 방어 수단이다 (D2, ADR-0005).
- **`.env.example`까지 무시** — 필요한 환경 변수가 저장소에 남지 않는다.
- **pre-commit 훅으로 `verify` 강제** — CI 없이도 강제할 수 있으나, 훅은 `--no-verify`로
  우회되고 커밋마다 전체 검사를 돌면 느려서 결국 우회하게 된다. 우회가 습관이 되면
  강제가 아니다.

- **rebase 머지** — 원래 커밋 메시지가 그대로 보존된다. 그러나 브랜치의 중간 커밋이
  전부 `main`에 올라와 되돌릴 단위가 흩어진다 (D5).
- **merge commit** — PR이 존재했다는 사실이 이력에 남는다. 그러나 커밋마다 병합 노드가
  붙어 이력이 두 갈래로 읽히고, 되돌리기에는 `-m` 지정이 필요하다 (D5).
- **머지 방식을 정하지 않고 그때그때** — 되돌리는 방법이 커밋마다 달라진다. 되돌려야
  하는 순간은 대개 급한 순간이다 (D5).

## 대가

- **시연 전까지 회귀를 사람이 로컬에서만 잡는다.** `verify`를 잊으면 깨진 채로 머지된다.
  이 공백은 CI 도입 전까지 닫히지 않는다 — **완화 수단이 문서뿐이고, 문서는 강제가
  아니다.** 이것을 알고 감수한다.
- **머지 게이트가 없으므로 D4의 PR 규약은 자율에 의존한다.** 급할 때 가장 먼저 깨지는
  종류의 규약이고, 급한 시기(시연 직전)에 정확히 깨질 것이다.
- **잠금 파일 충돌을 사람이 풀어야 한다.** 의존을 자주 추가하는 초기에 특히 자주 생긴다.
- CI를 나중에 붙이면 그동안 쌓인 lint 경고·타입 오류가 한꺼번에 드러날 수 있다.

## 재검토 조건

- 두 번째 사람이 커밋하게 되는 시점 → D3(CI), D5(브랜치 보호), D2(`.vscode/`)
- 프로토타입 시연(2026-08-31) 직후 저장소 존속 결정 → D3, D5
- GitHub 플랜이 바뀌어 브랜치 보호 API가 열리는 시점 → D6, ADR-0021 D6

## 기록

**2026-08-25 — D5(머지 방식) 추가.** 기존 결정을 바꾼 것이 아니라 **비어 있던 자리를
채운 것**이다. 이 ADR이 머지 게이트를 축으로 다루면서 *어떤 방식으로* 머지하는지를
정하지 않았고, 설계 ADR을 머지하는 시점에 그 공백이 드러났다. 이후 D-번호가 하나씩
밀렸다(옛 D5 → D6).
