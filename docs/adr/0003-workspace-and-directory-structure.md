# ADR-0003 — 워크스페이스 구성과 디렉터리 구조

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: workspace 구성(패키지 매니저·workspace 선언·태스크 러너), 폴더 구조, 네이밍

## 맥락

앱이 하나뿐인데(ADR-0002) 워크스페이스를 쓸 이유가 있는가 — 이것이 먼저 답할 질문이다.

답: 워크스페이스 **선언**은 비용이 거의 0이고(파일 한 개), 나중에 도입하려면
모든 경로·import·명령을 한 번에 옮겨야 한다. 반대로 **빈 패키지를 미리 만드는 것**은
비용이 계속 든다. 그래서 이 ADR은 **구조는 열어두고 내용물은 만들지 않는** 쪽으로
일관되게 결정한다.

## 결정

### D1. 패키지 매니저는 pnpm

근거:

- `workspace:*` 프로토콜을 지원한다. ADR-0004의 의존 방향 규칙이 이것에 기댄다.
- **엄격한 의존 격리**가 기본이다. 선언하지 않은 패키지를 import하면 실패한다.
  구현을 에이전트로 돌리는 이 저장소에서 이건 큰 값이다 — 에이전트가 우연히
  전이 의존을 끌어 쓰는 것을 **도구가** 막는다. 사람 리뷰에 기대지 않아도 된다.
- Lynx 툴체인(rspeedy)의 문서·예제가 pnpm 기준으로 쓰여 있어 막혔을 때 대조할 것이 있다.

### D2. `pnpm-workspace.yaml`은 `apps/*`와 `packages/*`만 선언한다

`tooling/*`은 **첫 tooling 패키지가 생길 때 추가한다.**

글롭 선언과 패키지 생성을 구분한다. 글롭은 비어 있어도 유지 비용이 0이지만, 빈 패키지는
`package.json`·`tsconfig`·이름·의존을 계속 따라 고쳐야 한다. `tooling/*`을 지금 안 넣는
이유는 다르다 — 공유 설정 패키지는 **설정을 공유할 소비자가 둘 이상일 때** 의미가 있고,
지금은 하나다. 글롭만 있고 영영 안 채워지면 그것도 잘못된 신호를 준다.

### D3. 태스크 러너(turbo/nx)를 도입하지 않는다

`pnpm --filter`와 루트 스크립트로 충분하다.

근거: 태스크 러너의 이득은 (a) 패키지 간 빌드 순서 자동 해결, (b) 결과 캐싱으로 반복
실행 단축이다. 패키지가 1개면 (a)는 해결할 것이 없고, CI가 없으면(ADR-0009) (b)의
반복 실행도 없다. 설정과 캐시 학습 비용만 남는다.

**도입 조건 (수치로 고정):**

- 워크스페이스 패키지가 **4개 이상**이 되거나,
- `pnpm verify` 전체 실행이 **5분**을 넘으면

둘 중 하나가 오면 turborepo를 먼저 검토한다.

### D4. 디렉터리 구조

```text
apps/
  mobile/              ReactLynx 앱 (ADR-0002)
    src/
    dist/              빌드 산출물. 추적하지 않는다 (ADR-0009)
packages/              공유 라이브러리. 첫 단계에는 디렉터리 자체를 만들지 않는다
tooling/               공유 설정. 첫 단계에는 없다 (D2)
docs/
  adr/                 결정 기록
  conventions/         규약 문서 (ADR-0010)
README.md              목차. 위 문서들로 가는 입구
```

정하는 것 셋:

- **문서는 `docs/` 아래.** 루트에 문서를 늘어놓지 않는다. 루트는 목차(`README.md`)만 갖는다.
- **산출물은 그것을 만든 앱 안에.** `apps/mobile/dist/`이지 루트 `dist/`가 아니다.
  루트에 두면 앱이 늘 때 무엇이 누구 것인지 안 보인다.
- **스크립트 디렉터리를 만들지 않는다.** `package.json`의 `scripts`로 충분하다. 스크립트가
  셸 한 줄을 넘어가기 시작하면 그때 `tooling/scripts` 패키지를 만든다(D2의 조건과 같다).

### D5. 앱 내부 구조는 **화면**을 1급 단위로 삼는다

```text
apps/mobile/src/
  app/          진입점. 루트 구성 — 화면 전환, 에러 경계, 프로바이더 (ADR-0007)
  screens/      화면 단위. 확정된 화면 목록과 1:1 대응
  components/   화면 둘 이상이 쓰는 컴포넌트만 (ADR-0011 D3)
  lib/          순수 로직·API 클라이언트. UI를 import하지 않는다
  styles/       전역 스타일. 토큰 값은 여기 두지 않는다 — 패키지에서 온다 (ADR-0011 D1)
```

근거: 화면 목록이 **이미 확정**됐다. 확정된 목록이 있으면 그것이 가장 안정된
분할 축이다. 폴더를 열어 화면 목록과 대조할 수 있다는 것 자체가 검증 수단이 된다 —
빠진 화면이 눈에 보인다. **대조할 목록은 `docs/screens.md`에 있다** (ADR-0010 D1).

`lib/`가 UI를 import하지 않는다는 규칙은 ADR-0004의 의존 방향 규칙을 앱 안에서
미리 연습하는 것이다. 나중에 `lib/`를 `packages/`로 올릴 때 그대로 떨어져 나온다.

### D6. 네이밍

| 대상 | 규칙 | 예 |
|---|---|---|
| 디렉터리 | kebab-case | `src/screens/order-detail/` |
| React 컴포넌트 파일 | PascalCase, **export 이름과 일치** | `OrderDetailScreen.tsx` |
| 그 외 파일 | kebab-case | `api-client.ts`, `use-navigation.ts` |
| 화면 컴포넌트 | `~Screen` 접미사 | `HomeScreen` |
| 훅 | `use~` 접두사, 파일도 `use-~` | `useNavigation` / `use-navigation.ts` |
| 테스트 파일 | `*.unit.test.ts` / `*.ui.test.tsx` / `*.integration.test.tsx` | ADR-0006과 같은 패턴 |

컴포넌트 파일만 PascalCase로 예외를 두는 이유: **파일명이 export 이름과 같으면 import
경로를 추측할 수 있다.** 에이전트가 코드를 쓸 때 경로를 틀리는 빈도가 줄고, 사람이
검색할 때도 한 번에 찾는다. 규칙이 하나 늘어나는 비용보다 이 이득이 크다.

macOS는 대소문자를 구분하지 않는 파일시스템이 기본이다. 대소문자만 바꾸는 rename은
git이 놓칠 수 있으므로, 규칙을 처음에 고정하고 나중에 바꾸지 않는다.

테스트 파일 패턴에 계층 이름을 넣은 것은 의도적이다 —
계층이 파일명에 드러나면 러너가 계층별로 골라 돌릴 수 있고, 파일을 열지 않아도 어느
계층인지 읽힌다 (ADR-0006 D4).

## 버린 대안

- **npm workspaces** — `workspace:*`가 없고 hoisting이 기본이라 선언하지 않은 의존을
  import해도 통과한다. 의존 방향 규칙(ADR-0004)을 도구가 못 지켜준다.
- **yarn berry (PnP)** — 재현성은 좋지만 Lynx 툴체인과의 PnP 호환을 검증할 시간이 1주에 없다.
- **bun** — 빠르지만 Lynx 툴체인에서의 검증 이력을 모른다. 프로토타입 일정에서 미지의
  런타임 문제를 감당할 여유가 없다.
- **turborepo 선제 도입** — D3 참조. 지금 넣으면 설정 시간이 화면 하나와 맞바꿔진다.
- **워크스페이스 없이 단일 패키지로 시작** — 지금 가장 단순하지만, 두 번째 앱이나
  공유 패키지가 생길 때 경로·import·명령을 한 번에 다 옮겨야 한다. 워크스페이스 선언
  비용(파일 1개)이 그 위험보다 훨씬 싸다.
- **feature 단위 분할(`src/features/`)** — feature 경계는 아직 정해지지 않았다. 화면
  목록은 확정됐다. 확정된 것으로 나눈다.
- **타입별 분할(`containers/`, `views/`, `hooks/`)** — 화면 하나를 고치는 데 폴더 넷을
  오간다. 1인 작업에서 문맥 전환 비용이 크다.

## 대가

- 앱이 하나인 동안 워크스페이스는 **순수한 오버헤드**다. `--filter` 인자가 모든 명령에
  붙고, 루트와 앱에 `package.json`이 둘 있다.
- 태스크 러너가 없으므로 패키지가 늘면 빌드 순서를 사람이 신경 써야 하고, 반복 빌드에
  캐시가 없다.
- 화면 축 분할은 화면 간 공유가 늘면 `components/`가 비대해진다. 그 시점에 feature 축을
  다시 봐야 한다.
- 파일명 규칙이 두 종류(kebab / Pascal)라 한 번은 헷갈린다. 규약 문서(ADR-0010)에 적어
  완화한다.

## 재검토 조건

- 패키지 4개 이상 또는 `verify` 5분 초과 → D3(태스크 러너)
- 두 번째 패키지 생성 → D2(`tooling/*` 글롭)
- `src/components/`가 20개를 넘거나 화면 간 공유가 화면 내 코드보다 많아지는 시점 → D5(분할 축)
