# ADR-0003 — 워크스페이스 구성과 디렉터리 구조

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: workspace 구성(패키지 매니저·workspace 선언·태스크 러너), 폴더 구조, 네이밍

## 맥락

앱이 하나뿐인데(ADR-0002) 워크스페이스를 쓸 이유가 있는가 — 이것이 먼저 답할 질문이다.

답: 워크스페이스 **선언**은 비용이 거의 0이고(파일 한 개), 나중에 도입하려면
모든 경로·import·명령을 한 번에 옮겨야 한다. 반대로 **빈 패키지를 미리 만드는 것**은
비용이 계속 든다. 그래서 이 ADR은 **구조는 열어두고 내용물은 만들지 않는** 쪽으로
일관되게 결정한다.

## 결정

### D1. 패키지 매니저는 pnpm

근거:

- `workspace:*` 프로토콜을 지원한다. ADR-0004의 의존 방향 규칙이 이것에 기댄다.
- **엄격한 의존 격리**가 기본이다. 선언하지 않은 패키지를 import하면 실패한다.
  구현을 에이전트로 돌리는 이 저장소에서 이건 큰 값이다 — 에이전트가 우연히
  전이 의존을 끌어 쓰는 것을 **도구가** 막는다. 사람 리뷰에 기대지 않아도 된다.
- Lynx 툴체인(rspeedy)의 문서·예제가 pnpm 기준으로 쓰여 있어 막혔을 때 대조할 것이 있다.

### D2. `pnpm-workspace.yaml`은 `apps/*`와 `packages/*`만 선언한다

`tooling/*`은 **첫 tooling 패키지가 생길 때 추가한다.**

글롭 선언과 패키지 생성을 구분한다. 글롭은 비어 있어도 유지 비용이 0이지만, 빈 패키지는
`package.json`·`tsconfig`·이름·의존을 계속 따라 고쳐야 한다. `tooling/*`을 지금 안 넣는
이유는 다르다 — 공유 설정 패키지는 **설정을 공유할 소비자가 둘 이상일 때** 의미가 있고,
지금은 하나다. 글롭만 있고 영영 안 채워지면 그것도 잘못된 신호를 준다.

### D3. 태스크 러너(turbo/nx)를 도입하지 않는다

`pnpm --filter`와 루트 스크립트로 충분하다.

근거: 태스크 러너의 이득은 (a) 패키지 간 빌드 순서 자동 해결, (b) 결과 캐싱으로 반복
실행 단축이다. 패키지가 1개면 (a)는 해결할 것이 없고, CI가 없으면(ADR-0009) (b)의
반복 실행도 없다. 설정과 캐시 학습 비용만 남는다.

**도입 조건 (수치로 고정):**

- 워크스페이스 패키지가 **4개 이상**이 되거나,
- `pnpm verify` 전체 실행이 **5분**을 넘으면

둘 중 하나가 오면 turborepo를 먼저 검토한다.

### D4. 디렉터리 구조

```text
apps/
  mobile/              ReactLynx 앱 (ADR-0002)
    src/
    dist/              빌드 산출물. 추적하지 않는다 (ADR-0009)
packages/              공유 라이브러리. 첫 단계에는 디렉터리 자체를 만들지 않는다
tooling/               공유 설정. 첫 단계에는 없다 (D2)
docs/
  adr/                 결정 기록
  conventions/         규약 문서 (ADR-0010)
README.md              목차. 위 문서들로 가는 입구
```

정하는 것 셋:

- **문서는 `docs/` 아래.** 루트에 문서를 늘어놓지 않는다. 루트는 목차(`README.md`)만 갖는다.
- **산출물은 그것을 만든 앱 안에.** `apps/mobile/dist/`이지 루트 `dist/`가 아니다.
  루트에 두면 앱이 늘 때 무엇이 누구 것인지 안 보인다.
- **스크립트 디렉터리를 만들지 않는다.** `package.json`의 `scripts`로 충분하다. 스크립트가
  셸 한 줄을 넘어가기 시작하면 그때 `tooling/scripts` 패키지를 만든다(D2의 조건과 같다).

### D5. 앱 내부 구조는 **화면**을 1급 단위로 삼는다

```text
apps/mobile/src/
  app/          진입점. 루트 구성 — 화면 전환, 에러 경계, 프로바이더 (ADR-0007)
  screens/      화면 단위. 확정된 화면 목록과 1:1 대응
  components/   화면 둘 이상이 쓰는 컴포넌트만 (ADR-0015 D3)
  lib/          순수 로직·API 클라이언트. UI를 import하지 않는다
  styles/       전역 스타일. 토큰 값은 여기 두지 않는다 — 패키지에서 온다 (ADR-0014 D1)
```

근거: 화면 목록이 **이미 확정**됐다. 확정된 목록이 있으면 그것이 가장 안정된
분할 축이다. 폴더를 열어 화면 목록과 대조할 수 있다는 것 자체가 검증 수단이 된다 —
빠진 화면이 눈에 보인다. **대조할 목록은 `docs/screens.md`에 있다** (ADR-0010 D1).

`lib/`가 UI를 import하지 않는다는 규칙은 ADR-0004의 의존 방향 규칙을 앱 안에서
미리 연습하는 것이다. 나중에 `lib/`를 `packages/`로 올릴 때 그대로 떨어져 나온다.

### D6. 네이밍

| 대상 | 규칙 | 예 |
|---|---|---|
| 디렉터리 | kebab-case | `src/screens/order-detail/` |
| React 컴포넌트 파일 | PascalCase, **export 이름과 일치** | `OrderDetailScreen.tsx` |
| 그 외 파일 | kebab-case | `api-client.ts`, `use-navigation.ts` |
| 화면 컴포넌트 | `~Screen` 접미사 | `HomeScreen` |
| 훅 | `use~` 접두사, 파일도 `use-~` | `useNavigation` / `use-navigation.ts` |
| 테스트 파일 | `*.unit.test.ts` / `*.ui.test.tsx` / `*.integration.test.tsx` | ADR-0006과 같은 패턴 |

컴포넌트 파일만 PascalCase로 예외를 두는 이유: **파일명이 export 이름과 같으면 import
경로를 추측할 수 있다.** 에이전트가 코드를 쓸 때 경로를 틀리는 빈도가 줄고, 사람이
검색할 때도 한 번에 찾는다. 규칙이 하나 늘어나는 비용보다 이 이득이 크다.

macOS는 대소문자를 구분하지 않는 파일시스템이 기본이다. 대소문자만 바꾸는 rename은
git이 놓칠 수 있으므로, 규칙을 처음에 고정하고 나중에 바꾸지 않는다.

테스트 파일 패턴에 계층 이름을 넣은 것은 의도적이다 —
계층이 파일명에 드러나면 러너가 계층별로 골라 돌릴 수 있고, 파일을 열지 않아도 어느
계층인지 읽힌다 (ADR-0006 D4).

### D7. 네이밍 — CSS 파일·클래스, `data-testid`, 상대 import

D6이 적지 않은 넷을 닫는다. **넷 다 코드에는 이미 패턴이 있고 문서에는 없었다.**
셋은 그 패턴을 추인하고, **하나는 이미 갈라져 있어서 한쪽을 고른다.**
다섯째 행(상태)은 **비워 두었다가 첫 사례가 나온 뒤 채웠다** (2026-09-02, `정정 기록`).
그 행만은 추인이 아니다 — 코드에 패턴이 없는 상태에서 처음 정한 것이다.

| 대상 | 규칙 | 예 |
|---|---|---|
| CSS 파일 | 짝이 되는 **컴포넌트 파일명의 kebab-case**. 같은 폴더에 둔다 | `HomeScreen.tsx` → `home-screen.css` |
| CSS 클래스 | 블록 = CSS 파일명(확장자 제외). 하위는 `블록-요소` **한 겹만** | `.home-screen` · `.home-screen-title` |
| CSS 클래스 (상태) | `블록-요소-상태`. 상태어는 **아래 예약 목록에서만** 고르고, base 클래스에 **더해** 붙인다 | `.bottom-navigator-label-selected` |
| `data-testid` | `블록-역할`. **클래스 블록과 같은 접두사를 쓰고 축약하지 않는다** | `home-screen-title` |
| 상대 import | **확장자를 붙이지 않는다** | `./HomeScreen` |

- **BEM의 `__`·`--`를 쓰지 않는다.** Lynx CSS는 전역이라 필요한 것은 계층 표기가 아니라
  **접두사**뿐이고, 접두사는 파일명이 이미 준다. 상태가 붙어 한 겹이 늘어난 뒤에도
  그대로다 — 구분자를 늘리는 대신 **상태어를 닫아** 경계를 준다(바로 아래).
- **상태(modifier)는 하이픈 한 겹을 더 써서 `블록-요소-상태`로 적는다.** 예약된 상태어는
  지금 **하나**다.

  | 상태어 | 뜻 | 첫 사용처 |
  |---|---|---|
  | `selected` | 여럿 중 지금 골라진 하나 | `.bottom-navigator-label-selected` · `.bottom-navigator-indicator-selected` |

  - **읽는 규칙은 하나다 — 마지막 토큰이 예약 상태어면 상태, 아니면 요소다.** 그래서
    예약어를 요소 이름으로 쓸 수 없다. BEM의 `--`가 하는 일을 **어휘**가 대신한다.
    구분자를 늘리면 경계를 매번 판단해야 하지만, 목록은 **대조하면 끝난다.**
  - **목록에 없는 상태어를 쓰지 않는다.** 새 상태가 필요하면 이 표에 행을 더한다
    (= ADR을 고친다). 어휘를 열어두면 `selected`·`active`·`current`·`on`이 섞이고,
    섞이는 순간 위의 읽는 규칙이 성립하지 않는다.
  - **base를 대체하지 않고 더해 붙인다.** base가 공통 값을, 상태 클래스는 **갈리는
    속성만** 선언한다. 요소 없이 블록에 바로 붙는 `블록-상태`도 같은 규칙이다.
  - **한 요소에 상태 클래스는 최대 하나.** 둘이 겹치면 같은 특이도가 셋이 되어 아래 순서
    규칙이 곧바로 무너진다. 겹쳐야 하는 자리가 생기면 재검토 조건이다.
  - **상태 클래스는 base 뒤에, 같은 파일에서 바로 다음에 선언한다.** 특이도가 같아
    순서가 승부를 가른다. 순서를 뒤집으면 **에러 없이 상태가 안 보인다** — 토큰 오타와
    같은 계열의 조용한 실패다(ADR-0014 D1). 파일 끝에 몰지 않는 이유는 base와 멀어지면
    무엇이 갈리는지 보려고 두 곳을 오가게 되기 때문이다.
  - **상태를 자동 테스트가 보는 경로는 클래스가 아니다.** `toHaveClass`를 쓰지 않기로
    했으므로(ADR-0006 D4) 클래스는 **시각 전용**이다. 상태를 단언해야 하면 `data-*`
    속성을 둔다. 상태 클래스마다 `data-testid`를 새로 만들지 않는다.
  - **변형(variant)은 이 규칙이 덮지 않는다.** 상태는 시간에 따라 변하고 변형은 변하지
    않는다. 사례가 없으므로 열지 않는다 (`docs/adr/README.md` 보류 표).
- **`data-testid`는 테스트가 실제로 질의하는 요소에만 붙인다.** 클래스와 문자열이
  같아질 수 있지만 **다른 계약**이다 — 클래스는 시각, testid는 테스트다. 한쪽을 바꿔도
  다른 쪽은 따라가지 않는다.
- **축약을 금지하는 이유**: `home-`은 화면이 아니라 탭 이름으로도 읽힌다. 홈 탭에는
  노티피케이션·여정 선택이 더 들어오고(`docs/screens.md`), 그때 `home-title`이 어느
  화면 것인지가 사라진다. **화면이 하나일 때는 안 보이는 충돌이다.**
- **상대 import에 확장자를 붙이지 않는 이유**: `moduleResolution: "bundler"`라
  **둘 다 통과해서 도구가 갈라주지 않는다.** `.js`는 실재하지 않는 파일을 가리키고
  (원본은 `.ts`·`.tsx`), 읽는 사람이 산출물 경로로 오해한다. 지금 여덟 곳 중 다섯이
  무확장이다. 갈린 축은 소스/테스트가 아니다 — `navigation.unit.test.ts`는 테스트인데
  무확장이다. **그냥 규칙이 없어서 갈렸다.**

**이 결정 이전에 쓰인 것은 옮긴다.** `home-title`·`home-icon` →
`home-screen-title`·`home-screen-icon`(TSX와 `ui` 테스트), `.js`를 붙인 import 세 곳
(`App.integration.test.tsx` · `HomeScreen.ui.test.tsx` · `storage.unit.test.ts`).
합쳐 일곱 줄이다. **일괄 이관을 다음으로 미루지 않는 이유**: 화면이 하나뿐이고,
다음 화면이 **이 파일들을 보고 복사한다**. 화면이 둘이 되면 잘못된 쪽이 다수가 된다.

## 버린 대안

- **npm workspaces** — `workspace:*`가 없고 hoisting이 기본이라 선언하지 않은 의존을
  import해도 통과한다. 의존 방향 규칙(ADR-0004)을 도구가 못 지켜준다.
- **yarn berry (PnP)** — 재현성은 좋지만 Lynx 툴체인과의 PnP 호환을 검증할 시간이 1주에 없다.
- **bun** — 빠르지만 Lynx 툴체인에서의 검증 이력을 모른다. 프로토타입 일정에서 미지의
  런타임 문제를 감당할 여유가 없다.
- **turborepo 선제 도입** — D3 참조. 지금 넣으면 설정 시간이 화면 하나와 맞바꿔진다.
- **워크스페이스 없이 단일 패키지로 시작** — 지금 가장 단순하지만, 두 번째 앱이나
  공유 패키지가 생길 때 경로·import·명령을 한 번에 다 옮겨야 한다. 워크스페이스 선언
  비용(파일 1개)이 그 위험보다 훨씬 싸다.
- **feature 단위 분할(`src/features/`)** — feature 경계는 아직 정해지지 않았다. 화면
  목록은 확정됐다. 확정된 것으로 나눈다.
- **타입별 분할(`containers/`, `views/`, `hooks/`)** — 화면 하나를 고치는 데 폴더 넷을
  오간다. 1인 작업에서 문맥 전환 비용이 크다.
- **CSS 클래스에 BEM 완전형(`block__element--modifier`)** — 계층과 상태가 이름에서
  읽힌다. **두 겹이 필요한 자리가 생긴 뒤에도 버린다**(2026-09-02, `정정 기록`).
  구분자 둘을 도입하면 **어디까지가 요소이고 어디부터가 modifier인지**를 매번 판단하게
  되는데, 그 판단을 **닫힌 상태어 목록이 더 싸게 없앤다** — 목록은 대조하면 끝난다.
  값을 치르는 범위도 다르다. BEM은 저장소의 **모든** 클래스 모양을 바꾸고 파일명·
  `data-testid`와도 어긋나지만, 상태어 목록은 상태가 붙는 클래스에만 닿는다 (D7).
- **상태를 `data-*` 속성 셀렉터로 읽기** — `.bottom-navigator-tab[data-selected="true"]
  .bottom-navigator-label`처럼 쓰면 상태의 출처가 **하나**가 되어 가장 깨끗하다. 계약이
  이미 그 속성을 고정해 두었으므로 클래스를 아예 안 만들어도 된다. 버린 이유는
  **이 스택에서 되는지 확인할 수단이 없다**는 것이다. `@lynx-js/css-serializer`는 셀렉터를
  문자열(`selectorText`)로 넘길 뿐이고 속성 셀렉터·자손 결합자를 실제로 매칭하는 것은
  네이티브 엔진이다 — 빌드도 테스트도 답을 주지 않고, **안 되면 조용히 아무 일도 일어나지
  않는다.** ADR-0014 D1이 중첩 `var()`로 한 번 겪은 형태다. 기기에서 확인되면 다시 본다
  (재검토 조건).
- **상태를 요소 이름으로 위장하기** — `.bottom-navigator-current`를 라벨과 지시선에 함께
  붙이면 한 겹을 안 넘는다. 그러나 **한 클래스가 라벨의 `color`와 지시선의 `background`를
  동시에 건드려야 해서 성립하지 않는다.** 둘로 나누면(`.bottom-navigator-marker` 등) 읽는
  사람이 그것이 상태인지 요소인지 알 수 없다 — D7이 없애려는 판단이 그대로 돌아온다.
- **접두사 없는 전역 상태 클래스(`.is-selected`)** — 짧고 어디서나 재사용된다. 그러나
  **Lynx CSS는 전역이라** 접두사 없는 이름이 다른 컴포넌트와 그대로 충돌한다. D7의 블록
  접두사가 존재하는 이유가 이것이고, ADR-0015 D2도 같은 근거를 쓴다.
- **`data-testid`를 클래스 이름과 같은 문자열로 못 박기** — 하나만 기억하면 된다.
  그러나 시각 리팩터링(클래스 rename)이 테스트를 깨게 되고, 그건 ADR-0006 D4의
  *"관찰 가능한 동작이 그대로면 테스트를 새로 쓰지 않는다"* 와 정면으로 부딪힌다.
  **접두사만 공유하고 두 계약은 따로 둔다** (D7).
- **상대 import에 `.js`를 붙이는 쪽으로 통일** — Node의 네이티브 ESM 해석으로 옮길 때
  그대로 간다. 그러나 이 저장소는 번들러로만 돈다(rspeedy·vitest)고 이미 정했고,
  실재하지 않는 파일명을 여덟 곳에 적는 값을 지금 낼 이유가 없다 (D7).

## 대가

- 앱이 하나인 동안 워크스페이스는 **순수한 오버헤드**다. `--filter` 인자가 모든 명령에
  붙고, 루트와 앱에 `package.json`이 둘 있다.
- 태스크 러너가 없으므로 패키지가 늘면 빌드 순서를 사람이 신경 써야 하고, 반복 빌드에
  캐시가 없다.
- 화면 축 분할은 화면 간 공유가 늘면 `components/`가 비대해진다. 그 시점에 feature 축을
  다시 봐야 한다.
- 파일명 규칙이 두 종류(kebab / Pascal)라 한 번은 헷갈린다. 규약 문서(ADR-0010)에 적어
  완화한다.
- **D7의 넷을 도구가 하나도 검사하지 않는다.** 클래스 접두사도, testid 이름도, import
  확장자도 `verify`를 통과한다. `moduleResolution: "bundler"`가 확장자 둘 다 받는 것이
  특히 그렇다 — **갈린 것을 발견한 것이 사람이 문서를 대조할 때였다.**
- **`data-testid`가 파일명에서 파생되므로 컴포넌트 rename이 테스트까지 번진다.**
  이름이 길어지는 비용도 함께 진다(`home-screen-title`).
- **상태 표기도 도구가 검사하지 않는다.** 위의 넷에 다섯째가 붙었다. 예약어 목록 대조도,
  base보다 뒤에 선언됐는지도 `verify`를 통과한다. **닫힌 목록은 사람이 대조하기 쉬우라고
  닫은 것이지 기계가 대조해서가 아니다.** 순서가 뒤집힌 경우만은 화면에 드러난다 —
  선택된 탭이 안 갈린다(`docs/e2e/`의 눈 확인). ADR-0014 D8처럼 검사를 지금 붙이지 않는
  이유는 실패가 **조용하지 않기 때문**이다. 그 검사는 조용한 실패에만 값이 있었다.
- **같은 상태가 두 곳에 표현된다.** 선택 여부가 `data-selected` 속성과 상태 클래스로
  각각 나간다. 둘 다 같은 식에서 파생되지만 **줄이 둘**이라 한쪽만 고칠 수 있다.
  속성 셀렉터가 확인되면(재검토 조건) 사라지는 대가다.

## 재검토 조건

- 패키지 4개 이상 또는 `verify` 5분 초과 → D3(태스크 러너)
- 두 번째 패키지 생성 → D2(`tooling/*` 글롭)
- `src/components/`가 20개를 넘거나 화면 간 공유가 화면 내 코드보다 많아지는 시점 → D5(분할 축)
- **예약 상태어가 넷을 넘거나, 한 요소에 상태 클래스가 둘 겹쳐야 하는 사례** → D7.
  어휘로 경계를 주는 방식이 한계에 온 것이므로 BEM 구분자를 다시 본다
- **상태가 아닌 변형(variant, 예 버튼의 primary/secondary)이 필요한 첫 사례** → D7.
  상태어 목록에 밀어 넣지 않는다 (`docs/adr/README.md` 보류 표)
- **Lynx에서 속성 셀렉터(`[data-*="…"]`)가 도는 것이 기기에서 확인되면** → D7.
  상태 클래스를 걷고 `data-*` 하나로 합칠지 다시 본다
- **네이티브 ESM으로 실행하는 코드가 생기면**(Node 스크립트 등) → D7의 import 확장자.
  번들러 밖에서 도는 코드는 이 규칙이 성립하지 않는다
- **D7의 이름 규칙이 두 번 이상 어긋난 채 머지되면** → 검사 수단을 다시 본다.
  약속만으로 안 되는 것이 확인된 것이므로 (ADR-0014 D8이 같은 판단의 선례다)

## 정정 기록

**2026-09-02 — D7에 상태(modifier) 표기를 채웠다.** 결정이 바뀐 것이 아니다. D7이 스스로
*"modifier가 필요한 첫 사례가 나오면 그때 정한다 — 지금 없다"* 라고 비워 둔 칸을 채웠다.
첫 사례는 LIB-221의 바텀 네비게이션 셸이다 — 선택된 탭의 라벨 `color`와 지시선
`background`가 갈려야 하는데, 인라인 `style`이 막혀 있고(ADR-0015 D2) 아이콘 외의 색은
CSS에서만 온다. 상태를 클래스가 아닌 것으로 표현할 길이 없다.

**제자리에서 고친 이유**(ADR-0010 D10): 이 저장소에 상태 클래스는 **하나도 없다** —
`home-screen.css`와 `error-boundary.css`를 열어 확인했다. 옛 결정으로 지어진 것이 없으니
추적할 대상이 없다. 새 D를 붙이면 CSS 클래스 이름 규칙이 두 자리로 갈리고
`docs/conventions/code.md` 네이밍 표의 한 행이 ADR 둘을 링크하게 된다.

**어떻게 틀려 있었나 — 문구가 아니라 자리다.** *"그때 정한다"* 는 미결정인데
`docs/adr/README.md`의 **보류 표에 행이 없었다.** ADR-0010 D5가 정확히 그것을 금지한다
(*"ADR 본문에만 적어두지 않는다. 본문에 흩어두면 그 ADR을 다시 열 일이 없어서 영영 안
본다"*). 재검토 조건에 한 줄이 남아 있어서 살아남았을 뿐이다. 같은 모양을 막으려고,
이번에 남는 미결정(변형/variant)은 **보류 표에 넣었다.**

함께 고친 것: `버린 대안`의 BEM 항목(*"지금 두 겹이 필요한 자리가 없고"* 가 거짓이 됐다.
결론은 같고 근거가 바뀌었다), 소진된 재검토 조건 한 줄, `docs/conventions/code.md`의
네이밍 표(ADR-0010 D4).
