# ADR-0005 — Node·pnpm 버전 정책

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: 런타임·패키지매니저 버전 정책

## 맥락

이 저장소는 사람 1명과 **에이전트**가 함께 코드를 만든다. 에이전트가 도는
환경과 사람의 로컬이 다른 Node에서 돌면, 한쪽에서만 나는 실패가 생긴다. 그런 실패는
원인이 코드가 아니라 환경이라 디버깅이 가장 오래 걸린다. 1주 일정에서 이건 감당할 수
없는 종류의 시간 손실이다.

그래서 버전 고정은 "좋은 습관"이 아니라 **일정 방어 수단**이다.

## 결정

### D1. Node는 22 LTS 계열

2026-08 기준 유지보수 중인 LTS 라인이고, 툴체인·CI 러너 이미지가 가장 오래 검증한
라인이다.

**최신 Active LTS를 굳이 쓰지 않는 이유**: 1주 일정에서 툴체인 호환 문제를 만나면
회복할 시간이 없다. 최신 라인의 이득(성능·신기능)은 프로토타입의 성공 기준
(ADR-0001 D4)에 영향을 주지 않는다. 얻는 것이 없는데 위험만 있으면 안 든다.

> **확인 필요**: rspeedy가 요구하는 최소 Node 버전이 22를 넘으면 이 결정을 갱신한다.
> 골격을 실체화할 때 확인한다 (`docs/adr/README.md`의 확인 목록).

### D2. pnpm은 10 계열

`workspace:*`(ADR-0004 D5)와 corepack 연동이 안정된 라인이다.

### D3. 고정 방식 — 세 곳이 각각 다른 일을 한다

| 위치 | 값의 형태 | 무엇을 위한 것인가 |
|---|---|---|
| `.nvmrc` | **정확한 버전** (`22.x.y`, **22.12 이상**) | 사람이 로컬을 맞추는 용도. `nvm use` 한 줄 |
| `package.json` `engines.node` | **범위** (`>=22.12 <23`) | 잘못된 버전을 막는 방어선 |
| `package.json` `packageManager` | **정확한 버전** (`pnpm@10.x.y`) | corepack이 읽어 자동으로 맞춘다 |
| **Lynx SDK** (자체 호스트) | **정확한 버전**, 하한 3.9 | 호스트를 우리가 빌드하므로 잠글 수 있다 (ADR-0012 D4) |
| **Lynx 런타임** (Explorer) | **하한 3.9** — 잠글 수단이 없다 | 개발 루프용 Explorer는 남의 빌드다. 고정 대신 **확인 절차**를 둔다 |

원칙 한 줄: **`packageManager`는 정확 버전(재현성), `engines`는 범위(운영 여유),
`.nvmrc`는 정확 버전(사람 편의).**

셋의 역할이 다르므로 형태도 다르다. `engines`까지 정확 버전으로 잠그면 Node 패치가
올라갈 때마다 전원이 막히고, 그러면 사람들이 `--ignore-engines`로 우회하기 시작한다.
우회가 습관이 되면 방어선이 사라진다. 그래서 **지킬 수 있는 만큼만** 잠근다.

`packageManager`만 정확 버전인 이유는 pnpm 마이너 차이가 lockfile 형식에 영향을 줄 수
있고, lockfile이 갈리면 `--frozen-lockfile`이 실패하기 때문이다.

**Lynx는 두 줄인 이유가 있다.** 하한 3.9는 디자인 시스템 소비가 요구한다(ADR-0011):
CSS 커스텀 프로퍼티와 SVG element가 3.9 기준으로 쓸 수 있다. 그런데 이 저장소에는
**Lynx가 두 곳에서 돈다** — 판정 환경인 자체 호스트(ADR-0012)와 개발 루프인 Explorer다.

- **자체 호스트의 SDK는 잠근다.** 우리가 빌드하므로 네이티브 의존 선언에 정확 버전으로
  박는다. 판정이 이쪽에서 나므로(ADR-0012 D5) 여기가 잠기면 기준이 고정된다.
- **Explorer는 잠글 수 없다.** 남이 빌드한 앱이고 사람이 받아 설치한다.

그래서 Explorer 쪽에만 고정 대신 **확인 절차**를 둔다.

- 첫 화면을 띄우기 전에 Explorer의 Lynx 런타임 버전을 확인하고, **그 버전을 저장소에
  적어둔다.** 어느 버전에서 통과했는지가 없으면 나중에 증상이 났을 때 비교 대상이 없다.
- 실패하는 방식이 나쁘기 때문이다 — **3.9 미만이면 `var(--token)`이 조용히 무효가 된다.**
  에러가 없고, 테스트 환경이 스타일을 계산하지 않으므로(ADR-0006 D4) 테스트도 못 잡는다.
  스타일이 안 먹는데 단서가 하나도 없는 상태가 된다.
- 못 맞추면 ADR-0011 D1(CSS 변수만)이 성립하지 않는다. TS 상수 경로가 fallback이 된다.

### D4. 버전을 올릴 때의 최소 검증

버전을 바꾸는 커밋은 아래를 통과한 뒤에만 만든다.

1. `pnpm install --frozen-lockfile`
2. `pnpm verify` (typecheck + lint + test + build, ADR-0006)
3. **자체 호스트 앱에서 앱이 실제로 뜨는 것까지 한 번 확인** (ADR-0012 D5)

3번이 있는 이유: 1·2는 번들을 만드는 쪽에서만 도는 검사다. **번들이 호스트에서 로드되는
것은 별개의 경계**이고, 여기서 깨지면 앞의 검사가 전부 통과해도 시연이 안 된다.
버전 변경은 툴체인 전체를 건드리므로 이 확인을 생략하면 안 된다.
Explorer만으로 확인하는 것은 이 항목을 통과시키지 않는다 — 판정 환경이 호스트다.

이 절차 없이 버전 커밋을 만들지 않는다.

## 버린 대안

- **Volta** — `.nvmrc` + `packageManager`로 되는 일에 도구를 하나 더 설치하게 한다.
  새 기여자의 첫 실행 장벽이 높아진다.
- **`engines`까지 정확 버전으로 잠금** — 패치 갱신마다 전원이 막히고, 우회가 습관이 된다.
- **버전을 고정하지 않음** — 지금 가장 빠르지만, 맥락에 적은 "환경 때문에 나는 실패"를
  그대로 떠안는다. 에이전트 구현 환경이 개입하면 이 위험이 커진다.
- **Docker로 개발 환경 통일** — 재현성은 가장 확실하지만, Lynx dev 서버에 실기기
  Explorer가 접속해야 하므로(ADR-0002) 네트워크 구성이 복잡해진다. 1주에 풀 문제가 아니다.

## 대가

- corepack이 꺼져 있는 환경에서는 `packageManager`가 무시된다. 그러면 사람이 pnpm을
  수동으로 맞춰야 하고, 이 결정의 재현성 보장이 그 환경에서만 사라진다. 규약 문서
  (ADR-0010)에 corepack 활성화를 첫 설정 단계로 적어 완화한다.
- `.nvmrc`의 정확 버전은 시간이 지나면 낡는다. 갱신하는 사람이 D4 절차를 밟아야 하므로
  갱신 비용이 0이 아니다. 그래서 실제로는 잘 안 올라간다 — 프로토타입 기간에는 문제가
  아니지만, 저장소가 오래 살면 부채가 된다.
- Node 22를 고르면서 최신 라인의 성능·기능을 포기한다.

## 재검토 조건

- rspeedy나 다른 필수 의존이 Node 22를 지원하지 않는 것이 확인되는 시점 (D1)
- Node 22가 EOL에 들어가는 시점
- 프로토타입 이후 저장소를 계속 쓰기로 결정되는 시점 — 그때 최신 LTS로 올린다
- Explorer의 Lynx 런타임이 **3.9 미만인 것이 확인되는 시점** (D3) → ADR-0011 D1을 함께 본다

## 정정 기록

**2026-08-25 — 사실 보강.** 결정(세 곳을 각각 다르게 고정한다)은 그대로다.

1. `engines.node` 범위가 `>=22 <23`이었다. rspeedy 공식 템플릿의 요구가
   `^20.19.0 || >=22.12.0`이라 **22.0~22.11을 통과시키는 방어선**이었다 — 막으라고 둔
   것이 실제로 막지 못했다. `>=22.12 <23`으로 좁히고 `.nvmrc`에도 하한을 달았다.
   README의 가정 `rspeedy가 Node 22 LTS를 지원한다`는 이것으로 해소됐다.
2. **Lynx 런타임 하한이 어디에도 없었다.** 이 저장소가 버전 축을 다루는 문서인데
   Node·pnpm만 있고 정작 앱이 올라가는 런타임이 빠져 있었다. D3에 축으로 넣었다.
