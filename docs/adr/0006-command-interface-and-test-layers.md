# ADR-0006 — 명령 인터페이스와 테스트 계층

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: 명령 인터페이스, 테스트 계층

## 맥락

두 축을 한 문서에 둔다. 서로를 정의하기 때문이다.

- 테스트 계층을 정하면 `test` 명령이 무엇을 도는지가 정해진다.
- 반대로 명령이 없는 계층은 돌지 않는다. 계층을 선언하는 것과 명령을 만드는 것이
  **같은 결정**이라, 따로 정하면 선언만 있고 돌지 않는 계층이 생긴다.

명령이 흩어지면 1인 저장소에서 특히 비싸다. "이 저장소는 무엇으로 빌드하나"를 매번
찾아야 하고, 에이전트에게도 매번 알려줘야 한다.

## 결정

### D1. 루트 명령

앱이 하나이므로(ADR-0002) 루트에서 전부 돈다.

| 명령 | 하는 일 | 하지 않는 일 |
|---|---|---|
| `pnpm dev` | rspeedy dev 서버. Explorer가 붙을 URL/QR을 낸다 | 타입 검사·린트 |
| `pnpm build` | Lynx 번들 산출 (`apps/mobile/dist/`) | **타입 검사** |
| `pnpm preview` | `rspeedy preview` — 빌드 산출물을 Explorer로 확인 | 빌드 |
| `pnpm typecheck` | `tsc --noEmit` | 코드 생성 |
| `pnpm lint` | 정적 검사 (`oxlint`) | **자동 수정** (`lint:fix`가 따로) |
| `pnpm format` | 포맷 적용 (`oxfmt`) | 검사만 하기 (`format:check`가 따로) |
| `pnpm test` | `test:unit` + `test:ui` + `test:integration` | e2e (D4) |
| `pnpm verify` | 순서대로: **format:check** → typecheck → lint → test → build | |

> **`build`에서 타입 검사를 명시적으로 뺀다.** 공식 템플릿(`create-rspeedy`)은
> `@rsbuild/plugin-type-check`을 devDependencies에 넣는다. 그대로 두면 `build`가
> 타입 검사를 겸하게 되어 아래 원칙과 어긋난다. **플러그인을 넣지 않는 것이 결정의
> 일부다** — 실체화할 때 기본값이 조용히 이기지 않도록 여기 적어둔다.

**도구는 `oxlint`와 `oxfmt`다.** 둘 다 Oxc 프로젝트이고 설정과 무시 규칙을 공유한다.

포매터를 넣는 이유는 취향이 아니다 — **CI가 없어(ADR-0009 D3) PR diff를 사람이 읽는 것이
유일한 게이트인데**(ADR-0009 D4), 구현 상당 부분을 에이전트가 만들고 그 출력은 포맷이
매번 다르다. 포맷 잡음이 diff에 끼면 "무엇이 바뀌었나"가 안 보이고, 그 게이트가 직접
약해진다. 그래서 **`format:check`를 `verify`의 첫 단계**에 둔다. 검사하지 않는 포매터는
적용을 사람 기억에 맡기는 것이고, 그러면 드리프트가 쌓인다.

> **`lint`와 `format`은 D2의 `--filter` 규칙을 따르지 않는다.** 둘은 워크스페이스 명령이
> 아니라 **저장소 전체 도구**다 — 루트의 설정 파일도 사람이 diff에서 읽는다. 범위가
> 넓은 것이 의도이고, 그래서 `-r`이 아니라 도구를 직접 부른다.
>
> **다만 두 곳은 뺀다.** 기준은 하나다 — **우리가 소유하지 않은 파일은 포맷하지 않는다.**
>
> - `**/*.md` — `oxfmt`이 표를 패딩으로 정렬하는데 **한글은 double-width라 정렬이 되지
>   않고 소스만 길어진다.** 포매터를 넣은 목적(diff 가독성)에 정면으로 반한다.
> - `apps/ios/**` — `Assets.xcassets`의 `Contents.json`은 **Xcode가 생성하고 소유한다.**
>   우리가 포맷하면 Xcode가 되돌리고 diff가 왕복한다. `.swift`는 애초에 대상이 아니다.

> **알고 감수하는 위험**: `oxlint`는 1.x 안정이지만 **`oxfmt`은 0.x다**(2026-08 기준
> 0.65). 0.x 포매터는 마이너 사이에 포맷 규칙이 바뀔 수 있고, 그러면 **전 파일 재포맷
> diff가 한 번 터진다** — 이 결정이 막으려던 것과 같은 종류의 사고다. 대안이었던
> Biome은 린터·포매터가 같은 2.x 한 도구였다. 그럼에도 Oxc를 고른 것은 두 도구가 같은
> 프로젝트라 설정·무시 규칙이 갈리지 않기 때문이다. 아래 재검토 조건이 이 위험을 잡는다.

**켜는 플러그인 셋.** oxlint 기본값은 `eslint` · `typescript` · `unicorn` · `oxc`뿐이고
나머지는 명시적으로 켜야 한다. 셋을 켠다 — 각각 이 저장소의 결정에 근거가 있다.

| 플러그인 | 근거 |
|---|---|
| `import` | **ADR-0004 D4가 순환 참조를 금지해놓고 강제 수단이 없었다.** `import/no-cycle`을 `error`로 켜서 그 결정을 실제로 지킨다 |
| `react` | ReactLynx가 React 훅 모델을 쓴다. `exhaustive-deps` |
| `vitest` | 러너가 vitest다 (D4) |

**`jsx-a11y`는 켜지 않는다.** 이유가 둘 겹친다 — (1) 규칙이 DOM을 전제한다(`<img>`의 alt,
`<div>`의 role). Lynx는 `<view>`/`<text>`를 렌더하므로 헛돈다. (2) ADR-0001 D3이 접근성
인증 수준을 판정 기준에서 뺐다.

> **알고 감수하는 손실**: oxlint의 `react` 플러그인 규칙 목록에서 **`rules-of-hooks`를
> 찾지 못했다**(2026-08 기준). `exhaustive-deps`는 있다. 즉 **훅을 조건문·반복문 안에서
> 부르는 실수는 lint가 잡지 못한다.** ESLint 대비 실제 손실이고, 그 오류는 런타임에
> 이상한 상태로 나타나 원인 추적이 어렵다. 완화 수단은 `unit`·`ui` 테스트뿐이다.

## 코드 밖의 린트 — 검토하고 지금은 넣지 않는다

린트를 코드에만 걸지, 커밋·문서·스타일까지 걸지 함께 봤다. **넷을 검토했고 넷 다 지금은
넣지 않는다.** 이유가 각각 다르므로 따로 적는다.

| 대상 | 판단 | 이유 |
|---|---|---|
| **커밋 메시지** (commitlint) | 넣지 않음 | **squash라서 `main`에 남는 것은 PR 제목이다**(ADR-0009 D5). 브랜치의 중간 커밋을 검사해도 남지 않는 것을 검사하는 셈이다. 정작 검사할 가치가 있는 PR 제목은 **CI가 있어야 검사되고**, CI는 보류다(ADR-0009 D3) |
| **Markdown 링크** | 넣지 않음 | 가치는 있다 — 이 저장소는 문서가 대부분이고 ADR이 서로를 번호로 참조한다. 실제로 ADR-0008이 대체될 때 참조 다섯 곳이 낡았다. 다만 도구를 하나 더 들이는 비용이 지금 규모에서 이득을 넘는다 |
| **CSS 토큰 이름** (stylelint) | **넣지 못함** | 아래 별도 항목 |
| **스펠 체크 · 브랜치 이름 · 미사용 의존** | 넣지 않음 | 문서가 한국어라 스펠 체크의 효용이 낮고, 브랜치 이름은 CI가 있어야 강제되며, 미사용 의존은 코드가 쌓여야 의미가 생긴다 |

**CSS 토큰 이름 검사는 넣고 싶지만 지금 만들 수 없다.** ADR-0011 D1이 *"`var(--오타)`는
조용히 무시되고 테스트도 스타일을 계산하지 않아 못 잡는다"* 를 **감수하는 실패**로 적어뒀다.
알려진 토큰 이름만 허용하는 검사를 걸면 그 실패가 메워진다. 그런데 **토큰 목록의 출처인
`@libitum/design-tokens`가 아직 배포되지 않았다.** 목록 없이 검사를 만들면 추측이 된다.
ADR-0011의 재검토 조건에 걸어뒀다.

**한 명령은 한 가지 이유로만 실패한다.** `build`가 타입 검사를 겸하면 빌드 실패
로그에서 원인이 타입인지 번들링인지 읽히지 않는다. `lint`가 자동 수정을 겸하면
"통과했다"와 "고쳐서 통과시켰다"가 구분되지 않고, 작업 트리가 조용히 바뀐다.

`verify`가 있는 이유는 ADR-0009와 맞물린다 — CI를 첫 단계에 두지 않기로 했으므로,
CI가 할 일을 사람이 한 줄로 돌 수 있어야 한다. 명령이 넷으로 흩어져 있으면 하나를
빠뜨린 채 PR을 올리게 된다.

### D2. 앱 필터 명령

```sh
pnpm --filter @libitums/mobile <cmd>
```

**루트 스크립트는 `pnpm -r`이 아니라 명시적 `--filter`를 쓴다.**

`-r`은 워크스페이스 전체를 돈다. 지금은 패키지가 하나라 결과가 같지만, 패키지가 늘면
**아무도 고치지 않았는데 명령의 범위가 조용히 넓어진다.** 그런 변화는 명령이 느려지거나
엉뚱한 곳에서 실패할 때에야 발견된다. 범위를 넓히는 것은 명시적 결정이어야 한다.

### D3. 로컬과 CI는 **같은 스크립트**를 쓴다

CI 전용 스크립트를 따로 만들지 않는다. 차이는 인자로만 준다
(`--frozen-lockfile`, `--reporter=json` 등).

근거: "로컬에서는 되는데 CI에서 깨진다"의 가장 흔한 원인은 코드가 아니라 **명령이 다른
것**이다. 스크립트를 하나로 두면 이 원인 자체가 없어진다.

### D4. 테스트 계층 — 셋은 넣고 하나는 넣지 않는다

| 계층 | 첫 단계 | 대상 | 파일 패턴 |
|---|---|---|---|
| `unit` | **포함** | 순수 로직 — 포맷·검증·화면 전환 리듀서(ADR-0007) | `*.unit.test.ts` |
| `ui` | **포함** | 컴포넌트 렌더·상호작용 | `*.ui.test.tsx` |
| `integration` | **포함** | 모듈·훅·컴포넌트의 협력, 인터랙션 이후 시나리오 | `*.integration.test.tsx` |
| `e2e` | **제외** | — | — |

**언제 어느 계층을 쓰는가.** 계층을 선언하는 것과 **쓰게 만드는 것**은 다르다. 위 표는
계층이 무엇인지만 정한다. 아래가 그것을 쓰는 규칙이다.

| 무엇을 바꾸나 | 어느 계층 |
|---|---|
| 순수 함수·리듀서를 만들거나 **반환값을 바꾼다** | `unit` |
| **컴포넌트를 만들거나 렌더 결과·상호작용을 바꾼다** | **`ui` — 같은 PR에서** |
| 모듈·훅의 협력, 인터랙션 이후의 흐름을 바꾼다 | `integration` |
| 내부 리팩터링 — **관찰 가능한 동작이 그대로다** | **새로 쓰지 않는다.** 기존 테스트가 통과하는 것이 증거다 |

기준은 *"눈에 보이는가"* 가 아니라 **"관찰 가능한 동작이 바뀌는가"** 다. 순수 함수도
반환값이 바뀌면 `unit`을 고쳐야 하고, 컴포넌트도 내부만 정리했으면 새 테스트가 필요 없다.

> **`ui`가 덮지 못하는 것을 함께 적는다.** 환경이 jsdom 기반이라 **계산된 스타일과
> 레이아웃을 단언할 수 없다.** 렌더 결과에는 클래스 이름만 남고 색·간격은 계산되지 않는다.
> 즉 `ui`가 덮는 것은 **무엇이 렌더되고 무엇에 반응하는가**이지 **어떻게 보이는가**가 아니다.
> 후자는 D6의 수동 확인 몫이다. 이 구분을 적지 않으면 *"ui 테스트가 있으니 시각 회귀도
> 잡힌다"* 고 오해하게 된다.

**강제 수단은 없다.** ADR-0009 D4의 PR 절차와 같은 형태의 약속이다 — 사람이 diff를 읽을 때
컴포넌트 변경에 `ui` 테스트가 따라왔는지 본다. 잊어도 `verify`는 통과한다.

`ui`·`integration` 계층은 **ReactLynx 전용 testing library**를 쓴다.
`@testing-library/react`를 그대로 쓸 수 없다 — Lynx는 DOM이 아니고 `<view>`/`<text>`
같은 자체 요소를 렌더하기 때문이다.

| 패키지 | 무엇 | 웹 대응물 |
|---|---|---|
| `@lynx-js/react/testing-library` | 렌더·질의·상호작용 | `@testing-library/preact` |
| `@lynx-js/testing-environment` | Lynx 환경 구현 (jsdom 기반) | `jsdom` |

**러너: vitest. 단, 이 라이브러리는 러너에 중립이다.**

공식 지원은 **Rstest와 Vitest 둘**이고, 문서가 둘을 나란히 놓는다. 소스를 보면 중립이
의도된 설계다 — 두 setup 파일이 러너에서 `expect`를 가져오는 줄 하나만 다르고 나머지는
같은 `common/runtime-setup` · `common/bootstrap`을 부른다. 공개 API(`render` ·
`fireEvent` · `screen` · `elementTree`)는 동일하고, 자동 cleanup은 `afterEach`와
`teardown` 중 있는 것을 골라 쓴다.

| | 공유된다 | 갈린다 |
|---|---|---|
| 테스트 코드 | 렌더·질의·단언·스냅샷 직렬화 전부 | `test`·`expect`를 어디서 import 하나 (globals면 그것도 없다) |
| 설정 | — | 설정 파일 하나, 변환 파이프라인(vite vs rspack) |
| 앱 설정 재사용 | — | **rstest에만 `withLynxConfig()`** — `lynx.config.ts`를 읽어 테스트 설정으로 변환한다 |

**vitest를 고르는 근거는 러너 일치다.** e2e를 넣게 되면 `@lynx-js/kitten-lynx-test-infra`가
vitest에서 돈다(아래 D4 e2e 절). 러너를 하나로 두면 설정·리포터·CI 인자가 갈라지지 않는다.
여기에 서버 연동 케이스에서 들일 목킹 도구의 생태계가 붙는다.

**필수 설정**: `vitest.config.ts`에 `@lynx-js/react/testing-library/plugins`의
`vitestTestingLibraryPlugin()`을 넣는다. `createVitestConfig`는 **deprecated**다.
테스트 코드가 러너에 중립이므로, 이 결정을 뒤집는 비용은 **설정 파일 하나 + import 한 줄**이다.

> **제약과 함정 (공식 문서·소스에서 확인)**
>
> - **계산된 스타일과 레이아웃은 없다.** 환경이 jsdom 기반이라 `style` 속성은 선언한
>   문자열 그대로 보존될 뿐 계산되지 않는다. 즉 `ui`·`integration`에서 **간격·색·크기가
>   실제로 어떻게 보이는지는 단언할 수 없다.** 그건 D6의 수동 확인 대상이다
>   (ADR-0011의 토큰 적용도 같은 이유로 자동 검증되지 않는다. `var(--오타)`가 조용히
>   무효가 되는 것도 여기서 안 잡힌다).
> - **`__BACKGROUND__`를 모듈 최상위에서 쓰지 않는다.** 컴포넌트 안에서 평가돼야 하고,
>   최상위에 두면 이중 스레드 동작이 틀어져 테스트 결과가 잘못 나온다.
> - **`rerender` 후에는 `container`를 다시 얻는다.** React Testing Library와 다르다.

**자동화 테스트를 아예 안 넣는 선택지를 버린 이유**: QC 루프를 여러 번 반복하는 것이
예정돼 있다. 반복분을 전부 손으로 돌면 1인 팀의 시간이 그것으로 다 간다. 순수 로직만이라도
자동화하면 손으로 볼 것이 줄어든다.

**`integration`이 다루는 것 — 셋 중 둘을 지금 넣는다.** 이 계층은 "API 목킹"이
아니라 **여러 실제 모듈의 협력**을 보는 자리다. 외부 IO만 경계에서 대체한다.

| 무엇 | 첫 단계 | 서버가 필요한가 |
|---|---|---|
| **함수·컴포넌트·훅 연동** — 개별 구성 요소가 의도한 순서대로 맞물리는가 | **포함** | 아니오 |
| **유저 인터랙션 시나리오** — 클릭·입력 이후 화면 전체가 어떻게 이어지는가 | **포함** | 아니오 |
| **서버 연동** — 성공·에러·갱신 등 응답 케이스별 동작 | **나중에 항목 추가** | 예 |

앞의 둘은 **API 명세와 무관하다.** 지금 있는 것(순수 로직·컴포넌트·화면 전환)만으로
성립한다. 그래서 계층을 통째로 미루지 않는다 — 미루면 `ui` 계층이 단일 컴포넌트만
보는 상태로 남고, **컴포넌트 사이**의 회귀를 잡을 자리가 없어진다.

세 번째만 미룬다. 명세 없이 목을 만들면 명세가 나온 뒤 목과 실제가 갈라진 것을 모른 채
통과하는 테스트가 남고, 그건 테스트가 없는 것보다 나쁘다. **계층을 새로 만드는 게
아니라 기존 파일에 케이스를 더하는 형태**이므로, 명세가 도착해도 구조는 바뀌지 않는다.

목킹 도구(msw 등)는 서버 연동 케이스를 넣을 때 함께 들인다. 그전에는 필요 없다.

**`e2e`를 제외하는 이유**: 수단은 **있다.** 도구가 없다거나 붙이는 비용을 모른다는
근거는 틀렸다. 조사한 결과 Lynx가 직접 만들어 배포하는 도구가 둘이다.

| 도구 | 무엇을 구동하나 | 러너 | 필요한 것 |
|---|---|---|---|
| `@lynx-js/kitten-lynx-test-infra` (0.1.6) | **Lynx Explorer(Android)** 를 CDP-over-ADB로. `page.goto()` · `page.locator()` · 네이티브 탭 | **vitest** | Android 에뮬레이터/실기기 + LynxExplorer APK + adb |
| `web-platform/playwright-fixtures` · `web-core-e2e` | 웹 타깃으로 렌더한 Lynx | Playwright | 웹 타깃 빌드 |

메인테이너가 말한 "Playwright ... via CDP"
([lynx-family/lynx#4208](https://github.com/lynx-family/lynx/discussions/4208),
2025-12-13, zhongyr · Collaborator)는 웹 타깃 쪽을 가리킨 것으로 읽힌다. 네이티브
Explorer 쪽은 Playwright가 아니라 kitten-lynx가 그 자리를 맡는다.

여기서 확정된 사실 둘:

1. **뷰 기반 도구(Maestro·Appium 계열)는 쓰지 않는다.** Lynx는 개별 뷰가 아니라 draw
   pass에서 캔버스로 직접 그린다. 접근성 속성을 붙여도 요소가 잡히지 않는다 — 위
   논의의 최초 보고가 그 증상이다. 구조적으로 신뢰할 수 없다.
2. **devtool이 크로미움 표준 CDP 엔드포인트를 노출하지 않는 것은 맞다.** 전송이
   `ws://127.0.0.1:<port>/mdevices/page/android` 릴레이이고 CDP가 봉투에 싸여 다닌다
   (`lynx-devtool`). `/json/version`·`webSocketDebuggerUrl`은 `lynx-devtool`과
   `debug-router` 어디에도 없다. **다만 그래서 우리가 어댑터를 써야 한다는 결론은
   틀렸다** — `@lynx-js/devtool-connector`가 이미 그 일을 하고 kitten-lynx가 그 위에 있다.

**그럼에도 첫 단계에서 제외하는 이유는 이제 도구가 아니라 환경이다.**

- Android 에뮬레이터 또는 실기기가 테스트 루프에 **상시** 있어야 한다. 에뮬레이터
  부팅 · APK 설치 · `adb reverse`가 로컬 루프에 들어오면 1주 일정에서 반복 비용이 크다.
- **개발도 시연도 iOS다**(ADR-0012). 즉 Android는 다른 이유로 이미 있는 환경이 아니라
  **오직 e2e만을 위해 새로 세우는 환경**이다. 이 결정이 뒤집힐 문턱이 그만큼 높아졌다.
- `0.1.6`이다. API가 움직일 수 있다.
- 첫 단계 성공 기준(ADR-0001 D4-4)이 이미 **사람이 Explorer에서 흐름을 통과시키는
  것**이다. e2e 자동화는 그 수동 확인을 대체하는 것이지, 없던 검증을 더하는 게 아니다.

그래서 첫 단계에는 핵심 사용자 흐름을 사람이 수동으로 확인한다.

**없는 계층의 명령을 미리 만들지 않는다.** `test:e2e`가 스크립트에 있고 테스트 파일이
0개면 종료 코드 0이 나온다. 그러면 "E2E가 통과했다"로 읽힌다. 통과와 부재는 구분돼야 한다.

### D5. 종료 코드

- 모든 명령은 실패 시 non-zero, 성공 시 0.
- `dev`는 장시간 프로세스이므로 이 계약에서 제외한다.
- **경고를 실패로 올리지 않는다.** `lint`는 에러만 non-zero다. `--max-warnings=0`을
  첫 단계에 넣지 않는다 — 프로토타입 속도를 깎고, 사람들이 경고를 끄는 방향으로
  움직이게 만든다.

### D6. `e2e`를 자동화하지 않는 대신, **e2e 대상 목록을 관리한다**

D4가 `e2e` 계층을 첫 단계에서 뺐다. 그러면 ADR-0001 D4-4("핵심 사용자 흐름을 Explorer
에서 처음부터 끝까지 수동으로 통과한다")가 **무엇을 통과시키라는 것인지 적힌 곳이 없다.**
0001은 성공 기준을 "재현 가능한 명령으로 적는다"고 해놓고 4번만 그것을 못 지키고 있다.
이 결정이 그 구멍을 메운다.

**위치**: `docs/e2e/` 아래에 **흐름 하나당 파일 하나.** `docs/conventions/` 아래에 두지
않는다 — 규약이 아니라 **검증 대상**이고, 규약 문서는 짧게 유지해야 한다(ADR-0010 D1).

```text
docs/e2e/
  README.md          형식 · 갱신 규칙 · 공통 전제. **목록은 두지 않는다**
  login.md
  <flow>.md          파일 하나 = 흐름 하나 = 나중의 테스트 파일 하나
```

**목록을 만들지 않는 이유**: 인덱스를 두면 그 인덱스가 디렉터리와 갈라지고, 아래에서
감수하기로 한 "목록이 화면과 갈라진다"가 **한 겹 더** 생긴다. 목록은 디렉터리 자체다.
폴더를 열어 화면 목록과 대조할 수 있다는 것이 곧 검증 수단이다(ADR-0003과 같은 논리).

**공통 전제는 `README.md`에 한 번만 쓴다.** 로그인이 있으므로(ADR-0012) 거의 모든
흐름이 "로그인된 상태에서 시작"으로 열린다. 파일마다 반복해 적으면 로그인 흐름이
바뀔 때 전부 고쳐야 한다.

**형식**: 파일 하나가 **나중의 테스트 파일 하나와 1:1**이 되게 쓴다.
`docs/e2e/login.md` → `login.e2e.test.ts`. 파일명이 대응을 강제한다.

```text
# <흐름 이름>              → 나중에 describe / test 이름
전제: <시작 상태>            → 나중에 beforeEach / goto
단계: 1. … 2. … 3. …        → 나중에 locator + tap/input
관찰: <무엇이 보이면 통과인가>  → 나중에 expect
```

**"관찰"은 인상이 아니라 식별 가능한 요소로 쓴다.** 자동화 도구가 CSS 셀렉터로 요소를
찾으므로(`page.locator('#id')`), "자연스럽게 보인다"가 아니라 "`#submit`이 사라지고
`#result`에 총액이 뜬다"로 쓴다. 이렇게 쓰면 이관이 기계적이다.

**갱신 규칙**: 화면을 추가하거나 흐름을 바꾸는 PR에서 **해당 흐름의 파일을 같은 PR에서**
고친다(ADR-0010 D4와 같은 형태). 강제 수단은 없다 — 약속이다. 파일이 갈려 있으므로
**PR diff에 어느 흐름이 바뀌었는지가 그대로 드러난다** — 약속을 지키기 쉬운 쪽이다.

**언제 채우나**: **디렉터리와 `README.md`만 지금 만든다.** 흐름 파일은 화면이 생길 때
하나씩 더한다.
앱이 없는 상태에서 단계를 쓰면 추측이 되고, 추측으로 쓴 체크리스트는 처음 도는 순간
전부 틀린다.

**이 결정이 바꾸는 것**: `e2e` 제외의 대가가 "회귀를 자동으로 못 잡는다"에서 **"회귀를
사람이 잡되, 무엇을 볼지는 고정돼 있다"** 로 낮아진다. 그리고 나중에
`@lynx-js/kitten-lynx-test-infra`를 들일 때 이 목록이 그대로 테스트 명세가 되므로,
자동화를 미루는 비용이 "나중에 처음부터 다시 생각하기"에서 "옮겨 쓰기"로 줄어든다.

**실패하는 방식 둘 — 알고 감수한다.**

1. **강제되지 않는다.** 건너뛰어도 아무 일이 일어나지 않는다. QC를 반복하는 동안
   "이번엔 이 흐름 안 봐도 되겠지"가 쌓이면 목록만 남고 아무도 돌지 않는다.
2. **파일이 화면과 갈라진다.** 화면을 고치고 그 흐름의 파일을 안 고치면 죽은 문서가
   된다. 죽은 체크리스트는 없는 것보다 나쁘다 — 돌았다고 착각하게 만든다. 갱신 규칙이
   유일한 완화책이고 그것도 약속이다.
3. **전체를 한 번에 훑기 어렵다.** 단일 파일이었다면 스크롤 한 번이었다. 흐름이 적을
   때는 이쪽이 손해다. `ls docs/e2e/`로 목록은 보이지만 내용은 파일을 열어야 한다.


## 버린 대안

- **`build`에 typecheck 포함** — 한 번에 도니 편하지만 실패 원인이 섞인다 (D1).
- **`pnpm -r`을 루트 스크립트로** — 범위가 조용히 넓어진다 (D2).
- **CI 전용 스크립트 분리** — 로컬/CI 괴리의 원인을 만든다 (D3).
- **자동화 테스트를 첫 단계에 아예 안 넣기** — 반복되는 QC를 전부 수동으로
  돌게 된다.
- **네 계층을 전부 선언하고 비워두기** — 빈 계층이 종료 코드 0을 내서 통과로 읽힌다 (D4).
- **`@testing-library/react`를 그대로 사용** — Lynx가 DOM이 아니라 동작하지 않는다.
  `@lynx-js/react/testing-library`가 그 자리를 맡는다 (D4).
- **Rstest** — 공식이 동등하게 지원하고, 앱에는 `withLynxConfig()`로 `lynx.config.ts`를
  테스트 설정에 재사용하는 경로까지 있다. rspack 기반이라 빌드와 변환 파이프라인도 같다.
  그럼에도 vitest를 고른 이유는 **e2e까지 러너를 하나로 두기 위해서**다(D4). 테스트
  코드가 러너에 중립이므로 이 선택은 나중에 싸게 뒤집을 수 있다.
- **Maestro·Appium 같은 뷰 기반 E2E 도구** — Lynx가 캔버스로 직접 그려서 요소가 잡히지
  않는다. 시도해볼 대상조차 아니다 (D4).
- **`--max-warnings=0`** — 1주 일정에서 경고 정리에 시간을 쓰게 된다 (D5).
- **Biome** — 린터와 포매터가 **같은 성숙도(2.x)로 한 도구** 안에 있다. `oxfmt`이 0.x인
  것과 대비된다. 버린 이유는 Oxc 쪽이 린터 규칙 수와 속도에서 앞서고, 두 바이너리가
  같은 프로젝트라 설정이 갈리지 않기 때문이다 (D1).
- **ESLint + Prettier** — 생태계 규칙이 가장 많다. 그러나 **Lynx 전용 lint 플러그인이
  없음을 확인했으므로**(lynx-stack에 해당 패키지 없음) 그 이점의 상당 부분이 이
  저장소에서는 살아나지 않는다. 의존과 설정 파일만 늘어난다 (D1).
- **포매터 없이 린터만** — 의존이 하나 준다. 그러나 diff 잡음을 막을 수단이 사라지고,
  그것이 이 저장소의 유일한 품질 게이트를 약화시킨다 (D1).
- **`format`을 `verify`에서 빼기** — `verify`가 짧아진다. 그러나 검사되지 않는 포맷은
  적용이 사람 기억에 달리고, 드리프트가 쌓인 뒤에 한꺼번에 드러난다 (D1).
- **e2e를 빼고 목록도 안 남기기** — 무엇을 수동으로 봐야 하는지가 사람 머리에만 남고,
  나중에 자동화할 때 처음부터 다시 정해야 한다 (D6).

## 대가

- `verify`를 **사람이 기억해서** 돌아야 한다. CI가 없으므로(ADR-0009) 강제 수단이 없다.
  잊으면 깨진 채로 머지된다. 규약 문서(ADR-0010)에 "PR 전 `verify`"를 적지만,
  **문서는 강제가 아니다.** 이 공백은 CI 도입 전까지 닫히지 않는다.
- `e2e`가 없으므로 실제 기기 위의 동작(호스트·번들 로드·기기 입력)은 자동으로 못 잡는다.
  `integration`이 화면 간 흐름을 덮지만 그것은 러너 안에서의 흐름이다. 기기 위의 회귀는
  D6의 목록을 사람이 도는 것으로만 잡힌다.
  QC 반복의 상당 부분이 수동으로 남는다.
- 경고를 실패로 안 올리므로 경고가 쌓인다. 프로토타입 이후 정리 비용이 된다.

## 재검토 조건

- API 명세 도착 → `integration`에 **서버 연동 케이스 추가** (계층은 이미 있다)
- Android 에뮬레이터를 로컬 또는 CI 루프에 상시 둘 수 있게 되는 시점 → D4의 `e2e` 계층
  (`@lynx-js/kitten-lynx-test-infra` + vitest). **도구 조사는 끝났다. 남은 건 환경뿐이다.**
  이때 D6의 목록이 그대로 입력이 된다
- `docs/e2e/`의 흐름 파일이 두 번 연속 갱신되지 않은 채 화면이 바뀐 것이 발견되면 → D6의
  갱신 규칙. 약속으로 안 되면 다른 수단을 찾는다
- **CI가 도입되면**(ADR-0009 D3) → D1의 "코드 밖의 린트" 표를 다시 본다. PR 제목 검사와
  Markdown 링크 검사가 그때 비용 없이 붙는다
- **`oxfmt`이 1.0에 도달하면** → D1. 0.x라서 감수한 위험이 사라진다. 그때까지는 버전을
  **정확 버전으로 고정**하고, 올릴 때 재포맷 diff가 나는지 먼저 본다
- **`oxfmt` 마이너 상향에서 전 파일 재포맷이 발생하면** → D1. 감수한 위험이 실제로
  터진 것이므로, 그 시점에 Biome 전환을 다시 검토한다
- 빌드 설정과 테스트 설정이 갈리기 시작하면(alias·define·플러그인을 두 곳에 적게 되면)
  → D4의 러너. rstest의 `withLynxConfig()`가 그 갈라짐을 없앤다. 테스트 코드는 그대로 둔다
- CI 도입(ADR-0009) → `verify`의 강제 수단이 생긴다. D5의 경고 정책도 이때 다시 본다

## 정정 기록

**2026-08-25 — 사실 보강.** 결정(명령 여섯·계층 셋·e2e 제외·목록 관리)은 그대로다.

D4가 **"러너: vitest"** 한 줄로 끝나 있었다. 공식 지원이 Rstest와 Vitest 둘이고 앱용
경로(`withLynxConfig`)는 rstest 쪽에만 있다는 사실을 **검토한 흔적이 없었다.**
ADR-0007과 같은 모양의 실수다 — 웹 생태계의 기본값을 근거 없이 가져왔다.
선택은 유지하되 근거와 버린 대안을 채웠다.

함께 채운 것: vitest의 필수 플러그인, 계산된 스타일·레이아웃 부재, `__BACKGROUND__`
최상위 함정, `rerender` 후 `container` 재취득, `build`에서 타입 검사 플러그인을 빼는
것이 결정의 일부라는 점, `preview` 명령.

**2026-08-25 — D1에 린터·포매터 도구와 `format` 명령을 넣었다.** 명령과 정책(`lint`,
`lint:fix`, 경고를 실패로 올리지 않는다)은 정해져 있었는데 **도구가 비어 있었다.**
골격을 세우는 단계에서 그 공백이 드러났다 — 명령만 있고 도구가 없으면 스크립트가
종료 코드 0을 내고, 그건 D4가 `test:e2e`를 두고 금지한 것과 같은 실패다.

함께 `format`·`format:check`를 더하고 `verify`의 구성을 바꿨다(앞에 `format:check`).
`verify` 구성을 인용하던 ADR-0001 D4-2 · ADR-0005 D4-2 · ADR-0012 D6도 함께 고쳤다.

**제자리에서 고친 근거**: `package.json`이 아직 커밋되지 않았다. 실체화 전이다
(ADR-0010 D10).

**2026-08-25 — D6의 저장 형태를 바꿨다.** `docs/e2e-scenarios.md` 하나 → `docs/e2e/`
아래 흐름당 파일 하나.

결정의 뼈대(e2e를 자동화하지 않는 대신 대상을 관리한다)는 그대로다. 바뀐 것은 저장
형태이고, 이유는 셋이다 — (1) 단일 파일은 **모든 PR이 같은 파일을 건드려** 무엇이
바뀌었는지 diff에서 안 보인다, (2) 파일명이 곧 테스트 파일명이 되어 **1:1이 사람의
규율이 아니라 이름으로 강제**된다, (3) 디렉터리 목록이 그대로 커버리지가 된다.
