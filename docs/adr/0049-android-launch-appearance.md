# ADR-0049 — Android 실행 시 색과 적응형 아이콘: 시작 구간을 JS 스플래시와 같은 주황으로 잇고, 런처 아이콘은 지금 원본으로 먼저 낸다

- 상태: **채택.** 「상태바 아이콘 전환은 후속 작업으로 분리」 · 「시스템 스플래시에 아이콘 없음」 · 「적응형 아이콘은 지금 원본으로 먼저」 · 「API 31+ 시작 구간의 상태바 아이콘이 나빠진 것을 받아들인다」는 **사용자 결정이다**(2026-10-06 — 아래 「사용자 결정」 U1 ~ U3 · U7).
  에뮬레이터 두 대(Pixel_8 AVD · API 37, R6_API30 AVD · API 30)에서 실행했다(2026-10-06).
  ⚠ **이 변경은 API 31+에서 시작 구간의 상태바 아이콘을 나쁘게 만들었다 — 알고 받아들인다.** 구현 전에는 그 구간이 회백색 바탕 · 검정 아이콘(색 쌍 20.12:1)이었고, 구현 뒤에는 주황 바탕 · 흰 아이콘(색 쌍 3.016:1 — 여유가 사실상 0이고, 띠 안의 시계 글자는 텍스트 기준 4.5:1에 못 미친다)이었다가 앱이 뜬 뒤 어두운 아이콘으로 **한 번 뒤집힌다**(「이 작업이 만든 변화」).
  **알고 받아들인 후퇴다** — 사용자가 접근성 점검의 수치와 주황 번쩍임 관찰 결과를 보고받은 뒤 직접 골랐다(U7). 첫 판은 root가 기본값으로 진행한 상태였고 리뷰가 그것을 되돌렸다(「정정 기록」).
  ⚠ **적응형 아이콘은 진짜 레이어 분리가 아니다.** 원본이 배경까지 합쳐진 1024px 한 장뿐이라 그 전체를 줄여 전경으로 쓰고 배경은 단색으로 뒀다(D5).
  ⚠ **실기 · 제조사 런처 · 테마 아이콘 모드 · API 26 ~ 29 · 31 ~ 36은 확인하지 않았다**(「확인한 것과 확인하지 못한 것」).
- 날짜: 2026-10-06
- 다루는 축: Android 앱을 켤 때 시스템이 그리는 구간(API 30 이하의 시작 창 · API 31+의 시스템 스플래시 · Lynx가 첫 프레임을 그리기 전의 창)의 색과 시스템 바 설정 ·
  앱 테마(`Theme.Duru`)의 API 수준별 구조 · 런처 아이콘(적응형)의 구성 · 디자인 토큰 값을 Android 리소스에 옮기는 방식
- 이어받는 결정: [ADR-0038](0038-android-minimal-host.md)(Android 최소 호스트 — 테마 · 아이콘을 다루지 않았다),
  [ADR-0014](0014-design-system-consumption-verified.md) D1 · D4 · D7(색은 `@libitums/design-tokens`의 토큰으로 쓰고 패키지에 없는 값을 지어내지 않는다 · 다크 모드는 제외),
  [ADR-0044](0044-android-tappable-inset.md)(edge-to-edge · 투명 시스템 바 — `MainActivity.layoutEdgeToEdge`가 코드로 적는 설정),

  [ADR-0046](0046-android-play-release.md) D2(`minSdk` 26 — API 25 이하 폴백 아이콘이 필요 없는 근거).

  공유 JS가 바뀌지 않아 성능 보고서 게이트 대상이 아니다.

근거 표시는 넷이다. **[코드 확인]** 이 저장소의 파일을 읽었다 · **[SDK 파일]** `~/Library/Android/sdk/platforms/android-36/data/`의 `res/values/*.xml` · `api-versions.xml`을 읽었다 ·
**[실측]** 2026-10-06, 위 두 에뮬레이터에서 잡은 프레임 · 스크린샷의 픽셀(무손실 `screencap` PNG는 값 그대로, `screenrecord` 영상은 코덱 오차가 있어 「영상」이라고 적는다) · **[추론]** 관찰 없이 이어 붙였다.
Android 공식 문서의 규격 수치(적응형 아이콘의 캔버스 · 안전 영역 등)는 이 작업에서 다시 열어 보지 못했다 — 기억으로 옮긴 것은 **[기억]** 으로 적는다.

## 맥락

이 변경 전 매니페스트의 아이콘은 `@drawable/app_icon`, 테마는 `@android:style/Theme.Material.Light.NoActionBar`였고, `res/`에 `mipmap-*` · 테마 · 색 리소스가 하나도 없었다 [코드 확인].
출시 관점 리뷰가 「실행 시 흰 화면」 · 「적응형 아이콘 없음」 · 「화면별 상태바 아이콘 색」 셋을 남겼고, 작업 `android-launch-appearance`의 계약 단계가 셋을 실측으로 가렸다.

1. **실행할 때 회백색 화면이 실제로 보였다** [실측]. API 37은 시스템 스플래시가 `#FAFAFA` 바탕에 흰 원 안의 축소된 정사각 아이콘(220px)으로 3.1 ~ 3.4초 보인 뒤 주황 JS 스플래시로 바뀌었다.
   API 30은 아이콘 없는 `#FAFAFA` 창이 0.57 ~ 0.60초 보였다. 3초대라는 길이는 느린 16 KB 페이지 에뮬레이터 이미지의 값이고 실기의 값이 아니다 [추론]. 색과 순서는 기기와 무관하다고 본다.
   - `#FAFAFA`는 `Theme.Material.Light`의 `windowBackground`가 풀린 값이다 [SDK 파일: `themes_material.xml` · `colors_material.xml`의 `material_grey_50`].
   - API 30에서 번들을 읽지 못한 실행(`debug` 빌드가 번들 서버 아닌 포트를 읽었다)에서는 시작 창의 상태바 띠가 회색(영상 `#747474` — 테마 `colorPrimaryDark` = `#757575` [SDK 파일]), 내비게이션 바가 검정이었다.
     번들을 읽은 실행에는 옅어지는 꼬리만 있었다.
2. **런처 아이콘이 흰 원 안에 축소돼 들어갔다** [실측]. API 37 홈 하단 줄에서 원 지름 157px 가운데 그림은 정사각 72px(46%)이고 양옆에 흰 띠가 27px씩 있었다. API 30 앱 서랍도 같은 모양이었다(수치는 재지 않았다).
3. **JS 스플래시의 색은 디자인 토큰 하나다** [코드 확인]. `.splash-screen` · `.app-splash`가 `var(--libitum-color-brand-primary)`를 쓰고, 그 값은 이 저장소가 아니라
   `@libitums/design-tokens@0.3.0`의 `dist/css/variables.css`에 `#F46B18`로 정의돼 있다. 다크 변형은 그 패키지에 없다. iOS 실행 화면(`LaunchScreen.storyboard`)도 같은 값이고 서브뷰가 없다 — 주황 한 면이다.
4. **`MainActivity.layoutEdgeToEdge`는 시스템 바 설정을 `onCreate`에서 코드로 적는다** [코드 확인] — 투명 상태바 · 내비게이션 바, 어두운 아이콘(`setAppearanceLightStatusBars(true)` · `setAppearanceLightNavigationBars(true)`).
   창 배경을 건드리는 코드는 없다. 그래서 `onCreate` 전에 시스템이 그리는 시작 창에는 이 설정이 닿지 않고 테마 값이 그대로 쓰인다(1의 회색 띠 · 검정 바가 그 결과다).
5. **아이콘의 원본은 배경까지 합쳐진 한 장뿐이다** [코드 확인]. `drawable/app_icon.png`는 1024×1024 RGB(알파 없음)였고 iOS의 `AppIcon.png`와 바이트가 같았다. 저장소에 SVG · 레이어가 나뉜 원본 · 단색 마크가 없다(`git ls-files`).
   그림은 대각 그러데이션 배경(`#FDA920` → `#FD3F29`)에 긴 그림자가 구워져 있고, 마크 안쪽 음영이 배경과 같은 주황 ~ 분홍 계열이다.
   마크의 가장 먼 점이 캔버스 중심에서 폭의 39.7%다 [실측 — 원본의 픽셀].
6. **`windowSplashScreen*` 속성은 API 31, `windowLightNavigationBar`는 API 27, `AdaptiveIconDrawable`은 API 26에 생겼다** [SDK 파일: `api-versions.xml`]. `minSdk`가 26이라 API 25 이하 폴백 비트맵과 `roundIcon`은 필요 없다.
   `windowSplashScreenBackground`를 지정하지 않으면 「system will calculate from windowBackground」다 [SDK 파일: `attrs.xml`의 주석 — API 37 실측(스플래시 바탕 = 창 배경)과 일치].
7. **어두운 화면 위의 상태바 아이콘이 가려진다** — 서사 화면(`#1B1613`) 위의 아이콘이 `#000000`이라 대비 1.17:1이다 [앞선 작업의 캡처를 픽셀로 읽음]. 어두운 상단을 가진 표면이 8종이다 [코드 확인 — 디자인 단계가 CSS에서 셌다].
   고치려면 화면이 호스트에 「지금 상태바 뒤가 어둡다」를 알리는 경로(공유 JS + 새 호스트 접점)가 든다 — route 이름으로는 가를 수 없다(한 route 안에서 단계가 바뀌고, 둘은 route가 아니라 겹침 레이어다).

### D1. 실행 색은 `#F46B18` 하나다 — 디자인 토큰 `--libitum-color-brand-primary`의 사본

Android XML은 CSS 변수를 읽지 못하므로 값을 `res/values/colors.xml`에 한 번 옮겨 적는다 [코드 확인].

| 리소스 | 값 | 쓰는 곳 |
|---|---|---|
| `@color/libitum_color_brand_primary` | `#F46B18` | 토큰의 사본. 이름이 출처를 말한다(토큰 이름을 snake_case로 옮겼다) |
| `@color/launch_background` | `@color/libitum_color_brand_primary` | 창 배경 · 시스템 스플래시 배경 |
| `@color/ic_launcher_background` | `@color/libitum_color_brand_primary` | 적응형 아이콘의 배경 레이어 |

- **결합**: 값이 두 곳(npm 패키지의 CSS · Android `colors.xml`)에 있다. **토큰 값이 바뀌면 `colors.xml`도 함께 바꿔야 한다.**
- **그 결합을 지키는 검사**: `devtools/android-bundle/host-launch-appearance.integration.test.mjs`의 HL2가 `launch_background`를 별칭 끝까지 풀어
  `@libitums/design-tokens`의 `variables.css`에 적힌 `--libitum-color-brand-primary`와 같은 `#RRGGBB`인지 본다. 어긋나면 — 토큰 파일을 찾지 못해도 — `pnpm test:android-bundle`(= `pnpm verify`)이 실패한다 [코드 확인].
  구분력은 한 번 확인했다: `launch_background`를 `#FFFFFF`로 바꾼 사본에서 HL1 · HL2와 계측 IC1 · IC3이 실패했다 [실측 — API 37].
- 새 토큰을 만들지 않았다. 필요한 색이 기존 토큰 하나다(ADR-0014 D4).
- **iOS의 사본은 이 검사 밖이다.** `LaunchScreen.storyboard`도 같은 값을 따로 적어 두고 있고 [코드 확인], 그 값과 토큰을 비교하는 검사는 이 변경이 더하지 않았다(iOS 변경 0).

### D2. 시스템 스플래시(API 31+)는 주황 한 면이고 아이콘이 없다 (사용자 결정 U2)

`values-v31/themes.xml`이 `android:windowSplashScreenBackground`를 `@color/launch_background`로, `android:windowSplashScreenAnimatedIcon`을 `@drawable/splash_icon_none`(전부 투명한 `shape`)으로 둔다 [코드 확인].

- iOS 실행 화면과 같은 인상이다 — 주황 한 면 다음에 JS 스플래시가 그 위에 흰 워드마크를 쓴다.
- **투명 drawable이 아이콘과 흰 원을 실제로 지운다** [실측 — API 37]. 계약 단계에서는 [기억]이었다. 무손실 캡처 여섯 장(첫 실행의 1.6초 · 다크 모드 1.6초, 새 실행의 1.0초 둘 · 0.6초 하나 · 다크 모드 1.6초)에서
  여섯 표본점이 정확히 `#F46B18`이고 화면 가운데 400×400px에 다른 픽셀이 0이었다. **API 31 ~ 36에서도 그런지는 재지 않았다.**
- `windowSplashScreenBackground`는 지정하지 않아도 창 배경에서 계산되지만(맥락 6) 그것에 기대지 않고 적는다.
- 그 밖의 스플래시 속성(`windowSplashScreenIconBackgroundColor` · `windowSplashScreenBrandingImage` · `windowSplashScreenAnimationDuration` · `windowSplashscreenContent`)은 두지 않는다(검사 규칙 `splash-icon`).

### D3. `androidx.core:core-splashscreen` 의존성을 넣지 않는다

플랫폼 속성만으로 닫힌다. 그 라이브러리가 주는 것은 (1) API 30 이하에도 「가운데 아이콘」 스플래시를 흉내 내는 것과 (2) 스플래시를 붙잡아 두는 조건 · 나가는 애니메이션 API다 [기억].
(1)은 원하지 않는다(D2 — 아이콘 없음. API 30 이하는 창 배경만 주황이면 JS 스플래시로 그대로 이어진다 [실측 API 30]). (2)는 범위 밖이다.
넣으면 Gradle 의존성과 `onCreate`의 설치 호출이 는다 — 호스트는 `android.app.Activity`를 그대로 쓰고 테마 부모도 플랫폼 테마다 [코드 확인].
HL4가 `app/build.gradle`에 `core-splashscreen` 문자열이 없음을 가드로 본다 [코드 확인].

### D4. `Theme.Duru` — 속성은 자기 API 수준 이상의 한정자에만 둔다

매니페스트 `<application android:theme>`가 `@style/Theme.Duru`다. `<activity>`에 테마를 따로 주지 않는다 — `PushNotificationTapActivity`(알림을 누르면 뜨고 `onCreate`에서 곧바로 `MainActivity`를 띄운 뒤 끝나는 중계)도 같은 테마를 물려받는다 [코드 확인].
그 Activity의 창이 보인다면 이제 주황이다 — 앱이 밝은 화면을 보이는 중에 알림을 누르면 주황이 번쩍일 수 있다는 것이 리뷰의 추론이었고, **영상에서는 관찰되지 않았다**
[실측 — API 37, 앱이 앞에 있을 때 2회 · 홈에서 2회 모두 주황 프레임 0장. 한계는 「확인한 것과 확인하지 못한 것」].
부모는 이전과 같은 `@android:style/Theme.Material.Light.NoActionBar`다(AppCompat · Material Components 테마를 들이지 않는다).

**API 수준별로 풀린 값** [코드 확인 — 계측 IC1 · IC3이 기기에서 풀린 값을 본다]:

| 속성 | API 26 (`values/`) | API 27 ~ 30 (`values-v27/`) | API 31+ (`values-v31/`) |
|---|---|---|---|
| `android:windowBackground` | `@color/launch_background` | 같음 | 같음 |
| `android:statusBarColor` · `android:navigationBarColor` | `@android:color/transparent` | 같음 | 같음 |
| `android:windowLightStatusBar` | `true` | 같음 | 같음 |
| `android:windowLightNavigationBar` | (없음 — API 27 속성) | `true` | `true` |
| `android:windowSplashScreenBackground` | (없음 — API 31 속성) | (없음) | `@color/launch_background` |
| `android:windowSplashScreenAnimatedIcon` | (없음) | (없음) | `@drawable/splash_icon_none` |

- **한정자끼리 스타일이 합쳐지지 않는다.** `values-v27` · `values-v31`의 `Theme.Duru`는 `values/`의 것을 통째로 대체하므로 세 파일이 각각 풀린 값 전체를 적는다 [코드 확인 — `values/themes.xml`의 주석].
  **이 세 파일 안에서** 한 파일만 고치고 다른 파일을 잊는 어긋남은 `host-launch-appearance.mjs`의 `launchAppearanceIssues`(규칙 12개)가 `pnpm test:android-bundle`에서 잡는다.
  **그 판정이 보는 것은 계약이 열거한 한정자 셋(API 26 · 27 · 31에서 풀린 값)뿐이다** [코드 확인 — 리뷰]. 다른 한정자의 덮어쓰기 — `values-v29` · `values-v33` · `values-land` · `values-ko`의 `Theme.Duru`,
  `mipmap-anydpi-v33/ic_launcher.xml`, `drawable-v31/splash_icon_none` — 는 **잡지 못한다**(`values-night*`만 따로 본다). 그런 파일은 지금 없다. 검사를 넓히는 일은 「후속 과제」 6이다.
- **시스템 바 설정을 테마에도 적는 이유**: `layoutEdgeToEdge`가 코드로 적는 값(맥락 4)을 `onCreate` 전의 시작 창에도 주려는 것이다. `MainActivity`는 고치지 않았다 — 테마는 같은 값을 더할 뿐이다.
  - **API 30 이하의 시작 창은 이 값을 따른다** [실측 — API 30]. 회색 상태바 띠와 검정 내비게이션 바가 사라졌고(구현 뒤 영상 넷에서 0장) 어두운 아이콘이 처음부터 보인다. API 26 ~ 29는 재지 않았다 [추론: 같다].
  - **API 31+의 시스템 스플래시는 `windowLightStatusBar` · `windowLightNavigationBar`를 따르지 않는다** [실측 — API 37]. 계약 단계의 추론이 틀렸다(「이 작업이 만든 변화」).
    그래도 `values-v31/`에 그대로 둔다 — `true`와 `false`의 결과가 같아 해롭지 않고 [실측], 그 한정자에서만 빼면 수준마다 값이 달라져 판정이 복잡해질 뿐 얻는 것이 없다.
- 3버튼 내비게이션에서 시스템이 내비게이션 바 자리에 까는 밝은 가림막(API 30의 주황 위 `#FEF0E8` [실측])은 그대로 남는다. 이 변경이 바꾸지 않는다.

### D5. 적응형 아이콘 — 지금 원본 전체를 80/108로 줄인 전경 + 단색 배경. monochrome 없음 (사용자 결정 U3)

| 리소스 | 내용 |
|---|---|
| `mipmap-anydpi-v26/ic_launcher.xml` | `<adaptive-icon>` — 배경 `@color/ic_launcher_background`, 전경 `@mipmap/ic_launcher_foreground`. **`<monochrome>` 없음** |
| `mipmap-{mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}/ic_launcher_foreground.png` | 정사각 108 · 162 · 216 · 324 · 432px RGBA. 원본 그림 **전체**를 캔버스의 80/108(80dp)로 줄여 가운데 두고 사방 14dp는 투명 |

- 매니페스트 `android:icon`은 `@mipmap/ic_launcher`다. `android:roundIcon` · API 25 이하 폴백(`mipmap-*/ic_launcher.png`)을 두지 않는다(맥락 6). `drawable/app_icon.png`는 지웠다 — 참조가 매니페스트 한 곳뿐이었다 [코드 확인 — HL5].
  알림의 작은 아이콘은 `ic_notification`이고 이 변경과 무관하다 [코드 확인].
- **진짜 레이어 분리가 아니다.** 원본이 배경까지 합쳐진 한 장이라(맥락 5) 마크만 떼어 낼 수 없다 — 색 임계값으로 떼면 마크 아래쪽이 통째로 빠지고 안에 구멍이 난다(디자인 단계가 해 봤다).
  배경만 만들려면 마크와 긴 그림자에 가려진 부분을 지어내야 한다. 그래서 **그림 전체를 전경으로** 쓴다.
- **80dp의 근거** [실측값(마크 반지름 39.7%) + 적응형 아이콘 규격의 산술 — 규격 수치(캔버스 108dp · 뷰포트 72dp · 안전 영역 지름 66dp)는 기억]:
  원본을 108dp에 그대로 깔면 마크 반지름이 42.9dp로 원형 마스크(36dp)를 넘어 잘린다. 마크가 안전 영역에 드는 상한이 83dp, 정사각 가장자리가 72dp 뷰포트 밖에 남는 하한이 72dp다. 그 사이의 80dp를 디자인 단계가 골랐다
  (마크는 안전 영역 안 1.3dp, 정사각 가장자리는 뷰포트 밖 4dp).
- **정지 상태에서 배경 레이어는 보이지 않는다.** 80dp 정사각이 72dp 뷰포트를 완전히 덮는다. 배경 단색을 원본 가장자리의 평균색이 아니라 토큰 값으로 둔 것은 그래서다 — 새 색을 들이지 않는다.
- **한계 셋**(디자인 단계의 판정):
  1. **이음매.** 전경 정사각의 가장자리(모서리마다 다른 그러데이션 색)와 단색 배경이 뷰포트 밖 4dp에서 만난다. 런처가 레이어를 따로 움직이는 효과를 쓰면 그 경계가 드러날 수 있다 [추론 — 런처별 동작을 모른다].
     에뮬레이터 기본 런처의 길게 누르기 · 끌기에서는 보이지 않았다 [실측 — API 37 · API 30, 눈으로 본 관찰].
  2. **적응형의 이점이 없다.** 전경과 배경이 따로 움직이는 깊이감이 없다.
  3. **iOS보다 마크가 커 보인다.** iOS는 마크가 아이콘 폭의 59%, Android 원형 마스크에서는 원 지름의 65%다 [원본 수치의 산술].
- **monochrome을 넣지 않는 이유**: 단색 마크 원본이 없고, 지금 그림은 윤곽이 아니라 안쪽 음영의 겹침으로 읽혀 단색으로 누르면 모양이 깨진다. 테마 아이콘을 켠 사용자에게 무엇이 보이는지는 확인하지 않았다.
- **전경 PNG는 iOS `AppIcon.png`에서 만든 사본이다.** 두 그림이 같은지 지키는 검사는 없다 — 원본이 바뀌면 사람이 `apps/android/tools/generate-launcher-foreground.swift`로 다시 만든다(방법은 [Android 호스트 README](../../apps/android/README.md)의 「실행 화면과 런처 아이콘」).
  크기와 알파 채널은 HL3이, 기기에서 풀린 레이어의 배치는 계측 IC2가 본다.
- **교체 조건**: 디자인 원본(「후속 과제」 4의 R1 ~ R4)이 오면 **리소스 이름을 바꾸지 않고** 레이어 파일만 교체한다. 배경이 그림이 되면 `ic_launcher.xml`의 배경 한 줄, 단색 마크(R3)가 오면 `<monochrome>` 한 줄과 검사 규칙 `adaptive-icon`의 그 조건이 바뀐다.

### D6. 실행이 끝난 뒤에도 창 배경을 주황으로 둔다 — `MainActivity` 변경 0

첫 화면이 선 뒤 창 배경을 셸 색(`#FFFDFC`)으로 되돌리는 코드를 두지 않는다(U4 — 묻지 않은 기본값).

- `MainActivity`가 새로 만들어질 때마다 JS가 부팅해 주황 스플래시부터 그린다 [코드 확인 — 초기 route가 `splash`]. 「Lynx가 그리기 전」의 올바른 색은 언제나 주황이다.
- Lynx가 그린 뒤에는 셸이 화면 전체에 배경을 칠한다 [코드 확인]. **주황 창 배경이 드러난 캡처는 0장이다** [실측 — API 37]: 키보드 4장 · 화면 전환 6장 · 분할 화면 2장 · 최근 앱 복귀 2장 · 구성 변경(다크 모드 · 화면 크기) 4장 모두 「가로줄의 절반 이상이 정확히 `#F46B18`인 줄」이 0이었다.
  **한계: 단일 캡처다**(0.2초 이상 간격). 전환 중의 프레임을 영상으로 전부 보지는 않았다.
- **대가: 번들을 읽지 못하면 화면이 「끝없는 주황」이 된다** [실측 — API 37 · API 30, 6초 · 11초 뒤]. 이전에는 끝없는 회백색이었다. 로고도 글자도 없다 — 정보량은 같지만 「빈 흰 화면」을 실패 신호로 적은 절차의 문면이 낡았고, 이 변경과 함께 고쳤다.

### D7. `-night` 변형을 두지 않는다

`values-night*`에 `Theme.Duru`와 D1의 색 셋을 정의하지 않는다(검사 규칙 `night-variant`). 다크 테마는 범위 밖이고(ADR-0014 D7) 토큰에도 다크 값이 없다(맥락 3).
어느 모드에서도 같은 값이라, `uiMode` 변경 때 Activity를 다시 만들지 않아 창 배경이 다시 읽히지 않는 것(ADR-0047 D2)이 문제가 되지 않는다. 다크 모드에서 콜드 스타트한 시스템 스플래시도 같은 주황이었다 [실측 — API 37].

## 이 작업이 만든 변화 — API 31+ 시작 구간의 상태바 아이콘

**계약 단계는 「시작 창이 테마의 `windowLightStatusBar`를 따른다」고 추론했고, 틀렸다.** e2e 실행이 API 37에서 반증했고 계약 r02가 원인을 실측으로 갈랐다.

- **API 31+의 시작 창에서 상태바 아이콘의 명암은 플랫폼이 스플래시 배경색으로 정한다. 앱이 테마로 바꿀 수 없다** [실측 — API 37 에뮬레이터 하나].
  `values-v31/themes.xml` 한 파일만 바꾼 빌드 넷(스플래시 배경 주황 / 흰색 × `windowLightStatusBar` `true` / `false`)을 차례로 깔아 쟀다.
  배경이 주황이면 속성이 어느 쪽이든 흰 아이콘, 배경이 흰색이면 속성이 `false`여도 검은 아이콘이었다 — 2×2가 전부 그랬다.
  구현 전 캡처(스플래시 배경 `#FAFAFA`)의 아이콘이 `#000000`이었던 것이 같은 규칙의 다섯째 관찰이다.
- **시작 창은 앱의 창이 아니다** [실측 — `dumpsys window`]. 창 이름이 `Splash Screen libitum.duru.android`, 종류가 `APPLICATION_STARTING`, 소유 uid가 SystemUI와 같다.
- **모르는 것**: 어느 밝기에서 갈리는지(문턱)는 모른다 — 아는 것은 `#F46B18`이 「어두운 쪽」, `#FAFAFA` · `#FFFFFF`가 「밝은 쪽」이라는 세 점뿐이다.
  시작 창을 만드는 쪽(SystemUI의 WM Shell)의 소스는 SDK에 들어 있지 않아 읽지 못했고, `attrs.xml`의 `windowSplashScreen*` 주석은 시스템 바를 언급하지 않는다 [SDK 파일].
  **API 31 ~ 36과 제조사 빌드는 재지 않았다** [추론: 같은 규칙].
  문턱의 **후보**는 하나 찾았다 — SDK 소스의 `ContrastColorUtil.isColorLight`가 「휘도 > 0.5」다 [SDK 파일 — 접근성 점검이 읽었다]. 시작 창이 그 함수를 쓰는지는 확인하지 못했다. 관찰된 세 점과 어긋나지는 않는다.

그 결과 API 37에서 사용자가 보는 것 [실측 — 무손실 캡처. 분포는 접근성 점검이 저장된 캡처를 다시 잰 값]:

| | 구현 전 시작 구간 | **구현 뒤 시작 구간** | 구현 뒤 JS 스플래시(앱의 창이 드러난 뒤) |
|---|---|---|---|
| 바탕 / 상태바 아이콘 | `#FAFAFA` / 검정 `#000000` | `#F46B18` / **흰색 `#FFFFFF`** | `#F46B18` / 검정 `#000000` |
| 색 쌍의 대비 | 20.12:1 | **3.016:1** | 6.963:1 |
| 시계 글자 — 4.5:1 이상인 픽셀 | 68.9% | **0%** | 65.9% |
| 띠 전체 — 3.0:1 이상인 픽셀 | 77.5% | 63.4% | 76.1% |
| 띠 전체 — 픽셀 평균 대비 | 13.83 | **2.60** | 5.54 |
| 구간 안에서 아이콘이 바뀌는가 | 바뀌지 않는다 | **흰색 → 검정으로 한 번 뒤집힌다.** 되돌아가지 않는다 | — |

재는 방법: 캡처 위 160줄의 최빈색을 배경으로, 배경과 다른 모든 픽셀을 전경으로 세고, 가로로 떨어진 묶음으로 시계와 아이콘을 가른다(절차 문서 L7의 `px.py dist`가 같은 값을 낸다).

- **3.016:1은 흰색 / `#F46B18` 색 쌍의 산술값이고 여유가 사실상 0이다.** 주황 위에서 「3.0 이상」은 곧 「정확히 순백」이다 — 둘째로 밝은 `#FFFEFE`가 이미 2.996이다. 가장자리가 한 단계만 섞여도 3.0 아래로 떨어진다.
  띠 전체의 「3.0 이상 63.4%」는 캡처에 따라 58.4 ~ 66.8%로 흔들린다(시계의 숫자 · 셀룰러 막대의 꺼진 칸 수 — 접근성 점검의 여덟 장). 최종 검증의 한 장은 71.1%였는데 **상태바의 알림 글리프가 다른 캡처다**(그 묶음이 150픽셀, 다른 캡처는 667픽셀 — 낮은 픽셀이 많은 묶음이 작아져 비율이 올랐을 뿐이다). 구현 전에도 77.5%였으므로, **나빠진 정도를 보여 주는 것은 색 쌍의 값(20.12 → 3.016) · 시계의 4.5 이상 픽셀(68.9% → 0%) · 평균(13.83 → 2.60)이다.**
- **브랜드 주황의 상대 휘도 0.298은 흰 아이콘이 3:1을 지키는 경계(0.300)에 있다** [계산]. 이 색 위에서는 검정(6.963)이 흰색보다 2.3배 낫다 — 플랫폼이 덜 나은 쪽을 고른 것이다.
- **WCAG로는 「기준을 넘는다」로 요약할 수 없다** [접근성 점검의 판단 — 해석이다].
  - 띠 안의 **시계는 텍스트**라 1.4.3(4.5:1)이 대응하고, 흰색의 상한이 3.016이라 **미달이다**(4.5 이상 픽셀 0%). 아이콘에는 1.4.11(3:1)이 대응하고 색 쌍으로는 넘지만 여유가 0.016뿐이다. 둘 다 「이 구간이 앱의 적합성 범위 안이라면」의 이야기다(아래). 첫 판의 「1.4.11을 0.016 차로 넘는다」는 띠 전체의 판정처럼 읽혀 실제보다 강했다(「정정 기록」).
  - **시스템이 그리는 시작 창이라 앱의 적합성 범위 밖으로 보는 근거가 더 있다 — 그러나 단정하지 못한다.**
    범위 밖으로 보는 근거: 그리는 주체가 앱이 아니다(시작 창의 소유 uid가 SystemUI와 같다 [실측]) · 네이티브 앱에 WCAG를 옮겨 읽는 지침(WCAG2ICT)은 플랫폼 소프트웨어를 따로 평가받는 대상으로 본다 · 1.4.11에는 「모양을 플랫폼이 정하고 저자가 고치지 않은 경우」의 예외가 있고, 이 명암은 앱이 테마로 바꿀 수 없다.
    범위 안으로 볼 여지: 인접색(스플래시 배경)은 앱이 골랐다 · 1.4.3에는 그런 예외가 없다 · Android는 edge-to-edge에서 시스템 바 아이콘의 가독성을 앱에 맡긴다.
    「운영체제의 상태바가 앱의 범위에 드는가」를 직접 말하는 규범 문면은 찾지 못했다.
  - **심각도는 Minor**로 봤다 [접근성 점검]. 이유: 구간이 수 초이고(에뮬레이터 3.13 ~ 4.27초 — 실기는 재지 않았다), 그 동안 화면에 앱의 정보가 없으며, 낮아진 것이 시스템 정보(시각 · 신호 · 배터리)이고 곧 6.963:1로 돌아오며, 그리는 주체가 플랫폼이고, 색 쌍으로는 비텍스트 3:1을 넘는다. 「문제가 아니다」가 아니라 **측정되는 가독성 저하를 알고 받아들인 것**이다.
- **뒤집힘은 여섯 실행 모두 정확히 한 번, 밝음 → 어두움이었다** [실측 — 저장된 영상 4 + 새 영상 2]. 뒤집힌 프레임이 워드마크가 처음 보인 프레임과 같은 경우가 셋, 그 뒤가 셋이었다.
  **뒤집힘 자체는 접근성 문제로 보지 않았다** [접근성 점검] — 한 방향 한 번이라 깜빡임 기준(반대 방향 변화의 한 쌍)에 해당하지 않고, 바뀌는 픽셀이 화면의 약 0.2%이며 움직임이 없다.
- **API 30 이하에는 이 변화가 없다.** 시작 창부터 어두운 아이콘이다 — 다만 그 「어두운 아이콘」은 검정이 아니라 `#622B0A`이고 주황과의 대비는 3.72:1이다 [실측 — API 30 무손실. 분포는 재지 못했다]. 그 값은 이 변경 전의 JS 스플래시에도 있었다.
- **뒤집힘을 없애는 일은 후속 상태바 전환 작업으로도 풀리지 않는다.** 첫 판은 「후속 작업의 요구사항」이라고 적었다 — 틀렸다(「정정 기록」).
  스플래시 동안 앱의 창도 밝은 아이콘으로 통일하면(선택지 B) 뒤집힘은 사라지지만 3.016:1 구간이 JS 스플래시 끝까지 길어진다(에뮬레이터에서 0.3 ~ 1.6초 더) — **접근성으로는 지금보다 나쁘다.**
  그래서 **후속 작업에서도 스플래시 표면은 검정 아이콘을 유지하는 것이 맞고**, 뒤집힘까지 없애려면 브랜드 주황 자체의 휘도를 0.183 이하로 낮춰 흰 아이콘이 4.5:1에 닿게 하는 길뿐이다 — 토큰 · iOS 실행 화면 · `colors.xml`을 함께 바꾸는 **디자인 결정**이다(「버린 대안」의 D2).

## 버린 대안

| 대안 | 버린 이유 |
|---|---|
| `androidx.core:core-splashscreen` | D3. 주는 것 둘 가운데 하나는 원하지 않고 하나는 범위 밖이다. 의존성과 `onCreate` 호출이 는다 |
| 시스템 스플래시에 앱 아이콘 그대로(플랫폼 기본) | 평평한 주황 위에 그러데이션 원반의 가장자리가 보이고, 이어지는 JS 스플래시에서 마크가 사라지고 워드마크가 나타나 로고가 두 번 바뀐다 |
| 시스템 스플래시에 전용 흰 마크 | 마크만 있는 원본이 없다. 있더라도 마크 → 워드마크 전환이 남는다 |
| 워드마크를 시스템 스플래시에 | 워드마크는 화면 폭의 70%라 스플래시 아이콘 영역을 넘고, 시스템 스플래시는 애니메이션 WebP를 받지 않는다 [기억] |
| 디자인 원본이 올 때까지 아이콘을 그대로 둔다 | 그동안 런처에 흰 원 안의 축소 아이콘이 남는다. 사용자가 U3에서 먼저 내는 쪽을 골랐다 |
| 원본을 108dp 한 레이어로 그대로 | 마크가 어떤 마스크에서도 잘린다(D5) |
| 색 임계값으로 뽑은 마크를 전경 · monochrome으로 | 마크 아래쪽이 빠지고 구멍이 난다. monochrome은 한번 넣으면 테마 아이콘 사용자에게 그 모양이 곧 브랜드다 |
| 배경 단색을 원본 가장자리의 평균색(`#FC6A1B`)으로 | 정지 상태에서는 어느 쪽도 보이지 않는다. 모서리 넷의 색이 서로 달라 어떤 단색도 전부 맞추지 못하므로 새 색을 들이지 않았다 |
| 실행 뒤 `MainActivity`가 창 배경을 `#FFFDFC`로 바꾼다 | D6. 드러나는 순간이 관찰되지 않았다. 드러나면 다시 연다(「재검토 조건」) |
| **B** — 스플래시 동안 앱의 창도 밝은 아이콘으로 둬 뒤집힘을 없앤다 | **접근성으로 지금(A)보다 나쁘다** — 3.016:1 구간이 JS 스플래시 끝까지 길어지고(에뮬레이터에서 0.3 ~ 1.6초 더), 지금 6.963:1인 구간을 잃는다. 얻는 것은 문제가 아닌 뒤집힘의 제거뿐이다. **후속 상태바 전환 작업에서도 채택하지 않는다 — 스플래시 표면은 검정 아이콘을 유지한다**(접근성 점검). 호스트가 스플래시의 끝을 모른다는 구현상의 걸림도 있다 |
| **D1** — 시스템 스플래시만 더 어두운 주황(휘도 0.183 이하)으로 | 흰 아이콘이 4.5:1에 닿지만 두 주황 사이에 화면 전체의 색 단차(1.49:1)가 새로 생긴다 — 이 작업의 목적(색이 튀지 않는다)을 깬다 |
| **D2** — 브랜드 토큰 자체의 휘도를 0.183 이하로 낮추고 스플래시를 밝은 아이콘으로 통일 | **대비를 잃지 않고 뒤집힘을 없애는 유일한 길이고 접근성으로는 가장 좋다**(흰 워드마크의 대비도 함께 오른다). 그러나 브랜드 색 변경이다 — 이 작업의 범위가 아니고 디자인 · 사용자의 결정이다. 버린 것이 아니라 **이 작업이 정하지 않은 것**이다. 하게 되면 Android 리소스에서만 다른 주황을 쓰지 않고 토큰 · iOS 실행 화면 · `colors.xml`을 함께 바꾼다 |
| **C** — 스플래시 배경을 「밝은 쪽」으로 판정되는 색으로 바꾼다 | 브랜드 색 · iOS 실행 화면 · JS 스플래시와의 일치 — 이 작업의 목적 — 를 깬다. 문턱을 몰라 어느 색이면 되는지도 재 봐야 안다 |
| `values-v31/`에서만 `windowLight*`를 뺀다 | 효과가 같고(D4) 한정자마다 값이 달라져 판정만 복잡해진다 |
| 상태바 아이콘의 화면별 전환을 이 작업에 넣는다 | U1. 계층 · 위험 · 게이트가 다르다 — 리소스만 바꾸는 변경이 공유 JS 변경의 성능 게이트와 접근성 단계에 함께 묶인다 |

## 대가

- **API 31+ 사용자는 실행 때마다 상태바 아이콘이 흰색으로 보이다 검게 바뀌는 것을 한 번 본다.** 그 구간의 색 쌍 대비가 20.12:1에서 3.016:1로 낮아졌고 시계 글자는 텍스트 기준 4.5:1에 못 미친다(「이 작업이 만든 변화」). 이 변경이 만든 것이고 **사용자가 알고 받아들였다**(U7). 후속 상태바 전환 작업으로도 뒤집힘은 남는다.
- **색 값의 사본이 하나 늘었다**(D1). 토큰이 바뀌면 `colors.xml`을 함께 바꿔야 한다 — 잊으면 `pnpm verify`가 실패한다(의도한 대가). iOS의 사본은 여전히 검사 밖이다.
- **적응형 아이콘이 이름만 적응형이다**(D5의 한계 셋). 테마 아이콘 모드에 대응하지 않는다.
- **전경 PNG 다섯 장이 iOS `AppIcon.png`의 손으로 만든 사본이다.** 원본이 바뀌어도 아무 검사도 실패하지 않는다.
- **번들을 읽지 못한 화면이 끝없는 주황이다**(D6). 스플래시가 길어진 것과 눈으로 구별되지 않는다.
- **`Theme.Duru`가 세 파일에 같은 줄을 되풀이한다**(D4). 한정자끼리 합쳐지지 않아서다. 어긋남은 검사가 잡는다.
- **확인이 에뮬레이터 두 대 · 기본 런처에 선다.** 런처의 마스크 모양 · 움직임 효과는 런처마다 다르다.

## 확인한 것과 확인하지 못한 것

절차와 항목 번호(L1 ~ L11)는 [Android 실행 시 색과 적응형 아이콘](../e2e/android-launch-appearance.md)이 진다. 기기 실행은 전부 2026-10-06, Pixel_8 AVD(API 37 · 제스처 내비게이션)와 R6_API30 AVD(API 30 · 3버튼)다.
e2e는 두 번 돌았다 — 첫 실행(HEAD `486ecc95`)은 판정 도구의 구간 정의 결함과 위의 흰 아이콘으로 **실패** 판정이었고, 도구와 L7의 기준을 고친 뒤의 재판정 + 새 실행(HEAD `e22758d2`, 제품 코드는 `dfbe03cb` 뒤로 변경 0줄)이 **통과** 판정이다.

## 후속 과제

**순서는 사용자가 정했다(2026-10-06): 1(상태바 아이콘 전환)이 다음 작업이고 2(워드마크 로드 실패)가 그 뒤다.** 3 ~ 5는 이 작업의 범위 밖에서 발견한 것, 6 ~ 8은 리뷰가 후속으로 둔 것, 9는 받아들인 후퇴에 붙은 출시 전 확인이다 — 3 ~ 9는 열 계획이 정해지지 않았다.

1. **상태바 아이콘의 화면별 전환**(U1 — 가칭 `android-status-bar-appearance`. **다음 작업 — 사용자 확정**). 어두운 상단을 가진 표면 8종에서 검정 아이콘의 대비가 1.17 ~ 1.90:1이다(맥락 7) — 화면이 떠 있는 내내 시계 · 신호 · 배터리가 사실상 보이지 않는다.
   **이 작업이 만든 것이 아닌 기존 결함이다.** 접근성 점검은 이것을 그 점검에서 가장 무거운 지적(Major)으로 봤다 — 시작 구간(수 초 · 3.016:1)과 달리 여기서는 명암을 앱이 직접 정하므로 「플랫폼이 정했다」는 예외가 서지 않는다.
   **접근성 점검은 첫 공개 출시 전에 반영할 것을 권했다. 출시를 이것에 묶을지는 사용자 결정이고 아직 정해지지 않았다.**
   그 작업에 넘기는 것:
   - **스플래시 표면은 검정 아이콘을 유지한다**(6.963:1). 첫 판은 「밝은 아이콘으로 통일할지 그 작업의 디자인이 정한다」고 넘겼다 — 접근성 점검에 따르면 통일(B)은 낮은 대비 구간을 늘릴 뿐이라 채택하지 않는다(「이 작업이 만든 변화」 · 「버린 대안」). 그러므로 **그 작업 뒤에도 API 31+의 뒤집힘은 남는다.**
   - API 31+ 시작 창의 명암은 앱이 못 바꾼다는 플랫폼 규칙.
   - 판정은 표면마다 색 쌍으로 건다 — 아이콘 3:1 **그리고 시계 글자 4.5:1**(상태바에는 텍스트가 있다). API 30 이하의 「어두운 아이콘」은 검정이 아니라 `#622B0A`다.
   - 이 작업이 남긴 것 둘을 함께 닫는다: 절차의 L7-a를 실패할 수 있는 판정으로 바꾸는 일, 알림 탭 경로의 주황 노출을 다시 보는 일(보이면 중계 Activity에 창을 만들지 않는 테마를 주는 것이 접근성 점검이 낸 후보다 — 정해진 것이 아니다).
   공유 JS와 새 호스트 접점이 들어 성능 보고서 게이트와 접근성 단계가 붙고, 호스트 모듈을 더하면 [ADR-0017](0017-host-native-capabilities-and-audio.md)의 입장 조건을 다시 따진다.
   ⟨2026-10-06 적용 기록⟩ **이 작업이 열렸고 결정은 [ADR-0050](0050-android-status-bar-icons.md)이 진다** — 화면이 표지(`data-statusbar="light-icons"`)를 달고 호스트가 Lynx 화면 갱신 콜백 안에서 트리를 읽어 명암을 맞춘다. 호스트 모듈은 더하지 않았다(ADR-0017의 입장 조건은 발동하지 않았다).
   위에서 넘긴 것 가운데 **받은 것**: 스플래시 표면의 검정 아이콘 유지(표지를 달지 않는다) · 시작 창의 플랫폼 규칙 · 표면마다 아이콘 3:1과 시계 4.5:1의 색 쌍 판정 · API 30의 어두운 아이콘이 검정 60%라는 것. 그래서 API 31+의 뒤집힘은 그대로 남았다.
   「표면 8종」은 그 작업의 계약이 고쳤다(젬 구매 화면은 제품에서 그려지지 않는다 — 목록은 ADR-0050 D2). **함께 닫으라고 넘긴 둘 가운데** L7-a는 실패할 수 있는 판정이 되지는 않았고 [절차 문서](../e2e/android-launch-appearance.md)에서 「판정이 아니라 받아들인 값의 기록」으로 뜻이 바뀌었으며(그 작업의 접근성 점검이 이것으로 닫힌 것으로 봤다), **알림 탭 경로의 주황 노출은 다시 보지 않아 열려 있다**(ADR-0050 「미확인 · 후속」 7).
   e2e의 항목별 실행 상태는 [상태바 아이콘 절차 문서](../e2e/android-status-bar-icons.md)가 진다.
2. **내장 번들 빌드에서 JS 스플래시의 손글씨 워드마크 이미지가 간헐적으로 로드에 실패한다** [실측] — **출시 빌드에 닿는 기존 결함 후보다.**
   실패한 실행의 logcat에 `LynxImageManager onFailed … Unsupported uri scheme`(`logo-handwriting…webp`)이 찍히고, 그때 `SplashScreen.tsx`의 `binderror={finish}`가 스플래시를 즉시 닫는다 [코드 확인] — 주황 약 0.1초 뒤 바로 첫 화면이다.
   - 워드마크가 보이지 않은 실행: **API 30 `bundled` 9실행 가운데 6실행 · API 37 `bundled` 11실행 가운데 1실행.** 로그 16개를 대조해 그 줄이 있는 실행과 워드마크가 없는 실행이 예외 없이 일치했다.
   - **이 변경의 회귀가 아니다** [실측]. 구현 전 커밋 `a2fcf3ec`의 빌드에서도 API 30 6실행 가운데 4실행에서 같은 로그와 함께 보이지 않았다.
   - **URI가 왜 가끔 풀리지 않는지는 확정하지 못했다.** 이미지 로더가 번들 안 상대 경로를 풀기 전에 요청이 가는 경합이라는 것은 [추론]이다. API 30에서 잦고 API 37에서 드문 까닭을 시스템 스플래시 유무와 시작 속도의 차이로 본 것도 [추론]이다. 모든 실행이 앱 데이터를 지운 직후의 콜드 스타트다.
3. **API 37에서 주황이 처음 보일 때 워드마크 애니메이션이 이미 진행돼 있다** [실측 — 에뮬레이터]. 워드마크가 처음 보인 프레임의 진행도가 첫 실행 네 번에서 37 ~ 73%, 새 실행 두 번에서 48%였다(구현 전 영상 둘은 같은 도구 정의로 57% · 91%).
   시스템 스플래시가 앱의 첫 그리기보다 늦게 걷힌다. **원인은 확인하지 못했고 에뮬레이터의 느린 시작이 만든 것일 수 있다** — 실기에서 먼저 재 본 뒤 정한다(U6). 이 변경 뒤에는 「주황 한 면 → 쓰다 만 워드마크가 나타남」으로 보인다.
4. **디자이너에게 요청할 원본** — 오면 D5의 레이어를 교체한다.

   | # | 요청 | 형식 | 없으면 |
   |---|---|---|---|
   | R1 | 마크만(투명 배경) | SVG, 또는 투명 PNG 1024px 이상 | D5의 구성 그대로(이음매 · 깊이감 없음) |
   | R2 | 배경만(그러데이션, 긴 그림자를 넣을지 포함) — 108dp 캔버스 전체를 가장자리까지 채운 것 | SVG, 또는 PNG 432px 이상 정사각 | 단색 `#F46B18` |
   | R3 | 단색 마크(monochrome용 — 한 색 + 알파, 음영 없이 윤곽으로 읽히게 다시 그린 것) | SVG | monochrome을 넣지 않는다 |
   | R4 | R1의 마크를 108dp 캔버스의 어디에 얼마 크기로 놓을지(안전 영역 66dp 안) | 수치 또는 배치된 파일 | 지금 배치의 마크 크기(47.0×52.3dp)를 그대로 쓴다 |
   | R5 | (스플래시에 아이콘을 넣기로 U2를 뒤집을 때만) 주황 위에 놓을 흰 마크 | SVG | 아이콘 없음 |

5. **알림 셰이드의 알림 머리에 단색 윤곽이 아니라 주황 앱 아이콘이 보인다** [실측 — API 37 에뮬레이터, 관찰]. 상태바에는 Duru 글리프가 아니라 일반 종 아이콘이 보였다. 알림에 실린 작은 아이콘은 `ic_notification` 그대로다(`dumpsys`).
   플랫폼이 셰이드에 앱 아이콘을 보여 주는 것으로 본 것은 [추론]이고, **이 변경 전의 모양과 대조하지 않았다.** 알림 아이콘의 재디자인은 이 작업의 범위 밖이다.
6. **검사 함수가 계약이 열거한 한정자만 본다** [코드 확인 — 리뷰]. `launchAppearanceIssues`는 API 26 · 27 · 31에서 풀린 값(`values` · `values-v27` · `values-v31`)과 `values-night*`만 본다.
   `values-v29` · `values-v33` · `values-land` · `values-ko` 같은 다른 한정자에 `Theme.Duru`나 색을 다시 정의하는 파일, `mipmap-anydpi-v33/ic_launcher.xml`(API 33+에서 아이콘을 통째로 바꾼다), `drawable-v31/splash_icon_none`(API 31+에서 스플래시 아이콘을 되살린다)이 생겨도 `pnpm verify`는 통과한다. 계약의 틈이다 — 검사를 「`res/`의 어느 한정자든」으로 넓히는 일은 계약부터 다시 고정한다.
7. **절차의 판정 도구가 문서의 코드 블록에만 있다** [리뷰]. `frames.swift` · `judge.py` · `px.py`는 [절차 문서](../e2e/android-launch-appearance.md)의 부록에서 꺼내 쓰고, 저장소의 어떤 테스트도 그것을 돌리지 않는다. 고칠 때마다 저장된 프레임으로 손으로 대조했다. 저장소로 옮기고 고정 입력으로 지키는 일이 남았다.
8. **iOS `LaunchScreen.storyboard`의 색을 토큰과 대조하는 검사가 없다** [코드 확인 — 리뷰]. Android 쪽은 HL2가 지키지만(D1) iOS의 사본은 손으로 맞춘다.
9. **출시 전 실기 확인**(접근성 점검이 U7 수용에 붙인 조건). 실기 한 대 이상에서 **흰 아이콘 구간의 길이**를 잰다 — 받아들인 근거의 하나가 「구간이 짧다」인데 잰 값은 에뮬레이터의 것뿐이다.
   같은 기회에 테마 아이콘을 켠 상태와 제조사 런처 한 종에서 아이콘을 찍는다(monochrome 없음 · 원형이 아닌 마스크 · 하단 줄 자리 — 전부 미확인이다).

## 정정 기록

**2026-10-06 — 첫 판(커밋 `ede6f7fc`)을 같은 날 고쳤다.** 리뷰가 되돌렸고, 그 뒤 접근성 점검 · 주황 번쩍임 관찰 · 사용자 결정이 들어왔다. 결정 D1 ~ D7은 한 글자도 바뀌지 않았다 — 바뀐 것은 결정이 딛고 선 사실의 서술과 U7의 상태다.

| 어떻게 틀렸나 | 고친 것 |
|---|---|
| **U7을 「root가 기본값으로 진행했고 사용자 답은 받지 못했다」로 둔 채 채택으로 적었다.** 이 작업이 만든 가시적 후퇴를 사용자 답 없이 닫은 것이다 — 리뷰가 되돌렸다 | 사용자가 접근성 점검과 번쩍임 관찰의 결과를 보고받은 뒤 직접 「받아들임」을 골랐다. U7을 사용자 결정 표로 옮기고 경위를 남겼다 |
| **「3.02:1 — WCAG 1.4.11을 0.016 차로 넘는다」가 실제보다 강했다.** 3.016은 색 쌍의 산술값이고 여유가 사실상 0이며(둘째로 밝은 픽셀이 2.996), 띠 안의 시계 글자에는 1.4.3의 4.5:1이 대응해 미달이다. 적합성 범위에 대한 판단도 빠져 있었다 | 「이 작업이 만든 변화」에 구현 전후 표(색 쌍 · 시계의 4.5 이상 픽셀 · 평균), 적합성 범위의 양쪽 근거, 심각도와 그 이유 |
| **「뒤집힘을 없애는 일은 후속 상태바 전환 작업의 요구사항」이라고 적고, 스플래시 표면의 명암을 그 작업의 디자인이 정할 물음으로 넘겼다.** 밝은 아이콘으로 통일하면 낮은 대비 구간이 길어져 지금보다 나쁘다 | 후속에서도 스플래시 표면은 검정 아이콘 유지. 뒤집힘까지 없애는 길은 브랜드 주황의 휘도를 낮추는 것(D2)뿐이라고 「버린 대안」 · 「후속 과제」 1에 |
| **절차의 L7-a를 「통과」로 옮겨 적었다.** 주황 위에서 실패할 수 없는 기준이었다 | 「받아들인 값의 기록」으로 |

| `PushNotificationTapActivity`의 시작 창을 「관찰하지 않았다」로만 뒀다 | 알림 탭 등 여섯 경로의 영상 관찰 결과와 한계를 더했다 |

**2026-10-06 — 둘째 리뷰 뒤(커밋 `3cb35a22`의 문면).** 번쩍임 관찰의 한계를 「수십 ms 미만의 한 프레임」으로 적은 것이 과소였다 — 영상의 프레임 간격은 대부분 0.1초 안팎이라 「약 0.1 ~ 0.2초 미만의 노출」로 고쳤다(「확인한 것과 확인하지 못한 것」).
「3.0 이상」 비율의 71.1%를 시계 · 셀룰러의 흔들림으로 설명한 것도 틀렸다 — 알림 글리프가 다른 캡처였다. 변경 범위의 SHA를 확인한 커밋으로 고쳤다.

## 재검토 조건

- **후속 상태바 전환 작업을 열면** → 「후속 과제」 1 · D4. 스플래시 표면은 검정 아이콘을 유지한다는 접근성 의견을 그 작업의 계약이 받는지 본다. 받지 않고 밝은 아이콘으로 통일하려 하면 「이 작업이 만든 변화」의 수치(3.016:1 구간이 길어진다)를 다시 건다.
  ⟨2026-10-06 적용 기록⟩ 그 작업이 열렸고 계약이 이 의견을 받았다 — 스플래시 표면은 표지를 달지 않아 검정 아이콘이다([ADR-0050](0050-android-status-bar-icons.md) D1 · D3).
- **실기에서 흰 아이콘 구간이 에뮬레이터의 값(3 ~ 4초)보다 길거나, 그 구간에 대한 사용자 보고가 나오면** → U7. 받아들인 근거(구간이 짧고 그 동안 앱의 정보가 없다)를 다시 본다.
- **브랜드 주황을 다시 정하게 되면**(디자인) → 「버린 대안」의 D2. 휘도 0.183 이하면 흰 아이콘이 4.5:1에 닿고 뒤집힘도 없앨 수 있다.
- **API 31 ~ 36 기기나 제조사 빌드에서 시작 구간의 아이콘이 흰색이 아니거나 색 쌍의 대비가 3.016:1과 다르게 재지면, 또는 스플래시에 아이콘 · 흰 원이 남으면** → 「이 작업이 만든 변화」 · D2. 받아들인 것은 API 37에서 잰 값이다.
- **앱이 떠 있는 동안 주황이 번쩍인다는 보고가 나오면**(알림 탭 · 다른 앱에서 복귀) → D4 · 「후속 과제」 1. 영상으로는 보이지 않았지만 약 0.1 ~ 0.2초 미만의 노출과 스냅샷 없는 웜 스타트는 배제하지 못했다.
- **`res/`에 `values` · `values-v27` · `values-v31` 밖의 한정자로 테마 · 색 · 아이콘 · 스플래시 drawable 파일을 더하게 되면** → 「후속 과제」 6. 지금 검사는 그 파일을 보지 않는다.
- **`@libitums/design-tokens`의 `--libitum-color-brand-primary` 값이 바뀌면** → D1. HL2가 실패한다 — `colors.xml`을 함께 바꾸고, 새 색에서 시작 구간의 아이콘 명암과 대비를 다시 잰다(문턱을 모른다). iOS의 `LaunchScreen.storyboard`도 손으로 맞춘다.
- **다크 테마를 들이면** → D7. `-night` 변형이 생기면 「다음 콜드 스타트의 시스템 스플래시는 새 모드를 따르지만 살아 있는 창은 옛 값」이 된다 [추론] — ADR-0047 D2의 `uiMode`와 함께 본다.
- **디자인 원본(R1 ~ R4)이 오면** → D5. 레이어 파일을 교체하고 한계 셋을 다시 판정한다. 아이콘 원본(`AppIcon.png`)만 바뀌어도 전경 PNG를 다시 만든다.
- **실기 · 제조사 런처에서 아이콘의 이음매가 보이거나 마크가 잘린다는 보고가 나오면** → D5.
- **실행 뒤 주황 창 배경이 번쩍인다는 보고가 나오면**(키보드 · 화면 전환 · 분할 화면) → D6. `MainActivity`가 첫 화면 뒤 창 배경을 셸 색으로 바꾸는 계약을 연다.
- **`minSdk`를 올리면** → D4. 31 이상이면 `values/` · `values-v27/`의 `Theme.Duru`가 필요 없어진다. 26 아래로 내리면 폴백 아이콘이 필요하다.
- **스플래시를 붙잡아 두거나 나가는 애니메이션을 넣어야 하면**(예: 「후속 과제」 3을 고칠 때) → D3. 그때는 `core-splashscreen`이 후보다.
- **「앱을 켜면 로고 없이 주황에서 바로 첫 화면으로 넘어간다」는 보고가 나오면** → 「후속 과제」 2. 이 ADR의 결정이 아니라 기존 결함 후보다.
