# ADR-0008 — 디자인 토큰과 컴포넌트 프리미티브

- 상태: **대체됨** — [ADR-0011](0011-design-system-consumption.md)
- 날짜: 2026-08-24

> **이 결정은 더 이상 유효하지 않다.** 토큰을 이 저장소가 소유한다는 전제가 사실과
> 달랐다 — 별도의 design-system 저장소가 원본을 소유하고 값은 이미 확정돼 있다.
> D3(다크모드 제외)만 ADR-0011 D5로 이어진다. 아래는 기록으로 남긴다.
- 다루는 축: 디자인 토큰, 컴포넌트 프리미티브

## 맥락

Frontend와 **Design이 같은 1인**이다. 디자인과 구현 사이에 전달 단계가 없다는 뜻이고,
그래서 "디자인 시스템"을 문서로 만들 이유가 약하다. 대신 **QC 루프 반복**이
예정돼 있다 — 색·간격을 여러 번 조정하게 된다는 뜻이다.

이 조합이 결정을 정한다: 문서화된 시스템은 필요 없지만, **한 곳만 고치면 전체가 바뀌는
구조**는 반드시 필요하다.

Lynx는 DOM이 아니다. `<div>`가 아니라 `<view>`, `<span>`이 아니라 `<text>`를 쓴다.
그래서 기존 React UI 라이브러리(MUI · shadcn/ui 등)는 **DOM을 전제하므로 쓸 수 없다.**
선택지가 아니라 사실이다.

## 결정

### D1. 토큰의 단일 출처는 CSS 커스텀 프로퍼티

`apps/mobile/src/styles/tokens.css` 하나가 유일한 출처다.
**TypeScript 상수로 이중 정의하지 않는다.**

근거: 스타일이 CSS에 있는데 값이 TS에 있으면, 값을 쓸 때마다 인라인 스타일을 쓰게
되고 Lynx의 CSS 처리를 못 쓴다. 그리고 두 곳에 있는 값은 **반드시 갈라진다.** 갈라진
토큰은 QC 루프에서 최악이다 — 색을 바꿨는데 일부만 바뀌고, 왜 그런지 찾는 데 시간이 간다.

범주는 넷으로 시작한다: **색 · 간격 · 타이포 · radius.** 그림자·애니메이션·z-index는
실제로 필요해질 때 추가한다.

> **확인 필요**: Lynx CSS가 커스텀 프로퍼티(`--var`)를 지원하는지. 미지원이면 이
> 결정을 새 번호로 갱신하고 빌드 타임 치환 방식을 검토한다.

### D2. 토큰 **값**은 이 결정에 넣지 않는다

값은 설계 결정이 아니라 **디자인 산출물**이다. 와이어프레임에서 나오며
디자인 작업이 채운다. 설계 단계에서 값을 추측해 넣으면, 와이어프레임과
다른 값이 코드에 먼저 들어가고 나중에 어느 쪽이 맞는지 알 수 없게 된다.

이 ADR이 정하는 것은 **값을 어디에 어떤 형태로 두는가**까지다.

`docs/adr/README.md`의 보류 표에 올라가 있다.

### D3. 다크모드는 첫 단계 제외

프로토타입 판정 기준(ADR-0001 D4)에 없다. 토큰 구조를 테마 전환 가능하게 미리 짜지도
않는다 — 그렇게 짜면 토큰 계층이 두 겹(의미 토큰 → 원시 토큰)이 되고, 값을 채우는
비용이 두 배가 된다. 필요해지면 그때 한 겹 넣는다.

### D4. 프리미티브 **패키지를 만들지 않는다**

`apps/mobile/src/components/`에 둔다. `packages/ui`를 만들지 않는다
(ADR-0004 D2의 "두 번째 소비자" 규칙을 그대로 따른다 — 소비자가 앱 1개다).

**승격 규칙:**

```text
화면 1개만 쓴다   →  그 화면 폴더 안에 둔다 (src/screens/<화면>/)
화면 2개 이상 쓴다 →  src/components/ 로 올린다
앱 2개 이상 쓴다   →  packages/ 로 올린다  (첫 단계에는 해당 없음)
```

**미리 올리지 않는다.** 두 번째 사용처가 실제로 생겼을 때 옮긴다.

### D5. 프리미티브는 Lynx 내장 요소를 감싸는 최소 래퍼만

`<view>` · `<text>` · `<image>`를 직접 쓰지 않고 래퍼를 통해 쓴다.

래퍼가 있는 이유는 추상화가 아니라 **토큰 적용 지점을 한 곳으로 모으는 것**이다.
래퍼가 없으면 각 화면이 스타일을 직접 붙이고, 토큰을 바꿔도 반영 안 되는 곳이 생긴다.
D1의 단일 출처가 무의미해진다.

**만들지 않는 것**: 실제로 쓰이지 않는 프리미티브. 20개를 미리 만들면 QC 루프 10회
동안 쓰지 않는 19개도 함께 유지해야 한다.

## 버린 대안

**토큰**

- **TypeScript 객체를 단일 출처로** — 타입 안전하지만 스타일이 CSS에 있어 매번 인라인
  스타일을 쓰게 되고, Lynx CSS 처리를 못 쓴다.
- **Tailwind** — 유틸리티 접근은 프로토타입 속도에 좋지만, Lynx가 지원하는 CSS
  하위집합과 Tailwind preset의 호환을 검증할 시간이 1주에 없다. 안 맞는 클래스가
  조용히 무시되면 원인 찾기가 어렵다.
- **토큰 없이 하드코딩** — 지금 가장 빠르다. 하지만 QC 루프 10회에서 색 하나 바꾸는 데
  전 파일을 고치게 된다. 10회 반복이 예정돼 있다는 사실이 이 대안을 버리게 한다.
- **의미 토큰 / 원시 토큰 두 겹 구조** — 테마가 여럿일 때 값을 한다. 테마가 하나면
  간접 참조 비용만 낸다 (D3).

**프리미티브**

- **UI 라이브러리 도입 (MUI · shadcn/ui 등)** — DOM 전제라 Lynx에서 쓸 수 없다.
  선택지가 아니다.
- **`packages/ui`를 먼저 만든다** — 소비자가 하나다. ADR-0004 D2 위반.
- **프리미티브 20개 선제 제작** — 쓰이지 않는 것의 유지 비용이 QC 루프 내내 든다.
- **래퍼 없이 `<view>` 직접 사용** — 토큰 적용이 화면마다 흩어져 D1이 무의미해진다.
- **Storybook** — 리뷰 상대가 자기 자신(FE=Design 1인)이라 얻는 것이 거의 없다.
  설정과 유지 비용만 든다.

## 대가

- **TS 코드에서 토큰을 타입 안전하게 읽지 못한다.** `var(--color-primary)`는 문자열이라
  오타가 컴파일 타임에 안 잡히고, 런타임에 "스타일이 안 먹는" 형태로만 드러난다.
  이건 실제로 아플 수 있는 대가다. 완화 수단은 프리미티브(D5)로 토큰 사용처를 좁히는
  것뿐이다.
- **다크모드가 나중에 요구되면 토큰 구조를 한 겹 늘려야 한다** — 값을 다시 배치하는
  작업이 생긴다.
- **화면마다 비슷한 스타일이 잠시 중복된다.** 두 번째 사용처가 나올 때까지 승격하지
  않기 때문이다(D4). 중복이 보기 싫어도 참는 것이 규칙이다.
- **Tailwind를 안 쓰므로 스타일 작성이 더 장황하다.** 1주 일정에서 이건 실제 속도 손실이다.
  그럼에도 호환 미검증 위험보다 낫다고 판단했다.

## 재검토 조건

- 확인 목록의 "Lynx CSS 커스텀 프로퍼티 지원" 가정이 어긋나는 시점 → D1
- 두 번째 앱 생성 → D4의 `packages/` 승격
- 다크모드 또는 두 번째 테마가 요구되는 시점 → D3
- `src/components/`가 20개를 넘는 시점 → 분류 방식을 다시 본다 (ADR-0003 D5와 함께)
