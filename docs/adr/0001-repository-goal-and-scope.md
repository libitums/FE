# ADR-0001 — 저장소 목표와 첫 단계 범위

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: 저장소 목표·제외 범위

## 맥락

이 저장소는 **신규 구성이다. 기존 저장소 전환이 아니다.**

확인한 사실: 커밋 1개(`134c3c6 Initial commit`), 추적 파일 1개(`README.md`, 2줄).
추인하거나 이관할 기존 패턴이 **0개**다. 따라서 이 ADR 묶음은 마이그레이션 계획이
아니라 초기 규약이다. "기존 코드가 이러니 이렇게 한다"는 근거를 쓸 수 없고, 전부
프로젝트 제약에서 근거를 끌어와야 한다.

프로젝트 제약 (Linear "소마 17기 서비스 프로토타입 개발"):

- 팀 3인. 그중 **Frontend&Design은 1인**이며, 구현 상당 부분을 에이전트로 돌린다.
- 타깃 날짜 **2026-08-31**. 이 ADR 작성일은 2026-08-24 — 약 1주.
- 목표는 **프로토타입**이다. 프로덕션 운영이 아니다.
- 기획·디자인 선행 산출물이 **완료돼 있다**: 요구사항 · 유저 플로우 · 화면 목록 ·
  와이어프레임(작성·리뷰).
- **API 명세와 백엔드 연동이 아직 없다.** 데이터 페칭과 통합 테스트를 미루는
  근거가 여기서 나온다 (ADR-0006, ADR-0007).

이 제약 조합 — **1인 · 1주 · 프로토타입 · 에이전트 구현** — 이 이후 모든 ADR의
공통 근거다. 특히 "추상화를 얼마나 미룰지"의 기준이 된다.

## 결정

### D1. 목표

`libitums/FE`는 소마 17기 서비스 프로토타입의 **사용자 대면 클라이언트**를 담는다.

첫 단계 목표를 한 문장으로: **2026-08-31까지, ReactLynx 앱 하나를 Lynx Explorer에서
핵심 사용자 흐름을 처음부터 끝까지 시연할 수 있는 상태로 만든다.**

여기서 **핵심 사용자 흐름**은 완료된 유저 플로우와 화면 목록이 정의한
것을 가리킨다. 이후 별도의 시나리오 문서가 나오면 그것을 따르되, 이 ADR은 문서 이름이
아니라 **흐름 자체**를 기준으로 삼는다 — 문서는 바뀌어도 기준은 남아야 한다.

"시연할 수 있는 상태"를 목표로 잡은 이유는, 프로토타입의 성공이 코드 품질이 아니라
**보여줄 수 있느냐**로 판정되기 때문이다. 이 문장이 범위 다툼이 생길 때의 기준이 된다.

### D2. 첫 단계에 포함하는 것

- ReactLynx 앱 1개 (`apps/mobile`) — ADR-0002
- pnpm workspace 골격과 디렉터리 규약 — ADR-0003
- Node·pnpm 버전 고정 — ADR-0005
- 루트 명령 인터페이스와 테스트 3계층 — ADR-0006
- 화면 전환·상태·데이터 접근의 최소 규약 — ADR-0007
- 디자인 토큰·아이콘 소비와 최소 프리미티브 — ADR-0011
- `.gitignore`와 PR 경유 머지 규약 — ADR-0009
- 규약 문서와 이 ADR 묶음 — ADR-0010

### D3. 첫 단계에서 **제외**하는 것

제외는 "나중에 안 한다"가 아니라 **"지금 하지 않는다"**는 뜻이다. 각각 재검토 조건은
해당 ADR에 있다.

| 제외 | 이유 |
|---|---|
| **두 번째 플랫폼의** 네이티브 호스트 | 한 플랫폼만 만든다. 나머지는 Explorer로 확인한다 (ADR-0012 D1) |
| 웹 타깃·관리자 앱 | 요구사항에 없다 |
| 스토어 배포·서명·릴리스 파이프라인 | 호스트를 만들되 배포는 하지 않는다. 시연은 시뮬레이터/기기에서 직접 실행한다 (ADR-0012 D2) |
| 푸시·딥링크·권한 요청 | 요구사항에 없다. 호스트가 여는 것은 저장소 모듈 하나뿐이다 (ADR-0012 D2) |
| CI 구성 | 커밋하는 사람이 1명이다 (ADR-0009) |
| `e2e` 테스트 자동화 | 수단은 있으나 Android 실행 환경이 없다. 대상 목록은 관리한다 (ADR-0006 D4·D6) |
| `integration`의 **서버 연동 케이스** | API 명세 부재. 계층 자체는 첫 단계에 있다 (ADR-0006) |
| 저장소 안의 공유 package (`@libitum/ui-lynx` 포함) | 소비자가 앱 1개다 (ADR-0004, ADR-0011 D3) |
| 디자인 토큰·아이콘의 **생성** | 원본과 빌드는 design-system 저장소가 소유한다. 이 저장소는 패키지로 **소비**만 한다 (ADR-0011) |
| 태스크 러너(turbo/nx) | 패키지가 1개다 (ADR-0003) |
| 상태 관리·데이터 페칭 라이브러리 | 아직 필요가 없다. 명세도 부재 (ADR-0007) |
| 다크모드·다국어·접근성 인증 수준·성능 예산 | 프로토타입 판정 기준이 아니다 |
| 인증 인프라·관측/에러 리포팅 SaaS | 백엔드 연동 이후 |

**이 ADR 자체의 제외 범위**: 이 결정 묶음은 저장소 생성·설정 파일 작성·Lynx 앱
생성·CI 구성을 **수행하지 않는다**. 실체화는 이후 단계에서 한다.

### D4. 성공 확인 기준

아래를 전부 만족하면 첫 단계가 끝난 것이다. 추상적 판단이 끼어들지 않도록
**재현 가능한 명령**으로 적는다.

1. 저장소를 처음 받은 기기에서 `pnpm install && pnpm dev`가 성공하고, Lynx Explorer가
   그 dev 서버의 번들을 로드해 첫 화면이 뜬다.
2. `pnpm verify`(= `format:check` + `typecheck` + `lint` + `test` + `build`, ADR-0006)가
   종료 코드 0으로 끝난다.
3. **자체 호스트 앱**이 `pnpm build` 산출물을 로드해 첫 화면이 뜬다. dev에서만 되는 것은
   통과가 아니고, Explorer에서만 되는 것도 통과가 아니다 (ADR-0012 D5).
4. 핵심 사용자 흐름(D1)을 **자체 호스트 앱에서** 처음부터 끝까지 수동으로 통과한다.
   **앱을 재시작해도 로그인이 유지된다.**
5. 저장소를 처음 보는 사람이 `README.md`와 `docs/`만 읽고 1~4를 재현한다.

5번이 있는 이유: 1인 저장소는 암묵지가 사람 머리에만 남는다. 그 사람이 자리를 비우면
프로토타입이 멈춘다.

## 버린 대안

- **첫 단계에 웹·모바일 두 타깃을 함께 세운다** — 1주에 두 타깃의 렌더링 차이를
  흡수할 시간이 없다. 공통 계층을 성급히 만들면 그 계층이 양쪽 모두에 안 맞는다.
- **목표를 "프로덕션 준비"로 잡는다** — 관측·에러 리포팅·성능 예산·접근성이 전부
  범위에 들어오고, 1주 안에 어느 것도 제대로 못 한다. 절반짜리 프로덕션 설비는
  프로토타입보다 나쁘다. 유지 비용은 내면서 신뢰는 못 주기 때문이다.
- **범위를 정하지 않고 시작한다** — 에이전트로 구현할 계획인데 범위가 없으면
  에이전트가 만들 것을 스스로 정한다. 그러면 사람이 매번 되돌린다.

## 대가

- 제외 목록이 길어 첫 단계 산출물이 "제대로 된 저장소"처럼 보이지 않는다. 외부에서
  보면 미완성으로 읽힐 수 있다.
- 프로토타입이 그대로 살아남아 서비스가 되면, 제외한 것을 **사용자가 있는 상태에서**
  들여와야 한다. 그때가 지금보다 비싸다. 이 위험을 알고 감수한다 — 대안은 쓰이지 않을
  설비에 1주 중 상당 부분을 쓰는 것이고, 그러면 프로토타입 자체가 안 나온다.
- 성공 기준 4번이 수동이라 사람 시간을 반복해서 쓴다. QC를 반복할 때마다 이 비용이
  그대로 다시 든다.

## 재검토 조건

- 프로토타입 시연(2026-08-31)이 끝나고 이 저장소를 **계속 쓰기로 결정**되는 시점.
  그때 D3의 제외 목록 전체를 한 번에 다시 본다.
- 타깃 날짜가 2주 이상 미뤄지면 — 시간 제약이 근거였던 결정들이 근거를 잃는다.
