# ADR-0051 — Android 번들 안 이미지 URL의 재작성: Lynx의 미디어 fetcher(비동기)가 아니라 동기 `ImageInterceptor`에 건다

- 상태: **채택.** 사용자 결정이 필요한 항목은 없었다 — 기대 동작이 요구사항에 분명하고, 고칠 곳이 Android 호스트 한 곳이며, 견준 대안 가운데 공유 JS · iOS에 닿지 않는 것이 하나뿐이다.
  ⟨최종 검증⟩ **닫힌 것 — 원래 결함(재작성 전의 `/static/…`으로 나가던 이미지 요청).** 근거: 강제 재현 계측 HW1이 수정 전 두 기기 각 10 / 10 실패 → 수정 후 각 10 / 10 통과(D3 — 최종 검증의 재검증에서도 각 5 / 5),
  dev 자연 조건의 `onFailed … Unsupported uri scheme`이 수정 전 2 / 20 · 2 / 20 · 12 / 150 → 수정 후 0 / 67 · 0 / 68 · 0 / 67 · 0 / 150, 내장 빌드 API 30 0 / 100(「재실행과 대조 측정」의 종합 표).
  **최종 검증은 통과로 끝났다** — 첫 실행은 테스트 결함 하나(R4)로 실패했고, 그것을 고친 `5aff7932`에서 재검증이 통과했다. 제품 결함은 나오지 않았다(「최종 검증」).
  **남은 것**: ① 자연 조건의 늦은 도착이 어디서 늦는가(원인 미확인 — 수정 후 1 / 218) ② 타이머로 닫히는 실행이 내장 빌드 · 실기에서 나는가(⟨r03⟩ 에뮬레이터의 내장 빌드에서 닫힌 것은 0건이나 **타이머 경계에 닿은 통과 실행은 관찰됐다** — 「리뷰와 계약 r03의 정정」) ③ U1(⟨사용자 결정⟩ 2026-10-07 「실기 측정을 출시 조건으로」 — 그 실기 측정은 아직 하지 않았다) ④ iOS의 같은 경합 ⑤ 네이티브(C++) 쪽 fetcher 소비자
  ⑥ ⟨r03⟩ **리뷰는 조건부 PASS였다**(P0 없음 — 판정의 근거는 「원래 결함이 닫혔다」까지이고 「출시 준비가 됐다」는 판정이 아니다). 리뷰의 지적과 계약 r03의 정정은 「리뷰와 계약 r03의 정정」이 진다.
  ⟨사용자 결정⟩ **재리뷰 r02(조건부 PASS)의 남은 머지 조건은 design 단계 생략의 사용자 승인 1건이었고, 2026-10-07 사용자가 승인해 닫혔다**(root의 기록 — 작업 증거 `user-decision`. 승인 뒤 리뷰가 다시 돈 것은 아니다). 판정의 범위(「원래 결함이 닫혔다」까지)는 그대로다.
  ⟨접근성 점검⟩ **accessibility 단계는 끝났다 — 차단 지적 0건 · 이 작업이 만든 접근성 문제 0건.** 권고 셋(R1 ~ R3)은 모두 수정 전부터 있던 성질이고 이 작업의 범위 밖이다(「미확인 · 후속」 22). TalkBack의 실제 낭독은 확인하지 못했다.
  design 단계는 시각 변경이 없어 돌리지 않았고 ⟨사용자 결정⟩ **그 생략은 승인됐다(2026-10-07, 사용자 — 호스트 Java만 변경 · 시각 변경 0).** 아래 ⚠ 줄들이 항목별 상태다.
  ⚠ ⟨재실행 · 대조⟩ **자연 조건의 콜드 스타트 반복(e2e)은 새 판정으로 다시 돌아 통과했다 — 그러나 「늦은 도착」의 원인은 닫히지 않았다.** 첫 실행(2026-10-07)은 **실패로 기록됐다** — API 30의 dev 빌드에서 워드마크 없이 4초 뒤 닫히는 실행이 나왔다(SW1 2 / 67 + 진단 반복 1 / 60).
  진단은 그것이 **이 수정이 만든 결함이 아니라 dev 빌드의 기존 성질(늦은 도착)** 이라고 판정했고, 계약 r02가 e2e 판정을 넷으로 갈랐다(「첫 e2e와 늦은 도착 증상」 · D5 · D6).
  재실행(검증 코드 `ac343e11`, 에뮬레이터 한 대씩)은 API 30 유효 67 PASS · FAIL 0 · LATE 1 · 판정 불가 1, API 37 67 PASS · LATE 0이었다. 수정 전 빌드와의 대조 측정(API 30, 빌드당 150회)은 FAIL(결함)이 수정 전 12 · 수정 후 0, LATE가 두 빌드 모두 0이었다.
  **진단의 「dev만 워드마크를 HTTP로 받아서 늦는다 · 수정 전에도 똑같이 있다」는 그 문면대로 확인되지 않았다**: 재실행의 LATE 한 건은 서버가 0 ms로 응답했는데 났고, 수정 전 빌드의 자연 조건에서는 LATE가 한 건도 관찰되지 않았다.
  지금 말할 수 있는 것은 「수정 후에만 LATE가 나거나 뚜렷이 많다는 신호는 없다 · **약 1% 안팎의 증가는 배제하지 못한다** · 첫 실행의 세 건은 미해결이다」까지다(「재실행과 대조 측정」). 항목별 실행 상태는 [절차 문서](../e2e/android-splash-wordmark.md)의 「실행 상태」가 진다.
  ⚠ ⟨r03⟩ **「타이머 경계는 dev 빌드의 일」이라는 앞선 문면은 틀렸다.** 내장 빌드에서 타이머로 **닫힌** 실행은 0건이지만(수정 전 155회 · 수정 후 300회), 타이머 경계(첫 화면 뒤 4.03 ~ 4.11 s)에 닿은 **통과** 실행은 내장 빌드에서 수정 전 · 후 모두 있다
  (수정 후 API 37 4059 ms, 수정 전 API 37 4030 · 4132 · 4031 · 4708 ms — 두 에뮬레이터를 함께 돌린 부하 조건). 그리고 **자연 조건에서 타이머로 닫힌 실행은 수정 후 빌드에서만 관찰됐다**(수정 전 0건) — 「리뷰와 계약 r03의 정정」.
  ⚠ ⟨사용자 결정⟩ **U1 — 「실기 측정을 출시 조건으로」(2026-10-07, 사용자)**: 워드마크가 늦게 뜰 때 4초 안전 타이머가 재생 도중 스플래시를 닫는 설계를 고칠지는 **지금 정하지 않는다.** ⟨r03⟩ 그 전제는 dev 빌드에 한정되지 않는다 —
  Play 내부 테스트 전에 실기의 릴리스 빌드에서 스플래시 길이를 재고 그 결과로 고칠지 정한다. 지금 코드는 그대로다. **그 측정은 아직 하지 않았다.** 이 수정의 머지는 막지 않는다(「미확인 · 후속」 10. 남는 위험의 수용은 20 — 그쪽은 정해지지 않았다).
  ⟨최종 검증⟩ **계측 HW5 · HW6의 테스트 결함(R1)을 고친 것은 두 기기에서 확인됐다** — HW5 · HW6 · HW7 각 5 / 5(`pm clear` 없이 연속, 매 회 서버에 워드마크 요청 1건). 표본은 기기당 15회다(「최종 검증」 · D6).
  ⚠ **실기에서는 수정 전도 수정 후도 재지 않았다.** 잰 것은 에뮬레이터 둘(Pixel_8 AVD · API 37, R6_API30 AVD · API 30)이다.
  ⟨최종 검증⟩ release AAB는 API 37 에뮬레이터의 스모크뿐이다(첫 e2e 20회 · 최종 검증 5회 — 수정 후만, bundletool 분할 설치. 업로드 키 서명본은 재지 않았다).
  ⚠ **미디어 fetcher를 떼면서 영향받을 수 있는 네이티브(C++) 쪽 소비자는 확인하지 않았다**(「대가」 1). ⟨r03⟩ 리뷰가 arm64 라이브러리 둘의 문자열을 검색한 것까지다 — 부재의 증명이 아니다.
  ⚠ **수용 기준 가운데 「로그인 뒤 화면에서 그림이 보이고 실패 줄 0」(AC8)은 계측이 아니라 첫 e2e의 수동 절차에서 채워졌다**(API 37 프롤로그 · 비주얼 노벨 · 아바타, API 30 프롤로그 — 「확인한 것과 확인하지 못한 것」). 자동 확인 수단은 여전히 없다.

  그 확장점을 다시 비동기 갈래로 되돌리지 않게 하는 검사 · 간헐 결함의 수용 기준(반복 횟수의 계산)

  **바꾸는 결정은 없다.** 재작성된 URL의 값(`HostPaths.media`) · 자산 URL의 모양(`/static/…`) · APK 안 위치(`assets/static/`) · `pnpm bundle:android` · 공유 JS · iOS 호스트 · Lynx 버전(4.0.1)이 그대로다.
  공유 JS(`apps/mobile/src`)가 바뀌지 않아 성능 보고서 게이트 대상이 아니다.

⟨2026-10-07 r02⟩ 이 문서는 같은 날 계약 r02(첫 e2e의 실패 → 진단 → 판정 분리)를 받아 고쳐졌다. **결정 D1 ~ D4의 제품 쪽 내용은 바뀌지 않았다** — 제품 코드에 더 고친 것이 없다. 더해진 것은 「첫 e2e와 늦은 도착 증상」 · D5 · D6이고, D4의 판정 신호와 dev 자연 조건의 횟수가 그 자리에서 대체됐다.

## 맥락

1. **증상** [실측]. 콜드 스타트에서 JS 스플래시의 워드마크 이미지 요청이 `Unsupported uri scheme`으로 실패하고, `SplashScreen.tsx`의 `binderror={finish}`가 스플래시를 3 ~ 283 ms 만에 닫는다(정상은 약 2.4 ~ 3.4 s).
   사용자에게는 「주황 한 면 뒤 로고 없이 바로 첫 화면」이다. [ADR-0049](0049-android-launch-appearance.md)의 작업이 범위 밖에서 발견했고, 그때는 원인을 몰랐다.
2. **워드마크의 `src`는 스킴 없는 절대 경로다** [코드 확인]. `import logoHandwriting from "./assets/logo-handwriting.webp"`의 값을 rspeedy가 `/static/image/logo-handwriting.<hash>.webp`로 낸다.
   `lynx.config.ts`에 `assetPrefix` · inline 한도 설정은 없고, `pnpm bundle:android`가 `dist/static/`을 `apps/android/app/src/main/assets/static/`으로 복사한다.
3. **호스트는 이 경로를 Lynx의 미디어 fetcher에서 바꾸고 있었다** [코드 확인 — 수정 전]. `MainActivity`가 `LynxViewBuilder.setMediaResourceFetcher(new BundledMediaFetcher(bundled, templateUrl))`로
   `/static/…`을 `asset:///static/…`(내장) 또는 `<번들 서버>/static/…`(dev)로 바꿨다. 값을 내는 것은 `HostPaths.media`다.
4. **오류의 출처** [바이트코드]. `Unsupported uri scheme! Uri is: …`는 Fresco의 `ProducerSequenceFactory`가 낸다(그 문자열 상수의 유일한 위치). `onFailed src:…` 줄은 Lynx의 `LynxImageManager$1`이 찍는다.
   즉 **Fresco에 스킴 없는 `/static/…`이 그대로 넘어간 요청이 있었다** — 재작성 전의 `src`로 요청이 만들어졌다.
5. **경합의 구조** [바이트코드 — `com.lynx.tasm.behavior.ui.image.LynxImageManager`].
   1. 생성자가 `mAsyncRedirect = (LynxContext.getMediaResourceFetcher() != null || getAsyncImageInterceptor() != null)`로 정한다. 호스트가 미디어 fetcher를 달았으므로 **항상 true**였다.
   2. 속성 반영 끝의 `updateRedirectCheckResult()`: `src`가 바뀌었고 `canParseUrl(src)`(`file://` · `content://` · `asset://` · `data:`로 시작)가 아니면 재작성 요청을 만든다.
      **현재 스레드가 메인이고 `mAsyncRedirect`면** `SRC_CHANGED` 플래그를 지우고 `LynxThreadPool.getBriefIOExecutor()`(`lynx-brief-io-thread`)에 `shouldRedirectUrl` 호출을 던진다. 끝나면 `mSrc`를 새 값으로 쓰고 UI 스레드에서 `SRC_CHANGED`를 다시 세운 뒤 `onNodeReady()`를 부른다.
      **메인이 아닌 스레드면** 그 자리에서 동기로 `mSrc = shouldRedirectUrl(…)`이다.
   3. `onLayoutUpdated`가 크기가 커지면 `DOWN_SAMPLING_SCALE_CHANGED`를 세운다.
   4. `onNodeReady()` → `updateNodeProps()`는 `SRC_CHANGED` **또는** `BLUR_RADIUS_CHANGED` · `DOWN_SAMPLING_SCALE_CHANGED` · `REGION_TO_DECODE_CHANGED`가 서 있으면 `updateImageSource()`를 부른다.
      이것이 `LynxThreadPool.postUIOperationTask`(스레드 이름 `LynxHighTaskN`)에 작업을 던지고, 그 작업이 **실행되는 시점의 `mSrc`** 로 요청을 만든다.
   5. 그래서 **2의 비동기 재작성이 끝나기 전에 4의 작업이 돌면 요청이 `/static/…`으로 나간다.** 두 작업은 서로 다른 풀에 있고 순서를 묶는 것이 없다.
      실패하면 `error` 이벤트가 JS로 가고, 그 뒤 재작성이 끝나면 `SRC_CHANGED`로 두 번째 요청이 바른 URL로 나간다.
   6. 이미지 UI가 어느 스레드에서 속성을 받는가 [바이트코드 — `LynxUIOwner.createViewAsync`]: 기본값 `enableCreateViewAsync = true`에서 UI 생성과 첫 속성 반영은 `LynxHighTask` 스레드에서 돈다 → 2의 동기 갈래 → **경합 없음.**
      UI 스레드가 그 작업이 끝나기 전에 도착하면 `createViewAsync not done, will create on ui thread`를 찍고 UI 스레드에서 직접 만든다 → 2의 메인 갈래 → **경합 가능.**
6. **간헐적인 까닭은 두 겹이다.** (가) 이미지 UI가 UI 스레드에서 만들어져야 하고(「not done」), (나) 그때 요청 작업이 brief-io의 재작성보다 먼저 돌아야 한다.
   자연 실패 16건(내장 6 + dev 10) 전부에 (가)의 로그 줄이 있었고, 이유 문자열 안의 URI는 항상 재작성 전의 `/static/…`이었다 [실측].

7. **내장 번들에만 있는 결함이 아니다** [실측]. dev(원격 번들) 빌드에서도 나고 오히려 잦다(아래 「재현 빈도」).

## 결정

### D1. 이미지 URL 재작성을 `ImageInterceptor`에만 건다 — 불린 스레드에서 값을 돌려준다

결함은 Lynx 안에 있다(벤더 AAR — 고치지 않는다). 우리가 가진 가장 낮은 경계는 **호스트가 URL 재작성을 Lynx의 어느 확장점에 거는가**다.
미디어 fetcher에 걸면 메인 스레드 갈래가 비동기가 되고, `ImageInterceptor`에만 걸면 `mAsyncRedirect`가 false라 **모든 스레드에서 속성 반영과 같은 호출 안에서 동기로 재작성된다**
[바이트코드 — `LynxImageManager.<init>` · `updateRedirectCheckResult` · `LynxImageMediaFetcherProxy.shouldRedirectUrl` → `ImageUrlRedirectUtils.redirectUrl` → `LynxContext.imageInterceptor().shouldRedirectImageUrl`].
요청이 재작성 전 `src`를 볼 틈이 없다.

- **`HostImageInterceptor`**(`apps/android/app/src/main/java/com/libitum/host/HostImageInterceptor.java`) [코드 확인]:
  - `shouldRedirectImageUrl(url)`은 `HostPaths.media(url, bundled, templateUrl)`를 돌려준다. **새 정책이 없다** — `null` · `/static/`로 시작하지 않는 값은 그대로다.
  - **스레드를 바꾸지 않는다.** 실행기 · 핸들러 · 잠금 · I/O · 로그를 두지 않는다. 이것이 수정의 핵심 성질이다.
  - `loadImage(…)`는 `handler`가 있으면 `handler.imageLoadCompletion(null, null)`을 한 번 부른다. Lynx 4.0.1에는 이 메서드를 부르는 곳이 없다 [바이트코드] — 인터셉터가 없을 때와 같은 응답이다.
    ⟨r02⟩ **「호출되지 않는 무동작」으로 그대로 둔다.** 첫 e2e의 실패 뒤 이 메서드가 원인 후보(H1)였으나 반증됐다(탐침 220회에 호출 0). Lynx는 인터셉터가 없을 때 스스로 `LynxViewClientGroup`을 인터셉터로 걸어 두므로 [바이트코드 — `LynxTemplateRender.init`]
    「인터셉터를 달면 `loadImage`를 구현해야 한다」는 새 의무가 생기지 않는다. `shouldRedirectImageUrl`만 쓰는 다른 동기 확장점은 4.0.1에 없다(`LynxViewClient.shouldRedirectImageUrl`도 같은 인터셉터 경로다).
    **이 전제(호출자가 없다)는 정적 검사 HR7 · HR8이 지킨다**(D6) — Lynx를 올려 호출자가 생기면 검사가 실패하고, 그때는 `loadImage`를 실제로 구현해야 한다.
- **결선** [코드 확인 — `MainActivity.onCreate`]: `builder.setMediaResourceFetcher(…)` 줄을 없앴고, `lynxView = builder.build(this);` **바로 다음, `renderTemplateUrl` 전에**
  `lynxView.setImageInterceptor(new HostImageInterceptor(bundled, templateUrl));`를 둔다. `BundledMediaFetcher.java`는 삭제했다(참조가 `MainActivity` 한 곳뿐이었다).
  `builder.setEnableGenericResourceFetcher(LynxBooleanOption.TRUE)`는 그대로다(debug의 번들 · HMR 로딩이 쓴다).
- **`app/src/main`에 `LynxMediaResourceFetcher`를 잇는 클래스 · `setMediaResourceFetcher(` · `setAsyncImageInterceptor(` 호출을 두지 않는다.** 어느 것이든 `mAsyncRedirect`를 다시 true로 만든다(D3의 검사가 본다).
- 바뀌지 않은 것: `HostPaths` · `AndroidTemplateProvider` · `DuruApplication` · `DebugSupport` · Gradle · 매니페스트 · `vendor-maven`, `apps/mobile` 전부(`SplashScreen.tsx`의 `binderror={finish}` · 안전 타이머 포함), `apps/ios` 전부.
  저장소의 diff로 `apps/ios` · `apps/mobile` · `packages`가 0줄이다 [코드 확인 — `git diff --stat 28ed9265 -- apps/ios apps/mobile packages`].

### D4. 수용 기준 — 간헐 결함의 반복 횟수는 수정 전 실패율에서 계산한다

⟨r02⟩ **아래 문단의 판정 신호는 e2e에서 D5의 넷으로 대체됐다**(`finalloopcomplete` 없음이 서로 다른 두 사건을 한 가지 실패로 셌다). 계측 HW1 ~ HW4의 단언은 그대로다. 첫 e2e는 아래 신호로 판정됐다.

실행 한 번의 판정 신호(모든 기준 공통): 그 실행의 logcat에서 **`LynxImageManager: onFailed` 0줄**(워드마크뿐 아니라 어떤 이미지든) **그리고** `finalloopcomplete` 1줄 이상 **그리고** `onFirstScreen` 1줄 이상.
번들 미로드는 실패도 통과도 아닌 「판정 불가」로 세고 횟수에서 뺀 뒤 다시 채운다. 스플래시 길이만으로는 판정하지 않는다 — 두 풀을 길게 잠재우면 어느 결선에서도 안전 타이머(4 s)가 스플래시를 닫는다 [실측].

**식**: 수정 전 실패율이 p일 때, 고치지 않았는데 n회 연속 성공할 확률은 (1 − p)^n이다. 이를 0.1% 미만으로 하려면 **n > ln(0.001) / ln(1 − p).**

| 기준 | 수정 전 p | n과 계산 | 증거로 세는가 |
|---|---|---|---|
| **강제 재현**(계측 HW1) | 수정 전 10 / 10 실패 → p의 95% 하한 0.05^(1/10) = 0.741 | n > ln(0.001) / ln(0.259) = 5.1 → **기기마다 10회 연속 통과**(6이면 족하나 red와 같은 수로 맞췄다. 0.259^10 = 1.4×10⁻⁶) | 증거 — 수정 전 10 / 10 실패의 기록이 전제다 |
| **dev 자연 조건**(e2e) | ⟨r02⟩ **0.10 — HEAD 그대로의 수정 전 debug로 다시 잰 값**(e2e-red: 두 기기 각 2 / 20). 계약 단계의 0.20(API 30 4 / 20) · 0.30(API 37 6 / 20)은 탐침 사본 빌드의 값이었고, 그 값으로 예고한 32회(0.8^32 = 7.9×10⁻⁴)는 쓰지 않는다 | n > ln(0.001) / ln(0.9) = 65.6 → 올림 66에 여유 1을 더해 **기기마다 PASS 67회**(0.9^67 = 8.6×10⁻⁴). **기기를 한 대씩 돈다**(다른 에뮬레이터 · 계측 · 빌드를 함께 돌리지 않고 시작과 끝의 `uptime`을 적는다). 판정은 D5 — FAIL 0, LATE는 상한 안 | 증거 — red가 성립했다(두 기기 모두 20회에 실패 2건, 기대한 줄과 일치). API 37은 첫 e2e의 0 / 67로 채워졌다. **API 30은 첫 e2e의 2 / 67 + 1 / 60을 버리고 다시 돈다**(서버 요청 기록이 없어 LATE로도 FAIL로도 다시 셀 수 없다) — 결과는 절차 문서. ⟨재실행 · 대조⟩ 다시 돌았다: API 30 유효 67 PASS · FAIL 0 · LATE 1, API 37 67 PASS · LATE 0(「재실행과 대조 측정」). p 0.10은 대조 측정의 수정 전 12 / 150 = 0.08(95% 구간 4.2 ~ 13.6%)과 어긋나지 않는다 — n은 다시 계산하지 않았다. ⟨r03⟩ **p 0.10은 점추정이고 67회만으로는 기준(10⁻³)에 닿지 않는다 — 결론은 합산 분모가 진다**(표 아래 「통계의 한계」) |
| **내장 번들 자연 조건**(e2e), API 30 | 0.071(5 / 70) | **100회 연속 통과** — 0.929^100 = 6.3×10⁻⁴. ⟨r03⟩ **이 값도 점추정이다**(p의 95% 하한 2.4%면 0.088 — 표 아래 「통계의 한계」) | 증거 — 점추정의 한계 안에서 |
| **내장 번들 자연 조건**(e2e), API 37 | 0.012(1 / 85) | 100회 — 약 0.30. **0.1%에 닿지 못한다**(닿으려면 584회). ⟨r02⟩ 표기를 맞춘다: p를 0.012로 반올림하면 0.988^100 = 0.299(절차 문서 · e2e 기록의 「≈ 0.30」), 분수 1 / 85 그대로면 (84 / 85)^100 = 0.306(계약 §7의 「0.31」)이다. 584회는 분수 기준이다(0.988이면 573회) | **세지 않는다.** 「회귀가 없다」의 연기 검사일 뿐이다 |
| 실패 경로(I1) | 결정적 | 기기마다 3회 | 가드 — 수정 전에도 통과한다 |

- ⟨r03⟩ **통계의 한계**(리뷰 P1-5 · 계약 r03.4):
  - **dev 자연 조건의 p = 0.10은 2 / 20 두 번의 점추정이다.** HEAD 그대로의 수정 전 dev를 합치면 16 / 190 = 8.4%(e2e-red 2 / 20 · 2 / 20 + 대조 측정 12 / 150)이고, 이 값이면 **n ≥ 79**가 필요하다 — 67회의 우연 통과 확률은 8.6×10⁻⁴이 아니라 **2.8×10⁻³**(기준 10⁻³ 초과)이다.
    **결론은 67회가 아니라 합산 분모가 진다**: 수정 후 dev에서 FAIL(결함)이 0건인 판정 난 시도가 API 30 **218회**(재실행 68 + 대조 측정 150) · API 37 **134회**(첫 e2e 67 + 재실행 67)이고, p = 8.4%에서 우연히 0건일 확률은 각각 4.7×10⁻⁹ · 7.6×10⁻⁶이다.
  - **내장 API 30의 6.3×10⁻⁴도 점추정**(5 / 70 = 7.1%)에 기댄다. p의 95% 하한 2.4%를 쓰면 100회의 우연 통과 확률은 **0.088**이다. 그리고 이 p는 e2e에서 다시 재지 않았다(계약 단계 값). API 37의 100회는 처음부터 증거로 세지 않았다.
  - 이 문서의 다른 자리에 적힌 「우연 통과 확률 0.9^67 = 8.6×10⁻⁴」 · 「0.929^100 = 6.3×10⁻⁴」는 전부 이 한계 아래에서 읽는다.
- 「연속 통과」는 실패가 한 번이라도 나오면 끊긴다. 한 번 실패한 뒤 횟수를 늘려 통과로 채우지 않는다.
- 자연 실패율은 부하에 흔들린다(앞선 6 / 9 대 이번 5 / 70). 그래서 e2e의 n은 **그 e2e를 도는 환경에서 다시 잰 p**로 확정한다.
- 절차 · 반복 실행기(`apps/android/tools/splash-wordmark-repeat.sh`) · 항목별 실행 상태는 [절차 문서](../e2e/android-splash-wordmark.md)가 진다.
  ⟨r02⟩ 이 ADR은 **첫 e2e의 결과만** 진단의 전제로 적었다(「첫 e2e와 늦은 도착 증상」). **그 뒤의 재실행 결과는 적지 않는다** — 절차 문서의 「실행 상태」가 정본이다.
  ⟨재실행 · 대조⟩ **바로 위 문장은 대체됐다.** 재실행과 대조 측정이 진단의 근거 수준을 바꿨으므로 그 요약을 「재실행과 대조 측정」에 적었다. 항목별 실행 상태(회차 · 부하 · 미실행)의 정본은 여전히 절차 문서이고, 대조 측정의 수치 · 계산의 정본은 하네스 작업 폴더의 `late-compare.md`다.

### D5. e2e의 실행 판정을 넷으로 가른다 — 「늦은 도착」은 통과도 이 결함의 실패도 아니다 ⟨r02⟩

첫 e2e의 판정은 `finalloopcomplete` 없음 하나로 **서로 다른 두 사건**(이 작업의 결함 · 늦은 도착)을 같은 실패로 셌다. 요청이 바른 URL로 나갔는지를 보지 않아 「요청이 틀렸다」와 「응답이 늦었다」를 가르지 못했다.
그래서 dev 항목은 **번들 서버의 요청 기록(시각 · 경로 · 상태)** 을 실행과 함께 남기고, 실행마다 아래 가운데 하나로 센다. 신호의 세부 · 실행기의 요약 줄 · 종료 코드는 [절차 문서](../e2e/android-splash-wordmark.md)의 「판정」이 진다(여기에 되풀이하지 않는다).

| 판정 | 조건 | 셈 |
|---|---|---|
| **PASS** | `onFirstScreen` ≥ 1 · `onFailed` 0 · `finalloopcomplete` ≥ 1 | 유효 시도 |
| **FAIL(결함)** | `onFailed` ≥ 1(어떤 이미지든) | 유효 시도 — 한 건이면 그 기준은 실패 |
| **FAIL(요청 없음)** | `onFirstScreen` ≥ 1 · `onFailed` 0 · `finalloopcomplete` 0이고 LATE의 증거가 하나라도 빠진다 | 유효 시도 — 한 건이면 실패. **내장 빌드는 서버가 없으므로 `finalloopcomplete` 없음이 항상 이것이다** |
| **LATE(늦은 도착)** | **dev에서만 가를 수 있다**(서버 기록이 있어야 한다 — 늦은 시작이 dev에서만 난다는 뜻이 아니다). `onFirstScreen` ≥ 1 · `onFailed` 0 · `error` 이벤트 0 · `finalloopcomplete` 0 **그리고** (a) 그 실행의 번들 요청 뒤에 서버가 워드마크(`/static/image/logo-handwriting.*`)에 **200으로 응답한 기록이 정확히 1건** **그리고** (b) 스플래시가 첫 화면 뒤 **3.0 s 이후**에 끝났다 | **통과가 아니다. 이 결함의 실패도 아니다.** 유효 시도에서 빼고 다시 채우며 건수를 따로 적는다 |
| 판정 불가 | `onFirstScreen` 0 | 뺀다 |

- **LATE의 상한**: 한 기기의 한 케이스에서 LATE가 **시도의 5%를 넘으면 그 실행 전체를 「환경 부적합」으로 버린다**(통과가 아니다). 단독 기기로 다시 돈다. 5%는 진단의 조용한 구간(0 / 116 — 95% 상한 2.5%)의 두 배다.
  ⟨r03⟩ 「시도」는 판정이 난 시도(PASS + FAIL + LATE)이고, **5%는 결함을 막는 방어선이 아니라 실행 품질의 문턱이다** — 두 배라는 여유에 통계적 의미는 없다(「리뷰와 계약 r03의 정정」).
- **실패를 정의로 지운 것이 아닌 근거**: 이 작업이 닫은 결함은 「재작성 전 URL로 나간 요청」이다. 그 요청은 Fresco가 스킴을 보고 즉시 거절해 `onFailed`를 찍고 **서버에 닿지 않는다** — LATE의 (a)를 채울 수 없고, 그 전에 FAIL(결함)이다.
  요청이 아예 만들어지지 않는 회귀도 (a)를 채우지 못해 FAIL(요청 없음)이 된다. 일찍 닫히는 회귀는 (b)를 채우지 못한다. 그리고 「수정 전에도 통과하는 기준」이 되지 않게, dev 자연 조건의 n은 수정 전 실패가 관찰된 조건(e2e-red)에서만 센다.
- **그 근거의 한계**:
  1. (a)는 「서버가 워드마크를 한 번 내줬다」까지만 본다. **앱이 그 응답을 받아 그렸는지는 보지 못한다** — 응답 뒤 앱 안에서 그림이 사라지는 결함이 있다면 LATE로 읽힌다. 자연 조건의 증상 20건에서 그림이 결국 도착했다는 탐침 관찰이 그 틈을 메우는 유일한 근거다.
  2. 첫 e2e의 세 건이 늦은 도착이었다는 것 자체가 [추론]이다. **재실행에서 FAIL(요청 없음)이 한 건이라도 나오면 이 진단은 틀린 것이고 계약으로 되돌린다.**
     ⟨재실행 · 대조⟩ 재실행과 대조 측정에서 FAIL(요청 없음)은 0건이었다 — 되돌리는 조건은 서지 않았다. 다만 그 0건의 검정력이 약하고 세 건은 미해결로 남는다(「재실행과 대조 측정」).
  3. 상한 5%는 원인을 모른 채 정한 값이다 — 너무 빡빡하거나 느슨할 수 있다. ⟨재실행 · 대조⟩ 그 뒤 관찰된 수정 후의 자연 조건 LATE는 1 / 218 = 0.46%(95% 구간 0.01 ~ 2.5%)다 — 상한은 고치지 않았다.
  4. (a)는 서버 기록과 실행을 구간으로 맞춘다(그 실행의 번들 요청부터 다음 실행의 번들 요청 전까지 — 기기 시계와 호스트 시계를 맞대지 않는다). 실행기가 그 구간을 잘못 자르면 판정이 틀린다.
  5. **내장 빌드에서는 늦은 도착을 가를 수 없다**(서버가 없다). 내장 빌드에서 같은 모양이 나오면 FAIL(요청 없음)로 서고, 그때는 사람이 읽어야 한다.
     ⟨r03⟩ 가설의 경우가 아니다 — 내장 빌드의 통과 실행이 타이머 경계에 닿은 것이 관찰됐다(「리뷰와 계약 r03의 정정」).
- **첫 e2e의 다른 결과는 그대로 유효하다**: API 37의 dev 0 / 67(실패가 0건이라 서버 기록 없이도 새 판정과 같다), 내장 100 / 100 · 100 / 100(내장에서는 `finalloopcomplete` 없음이 FAIL인데 0건이었다).

## 버린 대안

| 대안 | 기대는 가설 | 버린 까닭 |
|---|---|---|
| **번들에서**: Android 빌드에서만 `output.assetPrefix`를 `asset:///`로 줘 `src`가 처음부터 `asset:///static/…`이 되게 한다 | `canParseUrl`이 `asset://`를 재작성 대상에서 뺀다 [바이트코드]. **실측하지 않았다** | dev 빌드의 경합은 그대로 남는다(자연 10 / 40). 플랫폼별로 다른 번들이 생기고 `bundle:android`에 환경 분기가 든다. iOS와 번들이 갈린다 |
| **JS에서**: 스플래시가 첫 `error`를 무시하거나 `src`를 다시 건다 | 「두 번째 요청은 성공한다」(맥락 8 실측) | 증상만 가린다 — 실패하는 첫 요청과 `VisualNovelScene` · `Avatar`가 남는다. `apps/mobile/src` 변경이라 성능 보고서가 붙고 iOS 동작도 바뀐다. 「정말 실패하면 스플래시가 끝난다」(I1)를 타이머에만 맡기게 된다 |
| **호스트에서**: `LynxImageFetcher`로 이미지 로딩 전체를 대체한다 | — | 로딩 · 캐시 · 애니메이션 WebP 재생까지 호스트가 떠맡는다. 범위 초과 |
| **`enableCreateViewAsync`를 강제한다** | (가)만 막는다 | 페이지 설정이고 「not done」 대체 경로는 어차피 UI 스레드다. 보장이 안 된다 |

원인 후보로 세웠다 버린 가설도 있다: Fresco의 늦은 초기화(`Fresco.initialize`는 `Application.onCreate`에서 동기이고 오류는 스킴 판정이다) · fetcher가 LynxView 생성 뒤에 달린다(`builder.build` 전에 달았다) ·
템플릿 base URL이 첫 렌더보다 늦다(재작성은 생성자 값만 쓴다) · APK에 자산이 없다(같은 APK가 대부분 성공한다) · 실행 테마 작업의 회귀(구현 전 빌드에서도 났다).

## 대가

1. **미디어 fetcher를 떼면서 그것을 읽던 다른 소비자가 깨질 수 있다 — 네이티브 쪽은 확인하지 않았다.** 자바 쪽 소비자는 `LynxImageManager` · `LynxImageMediaFetcherProxy`뿐이다 [바이트코드 — lynx · xelement* · lynx-service-image의 클래스 전수 검색].
   **네이티브(C++) 쪽은 보지 못했다** [미확인]. 계측의 통과(D3 · 「확인한 것」)는 그 부재의 증명이 아니다.
   ⟨r03⟩ 리뷰의 확인: arm64 `liblynx.so` · `liblynx_v8_bridge.so`에 미디어 fetcher 관련 문자열이 없다. 문자열 검색 수준이고 다른 ABI · `xelement*` · `lynx-service-image`는 보지 않았다 — 여전히 부재의 증명이 아니다.
2. **인터셉터가 생기면 `canParseUrl`이 아닌 모든 `src`가 인터셉터를 지난다**(원격 `https://` 포함) [바이트코드 — `isLocalResource`가 `UNDEFINED`가 된다]. `HostPaths.media`가 원본을 돌려주므로 값은 같다(I3).
   `<svg src>` · 마크다운 이미지도 인터셉터를 읽지만 앱은 쓰지 않는다 [코드 확인]. 인터셉터에 정책을 더하면 그 비용이 모든 이미지에 든다.
3. **`ImageInterceptor`는 Lynx의 옛 확장점이다.** 버전을 올리면 없어지거나 fetcher와의 우선순위가 바뀔 수 있다. **정적 검사(HR1 ~ HR6)는 「우리 결선」만 지키고 Lynx의 동작은 지키지 못한다** — Lynx를 올릴 때 계측 HW1을 다시 돌린다(「재검토 조건」).
4. **결정적 증거(HW1)는 에뮬레이터가 필요해 `pnpm verify`에 없다.** `pnpm verify`에서 도는 것은 단위와 정적 결선뿐이다.
5. **HW1의 강제 수단이 Lynx의 내부 구조에 기댄다** — 공개 정적 풀(`LynxThreadPool`)의 이름과 스레드 수, 「not done」 로그 문구. Lynx가 바뀌면 강제가 걸리지 않을 수 있고, 그때 HW1은 조용히 통과하지 않고 「강제 불성립」으로 실패한다.
6. **결함 자체는 Lynx 안에 남아 있다.** 누군가 미디어 fetcher나 비동기 인터셉터를 다시 달면 되살아난다 — 막는 것은 HR1 · HR2 · HR4다.

## 미확인 · 후속

1. **iOS의 fetcher 경로에 같은 종류의 경합이 있는지 확인한다.** iOS 호스트도 `/static/`을 미디어 fetcher로 바꾼다(`apps/ios/Host/TemplateProvider.swift`의 `BundledMediaResourceFetcher`). 이 작업은 iOS를 보지 않았다.
2. **Lynx 상류에 `LynxImageManager.updateRedirectCheckResult`의 경합을 보고한다.** 하지 않았다.
3. **`VisualNovelScene` · `Avatar`가 한 번의 `error`로 그림을 영구히 치우는 것이 맞는지 정한다.** 네트워크 일시 오류에도 같다. 이 작업은 그 오류 정책을 바꾸지 않았다.
4. **실기 · release AAB에서 잰다.** Play 내부 테스트 전에 실기에서 내장 번들 반복의 축약판(20회)을 한 번 돌릴 것을 계약이 권했다(차단 아님). ⟨r03⟩ 실기의 내장 · release 빌드에서 스플래시 길이 분포를 재는 것을 **출시 조건으로 둘지**는 사용자 결정이다(10). ⟨사용자 결정⟩ **출시 조건으로 정해졌다(2026-10-07)** — 「차단 아님」은 이 수정의 머지에 한한 말이고, Play 내부 테스트 전에는 잰다(10).
5. **네이티브(C++) 쪽 미디어 fetcher 소비자의 유무.** ⟨r03⟩ 리뷰가 본 것은 arm64 `liblynx.so` · `liblynx_v8_bridge.so`의 문자열까지다. 다른 ABI · `xelement*` · `lynx-service-image`가 남았다.
6. **로그인 뒤 화면의 래스터 그림을 보는 자동 수단.** `SignedInScreenFixtureTest`에 그림이 있는 화면으로 가는 픽스처 인자가 필요하다. ⟨r02⟩ AC8 자체는 첫 e2e의 수동 절차로 채워졌다 — 남은 것은 자동화다.

8. **UI 스레드가 왜 비동기 생성을 기다리지 않는지**(첫 화면의 연산이 풀보다 먼저 도착한다는 것은 [추론]). 계약 단계의 탐침에서 워드마크는 128회 가운데 60회가 UI 스레드였고 온보딩의 두 그림은 160회 전부 비동기였다 [실측] — 첫 렌더의 이미지가 유독 노출된다.

    - ⟨2026-10-08 적용 기록 — [ADR-0052](0052-android-release-shrinking.md)⟩ **이 실기 측정은 minify를 켠 빌드로 해야 한다.** `release`와 `bundled`가 R8로 축소 · 난독화되도록 바뀌었고 R8이 기동 경로의 코드를 바꾸므로, 축소 전 빌드에서 잰 분포는 출시 바이너리의 값이 아니다.
      **이 ADR의 내장 빌드 반복 측정(SW2 · SW3 · SW8과 수정 전 155회)은 모두 축소 전 `bundled` · release의 것이다.** 축소한 `bundled`에서 본 것은 그 작업 e2e의 최소 확인 한 번뿐이다 — API 37 에뮬레이터, `pm clear` 10회에 PASS 10 / 10 · `onFailed` 0 · 판정 불가 0(스플래시 길이 중앙 2660 ms는 호스트 부하 3.7 → 12.7 아래의 기록이다).
      **표본 10회다** — 「축소한 빌드에서도 워드마크가 그려진다」까지이고, D4의 횟수(100회)나 타이머 경계의 분포를 대신하지 못한다. API 30 · 실기에서는 축소한 빌드로 재지 않았다. 이 ADR의 결정 D1 ~ D6은 바뀌지 않는다.
    **이 작업의 범위 밖이고 이 작업을 막지 않는다.** 고칠지는 결정되지 않았다 — [보류 표](README.md#보류-표)에 행이 남아 있다(조건이 「사용자 결정」에서 「실기 측정 뒤 재판단」으로 바뀌었다).
11. ⟨r02⟩ **dev 빌드에서 워드마크의 도착을 늦추는 것이 무엇인지.** 서버 뒤 어딘가라는 것까지다(「확정하지 못한 것」). ⟨재실행 · 대조⟩ 재실행도 같은 자리에서 멈췄다 — 14가 잇는다.
12. ⟨r02⟩ **첫 e2e의 세 건이 늦은 도착이었다는 것의 직접 증거.** 재실행이 서버 기록과 함께 돌아 LATE로 분류되는지가 간접 확인이다 — FAIL(요청 없음)이 나오면 진단이 틀렸다(D5의 한계 2).
    ⟨재실행 · 대조⟩ 재실행은 같은 로그 모양의 사건을 서버 기록과 함께 **한 건** 잡았고(LATE) FAIL(요청 없음)은 0건이었다. 세 건 자체는 서버 기록이 없어 **미해결로 남는다** — 다시 셀 방법이 없다.
13. ⟨r02⟩ **API 37에서의 늦은 도착 재현 · API 30에서의 변이 구분 · e2e 가드 SW9.** 하지 않았다. ⟨재실행 · 대조⟩ SW9는 두 기기에서 돌았다(D6). 앞의 둘은 여전히 하지 않았다 — 재실행의 API 37 SW1은 LATE 0 / 67이었다.
14. ⟨재실행 · 대조⟩ **서버가 즉시 응답했는데 워드마크가 늦게 뜨는 사건의 원인.** 자연 조건에서 약 0.5%로 관찰됐다(수정 후 1 / 218, 95% 구간 0.01 ~ 2.5% — **API 30 에뮬레이터 · dev 빌드**). 서버 뒤의 어느 단계(에뮬레이터의 네트워크 전달 · Fresco의 네트워크 · 디코드 · 표시 · 애니메이션 시작)인지 모른다.
    수정 전 빌드에서도 나는지는 자연 조건에서 관찰되지 않았고(0 / 150 — 수정 후도 같은 측정에서 0 / 150), 「수정이 약 1% 안팎으로 늘렸다」도 배제되지 않았다.
15. ⟨재실행 · 대조⟩ **그 사건이 내장 빌드 · 실기에서 나는지.** 내장 빌드는 첫 e2e 300회에 0건이다(API 37 · API 30 에뮬레이터. 내장에서는 같은 모양이 FAIL(요청 없음)으로 선다). 실기에서는 어느 빌드도 재지 않았다(4).
    ⟨r03⟩ 「0건」은 타이머로 **닫힌** 실행의 수다. 타이머 경계에 닿은 통과 실행은 내장 빌드에 있다(수정 후 1 / 300 · 수정 전 4 / 155 — API 37, 두 에뮬레이터 동시 부하. 「리뷰와 계약 r03의 정정」). 남은 물음은 「나는가」가 아니라 **실기 · 출시 빌드에서 얼마나 자주 경계를 넘는가**다.
16. ⟨재실행 · 대조⟩ **앱 안에서 워드마크가 도착한 시각을 찍는 계측이 없다.** Lynx는 성공한 이미지 요청을 로그로 남기지 않고, 진단의 탐침(리플렉션 · Fresco 요청 로그)은 일회용 사본에만 있었다 — Fresco 로그를 켠 뒤로는 증상이 재현되지 않았다. 14 · 15를 가르려면 이것이 먼저다.
17. ⟨재실행 · 대조⟩ **R1을 고친 HW5 · HW6의 기기 확인.** ⟨최종 검증⟩ **닫혔다** — 두 기기에서 각 5 / 5(D6 · 「최종 검증」). 남는 것은 표본의 크기(기기당 15회)다.
18. ⟨최종 검증⟩ **이 변경의 리뷰.** ~~아직 거치지 않았다.~~ ⟨r03⟩ **거쳤다 — 조건부 PASS**(P0 없음). 머지 전 조건 가운데 문서 · 계약 · 테스트 메시지의 정정은 반영됐고(「리뷰와 계약 r03의 정정」 — 리뷰가 그 반영을 다시 본 것은 아니다), 남은 것은 확장 단계(design 생략의 사용자 승인 — ⟨접근성 점검⟩ accessibility는 차단 지적 0건으로 끝났다. 22)와 사용자 결정(10 · 20)이다.
    ⟨사용자 결정⟩ **design 생략은 2026-10-07 사용자가 승인했다 — 재리뷰 r02(조건부 PASS)가 남긴 머지 전 조건 1건이 닫혔다**(승인 뒤 리뷰가 다시 돈 것은 아니다). 10은 출시 조건으로 정해졌고(실기 측정 전), 20(남는 위험의 수용)과 접근성 권고 R1 ~ R3의 채택은 정해지지 않았다.
    리뷰가 확인하지 못한 것: 테스트 · 빌드 · 에뮬레이터 실행, 회차별 logcat 묶음, `xelement*` · `lynx-service-image`, iOS, 실기.
19. ⟨최종 검증⟩ **최종 검증이 돌리지 않은 것.** `ButtonAccessibilityTest` · Maestro 전부 · API 30의 `SignedInScreenFixtureTest`와 세션 · 저장소 스크립트 · `*.artifacts.mjs` · 실기 · 업로드 키 서명 AAB(「최종 검증」).
20. ⟨r03⟩ **남는 위험 — 수용 여부는 사용자 결정이다**(계약 r03.6 · 리뷰).
    1. 수정이 자연 조건의 늦은 도착을 **약 1% 안팎 늘렸을 가능성은 배제되지 않았다**(단측 상한 1.98%). 자연 조건에서 타이머로 닫힌 실행은 수정 후 빌드에서만 관찰됐다(「리뷰와 계약 r03의 정정」의 「약점」).
    2. 첫 e2e의 API 30 세 건(3 / 127)은 서버 기록이 없어 분류하지 못했고 **미해결**이다(12).
    3. 실기 · 업로드 키 서명 AAB · iOS는 재지 않았다(1 · 4).
21. ⟨r03⟩ **리뷰가 후속으로 남긴 테스트 쪽 항목.** 변이의 원본 로그가 없다(HR7 가짜 jar · HW7 타이머 제거 · HW6 3000 · 비우기 뺀 대조 — 요약뿐, API 37에서만) · HW6의 「지연 불성립」 하한(D6) · 「HW6 API 30 13 / 15」의 원인.
22. ⟨접근성 점검⟩ **접근성 점검의 결과와 그 한계.** 출처는 하네스 작업 폴더의 `accessibility.md`다 [점검 HEAD `df47a263`, API 37 에뮬레이터 한 대 · debug(dev) 빌드. 코드는 고치지 않았다].
    - **차단 지적 0건. 이 작업이 만든 접근성 문제 0건.** 스플래시 워드마크의 `accessibility-label="Duru"` · `accessibility-traits="image"`는 그대로이고 공유 JS · iOS의 diff가 0이다 [코드 확인]. 바뀐 Java는 이미지 URL 문자열만 다시 쓴다 — View · 접근성 노드 · 포커스 · 색 · 애니메이션을 다루지 않는다.
      수정이 바꾸는 것은 스플래시의 체류 시간이다(실패하던 시작이 즉시 닫히지 않고 약 2.4 s 재생된다) — 이름을 읽을 시간이 생기는 쪽이다.
    - **권고 셋 — 모두 기존 성질이고 이 작업의 범위 밖이다**(채택 여부는 정해지지 않았다).
      - **R1 모션**: 시스템의 애니메이션 배율 셋을 0으로 둬도 워드마크의 손글씨 애니메이션(2.4 s)이 그대로 재생된다 [실측 — **1회**, 캡처 20장에서 획이 1.2 s 넘게 자란다]. 원인(이미지 디코더의 프레임 스케줄이라 배율을 따르지 않는다)은 추정이다. **WCAG 2.1 AA 위반이 아니다**(5초 미만 · 번쩍임 없음 · 상호작용이 일으킨 모션이 아니다).
        이 수정은 그 재생을 「대부분의 시작」에서 「매 시작」으로 만들었을 뿐 재생 여부를 정하는 코드를 바꾸지 않았다. 고치려면 공유 JS와 두 호스트 · 정지 그림 자산이 필요하다.
      - **R2 비터치 모드의 화면 전체 틴트**: 기기가 터치 모드가 아닐 때(키보드 · D-pad · 스위치, adb로만 시작한 에뮬레이터) LynxView 전체가 포커스를 받고 화면 전체가 약 0.875배로 어두워진다(스플래시 `#F46B18` → `#D65E15`, 워드마크 `#FFFFFF` → `#DFDFDF`) [실측 — 캡처].
        **원인은 추정이다**(View의 기본 포커스 하이라이트 — 켜고 끄는 대조를 하지 않았다). 점검은 이것을 「앞선 감사의 미확인 관찰」을 캡처로 뒷받침한 것이라고 적었다.
        **에뮬레이터의 캡처로 색을 견주는 실행은 터치 모드 여부를 적어야 한다** — 같은 화면이 두 색으로 찍힌다.
      - **R3 테스트 공백**: 스플래시 워드마크가 TalkBack에서 읽히는지, 스플래시 뒤 접근성 포커스가 어디에 놓이는지를 보는 자동 확인도 수동 절차도 없다. `ButtonAccessibilityTest`는 로그인 화면만 본다.
    - **확인하지 못한 것**: TalkBack의 실제 낭독(켜지 않았다 — 「Duru」가 읽히는지 · 2.4 s 안에 끝나는지 · 포커스 위치. `uiautomator dump`의 빈 `content-desc`는 Lynx가 TalkBack이 켜졌을 때만 가상 노드를 만들기 때문이라 결함의 증거가 아니다) · 내장(release) 빌드 · API 30 · 실기 · iOS(변경 없음) · R1과 R2의 원인.
      늦은 도착으로 주황 화면이 4초 이어질 때에도 `<image>` 노드와 라벨이 남는다는 것은 코드로만 봤다(기기 미확인).
    - **U1의 참고 관찰 — 결론으로 쓰지 않는다**: 점검의 터치 모드 대조 시작(1회)에서 찍은 캡처 2장(시작 후 약 1.6 s부터)에 워드마크가 없었다(주황뿐). **그 실행은 logcat을 보지 않아 느린 시작인지 판단하지 않았다** — 늦은 도착의 건수로 세지 않는다(10 · 14).

## 재검토 조건

- **Lynx 버전을 올리면** → D1 · D3. `ImageInterceptor`가 남아 있는지, `mAsyncRedirect`를 정하는 조건이 그대로인지 바이트코드로 다시 읽고 **계측 HW1을 두 기기에서 다시 돌린다.** HW1이 「강제 불성립」으로 실패하면 대기를 넣어 통과시키지 않고 풀 · 로그 문구부터 읽는다.
  ⟨r02⟩ **HR7이 실패하면**(`loadImage`의 호출자가 생겼거나 클래스 집합이 달라졌다) → D1 · D6. 기대값을 고쳐 통과시키기 전에 새 호출자를 읽는다 — 호출자가 생겼다면 `HostImageInterceptor.loadImage`의 무동작이 이미지를 이벤트 없이 끝낼 수 있다. `xelement*` · `lynx-service-image`는 HR7이 보지 못하므로 손으로 다시 확인한다.
- ⟨r02⟩ **e2e의 dev 반복에서 FAIL(요청 없음)이 한 건이라도 나오면** → 「첫 e2e와 늦은 도착 증상」 · D5. 「e2e-D1은 늦은 도착이다」라는 진단이 틀린 것이다 — 그 실행의 logcat과 서버 구간을 읽고 계약으로 되돌린다.
- ⟨재실행 · 대조⟩ **dev 반복의 LATE가 수정 후 빌드에서 뚜렷이 많아지거나, 앱 안의 도착 시각을 찍는 계측이 생기면** → 「재실행과 대조 측정」 · 「미확인 · 후속」 14. 지금의 「수정이 늘렸다는 신호가 없다」는 0 / 150 대 0 / 150 한 번에 기댄다.
- ⟨r02⟩ **「주황 화면이 4초쯤 이어지다 로고 없이(또는 쓰다 만 로고에서) 첫 화면으로 넘어간다」는 보고가 내장 빌드 · 실기에서 나오거나, 실기의 내장 빌드에서 워드마크가 마운트 뒤 1.6 s보다 늦게 뜨는 것이 측정되면** → U1(「미확인 · 후속」 10). dev 빌드에서 타이머로 닫히는 것은 알려진 성질이다.
  ⟨r03⟩ 에뮬레이터의 내장 빌드에서 타이머 경계에 닿은 **통과** 실행은 이미 관찰됐다(「리뷰와 계약 r03의 정정」) — 이 조건이 기다리는 것은 타이머로 **닫힌** 실행의 보고 · 측정, 또는 실기의 길이 분포다.
- ⟨r02⟩ **`SplashScreen.tsx`의 `entrySplashDurationMs`나 워드마크 애니메이션의 길이가 바뀌면** → D5 · D6. 경계 1.6 s(= 4.0 − 2.4) · LATE의 3.0 s · HW5 ~ HW7의 지연 값과 창이 그 두 수에서 나왔다.
