# ADR-0071 — 새 에피소드를 연결될 때마다 하나씩 받아 두고, 그림 · 음성까지 갖춘 뒤에 연다 (호스트 `ContentFileModule` · 신호 `contentSyncOpportunity`)

- 상태: **채택 — 클라이언트 · 호스트.** 서버 변경 0(공개 버킷 `content` 그대로, 매니페스트 형식 그대로).
  ⚠ **기기 확인은 일부다** — iOS 실기에서 EB1 · EB2(받기 → 열림 · 오프라인 그림)를 확인했고, 소리 · 연결 전환 · 포그라운드 · 셀룰러(EB3 ~ EB7) · Android는 남았다([e2e](../e2e/episode-background-download.md)).
  Lynx `<image src="file://…">`가 두 호스트에서 그려지는지도 아직 보지 않았다(EB2).
- 날짜: 2026-10-19.
- 사용자 결정(2026-10-19): 범위 = 본문 + 그림 · 음성 · 받는 때 = 연결될 때마다 + 포그라운드 복귀 · 연결 종류 = 셀룰러 포함 모두 · 반영 = 받는 즉시 · 원격 에피소드가 열리는 기준 = 본문 · 그림 · 음성을 **다 받은 뒤**.
- 이어받는 결정: [ADR-0056](0056-episode-content-delivery.md) D3(같은 실행 안에서 이미 연 본문을 닫지 않음 — 그대로) · D4(실패는 다음에 다시 — 「다음 실행」이 「다음 기회」로 넓어짐) · D9(실행당 1회 갱신 → **실행 시작 + 신호마다**) · D10(그림은 호스트 이미지 로더가 원격에서 — **받아 둔 파일이 먼저**) · 대안 3(파일 저장 모듈 — 이번에 연다) · 재검토 조건 2(그림 미리 받기 — 발동).
  [ADR-0060](0060-episode-voice-remote-audio.md) D1 · D7(음성은 스트리밍만 · 오프라인 무음 — **받아 둔 파일이 먼저**).
  [ADR-0029](0029-product-analytics-posthog.md)의 `episode_content_refreshed` — 실행당 최대 1회 그대로.

근거 표시: **[코드]** 저장소 코드 · **[실측]** 테스트 실행 · **[ADR]** 기존 결정 · **[추론]** 관찰 없이 이어 붙인 것.
계약의 정본은 작업 폴더의 spec(`.agent-harness/work/episode-background-download/spec.md`)이고 이 문서는 결정만 옮긴다.

## 맥락

1. **받기는 실행당 한 번이었다** [코드]. `useEpisodeContentRefresh`가 마운트에서 `refreshEpisodeCatalog`를 한 번 불렀다. 오프라인으로 켜면 그 실행에서는 다시 받지 않았다.
2. **그림 · 음성은 받아 두지 않았다** [ADR]. 그림은 `<image src>`에 원격 URL(ADR-0056 D10), 음성은 원격 스트리밍(ADR-0060). 오프라인에서는 그림이 비고 소리가 나지 않았다 — 내장 3편도 그림은 원격이다.
3. **연결 상태를 아는 자리가 없었다** [코드]. `NWPathMonitor` · `ConnectivityManager` · NetInfo가 앱 · 호스트 어디에도 없었다.
4. **재생기가 로컬 파일을 받지 않았다** [코드]. iOS `AudioPlaybackModule.resolve`와 Android `AudioPlaybackController`는 https URL과 번들 이름만 받았다.

## 결정

### D1. 호스트가 파일을 받아 앱 전용 폴더에 둔다 — `ContentFileModule`

- 메서드 셋: `download(url, path, callback)` · `fileUrl(path)`(동기) · `remove(prefix, callback)`. 모양은 [호스트 모듈 표](README.md#호스트-모듈-표)와 spec이 진다.
- 바이트는 JS를 지나지 않는다 — 호스트가 받아 임시 파일에 쓰고 원자적으로 옮긴다. 중간에 끊기면 대상 파일이 없다(반쯤 쓴 파일을 「받음」으로 보지 않는다).
- 루트: iOS `Application Support/content-files/`(백업 제외), Android `filesDir/content-files/`. 경로는 `[A-Za-z0-9._-]` 조각만, `.` · `..` · 빈 조각 · 선두 `/` 거부. URL은 https만.
- **입장 조건(ADR-0017 D1)**: (1) 화면 목록 — 카탈로그 에피소드(표지 · 학습 · 최종)가 오프라인에서 그림 · 소리를 잃으면 정체성을 잃는다(듣기는 이름이 능력이다). (2) 대체 경로 0 — `StorageModule`은 문자열 키-값(이미지 · m4a 바이트를 담을 수 없음), Lynx에 파일 API 없음, `<image>` 캐시는 앱이 비우기를 통제하지 못하고 음성에는 없다. (3) e2e — 비행기 모드에서 그림이 보이고 소리가 나는지를 눈과 귀로 판정한다(EB2 · EB3).

### D2. 받기 좋은 때를 호스트가 알린다 — 전역 이벤트 `contentSyncOpportunity`

- 보내는 때: 네트워크가 끊김 → 연결로 바뀔 때(등록 직후 첫 보고는 보내지 않음 — 실행 시작은 JS가 스스로 돈다)와 앱이 백그라운드 → 포그라운드로 돌아올 때(콜드 스타트의 첫 포그라운드는 보내지 않음). 셀룰러 · Wi-Fi를 가리지 않는다(사용자 결정).
- 인자는 없다 — 신호는 「지금 다시 돌아도 된다」뿐이고, 무엇을 받을지는 JS가 매니페스트로 정한다.
- 앱이 꺼져 있을 때는 받지 않는다(BGTaskScheduler · WorkManager 제외 — 범위 밖).

### D3. 에피소드를 하나씩 받는다 — 본문 → 그 에피소드의 그림 · 음성 → 다음 에피소드

- 차례는 내장 · 원격을 합친 `order` 순이다. 내장 에피소드도 그림 · 음성을 받는다(내장은 늘 열려 있고, 받는 것은 오프라인 그림 · 소리를 채우기 위해서다).
- 받을 목록은 본문 와이어의 키 이름으로 고른다: `…image_url` → 그 경로(선두 `content/` 뗌), `…audio_url` → `audio/<id>.m4a`. 화면이 주소를 만드는 규칙과 같다.
- **실패를 둘로 가른다.** 서버에 없다고 확정된 것(HTTP 400 · 403 · 404 · 410 — Supabase Storage는 없는 파일에 400을 낸다, 기기 관찰 2026-10-19)은 적어 두고 넘어간다 — 녹음하지 않은 줄 하나가 에피소드를 영영 「준비 중」에 묶지 않게. 그 밖(연결 · 입출력 · 5xx)은 그 에피소드에서 멈추고 다음 신호에 남은 것부터 이어 받는다.
- 다 갖춘 표시는 `libitum.content.assets.<id>` = `{sha256, missing}`이다. sha256은 그 본문의 것이라 새 version이 오면 다시 확인한다.

### D4. 원격 에피소드는 다 갖춘 뒤에 연다

- 파일 모듈이 있으면, 원격(내장을 이긴) 에피소드의 본문은 표시의 sha256이 그 본문과 같을 때만 카탈로그에 들어간다. 아니면 「준비 중」(내장본이 있는 id면 내장본).
- 파일 모듈이 없는 환경(Explorer · 옛 호스트)에서는 지금처럼 본문만으로 연다 — 받을 수 없는데 막으면 영영 열리지 않는다.
- 받는 중인 원격 에피소드(`pending`)는 맵 맨 끝 「준비 중」 구획과 같은 그림(`Episode n.` 카드)으로 선다 — 옛 흐린 자물쇠 + `COMING SOON` 캡션은 잠긴 사유(업데이트 필요 · 쓸 수 없음)에만 남는다(사용자 지적 2026-10-19).
- 에피소드 하나가 갖춰질 때마다 카탈로그를 다시 읽어 맵에 바로 낸다. 이미 열린 것은 같은 실행 안에서 닫지 않는다(ADR-0056 D3).

### D5. 주소는 받아 둔 파일이 먼저다

- `imageUrlOf`(그림 · 음성이 함께 쓰는 포트)가 받아 둔 파일이 있으면 `file://`, 없으면 원격 URL을 낸다.
- 재생기는 루트 안의 `file://`만 받는다(심볼릭 링크 · `..` · 이름만 비슷한 이웃 폴더 거부). 그 밖의 file 주소는 지금처럼 거부한다.

### D6. 받기는 한 번에 하나, 겹친 요청은 한 번으로

- 실행 시작과 신호가 짧은 사이에 겹쳐도 받기는 하나만 돈다. 도는 중에 온 요청은 몇 개든 끝난 뒤 한 번 더 돈다(`createSyncRunner`).
- 사용자에게 알리지 않는다. 던지지 않는다. 분석 이벤트는 실행당 처음 매니페스트를 받은 한 번만(ADR-0029 그대로).

## 버린 대안

1. **본문만 받고 그림 · 음성은 지금처럼 원격** — 빠르지만 오프라인에서 그림이 비고 소리가 나지 않는다. 사용자가 범위를 본문 + 자산으로 골랐다.
2. **JS가 받아 base64로 저장소에** — 바이트가 브리지를 두 번 건너고(받기 · 쓰기), UserDefaults/SharedPreferences에 MB 단위가 쌓인다. 음성은 그래도 재생기가 파일을 요구한다.
3. **본문만 받으면 바로 열기(자산은 뒤이어)** — 빨리 열리지만 그사이 오프라인이 되면 그림 · 소리가 빠진다. 사용자가 「다 받은 뒤」를 골랐다.
4. **연결 종류로 거르기(Wi-Fi만)** — 요금을 아끼지만 새 에피소드가 늦게 닿는다. 사용자가 모든 연결을 골랐다.
5. **매니페스트에 자산 목록 · 해시를 싣기** — 무결성은 좋아지지만 서버 쪽 매니페스트 생성기가 아직 없어 손으로 관리해야 한다. 재검토 조건 3.

## 대가

1. **받은 파일을 지우지 않는다.** 그림 경로가 에피소드 사이에 공유되어(`images/items/…`) 에피소드 단위로 지울 수 없다. 에피소드가 늘면 폴더가 자란다 — 재검토 조건 1.
2. **자산의 무결성을 검사하지 않는다.** HTTP 200이면 받은 것으로 본다(해시가 매니페스트에 없다).
3. **이미 본문만 캐시된 원격 에피소드는 업데이트 뒤 자산을 받을 때까지 「준비 중」으로 돌아갈 수 있다**(다음 실행부터 — 같은 실행 안에서는 닫지 않음) [추론].
4. **자산 받기의 성공률을 재지 않는다** — 새 이벤트를 두지 않았다. 실행 중 여러 번 도는 받기를 세는 규칙이 아직 없다 — 재검토 조건 2.
5. **셀룰러에서도 받는다** — 에피소드 하나에 그림 10여 장 · 음성 수십 개.
6. **앞 에피소드의 자산이 계속 일시 실패(예 5xx)하면 뒤 에피소드가 막힌다** — 차례가 `order` 순이고 못 갖춘 자리에서 멈추기 때문이다. 처음 설치에서는 내장 3편의 그림 · 음성을 다 받은 뒤에야 새 원격 에피소드로 간다. 서버의 파일이 404가 아닌 오류로 오래 남으면 재검토한다.

## 재검토 조건

1. 받은 파일 폴더가 기기에서 수백 MB를 넘거나 에피소드가 수십 편을 넘으면 — 정리 정책(LRU · 끝낸 에피소드 지우기)과 공유 경로의 참조 세기.
2. 「새 에피소드가 기기에 닿는 데 걸리는 시간」을 알아야 하면 — 받기 완료 이벤트.
3. 서버 쪽 매니페스트 생성기가 생기면 — 자산 목록 · 해시를 매니페스트로 옮기고 받은 파일을 검증.
4. 셀룰러 요금 불만이 나오면 — 연결 종류 거르기(신호에 `expensive`를 싣는다).

## 적용 기록

### 2026-10-19 — 음성 길이 맞춤 타이핑: 같은 차례 끝에 음성 정보 파일 하나를 더 받는다

결정을 바꾸지 않는다. 음성 정보 파일의 결정은 [ADR-0074](0074-voice-synced-typing.md)가 진다. 이 문서에 닿는 자리만 적는다.

- **받기 실행기 한 차례가 하나 늘었다** — 에피소드 받기(`refreshEpisodeCatalog`)와 그 이벤트가 끝난 **뒤** 버킷의 `audio/manifest.json`을 한 번 받는다. JS 텍스트 GET이라 파일 모듈과 무관하다(Explorer에서도 돈다).
  카탈로그나 정보 파일이 바뀌었으면 다시 읽기는 여전히 한 번이다.
- **D3의 순서 · 실패 갈래, D4, D6, 이벤트(실행당 1회)는 그대로다** — 정보 파일의 실패는 에피소드 받기를 막지 않고, 겹친 신호는 같은 실행기가 한 번으로 모은다.
- **D3의 「서버에 없음」(400 · 403 · 404 · 410) 규칙을 이 파일에도 쓴다** — 상수를 하나로 열었다(`ABSENT_HTTP_CODES`). 없음이면 기기의 저장본을 지운다(ADR-0074 D4).
