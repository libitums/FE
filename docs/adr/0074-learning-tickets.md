# ADR-0074 — 새 레슨은 학습 티켓 한 장을 쓴다 (최대 3장 · 1시간에 1장 충전 · 단조 원장 · 진행 스냅숏에 싣기 · 머리 칩 모달 · 티켓 없음 대화상자 · 하루 1장 무료)

- 상태: **채택 — 클라이언트 + 서버 병합 함수.** 호스트 · 콘텐츠 변경은 0이다.
  **사용자 결정**(2026-10-20)이다 — 아래 굵은 문장은 사용자가 정했다. 화면은 시안(Artifact 「학습 화면 리디자인」 캔버스의 E1 · E3 · E5 · E6m)을 따른다.
  ⚠ **기기에서 보지 않았다** — unit · ui · integration · SQL(embedded Postgres) 테스트와 번들 크기만 확인했다([학습 티켓 e2e](../e2e/learning-tickets.md) LT1 ~ LT10, 미실행).
  ⚠ **원격 DB에 마이그레이션을 적용하지 않았다** — 적용 전에는 서버가 `tickets`를 「모르는 최상위 키」로 받아 들어온 쪽 값을 남긴다(아래 D3 「적용 전」).
- 날짜: 2026-10-20.
- 다루는 축: 학습 횟수의 제한 — 무엇이 티켓을 쓰는가, 충전 규칙, 상태를 어디에 두고 어떻게 합치는가, 화면 넷, 「더 받기」의 임시 동작, 측정.
  **다루지 않는 것**: 결제 · 광고 · 초대 등 실제 충전 화면, 기기 시계 조작 방지, 충전 완료 알림, 학습 화면 머리 칩 줄, 칩 숫자가 줄어드는 움직임(시안 E4 — 사용자가 이번 범위에서 뺐다).

근거 표시: **[코드]** 저장소 코드(`apps/mobile/src/` 기준) · **[실측]** 빌드 · 테스트 · **[ADR]** 기존 결정 · **[추론]** 관찰 없이 이어 붙인 것.

## 맥락

1. 에피소드가 쌓이며 하루에 몰아서 끝까지 가는 학습이 가능해졌다 — 사용자가 하트 · 에너지 같은 제한을 원했고, 하트 · 에너지가 아닌 **티켓**을 골랐다(캔버스 5-A ~ 5-E).
2. 학습 진행은 이미 기기 미전송 저장 · 저장본 · 재시도 · 서버 병합을 탄다(ADR-0035 · ADR-0062) [ADR]. 오프라인에서도 티켓이 같이 돌아야 한다 — 사용자 요구.
3. 레슨 시작은 결선 두 함수로 모인다 — 튜토리얼 `onStartStep` · 카탈로그 `onStartCatalogUnit`. 맵 말풍선 `Start`와 결과 화면 `Try again`이 이 둘을 부르고,
   알림 · 푸시는 레슨을 열지 않는다(메신저 · 전화 · 비주얼 노벨만 — `push-routing.ts`) [코드].

## 결정

### D1. **최대 3장, 새 레슨이 한 장을 쓰고, 쓴 티켓은 먼저 쓴 것부터 1시간에 한 장씩 다시 찬다 — 사용자 결정**

- 새 레슨 = 아직 끝내지 않은 튜토리얼 스텝 · 카탈로그 유닛(레슨 · 문화 카드 · 최종 테스트). **끝낸 레슨 다시 하기는 쓰지 않는다 — 사용자 결정.**
- 결과 화면의 `Try again`도 새 시도라 한 장을 쓴다(끝내지 못한 레슨이다) [추론 — 사용자 미확인, 아래 「사용자 확인 필요」].
- 메신저 · 전화 · 비주얼 노벨 · 표지 · 프롤로그는 레슨이 아니라 쓰지 않는다.
- 잠긴 유닛은 원래 시작이 그러듯 무시하고 쓰지 않는다(`ticket-wiring.ts`가 해금 판정을 먼저 본다).

### D2. 원장은 단조 증가하는 세 값이다

`lib/learning-tickets.ts` — `{ refillAtMs, grantedMs, grantDay }`.

- 실효 충전 완료 시각 `E = refillAtMs − grantedMs`, 남은 장수 `3 − min(3, ⌈max(0, E − now) / 1h⌉)`.
- 쓰기 `refillAtMs ← max(E, now) + 1h + grantedMs` · 무료 한 장 `grantedMs += 1h, grantDay ← 오늘`.
- 세 값이 모두 늘기만 해서 **필드마다 큰 값이 곧 병합**이다 — 쓴 쪽(큰 `refillAtMs`)이 이겨 「남은 장수가 적은 쪽」이 되고(**사용자 결정**), 다른 기기에서 받은 무료 한 장(큰 `grantedMs`)도 잃지 않는다.
- 버린 것: 「쓴 시각 목록」(병합이 합집합이면 두 기기에서 같은 시각을 못 가르고, 무료 한 장을 지우는 연산이 단조가 아니다) · 「남은 장수 + 기준 시각」(합칠 때 어느 쪽 기준 시각을 남길지가 시각에 따라 바뀐다).

### D3. 원장은 진행 스냅숏의 선택 필드 `tickets`로 산다

- `LearningProgressSnapshotV1.tickets?`, `JourneyProgressState.tickets?` — 한 번도 쓰거나 받지 않은 원장(가득)은 싣지 않는다(옛 서버 · 옛 앱과 바이트가 같다).
- 그래서 **오프라인 · 미전송 · 저장본 · 재시도 · 계정 전환 · 계정 삭제 시 지움이 진행과 똑같다** — 새 저장 키가 없다(ADR-0062 표 그대로).
- 모양이 틀린 `tickets`는 가득으로 읽고 나머지 진행은 그대로 둔다(스냅숏 전체를 버리지 않는다 — `catalogProgress`와 같은 처리).
- 서버: 마이그레이션 `20261020120000_learning_progress_tickets.sql`이 `merge_learning_progress_v1`에 검증(객체 · 0 이상 안전 정수 둘 · `''` 또는 `YYYY-MM-DD`, 어기면 `22023 invalid learning tickets`)과 필드별 최댓값 병합을 더한다.
  **적용 전**에는 서버가 `p_saved || p_incoming`으로 들어온 쪽을 남긴다 — 앱이 불러올 때 이미 기기 쪽과 합친 값을 보내므로 한 기기에서는 차이가 없고, 두 기기가 같은 순간 저장할 때만 뒤에 온 쪽이 이긴다 [추론].

### D4. 화면 넷 — 시안 E1 · E3 · E5 · E6m

- **E1 머리 칩 · 모달**: 칩은 연속 · 트로피 다음에 숫자만(이름 「N tickets left」). 누르면 연속 · 트로피와 같은 전체 화면 지표 모달 —
  큰 숫자 + 「tickets left」, 「Next ticket in h:mm:ss」 알약(가득이면 없음), 칸 셋(왼쪽부터 지금 차는 칸 · 기다리는 칸 · 찬 칸, 차는 칸은 왼쪽에서 오른쪽으로 채움, 칸 아래 h:mm 또는 Ready), 안내, 「Get more tickets」.
  떠 있는 동안 1초마다 다시 그린다. 닫혀 있으면 다음 한 장이 차는 순간에 한 번만 다시 그려 칩 숫자를 올린다.
- **E3 말풍선**: 새 레슨의 `Start`에 티켓 아이콘 + 「1」 태그, 낭독 「Start. Uses 1 ticket」. 다시 하기에는 없다.
- **E5 결과 화면**: 튜토리얼 평가 · 카탈로그 유닛 완료에 「N tickets left」 한 줄(보상 카드 아래).
- **E6m 티켓 없음 대화상자**: 0장에서 새 레슨을 열려 하면 어느 화면 위에서든 가운데 대화상자 — 「Out of tickets」, 칸 셋을 원 둘레로 나눈 카운트다운(차는 칸이 시계 방향으로 참) 가운데 티켓 · h:mm · 「until your next ticket」, 안내, 「Get more tickets」, 「Back to map」.
  레슨은 열리지 않는다. ui-lynx `Dialog`가 자유 본문을 받지 않아 같은 `Overlay` 위에 앱 쪽 상자를 짓는다.
- 디자인 시스템 아이콘(@libitums/icons 0.5.0)에 티켓이 없어 `components/ticket-icon.ts`에 하나 둔다.

### D5. **「Get more tickets」는 Coming soon 안내 + 관심 이벤트이고, 초기 이벤트로 한 장을 바로 채운다 — 사용자 결정**

- 하루(기기 지역 날짜) 한 번, 가득이 아닐 때만 채운다 [추론 — 횟수는 사용자 미확인].
- 버튼 아래 안내 한 줄 — 받았으면 「…coming soon. Here's a free ticket for today!」, 아니면 「…coming soon.」.
- E6m에서 받으면 버튼 자리에 「Start lesson」이 서고, 누르면 그 한 장을 써서 막혔던 레슨을 연다.
- 충전 화면이 생기면 같은 버튼을 그 화면으로 잇는다 — 이 결정의 재검토 조건이다.

### D6. 측정 — 이벤트 둘

[ADR-0029](0029-product-analytics-posthog.md) D14 적용 기록. sink는 `episodeIntroEventSink`.
- `tickets_ran_out`(속성 없음) — E6m이 뜬 순간. `episode_lesson_started` 대비 비율이 「제한에 걸리는 정도」다.
- `ticket_more_tapped`(`surface`: `ticket_modal` | `out_of_tickets`, `granted`: 불리언) — 충전 화면 수요.

## 사용자 확인 필요

1. 결과 화면 `Try again`이 한 장을 쓰는 것(D1) — 무료로 하려면 `ticket-wiring.ts`에 재시도 표시를 하나 더한다.
2. 무료 한 장이 하루 한 번인 것(D5).
3. 원격 DB 마이그레이션 적용 — 사용자 확인 뒤 적용한다.

## 버린 대안

- 하트 · 에너지(캔버스 5-A · 5-B — 사용자가 다른 요소를 원했다).
- 자정에 한꺼번에 3장(사용자가 1장당 1시간을 골랐다).
- 서버 시각 기준 충전 — 오프라인에서 돌지 않는다(사용자 요구와 충돌). 기기 시계를 믿는 대가는 아래.
- 기기 전용 저장 — 재설치 · 기기 변경마다 가득으로 돌아간다(사용자가 서버 병합을 골랐다).

## 대가

- **기기 시계를 앞으로 돌리면 티켓이 찬다.** 서버 시각 검증이 없다(범위 밖).
- 원장 필드는 앱 버전이 오르며 줄어들 수 없다(단조) — 규칙(장수 · 시간)을 바꾸면 해석이 바뀐다. 장수를 늘리는 것은 안전하고, 줄이면 그 순간 남은 장수가 줄어 보인다.
- 머리 · 결과 화면 · 말풍선 · 대화상자에 번들 바이트가 더해졌다(성능 보고서).

## 재검토 조건

1. 충전 화면(결제 · 광고)이 생기면 D5를 다시 쓴다.
2. `tickets_ran_out` 비율이 레슨 시작의 큰 몫이면 장수 · 시간을 다시 본다.
3. 시계 조작이 측정되면 서버 시각 검증을 더한다.
