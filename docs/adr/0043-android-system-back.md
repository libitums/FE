# ADR-0043 — Android 시스템 뒤로가기

- 상태: **채택** — 에뮬레이터(Pixel_8 AVD · API 37)에서 3버튼과 제스처 둘 다로 실행했다(2026-10-05).
  ⚠ 세부 결정 셋(무응답과 미준비의 떠남 방식이 다름 · 대기 중 재누름 무시 · 요청 중 무동작)은 계약 단계가
  고른 기본값이고 사용자 확인 전이다(아래 「사용자 결정과 기본값」).
- 날짜: 2026-10-05
- 다루는 축: Android 시스템 뒤로가기(제스처 · 3버튼)의 판정 순서 · 화면과 층의 등록 규약 · 호스트 프로토콜 · 앱을 떠나는 방식
- 이어받는 결정: [ADR-0007](0007-app-internals-state-routing-data-errors.md) D3(전환은 `navReducer`가 진다 · 모든 화면에
  화면 내 back 수단) · D6(나가는 수단의 목적지는 라벨이 정한다), [ADR-0038](0038-android-minimal-host.md)(Android 호스트),
  [ADR-0017](0017-host-native-capabilities-and-audio.md) D3(호스트 접점은 모듈마다 파일 하나).
  **바꾸는 결정은 없다** — `NavAction` · `Screen` · `navReducer` · `ScreenWiring`이 그대로다.

## 맥락

Android 호스트의 `MainActivity`는 `androidx.activity`를 쓰지 않는 평범한 `android.app.Activity`이고, 호스트 · JS 어디에도
뒤로가기 처리가 없었다. 어느 화면에서든 시스템 뒤로가기를 누르면 Activity가 끝나 앱이 닫혔고, 학습 중이면 진행 중이던
화면을 잃었다. Android 호스트 출시 리뷰의 첫 지적이다.

이 저장소가 뒤로가기를 다루기 어려운 이유가 셋 있다.

1. **닫기에 화면 로컬 인자와 정리가 붙는다.** 메신저는 세션에서 이탈 결과를 계산해 싣고, 통화는 벨과 오디오를 멈춘 뒤
   나가고, 학습 화면의 `×`는 나가지 않고 확인창을 연다. App이 결선 콜백(`wiring.onExit*`)을 직접 부르면 이 정리가 빠진다.
2. **층(확인창 · 시트 · 모달 · 안내)의 열림을 App이 모른다.** 그 상태가 화면 로컬 state · 훅 · 컨텍스트에 흩어져 있다.
3. **JS가 응답하지 못하는 순간이 있다.** 번들 로드 전 · 로드 실패 · JS 스레드가 막힌 때다. 그때 뒤로가기가 먹히지
   않으면 사용자는 앱을 나갈 수 없다.

iOS에는 시스템 뒤로가기가 없다. iOS 호스트는 바꾸지 않고, 공유 JS의 변경이 iOS 동작을 바꾸지 않아야 한다.

## 결정

### D1. 판정 순서는 **층 > 화면 > `Nav` 기본값**이고 한 번에 한 건만 처리한다

누름 한 번에 아래를 위에서부터 보고 **처음 걸리는 한 건**만 한다.

| 순서 | 조건 | 동작 |
|---|---|---|
| 1 | 열린 층이 있다 | 그 층의 닫기. 화면은 그대로다. 여럿이면 나중에 열린 것 |
| 2 | 화면이 닫기를 등록했다 | **그 화면의 보이는 닫기를 누른 것과 같다** — 같은 전이 · 같은 부수효과 |
| 3 | 등록이 없고, 탭 루트이며 탭이 여정이 아니다 | 여정 탭 루트로 간다(`tabRootActions("journey")` 그대로). 앱은 닫히지 않는다 |
| 4 | 그 밖 | 앱을 떠난다(D5) |

- 2번 때문에 학습 화면의 뒤로가기는 나가지 않고 **나가기 확인창을 띄운다.** 확인창이 뜬 뒤 다시 누르면 1번이 걸려
  확인창만 닫힌다(취소와 같다). 뒤로가기만으로는 학습 화면을 나갈 수 없고, 나가는 길은 확인창의 `Leave`다.
- 3번은 사용자 결정이다(여정 탭을 거쳐 떠난다). 탭 전환이지만 `BottomNavigator`의 선택 경로를 거치지 않는다 — 버튼음과
  탭 열람 이벤트가 나지 않는다.
- 4번에는 여정 맵 · 닫기 수단이 없는 화면(스플래시 · 온보딩 첫 스텝 · 개발용 탐침 둘)에 더해 **쌓였는데 등록이 없는
  자리**가 든다. 정상 경로가 아니다 — 에러 경계 화면 · 마운트 직후 한 프레임 · 등록을 빠뜨린 새 화면이고,
  「갇히지 않는다」가 이긴다.
- 3 · 4번의 판정은 순수 함수 `defaultBackDecision(nav)`(`apps/mobile/src/app/back-decision.ts`)가 진다.
  화면별 동작의 전수는 이 문서가 세지 않는다 — 등록한 자리는 `git grep -n "useScreenBack\|useLayerBack" apps/mobile/src`로 훑는다.

### D2. 닫기 함수는 **소유자가 스스로 등록한다** — 모듈 수준 스택 하나와 등록 훅 둘

`apps/mobile/src/lib/back-handler.ts`의 스택 하나(`backHandlers`)에, 화면은 `useScreenBack`으로, 층은 `useLayerBack`으로
자기 닫기 함수를 올린다(`apps/mobile/src/lib/use-back-handler.ts`). 스택은 층 단에 등록이 하나라도 있으면 그중 가장 나중
것을, 없으면 화면 단의 가장 나중 것을 부른다.

**이 저장소에 「모듈 수준 스택 + 등록 훅」은 처음이다.** 새 화면과 새 층이 지킬 규약은 넷이다.

1. **쌓이는 화면은 `useScreenBack`을, 열리고 닫히는 층은 `useLayerBack`을 건다.** 걸지 않으면 그 화면에서의 뒤로가기는
   D1의 4번(앱을 떠남)이 된다 — 컴파일도 테스트도 빠진 등록을 잡지 않는다(「대가」).
2. **등록하는 함수는 `bindtap`에 묶인 바로 그 함수다.** 화면이 결선 콜백을 새로 조합하지 않는다. 인라인 클로저였다면
   이름 붙인 함수로 뽑아 버튼과 등록이 한 함수를 보게 한다.
3. **화면 단 등록은 보이는 닫기를 그리는 컴포넌트 한 곳에서만 한다.** 학습 다섯 화면은 `LearningShell`만 등록한다.
4. **닫기 수단이 없는 상태는 `null`을 넘긴다**(온보딩 첫 스텝 · 닫힌 층). 등록이 스택에서 빠진다.

단을 둘로 나눈 이유는 effect 순서다. 자식의 effect가 부모보다 먼저 돌아, 화면과 같은 렌더에 서는 층은 「나중 등록이
이긴다」만으로는 화면 밑에 깔린다. 단이 순서를 결정적으로 만든다. 불리언 인자 대신 이름이 다른 훅 둘로 둔다.

등록 · 해제는 effect에서 한다. 함수가 다른 함수로 바뀌어도 스택의 자리는 그대로이고 호출 대상만 최신이다.
화면은 여전히 `dispatch` · `NavAction`을 모른다(ADR-0007 D3).

### D3. 호스트 프로토콜 — 전역 이벤트 하나와 `SystemBackModule`의 메서드 둘

| 방향 | 이름 | 인자 |
|---|---|---|
| 호스트 → JS (전역 이벤트) | `systemBackPressed` | `[token]` — 누름마다 새 값인 10진 문자열 |
| JS → 호스트 | `SystemBackModule.ready()` | 없음. 리스너가 선 뒤 한 번 |
| JS → 호스트 | `SystemBackModule.respond(token, outcome)` | `outcome`은 `"handled"` 또는 `"leave"` |

- JS 쪽 결선은 `useSystemBack`(`apps/mobile/src/app/use-system-back.ts`) 하나이고 `AppSession`이 한 번 부른다. 응답은
  핸들러나 `dispatch`가 **돌아온 직후 동기로** 보낸다 — 렌더 커밋을 기다리지 않는다.
- 토큰이 문자열인 이유는 브리지의 수 타입 변환에 계약이 기대지 않기 위해서다. 비어 있지 않은 문자열이 아닌 인자는
  무시한다(상태 변화 0 · 응답 0).
- 호스트의 판정은 Android 의존이 없는 `SystemBackGate`가 지고 JUnit(`SystemBackGateTest`)이 잰다. `MainActivity`는 그
  판정을 실행만 한다. API 33 이상은 `OnBackInvokedCallback`, 26~32는 `onBackPressed()`가 같은 한 함수로 모인다.
  매니페스트의 `android:enableOnBackInvokedCallback="true"`가 33 이상을 앞 경로로 보낸다.
- 호스트 접점은 `apps/mobile/src/lib/system-back.ts`다. 모듈이 없는 환경(iOS 호스트 · Lynx Explorer)에서는 두 호출이
  `unavailable`을 돌려주고 던지지 않으며, 이벤트를 보내는 주체가 없어 리스너가 불리지 않는다 ⇒ **iOS 동작 변화 0.**

### D4. 응답을 **500ms** 기다리고, 기다리는 동안의 재누름은 무시한다

호스트는 이벤트를 보낸 뒤 `SystemBackGate.ACK_TIMEOUT_MS`(500ms) 동안 같은 토큰의 응답을 기다린다.

| 호스트 상태 | 입력 | 결과 |
|---|---|---|
| JS 미준비(`ready()` 전) | 누름 | `finish()` — 기다리지 않는다 |
| 준비 · 대기 없음 | 누름 | 이벤트 발신 + 500ms 타이머 |
| 준비 · 대기 있음 | 누름 | 무시 |
| 대기 중 | `respond(t, "handled")` | 대기 해제. 호스트는 아무것도 하지 않는다 |
| 대기 중 | `respond(t, "leave")` | 대기 해제 · `moveTaskToBack(true)` |
| 대기 중 | 500ms 경과 | 대기 해제 · `moveTaskToBack(true)` |
| 대기 중 | 모르는 `outcome` · 다른 토큰 | 대기 유지(타임아웃이 정리한다) |

**500ms는 실측값이 아니다.** 응답이 렌더를 기다리지 않으므로 정상 왕복은 그보다 훨씬 짧다고 보고 정했다. 에뮬레이터에서
확인한 것은 「타임아웃이 지난 뒤에도 앱이 앞에 남아 있다 = 응답이 그 안에 왔다」까지이고, 왕복 시간의 숫자는 재지 않았다
(호스트가 누름 · 응답 로그를 남기지 않는다).

### D5. 앱을 떠나는 방식은 둘이다 — 살아 있을 수 있으면 `moveTaskToBack`, 미준비면 `finish`

| 경우 | 구현 | 근거 |
|---|---|---|
| JS가 `leave`로 응답 | `moveTaskToBack(true)` | Android 12 이상의 루트 런처 Activity 기본 동작과 같고 8~11도 같게 맞춘다. LynxView · `Nav` · 진행이 살아 있어 다시 열면 그 화면이 스플래시 없이 선다 |
| 500ms 무응답 | `moveTaskToBack(true)` | JS가 느렸을 뿐일 수 있다. 살아 있을지 모르는 학습 세션을 폴백이 부수지 않는다 |
| JS 미준비 | `finish()` | 지킬 상태가 없고, Activity를 끝내야 다음 실행이 번들을 다시 읽는다. 백그라운드로만 보내면 로드에 실패한 빈 화면이 그대로 돌아온다 |

⚠ **JS가 준비되기 전의 뒤로가기는 앱을 끝낸다.** 에뮬레이터 실측에서 `ready()`는 프로세스 시작 뒤 **약 2.2초**에 왔다
(Pixel_8 AVD · API 37 · Debug APK · 로컬 HTTP 번들, 2026-10-05). 그 사이의 누름은 스플래시가 보이고 있어도 `finish()`다.
이 숫자는 그 한 구성의 관측이고 예산이 아니다.

### D6. 무동작으로 둔 자리 셋

로그인 요청 중 · 인증 코드 요청 중 · 계정 삭제 진행 중에는 등록된 함수가 불리지만 아무 일도 하지 않고, 응답은 `handled`다
(앱을 떠나지도 않는다). 보이는 뒤로 버튼이 그 상태에서 하는 일과 같다(삭제 진행 중의 취소 버튼은 비활성이다). 갇히지 않는
근거는 요청마다 타임아웃이 있어 끝나면 풀린다는 것이다.

Custom Tab(법률 문서 · 소셜 인증) · 권한 창 · 스토어 리뷰 창은 별도 Activity나 시스템 창이라 뒤로가기가 이 경로에 오지 않는다.

## 사용자 결정과 기본값

| 구분 | 내용 |
|---|---|
| 사용자 결정 (2026-10-05) | 쌓인 화면의 뒤로가기는 **화면의 닫기와 동일** · 탭 루트는 **여정 탭을 거쳐 떠남** |
| 요구사항의 추론을 계약이 코드 대조로 고정 | 층이 열려 있으면 그것부터 닫는다 · 확인창 위의 뒤로가기는 취소다 · 진입 구간도 「보이는 수단과 같게, 없으면 떠남」 · JS가 응답하지 못하면 기본 동작으로 떨어진다 |
| 계약 단계의 기본값 — **사용자 확인 전** | 무응답은 `moveTaskToBack`, 미준비는 `finish`(D5) · 대기 중 재누름 무시(D4) · 요청 중 무동작(D6) |

## 버린 대안

- **App이 `Nav`와 결선에서 뒤로가기 동작을 파생한다.** 닫기에 화면 로컬 인자와 정리가 붙어 있어(맥락 1) App이
  `wiring.onExit*`를 직접 부르면 「닫기와 같은 부수효과」가 깨진다. 층의 열림도 알 수 없어(맥락 2) 열림 상태 열 개를
  `ScreenWiring`으로 끌어올려야 한다.
- **뒤로가기를 `NavAction` `back`으로 dispatch한다.** 「나가는 수단은 그 화면이 자기 방식으로 진다」와 어긋난다 —
  학습 화면은 확인창 없이 빠져나가고 메신저의 미완료 이탈 이벤트가 나지 않는다. 새 `NavAction`도 더하지 않았다.
- **Provider(컨텍스트)로 스택을 내린다.** `AppSession`의 트리와 기존 테스트 헬퍼를 전부 고쳐야 하고, 화면을 고립
  렌더하는 `ui` 테스트마다 래퍼가 필요해진다. 모듈 수준 싱글턴은 래퍼 없이 `backHandlers.runTop()`으로 뒤로가기를 흉내 낸다.
- **단을 나누지 않고 「나중 등록이 이긴다」 하나로 둔다.** effect 순서 때문에 화면과 같은 렌더에 서는 층이 화면 밑에
  깔린다(D2).
- **떠남을 전부 `finish()`로 한다.** 여정 맵에서 뒤로가기를 누를 때마다 다음 실행이 번들을 처음부터 읽고, 느린 JS를
  무응답으로 오판하면 살아 있던 학습 세션을 잃는다.
- **떠남을 전부 `moveTaskToBack`으로 한다.** 번들 로드에 실패한 Activity가 백그라운드에 남아 다시 열어도 빈 화면이다.
- **무응답 대기 없이 JS에 맡긴다.** JS가 막힌 동안 뒤로가기로 앱을 나갈 수 없게 된다(맥락 3).

요구사항이 범위 밖으로 둔 것은 대안이 아니라 제외다 — 예측형 뒤로가기 미리보기 애니메이션 · 「한 번 더 누르면 종료」
안내 · 닫기 수단이 없는 화면에 새 닫기 UI를 만드는 것 · iOS 가장자리 스와이프.

## 대가

- **모듈 수준 싱글턴이 생겼다.** 스택은 앱 전체에 하나이고 React 트리 밖에 있다. 등록이 해제되지 않으면 사라진 화면의
  함수가 불린다 — 해제를 지는 것은 훅의 effect 정리 하나다.
- **등록을 빠뜨려도 아무것도 빨개지지 않는다.** 새 화면이 `useScreenBack`을 걸지 않으면 뒤로가기가 조용히 앱을 떠난다.
  `Screen` union의 exhaustiveness 검사 같은 강제가 이 축에는 없고, 지키는 것은 D2의 규약과 화면별 `*.back.ui.test.tsx`다.
- **뒤로가기만으로 나갈 수 없는 화면이 있다.** 학습 화면은 뒤로가기 두 번이 「확인창 열림 → 닫힘」의 제자리 토글이다.
  의도한 동작이지만 보조기술 사용자에게는 비용이 크다(「알려진 한계」).
- **시스템의 뒤로가기 미리보기 애니메이션이 뜨지 않는다.** 콜백이 늘 등록돼 있기 때문이다.
- **JS 준비 전 약 2.2초 동안의 뒤로가기는 앱을 끝낸다**(D5). 스플래시에서 실수로 누르면 다음 실행은 콜드 스타트다.
- **탭 루트에서 여정 탭으로 가는 전이는 탭을 직접 누른 것과 신호가 다르다** — 버튼음이 없다.
- **에러 경계 화면에서 다른 탭 루트였다면 뒤로가기가 화면을 바꾸지 못한다.** `Nav`만 여정으로 바뀌고 화면은 `Retry`
  전까지 그대로다. 이 작업에서 바꾸지 않았다.
- **호스트 모듈이 하나 늘었다.** [호스트 모듈 표](README.md#호스트-모듈-표)의 첫째 재검토 트리거가 다시 발동했다.
  ⚠ **ADR-0017 D1의 입장 조건 셋을 이 작업이 판정한 기록은 없다.** 사실만 적는다 — (1) 이 모듈을 요구한 것은
  `docs/screens.md`의 화면이 아니라 플랫폼 동작(출시 리뷰 지적)이다. (2) `@lynx-js/types@4.1.0`의 타입 정의에 뒤로가기
  계열 이름은 0건이다(`backpress` · `onBack` · `hardwareBack` · `systemBack` · `keycode_back`으로 훑었다). **설치된 Android
  Lynx SDK의 등록 목록은 훑지 않았다.** (3) [절차 문서](../e2e/android-system-back.md)에 항목으로 적혀 있고 실행했다.

## 확인한 것과 확인하지 못한 것

| 무엇 | 상태 | 증거 |
|---|---|---|
| 층 · 화면의 닫기 · 탭 루트 → 여정 · 떠남 · 다시 열면 스플래시 없이 그 화면 | 에뮬레이터 실행 통과 (3버튼 · 제스처) | [절차 문서](../e2e/android-system-back.md)의 「실행 결과」 |
| 번들 로드 실패에서 `finish()` | 에뮬레이터 실행 통과 | 같은 문서 B8(a) |
| JS 준비 전 누름의 `finish()` | 에뮬레이터에서 **8회 중 1회만** 재현 — 주입 시점이 흔들린다 | 정본 증거는 JUnit `SystemBackGateTest` SG1(미준비 누름 = `FINISH`) |
| **실제 JS 무응답(500ms 타임아웃)** | **에뮬레이터에서 확인하지 못했다** — JS를 멈출 수단이 없다 | JUnit `SystemBackGateTest` SG6 · SG9 |
| **첫 유닛 안내 가림막 위의 뒤로가기** | **에뮬레이터에서 확인하지 못했다** — 계측 픽스처가 진행 불러오기에 404를 돌려줘 안내가 서지 않는다 | `integration` IB7(`App.system-back.integration.test.tsx`) · `ui` UL8(`PrologueCallScreen.back.ui.test.tsx`) |
| 요청 중 무동작(로그인 · 인증 코드 · 계정 삭제) | 에뮬레이터 절차의 대상이 아니다(모의 서버 없음) | `ui` 계층 |
| API 26~32(Android 8~12)의 `onBackPressed()` 재정의 경로 | **컴파일만 확인됐고 실행된 적이 없다** — 실행한 AVD는 API 37 하나이고, 그 버전은 `OnBackInvokedCallback` 경로만 탄다 | 없음. [절차 문서](../e2e/android-system-back.md)의 L1(API 32 이하 AVD에서 B2 · B5 · B6)이 **미실행**으로 적혀 있다 |
| 절차 문서의 고쳐진 판정 기준(준비 · B3 · B7 · B8)으로의 재실행 | **기준 변경 후 미실행** — 에뮬레이터 결과는 커밋 `d454723f` 시점의 절차로 얻었고, 그 뒤 고쳐진 글대로는 다시 돌리지 않았다 | 같은 문서 「실행 결과」의 「현재 기준」 칸 |
| TalkBack을 켠 상태의 동작 | **실행하지 않았다** | [절차 문서](../e2e/android-system-back.md)의 T1~T6 |

## 알려진 한계

- **학습 화면의 뒤로가기 2회가 TalkBack 사용자에게 소리 없는 토글이 된다** · **뒤로가기로 여정 탭에 갈 때 버튼음이 없다.**
  둘 다 전환 통지 축이고 [ADR-0016](0016-assistive-technology-semantics.md) D8의 ⟨2026-10-05⟩ 적용 기록이 진다.
  해결은 이 작업의 범위 밖이다(후속).
- **TalkBack의 뒤로 제스처가 이 경로를 타는지 이 빌드에서 확인한 적이 없다.** Android 일반 동작에 기댄 전제다.
- **3버튼 내비게이션에서 하단 탭 바가 시스템 내비게이션 버튼과 겹쳐 그려진다.** 뒤로가기 작업 직전 커밋 `444fcfd6`에서도
  같아 이 결정의 회귀가 아니다. 별도 bugfix로 진행한다.

## 재검토 조건

- **등록을 빠뜨린 화면이 한 번이라도 머지되면** → D2. 규약 대신 강제(예: `Screen` 멤버와 등록의 대조 검사)를 둘지 본다.
- **500ms 안에 정상 응답이 오지 못한 사례가 관측되면**(화면이 처리했는데 앱이 백그라운드로 간다) → D4의 값.
- **`ready()`까지의 시간이 줄거나 스플래시에서 앱이 끝난다는 보고가 오면** → D5의 미준비 분기.
- **예측형 뒤로가기 미리보기가 요구되면** → D3. 콜백을 늘 등록해 두는 구조와 함께 다시 본다.
- **targetSdk(오늘 34)가 36 이상으로 오르면** → D3의 두 경로가 그대로 서는지 API 26~32와 함께 실행해 확인한다.
- **ADR-0016 D8(전환 통지)이 열리면** → 「알려진 한계」의 두 항목을 그 결정으로 닫는다.
- **iOS에 뒤로 제스처(가장자리 스와이프)가 요구되면** → D2의 스택을 그대로 쓸 수 있는지 본다. 호스트 프로토콜(D3)은 Android 전용이다.
