# ADR-0115 — 컴패니언 답변은 SSE 하나로 흘리고, v1은 Supabase Realtime을 쓰지 않는다

- 상태: **제안** — FE 팀 리뷰 대기. `feat/companion-m1`의 `chat-send`가 이미 이 결정대로 쓰였다. **Lynx 앱에서 스트림을 읽을 수 있는지는 아직 확인하지 않았다**(PRD §7 위험 1).
- 날짜: (채택일에 적는다)
- 다루는 축: 한 턴의 답변 · 피드백 · 번역 · 상태가 **어떤 길로** 앱에 오는가, 끊기면 **어떻게 회복하는가**.
  **다루지 않는 것**: 이벤트 하나하나의 필드(→ [API 명세 §4](../specs/ai-companion-api.md)) · 계약을 어디에 적는가(→ [ADR-0113](0113-companion-contract-package.md) 초안) · 선톡 푸시(→ API 명세 §2.3.1).
- 이어받는 결정: [ADR-0007](0007-app-internals-state-routing-data-errors.md)(앱의 데이터 · 오류 처리 — 적용 기록만).

근거 표시: **[코드]** 저장소 코드 · **[사용자]** 사용자 결정 · **[추론]** 관찰 없이 이어 붙인 것.

## 맥락

1. **답이 길고 느리다** [코드 — `chat-send-turn.ts`]. 메인 답변은 토큰 단위로 나오고, 피드백 · 번역은 다른 호출이다. 다 끝난 뒤 한 번에 주면 첫 글자가 몇 초 늦다.
2. **한 턴의 정보가 여러 갈래다** [코드]. 답 조각(`delta`) · 피드백(`correction`, 메인과 병렬) · L1 번역(`translation`, 답 뒤 따로 호출 — 2026-11-09) · 말투 단계(`state`) · 차감(`done`) · 고지 · 위기 안내.
3. **Realtime은 채널 · 구독 · RLS 정책을 새로 들인다** [추론]. 컴패니언 표는 PostgREST에 노출하지 않고 정책도 두지 않는다([ADR-0112](0112-companion-schema.md) 초안). Realtime의 Postgres 변경 구독은 그 방침과 맞지 않는다.
4. **앱은 Lynx다** [코드 — 2026-11-08 기준 `getReader` · `EventSource` 0건]. 응답 본문을 스트림으로 읽는 자리가 아직 없다.

## 결정

### D1. 한 턴 = `POST chat-send` 하나 = SSE 응답 하나

- 스트림을 열기 전 실패(인증 · 접근 · 연령 · 시간 상한 · 크레딧)는 HTTP 상태 + JSON 하나. 연 뒤는 SSE `error` 하나로 끝난다.
- 피드백 · 번역은 **같은 스트림에 끼운다** — `correction`은 `start` 뒤 `done` 앞 어디든, `translation`은 마지막 `delta` 뒤 `state` 앞. 다른 연결 · 폴링을 두지 않는다.
- 순서 규칙(API §4.3)은 계약 패키지의 순수 함수가 검사하고, 통합 테스트가 고정한다.

### D2. 이어 받기는 없다 — 끊기면 목록을 다시 읽는다

- `Last-Event-ID`를 지원하지 않는다. 서버는 연결이 끊겨도 턴을 끝까지 처리해 저장한다. 앱은 `companion_list_messages`로 결과(조각 · 번역 · 피드백 카드)를 받는다.
- 같은 메시지 재전송은 `client_message_id`로 멱등이다(API §1.4).

### D3. v1은 Realtime을 쓰지 않는다

- 선톡은 푸시(연결 예정) + 다음 목록 조회로 보인다. 앱이 켜져 있을 때 바로 띄우지 않는다.

## 버린 대안

- **Supabase Realtime(Broadcast · 변경 구독)** — 맥락 3. 앱 상태가 두 길(HTTP 응답 · 채널)로 갈라지고, 노출하지 않기로 한 스키마에 정책을 열어야 한다.
- **WebSocket 자체 서버** — Edge Function 밖에 상주 서버가 생긴다.
- **스트리밍 없이 한 번에 JSON** — 맥락 1. 미성년자 · 나이 모름은 동기 출력 검사 때문에 어차피 다 만든 뒤 보내지만, 성인의 첫 글자 지연을 늘릴 이유가 없다. Lynx에서 스트림을 못 읽을 때의 **대체 경로**로는 남는다(재검토 조건).
- **피드백 · 번역을 따로 요청** — 왕복이 늘고, 앱이 「다 왔다」를 판단할 기준이 둘이 된다.

## 대가

- 앱(또는 호스트 네이티브 모듈)이 SSE 파서를 가져야 한다 — 계약 패키지의 `sse-parse.ts`를 같이 쓴다.
- 미성년자 · 나이 모름 턴은 출력 검사를 기다려 첫 글자가 늦다(PRD §3.11).
- Edge Function 실행 시간 상한 안에 메인 + 피드백 + 번역(6초)이 들어가야 한다(PRD O19).

## 재검토 조건

- **Lynx에서 응답 본문을 스트림으로 읽지 못하면** — 호스트 네이티브 모듈이 스트림을 받아 JS로 넘기는 길을 먼저 보고, 그것도 안 되면 「한 번에 JSON」으로 내린다.
- 앱 안 실시간 선톡 · 여러 기기 동시 사용 · 타이핑 표시 같은 **서버가 먼저 미는** 요구가 생기면 Realtime을 다시 본다.
- 한 턴이 Edge Function 실행 시간 상한에 자주 닿으면 길(백그라운드 작업 + 조회)을 다시 본다.
