# ADR-0004 — package 경계·책임과 의존 방향

- 상태: 채택
- 날짜: 2026-08-24
- 다루는 축: package 경계와 책임, 의존 방향, 네이밍(패키지 이름·scope)

## 맥락

이 결정을 처음 쓸 때 워크스페이스에는 패키지가 **하나뿐이었다**(`apps/mobile`, ADR-0002).
2026-09-10에 배포 가능한 `packages/ui-lynx`와 그 검증 소비자인 `apps/storybook-lynx`가
추가되어, 아래 경계와 의존 방향은 실제 강제 대상이 됐다.

규칙이 없으면 두 번째 패키지가 생기는 **그 순간에** 정하게 되고, 그때는 이미 코드가
있어서 규칙이 코드에 맞춰 굽는다. 지킬 것이 없는 지금이 가장 편향 없이 정할 수 있는
시점이다.

이 ADR의 두 축(경계·방향)을 한 문서에 두는 이유는 서로를 정의하기 때문이다 — "무엇을
패키지로 만드는가"의 답이 "무엇이 무엇을 import할 수 있는가"에 의존한다.

## 결정

### D1. 앱과 라이브러리의 구분

| | `apps/*` | `packages/*` |
|---|---|---|
| 무엇인가 | **산출물을 내는** 것 (Lynx 번들) | **import되는** 것 |
| import 대상이 되는가 | **아니다** | 그렇다 |
| 진입점 | 빌드 설정이 정한다 | `exports` 필드가 정한다 |

앱은 그래프의 **잎(leaf)**이다. 무엇도 앱을 import하지 않는다. 이 한 줄이 D4의
"앱→앱 금지"를 자동으로 함의한다.

### D2. package 생성 조건 — **두 번째 소비자가 실제로 나타났을 때만**

"나중에 공유할 것 같아서" 만들지 않는다. 소비자가 하나면 그 소비자 안에 둔다.

첫 단계에는 `packages/` 아래에 아무것도 만들지 않는다. **디렉터리 자체도 만들지 않는다.**

단, 명시적 산출물이 재사용 가능한 배포 패키지이고 실제 런타임 검증 소비자를 함께 요구한
2026-09-10 작업은 ADR-0015 D3의 좁은 예외를 충족했다. `packages/ui-lynx`와
`apps/storybook-lynx`를 함께 만들되 기존 제품 화면을 강제로 이관하지 않는다.

근거: 소비자가 하나일 때 만든 경계는 그 하나의 사정에 맞춰진다. 두 번째 소비자가
왔을 때 그 경계가 맞을 확률은 낮고, 이미 패키지가 되어 있으면 고치는 비용이 앱 안에서
고치는 것보다 크다(버전·exports·의존 선언이 함께 움직인다).

에이전트로 구현하는 저장소에서 이 규칙은 특히 중요하다 — 에이전트는 "확장 가능한
구조"를 요청받지 않아도 만드는 경향이 있다. 규칙을 문서에 박아두면 되돌릴 근거가 된다.

### D3. 공개 API 경계

- 각 패키지는 `package.json`의 `exports` 필드로 진입점을 **명시**한다.
- **`./src/*` 같은 와일드카드 서브패스를 열지 않는다.** 열면 경계가 없는 것과 같다.
- 소비자는 `@libitums/x`만 import한다. `@libitums/x/src/internal/thing`은 금지이고,
  `exports`가 이것을 **런타임에서** 막는다. 규약이 아니라 도구가 지킨다.

### D4. 의존 방향

```text
apps/*  ──▶  packages/*  ──▶  packages/*
                                (순환 금지)

tooling/*  ──devDependency만──▶  모든 패키지
```

| 방향 | 허용 | 이유 |
|---|---|---|
| `apps/*` → `packages/*` | O | 정상 방향 |
| `packages/*` → `apps/*` | **X** | 라이브러리가 앱을 알면 그 라이브러리는 재사용될 수 없다 |
| `apps/*` → `apps/*` | **X** | 공유가 필요하면 `packages/`로 올린다. 앱끼리 직접 참조하면 두 앱이 한 앱이 된다 |

> **이 규칙에는 강제 수단이 있다.** `import/no-cycle`을 `error`로 켜두었으므로
> `pnpm lint`가 순환 참조를 잡는다 (ADR-0006 D1). 이 ADR의 결정 중 문서 밖에서
> 지켜지는 것은 이것 하나다.
>
> **`apps/ios`가 `apps/mobile`의 번들을 로드하는 것은 이 규칙의 예외가 아니라 대상이
> 아니다.** 호스트는 빌드 시점에 `apps/mobile`을 참조하지 않는다 — 런타임에 URL이나
> 산출물 파일을 읽을 뿐이고, `package.json` 의존이 생기지 않는다(ADR-0012 D1·D2).
> 이 표는 **패키지 의존 그래프**에 대한 규칙이다.
| `packages/*` → `packages/*` | O (순환 금지) | |
| 제품 코드 → `tooling/*` | **X** | tooling은 빌드 시점 도구다. 런타임에 들어가면 번들에 섞인다 |

### D5. 워크스페이스 내부 참조는 항상 `workspace:*`

버전 범위(`^1.0.0`)를 쓰지 않는다.

근거: 범위를 쓰면 pnpm이 상황에 따라 레지스트리 버전을 설치할 수 있다. 그러면 로컬과
CI가 **다른 코드**를 실행하면서 둘 다 성공한다. 이런 실패는 재현이 안 되고, 재현이
안 되는 실패를 1인이 디버깅하면 하루가 사라진다. `workspace:*`는 "항상 이 저장소의 것"을
뜻하므로 그 여지를 없앤다.

### D6. 순환 참조는 **실패로 처리한다**

발견하면 고친다. 예외를 두지 않는다.

**첫 단계에는 자동 검사 도구를 도입하지 않는다.** 패키지가 1개라 순환이 구조적으로
불가능하기 때문이다. 없는 문제를 위한 도구는 설정 비용만 낸다.

도입 시점: **두 번째 워크스페이스 패키지가 생기는 커밋.** 그 커밋에서 순환 검사를
`verify`에 넣는다(ADR-0006). 이것을 잊지 않도록 ADR-0010의 체크리스트에 넣어 둔다.

이 조건은 2026-09-10에 충족됐다. `madge --circular`를 `pnpm cycle:check`로 두고
`lint`를 통해 `verify`에 연결했다. 검사 범위는 현재 TypeScript/TSX 의존 그래프인
`packages/ui-lynx/src`와 `apps/storybook-lynx/src`다.

패키지 내부(파일 간) 순환은 별개다. 이것은 도구 없이 리뷰에서 본다 — 프로토타입
규모에서 파일 간 순환은 대개 `lib/`가 UI를 import할 때 생기고, 그건 ADR-0003 D5가
이미 금지한다.

### D7. 이름과 scope

- 모든 워크스페이스 패키지는 `@libitums/<디렉터리명>`. 앱도 포함한다 —
  `apps/mobile` → `@libitums/mobile`.
- 앱에도 같은 scope를 주는 이유: `pnpm --filter @libitums/mobile`처럼 필터 인자가
  일관되고, 이름 충돌이 없다. "앱은 scope 없이"처럼 예외를 두면 명령마다 형태가 달라진다.
- **모든 패키지는 `"private": true`가 기본이다.** npm에 발행하지 않는다.
  발행이 필요해지면 그 패키지 하나만 개별로 해제한다.

`private: true`를 기본으로 두는 이유는 사고 방지다. 프로토타입 코드가 실수로 공개
레지스트리에 올라가면 되돌릴 수 없다.

## 버린 대안

- **처음부터 `packages/ui`, `packages/api`, `packages/config`를 만들어 둔다** —
  구조는 그럴듯해 보이지만 각 패키지가 자기 `package.json`·`tsconfig`·빌드 설정을
  요구한다. 1주 일정에서 이 설정 시간은 화면 구현 시간에서 나온다. 그리고 내용이
  없으면 경계가 근거 없이 굳는다.
- **`exports` 없이 디렉터리 import 허용** — 지금 편하지만 소비자가 내부 구조에
  의존하게 되어 리팩터링이 파괴적 변경이 된다.
- **패키지에 실제 semver를 붙이고 범위로 참조** — 외부에 배포할 때나 의미가 있다.
  발행하지 않기로 했으므로(D7) 버전 관리 비용만 낸다.
- **순환 검사 도구(madge 등)를 지금 넣는다** — 검사할 대상이 없다.
- **앱은 scope 없이 `mobile`** — 필터 인자 형태가 패키지마다 달라진다.

## 대가

- **앱이 하나인 동안 "올릴 곳"이 없어 공유 코드가 `apps/mobile/src/lib/`에 쌓인다.**
  두 번째 앱이 생기는 시점에 한 번의 이관 비용을 낸다. 이걸 감수하는 이유는, 지금
  패키지를 미리 만들면 그 경계가 **근거 없이** 굳고 이관 비용을 나중에 더 크게 내기
  때문이다. 이관 비용을 완화하려고 ADR-0003 D5가 `lib/`에 "UI를 import하지 않는다"는
  제약을 미리 걸어뒀다 — 그러면 그대로 떨어져 나온다.
- pnpm의 엄격한 격리 때문에 전이 의존을 쓸 수 없어, 의존을 명시적으로 추가하는 순간이
  자주 온다. 처음에는 번거롭다.
- `madge`가 새 루트 개발 의존과 검사 시간을 추가한다.
